# Требования к изменениям кода

## Scope текущего этапа Control Center

- Текущий этап ограничен UI, бизнес-логикой и согласованными бизнес-API.
- Не добавляй auth/session/RBAC: вход, выход, восстановление сессии, auth-редиректы, permissions и ограничения интерфейса по пользователю требуют отдельного согласования модели/API и нового spec change. Удаление прежних auth-зависимостей в рамках согласованного change разрешено.
- Сохраняй безопасность, бизнес-валидацию, обработку ошибок, доступность и запрет E2E/browser-тестов без отдельного разрешения; предметные auth-поля бизнес-сущностей не являются auth-контекстом.

## Перед изменением

- Изучи затронутый сценарий и соглашения в соседних файлах. При исправлении ошибки проверь все места вызова и устрани причину, а не только симптом.
- Прежде чем писать своё решение, проверь по порядку: существующий код проекта, стандартные возможности языка и платформы, API используемого фреймворка, уже установленные библиотеки. Используй подходящее готовое решение вместо самописного аналога.
- Новую зависимость добавляй только если существующие средства не покрывают задачу и польза оправдывает стоимость поддержки. Не добавляй библиотеку ради нескольких простых строк.
- Не обходи штатные механизмы фреймворка самодельными роутингом, загрузкой данных, состоянием или формами без конкретной причины.

## Читаемость и декомпозиция

- Имена должны объяснять предметное назначение; комментарии — причину неочевидного решения, а не пересказывать код. Предпочитай явный поток управления с понятными условиями сжатым выражениям.
- Функция должна решать одну понятную задачу на одном уровне абстракции. Если она смешивает самостоятельные ответственности, выделяй операции с предметными именами и проверяй все места вызова. Не дроби связную логику ради числа строк или метрики; минимизируй ненужные переходы между файлами. Читаемость важнее краткости.
- Не добавляй абстракции «на будущее», обёртки без пользы и изменения вне задачи. Сохраняй стиль проекта и внешнее поведение, в том числе валидацию на границах, обработку ошибок, безопасность и доступность.

## Проверки перед завершением

- Для изменённой логики добавь или обнови тест на существенный сценарий и граничный случай.
- Не повышай пороги сложности, не добавляй широких исключений файлов, не отключай правила и не ослабляй утверждения тестов только ради зелёных проверок. Если исключение необходимо, обоснуй его и ограничь область действия.
- Запусти подходящие проверки: `yarn typecheck`, `yarn lint` (без предупреждений), `yarn test`, `yarn format:check`. При изменении API-типов — `yarn api:check`; сборки — `yarn build`. По умолчанию пользовательские сценарии проверяй unit/component-тестами; E2E/browser-тесты допустимы только по отдельному явному разрешению пользователя.
- Если проверку нельзя запустить или она падает по причине вне изменений, явно укажи команду и причину в ответе. Различай пройденные, упавшие и не запущенные проверки.
- E2E/browser-тесты запрещены в рамках проекта по умолчанию: не создавай новые, не редактируй существующие и не запускай их без отдельного явного разрешения пользователя. При таком разрешении ограничивай их только требуемыми пользовательскими сценариями.
- Перед ответом просмотри diff: нет ли случайных файлов, отладочного кода и изменений вне задачи; проверь сохранение поведения.

## Итоговый ответ

- Кратко перечисли, что изменено, какие проверки выполнены и что осталось непроверенным.

## FSD и файловая декомпозиция

- Соблюдай направление зависимостей `app` → `pages` → `widgets` → `features` → `entities` → `shared`; слайсы одного слоя не импортируют друг друга.
- Внешний код обращается к слайсу через его публичный `index.ts`; внутри слайса используй прямые импорты собственных модулей. Не обходи публичный API через алиасы, относительные пути, type-only импорты или re-export.
- Shared и слой приложения организуй по техническим сегментам, а не по искусственным предметным слайсам. Не создавай глобальные свалки `app/types`, `app/constants` или `app/handlers`.
- Именованные `type`/`interface`, включая props, размещай в `types/*.types.ts` ближайшего владельца; предметные runtime-константы, enum, справочники и defaults — в `constants/*.constants.ts`; именованные UI-обработчики — в `handlers/`. Схемы, результаты hooks, локальные вычисления и callback-и библиотечных операций не являются предметными константами.
- Один рукописный React-компонент размещай в отдельном файле. Приватных детей помещай в подпапку владельца; компонент с несколькими потребителями поднимай только к ближайшему общему владельцу, не копируй и не переноси автоматически в `shared`.
- Не дроби связную логику, вспомогательные функции или JSX только ради числа строк/метрик. Обязательное размещение деклараций и компонентов — это правило владения, а не требование создавать бессмысленные обёртки.
- Framework entrypoints, специальные экспорты и typegen сохраняй; route-модули могут быть тонкими адаптерами. `app/shared/api/schema.d.ts` и `scripts/generate-api-types.mjs` — generated-контракт и не декомпозируются вручную.
- Исходники shadcn не получают общего исключения для `shared/ui`: спорные compound-файлы согласовываются адресно с перечислением файла, правила и последствий upstream-обновлений. До согласования исключения не добавляй.
- Согласованы адресные исключения для текущих shadcn compound-файлов: `react/no-multi-comp` отключён только в `app/shared/ui/{breadcrumb,bubble,button-group,card,dialog,drawer,dropdown-menu,popover,scroll-area,select,sheet,sidebar,tabs,toggle-group,tooltip}.tsx`; правило типов допускает в `drawer.tsx` и `sidebar.tsx` только локальные `DrawerContextProps` и `SidebarContextProps` соответственно. Это сохраняет upstream single-file API и не создаёт расхождение при обновлениях; новые файлы в список не добавляются без отдельного согласования.

Корректно: `features/surface-registration/types/*.types.ts`, `constants/*.constants.ts`, `handlers/*.ts`, приватный шаг в подпапке владельца и внешний импорт через `features/surface-registration/index.ts`.

Некорректно: импорт `features/other-slice/model/internal` из соседнего слайса, импорт внутреннего файла entities из pages, `app/types` как общая свалка или требование вынести локальный вычисленный `const` в constants только из-за синтаксиса.
