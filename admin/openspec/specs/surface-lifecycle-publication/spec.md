# surface-lifecycle-publication Specification

## Purpose

Предоставить карточке поверхности управляемую публикацию и lifecycle-операции на основе существующего бизнес-API, сохраняя точные серверные данные подключения, честную обратную связь и восстановление после ошибок.

## Requirements

### Requirement: Server-owned placement code

Карточка поверхности SHALL отображать `connection.embed_code` из успешного detail-ответа без изменения пробелов, переносов, атрибутов или содержимого. UI MUST NOT генерировать embed-код, токен, `channel_id`, секрет или атрибут `data-token` из домена, UUID, конфигурации или HTML-прототипа. Если сервер вернул `null`, пустую строку или строку из пробелов, UI SHALL явно показать отсутствие кода и SHALL отключить копирование.

#### Scenario: Server code is shown as text

- **WHEN** detail API возвращает непустой `connection.embed_code`
- **THEN** карточка показывает исходную строку как текст, не исполняет её как HTML/script и не добавляет к ней фиктивные значения

#### Scenario: Server code is unavailable

- **WHEN** detail API возвращает `connection.embed_code = null` или пустую строку
- **THEN** пользователь видит понятное состояние «код не сохранён», кнопка копирования недоступна, а UI не пытается получить код из другого поля

### Requirement: Exact copy feedback

Кнопка копирования SHALL передавать в Clipboard API ровно серверную строку embed-кода. Доступный toast или live-status SHALL сообщать об успехе только после успешного завершения Clipboard API. При reject или недоступности API SHALL показываться сообщение об ошибке с возможностью повторить действие или скопировать видимый код вручную; ложный успех запрещён.

#### Scenario: Copy succeeds

- **WHEN** пользователь нажимает доступную кнопку копирования и Clipboard API успешно завершается
- **THEN** в буфер передаётся точная строка, а пользователь видит доступное сообщение «код скопирован»

#### Scenario: Copy fails

- **WHEN** Clipboard API отклоняет запрос или недоступен
- **THEN** код остаётся видимым, появляется доступное сообщение об ошибке, сообщение об успехе не появляется и повтор возможен без перезагрузки карточки

### Requirement: Lifecycle status and actions

Карточка SHALL показывать фактический серверный `status` и предоставлять MVP-действия по согласованным бизнес-правилам: `publish` из `configured`, `review`, `sandbox`; `disable` из `prod`; `enable` и `archive` из `disabled`; `restore` из `archived`. Из `draft` публикация SHALL быть недоступна до сохранения и получения допустимого статуса от сервера. UI MUST NOT предоставлять запуск `sandbox` или выполнять его скрыто. Существующие `review` и `sandbox` SHALL оставаться читаемыми статусами, не обязательными этапами MVP.

Обе точки публикации SHALL применять одинаковые ограничения. Во время проверки, сохранения, выполнения команды и обязательного обновления данных SHALL блокироваться повторные и конкурирующие записи, включая редактирование отправляемого состава сценариев. Проверка доступности SHALL выполняться также непосредственно перед отправкой, а не только через disabled-кнопки.

Итоговый статус SHALL приниматься из ответа операции и последующего detail-запроса; UI MUST NOT синтезировать статус или проверку готовности. Возврат и восстановление SHALL отправлять только соответствующую команду, без автоматического `publish`. Текущее поведение мока принимается: если он возвращает иной статус, включая `prod`, UI SHALL честно показать полученный статус без локальной подмены на `configured` и без заявления, что пользователь выполнил публикацию.

#### Scenario: Lifecycle action succeeds

- **WHEN** доступная операция получает валидный `SurfaceStatusResponse`
- **THEN** карточка показывает статус из ответа, обновляет detail и реестр и сообщает о выполненной операции без фиктивных данных

#### Scenario: Lifecycle action is rejected

- **WHEN** API отклоняет команду из-за конфликта, валидации, отсутствия поверхности или сети
- **THEN** последний подтверждённый снимок сохраняется, локальный успех не возникает; для 409 сначала доступно ручное обновление карточки, для остальных ошибок — управляемый повтор с проверкой актуальной доступности

#### Scenario: Disabled and archived surfaces cannot publish directly

- **WHEN** открыта отключённая или архивная поверхность
- **THEN** обе точки публикации недоступны; сначала требуется соответственно возврат в работу или восстановление, затем доступность пересчитывается по серверному статусу

#### Scenario: Accepted mock returns a previous status

- **WHEN** restore возвращает `prod` вместо ожидаемого по правилам аналитика `configured`
- **THEN** UI показывает серверный `prod`, сообщает о восстановлении, не отправляет publish и не открывает окно успеха публикации

#### Scenario: No sandbox workflow in MVP

- **WHEN** пользователь открывает карточку в любом поддержанном статусе
- **THEN** запуск песочницы отсутствует, checklist не требует её прохождения, запрос sandbox не отправляется, статус sandbox при его наличии отображается корректно

### Requirement: Publish requires confirmation and truthful success

Перед публикацией UI SHALL показать подтверждающее модальное окно. Отмена SHALL закрывать его без сохранения и без publish-запроса, возвращая фокус к кнопке. После подтверждения UI SHALL проверить текущий состав сценариев и параметры, сохранить их через существующий `PUT /enabled-skills`, получить свежую карточку и только затем отправить bodyless `POST /surfaces/v1/surfaces/{surface_id}/publish`. Для публикации SHALL требоваться хотя бы один сценарий в отправляемом и подтверждённом сервером составе, допустимый статус и успешные проверки параметров. Пустое приветствие SHALL NOT вводиться как самостоятельный новый блокер публикации; действующие проверки контрактов сохраняются.

Ошибка подготовки, сохранения или чтения перед публикацией SHALL останавливать цепочку без POST publish. UI SHALL сохранить пользовательские данные и показать этап ошибки. Успешное сохранение перед неуспешной публикацией MUST NOT откатываться фиктивно: последнее подтверждённое серверное состояние остаётся видимым. Повтор публикации SHALL заново проверять и сохранять актуальный состав, а не обходить этап подготовки прямым POST.

Успех публикации SHALL показываться только после подтверждённого `status = prod` и успешного обновления detail с `prod`. При ошибке команды, неожиданном статусе или ошибке обновления UI MUST NOT показывать окно подтверждённой публикации. Успешная команда с неудачным refresh SHALL предлагать повтор чтения, а не повторную запись.

Обязательное чтение перед публикацией SHALL начинаться после успешного PUT; ответ запроса, начатого до сохранения, MUST NOT считаться его подтверждением или перезаписывать результат более позднего чтения. Решение о публикации SHALL использовать полученную свежую карточку. При 409 SHALL применяться ручное обновление и новый запуск действия по требованию `Accessible errors, retry and scope boundaries`.

#### Scenario: Publish is cancelled

- **WHEN** пользователь отменяет подтверждение
- **THEN** PUT и POST не отправляются, черновик и статус сохраняются, фокус возвращается к кнопке публикации

#### Scenario: Publish succeeds

- **WHEN** подтверждена публикация допустимой поверхности с валидным непустым составом
- **THEN** текущие параметры сохраняются перед POST publish, свежая карточка подтверждает prod, появляется доступное окно успеха без обещания нового embed-кода

#### Scenario: Empty current draft prevents publication

- **WHEN** на сервере есть сценарии, но пользователь снял все в текущем черновике
- **THEN** обе точки публикации недоступны; отдельное сохранение пустого состава по-прежнему разрешено для неархивной поверхности

#### Scenario: Save failure prevents publication

- **WHEN** подготовка параметров или PUT enabled-skills завершается ошибкой
- **THEN** publish не вызывается, ошибка сохранения видна, черновик остаётся для исправления и повтора

#### Scenario: Preparation refresh changes eligibility

- **WHEN** после успешного сохранения свежая карточка имеет archived, disabled, draft, prod либо пустой состав
- **THEN** POST publish не отправляется и пользователю объясняется актуальное состояние

#### Scenario: Publish failure follows a successful save

- **WHEN** состав успешно сохранён, но publish отклонён
- **THEN** сохранённый состав не объявляется несохранённым, статус не заменяется prod, повтор проходит полную проверку доступности и подготовку

#### Scenario: Refresh cannot confirm publication

- **WHEN** publish ответил успешно, но detail не загрузился или не подтвердил prod
- **THEN** отображается отдельное сообщение о невозможности подтвердить итог, доступно повторное чтение и окно успеха не открывается

#### Scenario: Earlier read cannot authorize publication

- **WHEN** до сохранения начался GET карточки, а PUT завершился успешно
- **THEN** UI ждёт нового чтения, начатого после PUT, и не отправляет publish на основании старого ответа; старый ответ не заменяет более свежие сведения

### Requirement: Configuration and card refresh

Сохранение конфигурации SHALL использовать существующий `PUT /surfaces/v1/surfaces/{surface_id}/configuration` и опубликованный request/response contract; lifecycle-действия SHALL не подменять этот запрос самодельным payload и SHALL NOT отправлять конфигурацию в POST-операциях, у которых тело контрактом не предусмотрено. После успешного сохранения конфигурации или lifecycle-операции SHALL выполняться обновление detail-карточки, включая статус, `updated_at`, configuration, connection и enabled skills.

#### Scenario: Configuration save is accepted

- **WHEN** существующий экран конфигурации отправляет валидный payload в `PUT /configuration` и получает успешный ответ
- **THEN** карточка показывает серверный статус и дату ответа, затем получает свежие configuration и connection через detail-запрос

#### Scenario: Refresh after mutation fails

- **WHEN** mutation успешна, но следующий detail-запрос завершается ошибкой
- **THEN** пользователь видит сообщение о проблеме обновления и кнопку retry, последний корректный снимок остаётся видимым, а UI не подменяет отсутствующие поля значениями из прототипа

### Requirement: Accessible errors, retry and scope boundaries

Ошибки чтения, копирования, сохранения и lifecycle SHALL быть различимы от loading, empty и успешных состояний, иметь доступное текстовое сообщение и управляемое восстановление. Повтор после ошибки, отличной от 409, SHALL выполнять новое обращение для того же целевого действия после проверки доступности и без параллельной отправки; публикация сохраняет обязательную подготовку. Повтор чтения после успешной записи SHALL выполнять только GET. Реализация MUST NOT добавлять auth/session/RBAC/permissions или user-based UI restrictions и MUST NOT добавлять или запускать E2E/browser-тесты.

После 409 при сохранении или lifecycle UI SHALL показать причину и кнопку «Обновить карточку», без автоматического GET или повторной записи. До успешного обновления UI SHALL блокировать повтор конфликтной последовательности во всех точках запуска. Кнопка обновления SHALL выполнять только GET и сохранять несохранённый черновик. После успешного чтения доступность SHALL пересчитываться, но действие MUST NOT запускаться автоматически: пользователь заново выбирает доступное действие, а публикация требует нового подтверждения и подготовки. Если обновление не удалось, SHALL оставаться ошибка чтения и повтор только GET. SANDBOX_CHECK_REQUIRED SHALL NOT запускать песочницу или сопровождаться обещанием, что обновление устранит причину отказа.

#### Scenario: Retry after failed action

- **WHEN** первая попытка lifecycle-операции получает ошибку, отличную от 409, и пользователь нажимает «Повторить»
- **THEN** при допустимом состоянии выполняется новый запрос той же операции с необходимой подготовкой, controls возвращаются в обычное состояние после завершения, а прежний error-state заменяется результатом нового запроса

#### Scenario: Conflict refresh never repeats a write

- **WHEN** операция получила 409 и пользователь нажимает «Обновить карточку»
- **THEN** отправляется только GET, черновик сохраняется, доступность пересчитывается по свежему статусу и никакой PUT или POST автоматически не повторяется

#### Scenario: Conflict refresh permits a new confirmed publication

- **WHEN** после 409 успешный GET подтвердил допустимое состояние и пользователь заново запускает публикацию
- **THEN** открывается новое подтверждение; только после согласия выполняются подготовка, сохранение, проверка свежей карточки и publish

#### Scenario: Conflict refresh fails or prohibits the action

- **WHEN** GET после 409 завершается ошибкой либо возвращает archived для попытки публикации
- **THEN** публикация не запускается; при ошибке доступен повтор GET, при archived действуют правила архивной карточки

#### Scenario: No authentication side effects

- **WHEN** пользователь открывает карточку или выполняет lifecycle/copy/publish action
- **THEN** UI обращается только к surface business API и Clipboard API, не вызывает auth endpoint и не меняет доступность действий на основании несуществующего пользовательского permission-контекста

### Requirement: Archived surface is read-only

Архивная поверхность SHALL оставаться доступной для просмотра и копирования существующего embed-кода, но SHALL запрещать редактирование и сохранение сценариев и конфигурации, а также публикацию. UI SHALL объяснять необходимость восстановления. Запрет SHALL действовать в обработчиках записи и во всех точках интерфейса. После восстановления доступность SHALL пересчитываться по фактическому ответу сервера.

#### Scenario: Editing an archived surface

- **WHEN** загружена карточка со status archived
- **THEN** редактор и сохранение недоступны, запросы PUT и publish не отправляются, просмотр и restore остаются доступны

#### Scenario: Archive during an unsaved edit

- **WHEN** archive успешно выполнен при наличии локального черновика сценариев
- **THEN** UI блокирует запись черновика и не сохраняет его автоматически в архив; серверное состояние не подменяется локальными изменениями

### Requirement: MVP editing and deferred functionality boundaries

Перед публикацией SHALL сохраняться все данные, редактируемые существующей карточкой. На текущем этапе это состав сценариев и параметры; отсутствующий редактор конфигурации SHALL NOT заменяться фиктивным PUT неизменённой конфигурации, defaults из прототипа или самодельным переводом draft в configured. Существующий контракт PUT configuration SHALL сохраняться для отдельного конфигуратора. UI MUST NOT представлять history-заглушку как реальную историю или обращаться к выдуманному API аудита.

#### Scenario: Configuration editor is not available

- **WHEN** конфигуратор остаётся заглушкой, а пользователь публикует configured-поверхность
- **THEN** сохраняется актуальный состав сценариев, конфигурация не перезаписывается вымышленным payload, sandbox и аудит не вызываются

#### Scenario: Draft remains a draft after saving skills

- **WHEN** сохранение состава не перевело draft в configured на сервере
- **THEN** карточка сохраняет draft и недоступность публикации, не выполняя скрытый PUT configuration ради смены статуса

#### Scenario: Server confirms configured after saving skills

- **WHEN** пользователь отдельно сохранил валидный непустой состав draft-поверхности и серверный ответ с последующим свежим GET подтвердили configured
- **THEN** публикация становится доступной в обеих точках без автоматического POST publish и без PUT configuration; локального присваивания статуса нет
