# api-registry-search Specification

## Purpose

Позволить находить описания API по полному серверному отбору, делиться им по ссылке и повторно применять именованные фильтры.

## Requirements

### Requirement: Server owned registry selection

Реестр SHALL иметь вкладки «Все», «Внутренние», «Исходящие», «Входящие» и показывать метод, название и путь, группу и источник, версию и статус. Поиск SHALL отправляться для query длиной 2–200 по имени, коду, пути и описанию; единичный символ MUST NOT отправляться как query и SHALL сопровождаться пояснением. Очистка SHALL убирать query. Мультиселекты методов, источников и статусов SHALL использовать section lookups; условия SHALL предоставлять AND/OR, совместимые поля и операторы из metadata с учётом опубликованного DTO, не более 50 условий и явное применение. `landing_category` MUST NOT отправляться как поле условия при текущем DTO.

Фильтры и условия SHALL сочетаться в одном серверном запросе, сортировка и пагинация выполняться сервером. Limit SHALL быть 1–100, исходно 20; изменение отбора SHALL сбрасывать offset. Доступные сортировки SHALL соответствовать опубликованным полям, третий клик SHALL возвращать default `-updated_at`. Групповой столбец MUST NOT выдавать составную сортировку за поддержанную сервером.

#### Scenario: Combined conditions

- **WHEN** пользователь применяет два выбранных HTTP-метода, фильтр источника и OR-условия, затем открывает следующую страницу
- **THEN** сервер получает полный отбор и соответствующий offset, а список не фильтруется и не сортируется только по загруженной странице

#### Scenario: Short or empty search

- **WHEN** введён один символ либо поиск возвращает валидный пустой набор
- **THEN** первый ввод не отправляется как query и ограничение объясняется; во втором случае показано отсутствие совпадений с возможностью сброса

### Requirement: Group counts use the same server selection

Счётчики вкладок SHALL вычисляться из серверного `pagination.total_items` с одним и тем же применённым отбором, исключая только выбранную вкладку как быстрый `group_code`: без группы для «Все», с соответствующей группой для остальных. Существующие условия по группе SHALL сохраняться. Счётчики MUST NOT выводиться из текущей страницы или суммировать неподтверждённые данные. Loading и отказ отдельного счётчика SHALL отличаться от подтверждённого нуля; устаревшие ответы MUST NOT замещать актуальные.

#### Scenario: Counts with an active selection

- **WHEN** применены query, несколько статусов и условие по группе, а затем выбрана другая вкладка
- **THEN** каждый счётчик использует те же query/статусы/условия и соответствующую свою вкладку, независимо от offset таблицы

#### Scenario: Count failure

- **WHEN** запрос одного счётчика завершился ошибкой, а другие завершились успешно
- **THEN** проблемный счётчик не показывает фиктивный ноль и может быть повторён без подмены остальных результатов

### Requirement: Full shareable selection

URL SHALL сохранять и восстанавливать выбранную группу, query, все мультиселекты, условия, sort, limit и offset. Скопированная ссылка SHALL включать действующий basename; Back/Forward SHALL восстанавливать отбор. Некорректные параметры SHALL приводить к видимой диагностике и безопасному исправлению/сбросу, а не к некорректному запросу. Сброс SHALL очищать весь отбор, удаление только условий SHALL сохранять быстрые фильтры. Успех копирования SHALL объявляться только после успешной операции clipboard.

#### Scenario: Link round trip

- **WHEN** другой пользователь открывает ссылку на входящие API с методами и OR-условиями
- **THEN** восстанавливается тот же полный отбор и соответствующий поиск выполняется сервером

#### Scenario: Clipboard failure

- **WHEN** браузер отклоняет запись ссылки
- **THEN** показывается ошибка и отсутствует ложное сообщение об успешном копировании

### Requirement: Persistent named filters

Создание, просмотр, применение и удаление именованных фильтров SHALL использовать managed saved-filters с `resource=api-endpoints`, не память браузера. Имя SHALL содержать непробельный символ и иметь длину 1–150. Сохраняемый search SHALL включать группу, query, мультиселекты, условия и сортировку в опубликованных полях; применение SHALL начинаться с offset=0. Список SHALL поддерживать серверную пагинацию. Совпадение имён MUST NOT приводить к недокументированной перезаписи. Полученный search SHALL валидироваться до применения; повреждённый или непредставимый в единственной вкладке search с несколькими группами SHALL быть доступен для удаления без изменения текущего отбора.

После принятого создания UI SHALL прочитать фильтр по выданному ID и проверить семантическую сохранность полного отбора. Эквивалентные формы одного значения группы SHALL считаться одинаковыми. Ошибка чтения или несовпадение SHALL сообщать, что восстановление не подтверждено; повтор SHALL выполнять только чтение, не автоматически повторять POST. Изоляция фильтров между пользователями принадлежит backend и не подтверждается mock-сценарием.

#### Scenario: Persist and restore group

- **WHEN** пользователь сохраняет фильтр для входящих API с OR-условиями, затем перезагружает страницу и применяет его
- **THEN** отбор получается из API, группа и условия восстановлены, поиск начинается с первой страницы

#### Scenario: Saved filter readback fails

- **WHEN** POST подтверждён и вернул ID, но последующее чтение завершилось ошибкой
- **THEN** UI не заявляет подтверждённое восстановление, сохраняет ID для повтора GET и не создаёт второй фильтр автоматически

#### Scenario: Invalid saved search

- **WHEN** API возвращает фильтр с неподдерживаемым условием
- **THEN** текущий отбор не изменяется, причина объясняется, а удаление фильтра остаётся доступным
