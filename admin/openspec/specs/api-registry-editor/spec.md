# api-registry-editor Specification

## Purpose

Дать пользователю безопасно описывать эндпоинты, их параметры и ответы в единой карточке с подтверждённым серверным сохранением.

## Requirements

### Requirement: Unified endpoint draft and validation

Карточка SHALL предоставлять вкладки «Основное», «Запрос» и «Ответы», одну несохранённую модель и живое текстовое превью метода и пути. Создание SHALL использовать контрактные defaults internal/draft, `publish_on_landing=false`, `auth_required=true` и пустые коллекции. Доступны название, код, метод, путь, версия, группа, источник, статус, владелец, внешний ответственный, описание, теги, настройки публикации, базовый URL, категория и пример cURL. Настройки описывают внешний API и MUST NOT менять сессию админки или выполнять запросы к указанному адресу.

Name, code, method, path и group SHALL быть заполнены согласно контракту; name не состоит из пробелов, code соответствует `^[a-z][a-z0-9_]*$` и длине до 100, path начинается с `/`, не содержит пробельных символов и имеет длину до 500. Версия ограничена 16, name — 255, owner — 200, base URL — 500 символами; непустой base URL SHALL быть HTTP/HTTPS. Конфликты уникальности name, code и `(method,path,version)` SHALL окончательно определяться сервером. При ошибке SHALL сохраняться весь ввод, показываться полевые ошибки и обеспечиваться переход к соответствующей вкладке/полю.

#### Scenario: Validation and conflict

- **WHEN** путь не начинается с `/` либо сервер сообщает конфликт кода с записью вне загруженной страницы
- **THEN** соответствующее поле получает понятную ошибку, введённые параметры и ответы сохраняются, успех не показывается

#### Scenario: Publication configuration is descriptive

- **WHEN** пользователь вводит base URL, cURL с плейсхолдером и признак требуемой авторизации
- **THEN** значения сохраняются как текстовые данные карточки, не исполняются и не изменяют авторизацию админки

### Requirement: Group and external-user selection preserve values

Справочники SHALL загружаться из `/catalogs/lookups/api`; ответственные SHALL искаться через согласованный API пользователей с пагинацией и сохраняться по внешнему строковому ID, не принудительно UUID. Для internal поле источника скрыто; для outgoing требуется источник панели, для incoming — источник внешней системы согласно аналитике. Коды SHALL использоваться из серверных lookup и согласованного соответствия группе; неоднозначное `mpmm`/`mppm` MUST NOT автоматически заменяться предполагаемым alias.

Если lookup не загружен, код неактивен или ранее сохранённое значение отсутствует на текущей странице, UI SHALL сохранять идентификатор и показывать понятное ограничение; новые назначения неподтверждённых или неактивных значений MUST NOT отправляться. Явная смена группы SHALL очищать несовместимый источник и требовать допустимый новый без неявной подстановки.

#### Scenario: Directory failure

- **WHEN** сохранённый ответственный не попал в текущую страницу либо загрузка lookup завершилась ошибкой
- **THEN** его ID и выбранные значения сохраняются, изменение других полей не стирает их и показывается причина недоступности вариантов

#### Scenario: Group change

- **WHEN** пользователь переводит исходящий эндпоинт во входящий и прежний источник несовместим
- **THEN** прежний источник не отправляется как входящий и требуется подтверждённый вариант для новой группы

### Requirement: Parameters and response examples

Параметры SHALL поддерживать location, name, data_type, description и required, до 100 элементов; порядок SHALL изменяться мышью и клавиатурой. Ответы SHALL поддерживать HTTP-код, непустое описание и опциональный JSON-пример, до 100 элементов. Коды SHALL быть строками 100–599 и не повторяться в карточке. `request_body` и непустые примеры SHALL проверяться как JSON, но сохраняться с исходным форматированием; пустой или состоящий из пробелов ввод SHALL превращаться в null. Выбранный ответ SHALL показываться в безопасном текстовом предпросмотре без исполнения разметки.

#### Scenario: Reorder and clear

- **WHEN** пользователь клавиатурой переставляет существующие параметры и удаляет все ответы
- **THEN** изменение порядка видно и сохраняется вместе с пустым массивом ответов, существующие ID параметров не меняются

#### Scenario: Invalid or hostile example

- **WHEN** пример содержит невалидный JSON либо валидный JSON со строкой `<script>`
- **THEN** невалидный пример не сохраняется и получает ошибку; валидная строка показывается буквально без выполнения скрипта

### Requirement: Atomic server-confirmed save

Создание SHALL использовать POST, изменение — частичный PUT одного агрегата. Переданные коллекции параметров/ответов SHALL заменяться целиком, `[]` SHALL очищать коллекцию, пропущенное поле SHALL не изменяться. При сохранении существующих строк SHALL передаваться их серверные ID; новые получают ID от backend, порядок определяется массивом. Повторная отправка во время pending MUST NOT создавать дубли; пустой PUT MUST NOT отправляться. При серверной или сетевой ошибке draft и dirty SHALL сохраняться, успех MUST NOT показываться.

#### Scenario: Atomic rejection

- **WHEN** изменены метаданные и порядок параметров, но сервер отклоняет любой элемент
- **THEN** пользователь видит ошибку, черновик не теряется и UI не утверждает частичное успешное сохранение

#### Scenario: Create confirmed but follow-up fails

- **WHEN** POST вернул ID, но последующий GET карточки не удался
- **THEN** UI сохраняет ID для повторного GET и автоматически не повторяет POST

### Requirement: Approved status transitions and hidden pause

Статус SHALL использовать доступные серверные значения `draft`, `active`, `deprecated`, `archived` согласно согласованному контракту и изменяться в едином черновике. Выбор archive, включая выбор через поле статуса, SHALL требовать подтверждения; изменение SHALL считаться сохранённым только после успешного POST новой карточки либо PUT существующей. При отмене подтверждения статус не меняется. Кнопка «Приостановить» MUST NOT отображаться, `paused` MUST NOT отправляться до отдельного согласования; архив, устаревание и DELETE MUST NOT использоваться как её замена.

#### Scenario: Archive confirmation and save

- **WHEN** пользователь подтверждает архивирование сохранённой карточки, но ещё не нажал «Сохранить»
- **THEN** изменён только черновик, запрос и уведомление об успешной архивации отсутствуют

#### Scenario: Pause unavailable

- **WHEN** открыта карточка при текущем контракте
- **THEN** кнопка «Приостановить» отсутствует и `paused` не предлагается как новый статус

### Requirement: Unsaved changes protection

Переход по меню, крошкам или Back SHALL предупреждать только при фактических несохранённых изменениях. Диалог SHALL предлагать остаться или выйти без сохранения; закрытие/перезагрузка документа SHALL использовать штатное предупреждение браузера. Переключение вкладок MUST NOT вызывать потерю ввода. Возврат к сохранённым значениям и успешное сохранение SHALL снимать dirty; ошибка сохранения MUST NOT снимать dirty или автоматически повторять запись.

#### Scenario: Stay on dirty card

- **WHEN** пользователь изменяет ответ, выбирает переход в реестр и затем «Остаться»
- **THEN** карточка и её черновик сохраняются, запрос сохранения не отправляется

#### Scenario: Clean navigation

- **WHEN** пользователь отменил все изменения либо сервер подтвердил сохранение
- **THEN** выход не показывает предупреждение о потере данных
