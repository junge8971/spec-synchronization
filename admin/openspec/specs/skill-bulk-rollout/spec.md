# skill-bulk-rollout Specification

## Purpose

Позволить выполнять массовый выкат выбранных на текущей странице навыков из белых списков в prod с подтверждением и отдельным результатом каждого элемента.

## Requirements

### Requirement: Visible-row selection

Реестр SHALL предоставлять доступные чекбоксы показанных строк и панель выбранных навыков со счётчиком. «Выбрать все» SHALL обозначать только текущие показанные строки. Смена страницы, фильтра или сортировки SHALL сбрасывать выбор; скрытые элементы MUST NOT неявно попадать в команду. Действия и результаты SHALL быть доступны с клавиатуры и различаться текстом, а не только цветом.

#### Scenario: Select current page

- **WHEN** пользователь нажимает «Выбрать все» на странице реестра
- **THEN** выбраны только показанные навыки, а счётчик панели соответствует их числу

#### Scenario: Change registry view

- **WHEN** после выбора пользователь меняет страницу, фильтр или сортировку
- **THEN** выбор сбрасывается, ранее выбранные скрытые навыки не отправляются в следующую команду

### Requirement: Contract-backed eligible rollout

Реестр SHALL предлагать `whitelist → prod` и, по решению пользователя для MOS-1772, `approved → whitelist` через опубликованный POST status с expected_version и UUID Idempotency-Key для каждого навыка. UI MUST NOT считать `review` согласованным или автоматически принимать решение ревью. `approved` SHALL обозначать только фактически полученный статус. Эти варианты MUST NOT объявляться гарантией принятия конкретного перехода backend.

Оба действия SHALL использовать общий выбор видимых строк. Пустой выбор, наличие неподходящего для выбранного действия статуса или ошибка обновления данных SHALL блокировать это действие с пояснением; неподходящие строки MUST NOT молча пропускаться. Перед отправкой UI SHALL показывать имена, ID, версии и число выбранных навыков, переход и предупреждение о частичном успехе в одном подтверждении. Для выката в prod SHALL явно указываться продуктивный контур. Отмена MUST NOT отправлять запросы. Известное изменение status/version выбранных записей до отправки SHALL требовать нового подтверждения. Во время выполнения группы SHALL предотвращаться повторный запуск любого массового действия и изменение подтверждённого состава.

#### Scenario: Confirm production rollout

- **WHEN** пользователь выбирает навыки в whitelist и подтверждает выкат в продуктивный контур
- **THEN** команды используют только подтверждённые ID и версии, целью каждого перехода является prod

#### Scenario: Confirm whitelist transition

- **WHEN** пользователь выбирает два или более навыка в approved и подтверждает перевод
- **THEN** окно перечисляет их ID и версии, предупреждает о частичном результате, а каждая команда использует соответствующую версию и цель whitelist

#### Scenario: Ineligible selection

- **WHEN** выбор пуст или содержит навык, статус которого не подходит выбранному действию, включая review для перевода в whitelist
- **THEN** это действие недоступно с пояснением, неподходящие строки не пропускаются молча и не объявляются успешно переведёнными

#### Scenario: Cancel or stale confirmation

- **WHEN** пользователь отменяет подтверждение либо до отправки стало известно об изменении status/version выбранного навыка
- **THEN** команды по этому подтверждению не отправляются; для изменившихся данных требуется новое подтверждение

### Requirement: Sequential commands and per-item outcome

Команды SHALL выполняться последовательно, не более одной одновременно, без batch-запроса и автоматических повторов. Ошибка одного навыка SHALL сохраняться в отчёте, остальные подтверждённые элементы SHALL продолжать обрабатываться. Уход со страницы или вкладки SHALL прекращать отправку ещё не начатых команд без утверждения об отмене уже отправленной.

UI SHALL показывать отдельный результат по ID и цели и различать полный успех, частичный успех, отказ и неизвестный исход. Успех перехода SHALL подтверждаться валидным ответом с запрошенным prod или whitelist; другой status SHALL показываться с предупреждением, не как целевой успех. Timeout, сетевая ошибка, 5xx или невалидный успешный ответ SHALL означать неизвестный исход. Подтверждённый отказ MUST NOT приводить к оптимистическому изменению статуса; при неизвестном исходе UI MUST NOT утверждать, что статус не изменился. После обработки SHALL обновляться реестр, очередь ревью и затронутые карточки; отчёт SHALL сохраняться при обновлении данных в рамках открытой страницы. UI MUST NOT создавать фиктивную запись аудита или утверждать серверную запись автора и времени без доказательства backend.

#### Scenario: Successful sequential rollout

- **WHEN** пользователь подтверждает группу из нескольких навыков и повторно нажимает действие во время выполнения
- **THEN** следующая команда отправляется только после завершения предыдущей, повторное нажатие не создаёт вторую группу, успешные результаты показаны по каждому навыку

#### Scenario: Partial success

- **WHEN** сервер подтверждает целевой статус для одного навыка и отклоняет другой, в том числе из-за изменения версии
- **THEN** результаты отображаются отдельно, остальные элементы обрабатываются, данные обновляются без сообщения об успехе всей группы и без автоматической повторной команды с новой версией

#### Scenario: Response differs from target

- **WHEN** валидный ответ содержит status, отличный от запрошенного prod или whitelist
- **THEN** UI показывает фактическое состояние и предупреждение, не объявляя целевой переход успешным

#### Scenario: Switch skills section tabs during rollout

- **WHEN** пользователь уходит с вкладки реестра на «Домены» или «Ревью» и возвращается до либо после ответа на уже отправленную команду
- **THEN** отчёт и блокировка текущего запроса сохраняются; видны обработанные, ожидающие ответа и неотправленные навыки; оставшиеся команды не отправляются автоматически даже после возвращения на вкладку
- **AND** сохранение состояния ограничено открытой страницей навыков, без persistent queue или восстановления после перезагрузки

#### Scenario: Owner changes during a run

- **WHEN** владелец сессии сменился до завершения группы
- **THEN** новые команды прежней группы не отправляются и запоздалые результаты не выдаются за результат нового владельца

### Requirement: Read current state before a new attempt

При неизвестном исходе UI SHALL предлагать чтение актуальной карточки, а не повтор команды. Ошибка чтения SHALL сохранять неопределённость. Успешное чтение SHALL показывать текущее состояние без утверждения, что именно потерянная команда его установила. Новая попытка SHALL требовать актуального исходного статуса выбранного действия (`whitelist` для prod либо `approved` для whitelist), нового осознанного выбора/подтверждения, актуальной версии и нового Idempotency-Key. Подтверждённо успешные элементы MUST NOT автоматически повторяться; действие повтора всей группы SHALL отсутствовать. Сохранение очереди и отчёта после перезагрузки не требуется.

#### Scenario: Lost response

- **WHEN** соединение оборвалось после отправки команды
- **THEN** результат этого навыка обозначен как неизвестный, доступно чтение состояния без автоматического POST, отчёт остальных элементов сохраняется

#### Scenario: Refresh after unknown outcome

- **WHEN** после неизвестного исхода чтение возвращает целевой статус, исходный статус либо ошибку
- **THEN** целевой статус не предлагается повторно для той же команды; исходный допускает только новую явно подтверждённую попытку с актуальной версией; ошибка чтения не разрешает повтор команды по старым данным
