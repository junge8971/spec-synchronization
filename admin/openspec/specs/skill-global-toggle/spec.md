# skill-global-toggle Specification

## Purpose

Предоставить достоверное состояние навыка и подтверждённое глобальное включение/отключение с обязательными полями и восстановлением после неизвестного исхода команды.

## Requirements

### Requirement: Server skill state

UI SHALL читать status/version карточки навыка. При prod SHALL показываться полоса «Активен» с действием «Отключить», при disabled — «Отключён» с действием «Включить». При остальных статусах полоса SHALL отсутствовать. Действия SHALL соблюдать существующую permission-модель, без ролей прототипа или новых назначенных клиентом разрешений. Полоса SHALL содержать текстовое состояние независимо от цвета и сохранять доступность на узком экране.

Ошибка чтения MUST NOT трактоваться как отключение; команда по устаревшим данным SHALL быть недоступна до успешного чтения. Длительности, инциденты, статистика и список поверхностей SHALL оставаться вне MVP.

#### Scenario: Read actionable state

- **WHEN** успешно загружен навык в prod или disabled
- **THEN** UI показывает соответствующее состояние и разрешённое текущими permissions действие без вымышленных метрик

#### Scenario: Other status

- **WHEN** карточка имеет статус, отличный от prod и disabled
- **THEN** полоса глобального переключения отсутствует, а статус карточки не подменяется на «Активен»

#### Scenario: Read failed

- **WHEN** чтение карточки завершилось ошибкой
- **THEN** UI показывает ошибку и повтор, не объявляет навык отключённым и не разрешает команду по старой версии

### Requirement: Confirm global disable and enable

Перед каждым действием UI SHALL открывать отдельный диалог с названием навыка, понятным действием и пояснением глобального эффекта на всех поверхностях, где навык подключён. UI MUST NOT обещать мгновенное применение или запись аудита без серверного подтверждения этих гарантий.

Отключение SHALL требовать текстовое «Основание» и «Что увидит пользователь». Включение SHALL требовать текстовое «Основание», без поля сообщения. После trim основание SHALL содержать 1–32 символа, сообщение отключения — минимум один символ. Поля SHALL начинаться пустыми, без фиктивных defaults; значения из прототипа MUST NOT объявляться серверным справочником. Невалидный ввод MUST NOT отправляться.

Диалоги SHALL предоставлять «Отмена» и «Отключить навык» либо «Включить навык», доступные подписи, ошибки полей и клавиатурный фокус. Отключение SHALL визуально обозначаться destructive-действием. Отмена MUST NOT отправлять запрос. При закрытии фокус SHALL возвращаться на инициатор, если он присутствует.

#### Scenario: Confirm disable

- **WHEN** пользователь подтверждает отключение prod-навыка с валидным основанием и сообщением
- **THEN** отправляется POST disable именно этого навыка с reason, fallback_text, expected_version подтверждаемой карточки и UUID Idempotency-Key; POST status и обновления поверхностей не выполняются

#### Scenario: Confirm enable

- **WHEN** пользователь подтверждает включение disabled-навыка с валидным основанием
- **THEN** отправляется POST enable с reason, expected_version и UUID Idempotency-Key, без fallback_text

#### Scenario: Invalid form

- **WHEN** основание после trim пустое или длиннее 32 символов либо сообщение отключения пустое
- **THEN** UI показывает ошибку соответствующего поля и не отправляет команду; основание длиной 32 символа допустимо

#### Scenario: Cancel confirmation

- **WHEN** пользователь отменяет диалог
- **THEN** запрос не отправляется и состояние навыка не меняется

### Requirement: Consistent global action outcome

UI SHALL предотвращать повторную отправку в pending. Подтверждение SHALL относиться к skill_id, status и version; известное изменение снимка до отправки SHALL требовать нового чтения и подтверждения. Смена навыка SHALL закрывать старую форму; её поздний ответ MUST NOT менять другую карточку.

Отображение SHALL меняться только по валидным серверным данным. Ответ команды SHALL соответствовать выбранному skill_id и действию; невалидный или несовпадающий ответ MUST NOT считаться успехом. После успеха UI SHALL перечитывать карточку для актуальной version и обновлять связанные данные реестра; новая команда MUST NOT отправляться до успешного чтения. UI MUST NOT синтезировать version или статус результата.

Известный отказ SHALL сохранять контекст и ввод без сообщения об успехе. Неизвестный исход SHALL предоставлять перечитывание без автоматической повторной/обратной команды. Новая команда SHALL требовать актуального чтения и нового подтверждения. UI SHALL использовать согласованный с backend переход prod → disabled → prod через disable/enable с глобальным действием на подключённых поверхностях. Текущая реализация согласована по подтверждению пользователя от 13.10.2026 после консультации с backend. Согласование MUST NOT выдаваться за выполненный интеграционный прогон; схемы и моки MUST NOT считаться доказательством фактического поведения стенда. Конкретный срок применения и HTTP/business-код concurrency этим подтверждением не задаются.

#### Scenario: Pending or changed version

- **WHEN** пользователь повторно нажимает действие в pending либо до отправки получена новая version/status
- **THEN** второй запрос не создаётся, а изменившийся снимок требует нового подтверждения

#### Scenario: Success and refresh

- **WHEN** сервер вернул валидное подтверждение команды
- **THEN** UI использует серверный результат и перечитывает карточку; отсутствие version в ответе не заменяется локальным инкрементом

#### Scenario: Refresh failed after success

- **WHEN** команда подтверждена, но последующий GET карточки не удался
- **THEN** UI сообщает об ошибке обновления отдельно от успеха команды и блокирует следующую команду до успешного чтения, не повторяя мутацию

#### Scenario: Request rejected

- **WHEN** сервер отклоняет команду, включая ошибку валидации или устаревшей версии
- **THEN** UI показывает ошибку без локального успеха и сохраняет ввод; конкретный HTTP-код concurrency не выдумывается

#### Scenario: Response lost or invalid

- **WHEN** ответ потерян, невалиден либо не соответствует skill_id/action
- **THEN** UI не объявляет успех или гарантированную отмену и предлагает чтение; ошибка чтения сохраняет неопределённость, успешное чтение не приписывает состояние потерянному запросу

#### Scenario: Skill changed during request

- **WHEN** пользователь открыл другую карточку до завершения команды
- **THEN** ответ старой команды не меняет состояние и форму нового навыка
