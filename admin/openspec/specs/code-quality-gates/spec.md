# Code Quality Gates Specification

## Purpose

Закрепить понятные правила сопровождения кода агентом и единый проверяемый барьер качества, который не позволяет считать lint с предупреждениями успешной проверкой.

## Requirements

### Requirement: Project agent guidance defines readable decomposition

Проект SHALL предоставлять в `AGENTS.md` требования к декомпозиции по ответственности, предметным именам, явному потоку управления и сохранению поведения. Требования SHALL предпочитать читаемость краткости, запрещать дробление только ради метрик и абстракции без текущей необходимости. Правила SHALL требовать соблюдения FSD и размещения типов, предметных констант, обработчиков и компонентов в предназначенных для них файлах и каталогах ближайшего владельца. Соблюдение обязательной структуры SHALL NOT считаться необязательным дроблением ради метрик.

#### Scenario: Function mixes responsibilities

- **WHEN** агент изменяет функцию, совмещающую самостоятельные ответственности
- **THEN** он оценивает выделение именованных операций по смыслу, а не по числу строк, и проверяет вызывающие места

#### Scenario: Existing code is already cohesive

- **WHEN** затронутая функция решает одну понятную задачу, не содержит существенного дублирования и соответствует обязательным правилам размещения
- **THEN** правила не требуют добавлять обёртки или новые файлы ради формальной декомпозиции

#### Scenario: Cohesive code violates mandatory placement

- **WHEN** файл содержит связную логику, но также типы, константы, обработчики или несколько компонентов в нарушение правил размещения
- **THEN** агент разделяет декларации по назначению и владельцу, сохраняя поведение и не создавая ненужных абстракций

### Requirement: Lint warnings block acceptance

Полная lint-проверка проекта и lint-проверка staged-кода SHALL завершаться ненулевым кодом при наличии хотя бы одной оставшейся ошибки или предупреждения. При отсутствии диагностик lint SHALL завершаться успешно. Проверки SHALL охватывать поддерживаемый рукописный код приложения, моков, скриптов, тестов и конфигурации.

#### Scenario: Warning without errors

- **WHEN** проверяемый код вызывает предупреждение о сложности, но не содержит lint-ошибок
- **THEN** полная проверка завершается неуспешно, а staged-проверка блокирует commit, если этот код входит в staged-набор

#### Scenario: Clean code

- **WHEN** в проверяемом коде нет ошибок и предупреждений
- **THEN** lint-проверка завершается с кодом 0

### Requirement: Quality rules cannot be bypassed to accept a refactor

Правила для агента SHALL запрещать повышение порогов сложности, широкие исключения файлов, отключение правил и ослабление тестовых утверждений только ради зелёных проверок. Любое необходимое исключение SHALL иметь конкретное обоснование и минимальную область действия.

#### Scenario: Refactored code still exceeds complexity limit

- **WHEN** после декомпозиции остаётся предупреждение о сложности
- **THEN** агент продолжает упрощение либо явно сообщает о препятствии, а не скрывает предупреждение изменением порога

### Requirement: Verification reports distinguish executed and missing checks

Правила для агента SHALL требовать проверки сохранения поведения, просмотра итогового diff, запуска подходящих проверок типов, lint, форматирования и тестов, а для соответствующих изменений — сборки и актуальности генерируемых API-типов. E2E/browser-тесты SHALL NOT создаваться, редактироваться или запускаться без отдельного явного разрешения пользователя; при разрешении их область SHALL ограничиваться согласованными сценариями. По решению пользователя автоматические проверки ограничиваются unit- и интеграционными тестами без UI-компонентных и E2E-наборов. Итог SHALL различать успешные проверки, ошибки и проверки, которые не выполнялись.

#### Scenario: Environment prevents verification

- **WHEN** проверка недоступна или падает по причине вне изменения
- **THEN** агент сообщает команду и причину ограничения и не объявляет эту проверку успешной

#### Scenario: Logic is refactored

- **WHEN** меняется структура нетривиальной логики
- **THEN** существенный сценарий и граничный случай остаются покрыты исполняемыми unit- или интеграционными тестами; существующие подходящие тесты переиспользуются без обязательного дублирования

#### Scenario: Browser tests are not authorized

- **WHEN** пользователь разрешил структурную миграцию, но отдельно не разрешал E2E/browser-тесты
- **THEN** агент не создаёт, не редактирует и не запускает их и явно сообщает, что browser-проверка не выполнялась

### Requirement: Application code respects FSD ownership and public APIs

Весь рукописный код приложения SHALL соблюдать направление зависимостей от слоя приложения через pages, widgets, features, entities к shared, кроме адресных optional-исключений ниже. Слайсы одного слоя SHALL NOT зависеть друг от друга. Внешние потребители SHALL обращаться к слайсу через его публичный API, а не внутренние файлы. Внутри слайса SHALL использоваться прямые внутренние импорты без обращения через собственный публичный API. Shared и слой приложения SHALL организовываться по сегментам без искусственных предметных слайсов. Эти ограничения SHALL одинаково применяться к алиасам, относительным путям, type-only импортам и re-export.

Адресные исключения SHALL разрешать размещение нового предметного кода базы знаний в `app/optional/knowledge-base/` и A/B-тестирования в `app/optional/ab-testing/` вместо глобальных FSD-слайсов ради изолированного удаления вместе с документированными точками регистрации. Их внешние runtime-потребители SHALL ограничиваться композицией приложения через публичный API соответствующего модуля; framework-конфигурация SHALL сохранять специальные route entrypoints. Каждый модуль SHALL зависеть только от собственных модулей, shared и публичных API entities, а не от application internals либо чужих pages/widgets/features. Другие бизнес-слайсы и shared MUST NOT импортировать эти модули; optional-модули MUST NOT импортировать друг друга. Исключения MUST NOT отключать lint, проверки компонентов/деклараций и границ или распространяться на другие optional-модули автоматически.

#### Scenario: Dependency points to a higher layer or sibling slice

- **WHEN** код импортирует более высокий слой или другой слайс того же слоя вне адресного исключения
- **THEN** архитектурная проверка завершается ошибкой с указанием нарушающей зависимости

#### Scenario: External consumer bypasses a slice public API

- **WHEN** внешний потребитель импортирует внутренний файл слайса через алиас, относительный путь или re-export
- **THEN** архитектурная проверка отклоняет зависимость

#### Scenario: Internal implementation uses a local module

- **WHEN** модуль слайса напрямую импортирует допустимый внутренний модуль того же слайса
- **THEN** архитектурная проверка разрешает такой импорт

#### Scenario: New slice is introduced

- **WHEN** появляется новый слайс, не существовавший при первоначальной настройке проверок
- **THEN** к нему автоматически применяются те же ограничения границ и публичного API

#### Scenario: Optional module consumes stable dependencies

- **WHEN** KB или A/B импортирует shared либо публичный API entities, а приложение подключает публичный API соответствующего модуля или framework route entrypoint
- **THEN** архитектурная проверка разрешает адресную зависимость, сохраняя структурные проверки файлов

#### Scenario: Business code depends on optional implementation

- **WHEN** другой бизнес-раздел/shared импортирует KB или A/B либо optional-модуль импортирует чужой feature или application internals, в том числе относительным/type-only импортом или re-export
- **THEN** архитектурная проверка отклоняет зависимость и не позволяет сделать удаление optional-модуля зависимым от другого раздела

#### Scenario: Optional modules depend on each other

- **WHEN** A/B импортирует KB или KB импортирует A/B любым видом импорта либо re-export
- **THEN** архитектурная проверка отклоняет зависимость, даже через публичный index.ts

### Requirement: Declarations are located by purpose within their owner

Именованные типы и интерфейсы, включая props, SHALL размещаться в `types/*.types.ts` ближайшего владельца. Предметные константы, runtime enum, фиксированные справочники и значения по умолчанию SHALL размещаться в `constants/*.constants.ts`. Логика именованных обработчиков UI-событий SHALL размещаться в `handlers/` соответствующего владельца; stateful-обработчики SHALL сохранять правила React hooks и корректные зависимости. Эти каталоги SHALL находиться внутри подходящих FSD-сегментов или локальных групп компонентов, а не в общих свалках разных предметных областей. Правила SHALL отличать фиксированные предметные значения от локальных вычислений, схем валидации, результатов hooks и callback-функций библиотечных операций.

#### Scenario: Component declares named props inline

- **WHEN** компонент содержит локальную декларацию типа props вне разрешённого файла типов
- **THEN** проверка размещения именованных типов сообщает нарушение; тип переносится к владельцу с сохранением контракта компонента

#### Scenario: Fixed configuration shares a file with event logic

- **WHEN** файл обработчика содержит предметный справочник или значения формы по умолчанию
- **THEN** агент выносит эти значения в каталог констант владельца и проверяет сохранение мутабельности и ссылочной семантики

#### Scenario: Handler depends on form and navigation state

- **WHEN** обработчик переносится из компонента или хука и использует форму, состояние либо навигацию
- **THEN** сохраняются корректные зависимости, порядок эффектов и поведение повторных вызовов без stale closures

#### Scenario: Local computation uses const

- **WHEN** локальный результат вычисления или hook result объявлен через `const`
- **THEN** правила не требуют переносить его в файл предметных констант только из-за способа объявления

#### Scenario: Type is inferred from a validation schema

- **WHEN** тип выводится из схемы валидации
- **THEN** после разделения файлов сохраняются выводимость типа и единый источник контракта без дублирования схемы и runtime-цикла

### Requirement: Components are separated and nested by ownership

Каждый рукописный React-компонент SHALL иметь отдельный файл, если конкретный контрактный случай не покрыт явно разрешённым исключением. Приватные дочерние компоненты SHALL размещаться в подпапках владельца. Компонент с несколькими потребителями SHALL размещаться у ближайшего общего допустимого владельца, а не копироваться или автоматически переноситься в shared. Структура SHALL отражать владение, а не каждое вложение JSX.

#### Scenario: Multiple components share a file

- **WHEN** один файл содержит несколько компонентов и не имеет разрешённого адресного исключения
- **THEN** автоматическая проверка компонентов отклоняет файл

#### Scenario: Child belongs to one component

- **WHEN** дочерний компонент используется только одним компонентом-владельцем
- **THEN** он имеет отдельный файл в подпапке этого владельца

#### Scenario: Child gains another consumer

- **WHEN** компонент нужен нескольким потребителям
- **THEN** его размещение отражает общего владельца и сохраняет FSD-границы без дублирования реализации

### Requirement: Structural checks cover the whole handwritten application

Полная проверка `yarn lint` SHALL выполнять автоматические проверки FSD-границ, публичных API, числа компонентов на файл и размещения именованных типов для рукописного приложения, включая новые файлы, за исключением согласованно пропускаемых при обходе Git-игнорируемых файлов. Проверяемые правила структуры каталогов SHALL входить в тот же барьер качества. Staged-проверка SHALL NOT позволять обходить архитектурные ограничения проверкой только изменённого импортируемого файла. По решению пользователя отдельные исполняемые тесты этих правил удаляются; их отсутствие MUST NOT считаться доказательством эквивалентности правил. Семантические правила, не распознаваемые надёжно автоматически, SHALL оставаться явной обязанностью агента и review, а не объявляться полностью покрытыми линтером.

#### Scenario: Old file violates a new rule

- **WHEN** проверка обнаруживает нарушение в проверяемом существующем, а не только новом файле
- **THEN** нарушение блокирует приёмку и не скрывается legacy-baseline или широким исключением

#### Scenario: Import target changes ownership

- **WHEN** staged-изменение переносит модуль так, что существующий потребитель нарушает архитектурную границу
- **THEN** архитектурная проверка охватывает необходимые зависимости полного приложения и обнаруживает нарушение

#### Scenario: Rule configuration changes

- **WHEN** обновляется конфигурация структурных проверок
- **THEN** правила и их области действия сохраняются, а отсутствие удалённых автоматических тестов явно учитывается как ограничение проверки

### Requirement: Migration preserves generated and framework contracts with explicit exceptions

Миграция SHALL охватывать весь существующий рукописный код приложения и соответствующие unit/component-тесты, сохраняя URL, API-контракты, поведение, валидацию, обработку ошибок и доступность. Генератор API-типов, его выходной путь и генерируемые файлы SHALL сохраняться без ручной декомпозиции. Framework entrypoints, специальные экспорты и typegen SHALL сохранять совместимость. Исключения для исходников shadcn SHALL требовать отдельного явного согласования конкретных файлов, правил и причин; весь `shared/ui` SHALL NOT исключаться из проверок. Несогласованные исключения SHALL NOT считаться принятыми или позволять объявить миграцию завершённой.

#### Scenario: Generated API schema is checked

- **WHEN** миграция затрагивает потребителей сгенерированных API-типов
- **THEN** генератор и его выходной путь остаются прежними, а проверка актуальности типов проходит без ручного исправления generated-файла

#### Scenario: Framework module is decomposed

- **WHEN** реализация framework-модуля разделяется по файлам
- **THEN** обязательные экспорты и точки входа сохраняются, typegen и сборка проходят, публичные URL остаются прежними

#### Scenario: Shadcn compound component conflicts with a rule

- **WHEN** исходник shadcn требует решения между разделением компонентов и исключением
- **THEN** агент предъявляет конкретные файлы, правила и последствия для согласования и не отключает проверки для всего `shared/ui`

#### Scenario: Migration is declared complete

- **WHEN** агент завершает структурную миграцию
- **THEN** весь рукописный код соответствует правилам либо явно согласованным адресным исключениям, проверки сохранения поведения выполнены, а исходные пользовательские правки сохранены

### Requirement: Response templates optional ownership exception

В дополнение к существующим адресным optional-исключениям правила SHALL разрешать предметный код шаблонов ответов в `app/optional/response-templates/` ради независимого удаления. Это адресное расширение правила Application code respects FSD ownership and public APIs SHALL NOT давать исключений другим модулям или ослаблять существующие границы. Композиция приложения SHALL обращаться через публичный index.ts; framework-конфигурация SHALL сохранять штатные route entrypoints. Модуль SHALL зависеть только от собственного кода, shared и публичных API entities. Другие бизнес-слайсы, shared и optional-модули MUST NOT импортировать response-templates; response-templates MUST NOT импортировать другие optional-модули, чужие pages/widgets/features или application internals. Проверки SHALL охватывать relative/type-only импорты и re-export, размещение деклараций и один компонент на файл без новых широких исключений. Правила проекта и lint SHALL описывать одинаковую адресную границу.

#### Scenario: Permitted dependencies

- **WHEN** response-templates импортирует shared либо публичный API entities, а композиция подключает его index.ts
- **THEN** архитектурная проверка разрешает зависимость и сохраняет остальные структурные проверки

#### Scenario: Cross module import

- **WHEN** response-templates импортирует код базы знаний либо другой optional-модуль импортирует response-templates, включая относительный type-only импорт или re-export
- **THEN** проверка отклоняет импорт, даже если он проходит через публичный index.ts

#### Scenario: Internal API bypass

- **WHEN** внешний потребитель обращается к внутреннему файлу response-templates вне штатного framework route entrypoint
- **THEN** проверка отклоняет зависимость, включая алиас и относительный путь

### Requirement: System-state optional ownership exception

В дополнение к действующим адресным FSD-исключениям предметный код system-state SHALL размещаться в `app/optional/system-state/`, а серверные моки — в `mocks/system-state/` ради независимого удаления. Application composition SHALL подключать публичный API модуля, framework-конфигурация — штатные route entrypoints. Модуль SHALL зависеть только от собственного кода, shared и публичных API entities, а не от application internals или чужих pages/widgets/features. Shared, другие бизнес-слайсы и optional-модули MUST NOT импортировать system-state; system-state MUST NOT импортировать другие optional-модули. Ограничения SHALL применяться к алиасам, relative/type-only импортам и re-export.

Правила проекта, lint и исполняемые архитектурные проверки SHALL согласованно фиксировать только это адресное исключение, не отключая существующие проверки деклараций, компонентов и границ. Удаление модуля и документированных точек подключения MUST NOT требовать изменений предметного кода других разделов или удаления общих DTO.

#### Scenario: Allowed optional dependency

- **WHEN** system-state импортирует shared либо публичный API entities, а приложение подключает его публичный descriptor
- **THEN** архитектурная проверка разрешает эти зависимости и продолжает проверять размещение деклараций и компонентов

#### Scenario: Cross-module dependency

- **WHEN** база знаний импортирует system-state или system-state импортирует внутренний код другого optional-модуля, в том числе type-only или через re-export
- **THEN** архитектурная проверка отклоняет зависимость

#### Scenario: Remove the optional module

- **WHEN** удалены папки system-state и документированные точки регистрации
- **THEN** остальные разделы и общие контракты остаются сборочными без зависимости от удалённого бизнес-кода

### Requirement: API registry optional ownership exception

В дополнение к действующим адресным FSD-исключениям предметный код API registry SHALL размещаться в `app/optional/api-registry/`, а серверные моки — в `mocks/api-registry/` ради независимого удаления. Application composition SHALL подключать публичный API модуля, framework-конфигурация — штатные route entrypoints. Модуль SHALL зависеть только от собственного кода, shared и публичных API entities, а не от application internals или чужих pages/widgets/features. Shared, другие бизнес-слайсы и optional-модули MUST NOT импортировать API registry; API registry MUST NOT импортировать другие optional-модули. Ограничения SHALL применяться к алиасам, relative/type-only импортам и re-export.

Правила проекта, lint и исполняемые архитектурные проверки SHALL согласованно фиксировать только это адресное исключение, не отключая существующие проверки деклараций, компонентов и границ. Удаление модуля и документированных точек подключения MUST NOT требовать изменений предметного кода других разделов или удаления общих DTO.

#### Scenario: Allowed optional dependency

- **WHEN** API registry импортирует shared либо публичный API entities, а приложение подключает публичный descriptor
- **THEN** архитектурная проверка разрешает эти зависимости и продолжает проверять размещение деклараций и компонентов

#### Scenario: Cross-module dependency

- **WHEN** API registry импортирует базу знаний или другой optional-модуль импортирует API registry, в том числе через relative/type-only импорт или re-export
- **THEN** архитектурная проверка отклоняет зависимость, даже через публичный index.ts

#### Scenario: Remove the optional module

- **WHEN** папки API registry и документированные точки регистрации удалены в отдельной копии
- **THEN** остальные разделы и общие контракты остаются сборочными без зависимости от удалённого бизнес-кода

### Requirement: Oxlint replaces ESLint without losing lint rules

Полная проверка `yarn lint`, исправление `yarn lint:fix` и staged-проверки SHALL использовать Oxlint и, при необходимости, готовые совместимые плагины и проверки без запуска ESLint. Пакет ESLint MAY оставаться зависимостью используемых плагинов; самописные lint-инструменты и плагины SHALL NOT использоваться. Прежние конфигурация, тестовые привязки и зависимости, более не нужные после перехода, SHALL быть удалены. Новые проверки SHALL сохранять поведение действующих правил, их параметры, тяжесть диагностик, области действия и согласованные адресные исключения, кроме отдельно согласованных ниже различий; имена правил и пакеты при этом могут отличаться. Другие неподтверждённые эквиваленты SHALL блокировать завершение миграции, а не устраняться отключением правила или расширением исключения.

#### Scenario: Existing rule rejects a violation

- **WHEN** поддерживаемый рукописный файл содержит нарушение действующего правила сложности, React Hooks, доступности, импорта или размещения деклараций
- **THEN** новая проверка обнаруживает соответствующее нарушение с сохранёнными параметрами и не принимает его из-за замены линтера

#### Scenario: Existing valid code and exceptions

- **WHEN** проверяется допустимый код или согласованное адресное исключение, включая перечисленные compound-файлы shadcn и разрешённые контекстные типы
- **THEN** новая проверка принимает соответствующий случай без нового широкого исключения

#### Scenario: Inline globals and plugin directives

- **WHEN** исходный код требует дополнительные глобальные имена или точечное отключение правила JS-плагина
- **THEN** globals задаются в конфигурации Oxlint, а директивы используют имена соответствующих Oxlint-плагинов; прежние `/* global … */` и старые имена ESLint-плагинов не гарантируются

#### Scenario: Current Vite URL import

- **WHEN** проверяется текущий импорт `pdfjs-dist/build/pdf.worker.min.mjs?url`
- **THEN** готовые резолверы и boundaries-плагин проверяют наличие цели без общего исключения `core-modules`; новые `?url`-импорты могут требовать отдельной настройки

#### Scenario: Import-order autofix

- **WHEN** автоматически исправляется порядок импортов
- **THEN** применяется поведение исходного готового плагина `import/order`, которое может переместить отдельный комментарий, как в прежнем ESLint

#### Scenario: No equivalent is established

- **WHEN** для действующего правила, его опции или области действия не подтверждён эквивалент готовыми средствами без запуска ESLint
- **THEN** миграция не объявляется завершённой и конкретный пробел выносится на согласование

#### Scenario: Legacy lint command is removed

- **WHEN** миграция объявляется завершённой
- **THEN** полный lint, lint с исправлениями и staged-проверка не запускают ESLint, а прежние конфигурация и неиспользуемые зависимости удалены; пакет ESLint допускается только как зависимость используемых готовых плагинов

### Requirement: Replacement preserves full and staged lint coverage

Новый lint-барьер SHALL охватывать поддерживаемые рукописные файлы приложения, моков, скриптов, тестов и конфигурации. По решению пользователя форматирование проверяется отдельно от полного lint и в staged-барьере. По решению пользователя полные команды MAY пропускать файлы, исключённые Git при стандартном обходе Oxlint/Oxfmt; это сужение области MUST быть указано явно. Staged-исправления и проверки архитектуры полного неигнорируемого приложения SHALL сохранять действующие гарантии. Смена инструмента SHALL NOT молча исключать другие файлы или заменять полную проверку анализом только staged-файлов.

#### Scenario: Warning or formatting violation

- **WHEN** проверяемый файл содержит предупреждение о сложности выше прежнего порога либо нарушение форматирования
- **THEN** lint или проверка форматирования соответственно завершается неуспешно при оставшейся диагностике

#### Scenario: Staged target invalidates an unchanged consumer

- **WHEN** staged-изменение расположения модуля делает импорт неизменённого потребителя нарушением FSD или публичного API
- **THEN** staged-барьер проверяет необходимые зависимости всего приложения и отклоняет изменение

#### Scenario: New slice and alternate imports

- **WHEN** новый неигнорируемый FSD-слайс или разрешённый optional-модуль нарушает границу через алиас, относительный или type-only импорт либо re-export
- **THEN** полный lint обнаруживает нарушение, а новый FSD-слайс получает соответствующие ограничения без ручного добавления в список проверяемых

#### Scenario: Git-ignored files in full commands

- **WHEN** полный lint или форматирование обходит файлы, исключённые Git
- **THEN** прямой обход может пропустить их, в том числе прежние 529 нарушений OpenSpec; это не считается исправлением этих файлов

#### Scenario: Generated file passed to staged check

- **WHEN** в staged-набор явно передан согласованно исключённый generated-файл API-типов и других нарушений нет
- **THEN** staged-проверка завершается успешно без ложной ошибки об игнорируемом файле

### Requirement: Oxfmt replaces project formatting commands without reducing coverage

Команды `yarn format`, `yarn format:check`, а также форматирование в staged-барьере SHALL использовать Oxfmt вместо самостоятельного вызова Prettier и SHALL NOT использовать самописные инструменты форматирования. Полные `lint` и `lint:fix` SHALL NOT запускать форматтер. Они SHALL сохранять поддерживаемые типы файлов, корпоративные настройки форматирования, согласованные исключения и поведение исправлений, кроме согласованного стандартного игнорирования Git-исключённых файлов при полном обходе. При переносе корпоративного preset в новый конфиг SHALL сохраняться проверяемое соответствие его настройкам. Неподдерживаемые случаи или расхождения форматирования SHALL быть явно представлены на согласование, а не скрыты широкими исключениями или массовым переформатированием. Использование Prettier, встроенного в npm-версию Oxfmt для отдельных форматов, допускается и не считается самостоятельным вызовом Prettier проектом.

#### Scenario: Clean and unformatted files

- **WHEN** `yarn format:check` проверяет соответствующий прежнему набор файлов и один из них не отформатирован
- **THEN** команда не изменяет файлы, сообщает нарушение и завершается неуспешно; корректно отформатированный набор проходит

#### Scenario: Formatting commands preserve scope

- **WHEN** выполняются `yarn format`, `yarn format:check` или staged-проверка для поддерживаемых JS/TS, JSON, CSS/SCSS, YAML, Markdown, HTML, MDX или SVG-файлов
- **THEN** соответствующие проверка и исправление сохраняют параметры и согласованные области действия, включая принятое пользователем игнорирование Git-исключённых файлов; иные несовпадения являются блокером согласования

#### Scenario: Shared preset changes

- **WHEN** при использовании или обновлении корпоративного preset настройки проекта расходятся с настройками Oxfmt
- **THEN** проверяемое соответствие обнаруживает расхождение и не позволяет считать перенос стиля подтверждённым

#### Scenario: Bundled formatting support

- **WHEN** Oxfmt форматирует HTML или MDX с помощью встроенного Prettier
- **THEN** проект не требует самостоятельного вызова Prettier и сохраняет проверку соответствующего формата

### Requirement: Full test execution preserves the retained checks and isolation

Полный `yarn test` SHALL запускать только оставшиеся unit- и интеграционные тесты приложения и возвращать ненулевой код при отказе любого набора. По решению пользователя компонентные и E2E-тесты SHALL быть удалены; hook-тесты, проверяющие бизнес-логику без рендеринга пользовательского интерфейса, SHALL сохраняться как unit/интеграционные. Отдельные Node-тесты реализации моков, линтера, форматтера, архитектурных правил, API-контрактов, безопасности, production-конфигурации, PDF и SPA-сервера также удалены; их отсутствие MUST NOT выдаваться за сохранение прежнего покрытия. Runtime-моки и lint/FSD-правила SHALL оставаться действующими. Оставшиеся тесты SHALL сохранять изоляцию состояния и очистку ресурсов. Выборочный или watch-запуск SHALL NOT считаться заменой полного набора.

#### Scenario: Test group fails

- **WHEN** любой тестовый набор полного `yarn test` завершается ошибкой
- **THEN** полная команда завершается неуспешно и указывает отказавший набор

#### Scenario: Tests execute concurrently

- **WHEN** повышается параллельность или меняется окружение тестов
- **THEN** тестовые файлы не влияют друг на друга через структуру приложения, глобальное состояние, порты или fixtures, а повторные полные прогоны сохраняют результат

#### Scenario: Removed test categories

- **WHEN** разработчик запускает полный `yarn test` после удаления согласованных категорий тестов
- **THEN** unit- и интеграционные тесты выполняются, а компонентные, E2E и отдельные удалённые Node-тесты не запускаются

#### Scenario: Expensive retained tests

- **WHEN** измерения выявляют длительные оставшиеся unit- или интеграционные тесты
- **THEN** их оптимизируют без ослабления сохранённых утверждений или удаляют по решению пользователя, явно фиксируя потерянное покрытие; постоянные таймауты не увеличиваются

### Requirement: Performance claims are supported by comparable measurements

Изменение SHALL содержать воспроизводимые замеры полного lint, `yarn format:check` и полного тестового набора до и после, включая время Vitest, ранее существовавший Node-этап, условия среды и кэша, количество запусков, медиану wall-clock времени и результаты проверок. Анализ тестов SHALL выявлять измеренные узкие места и оценивать пригодные варианты оптимизации с учётом стабильности и стоимости поддержки. Сравнение SHALL явно указывать удалённые категории тестов и MUST NOT выдавать сокращённый набор за прежнее покрытие; неподтверждённый результат SHALL быть явно отмечен как ограничение.

#### Scenario: Comparable improvement

- **WHEN** не менее трёх сопоставимых запусков до и после показывают уменьшение медианы при сохранении успешных проверок
- **THEN** отчёт указывает команду, условия, обе медианы, наблюдаемую разницу и любые изменения покрытия

#### Scenario: No safe test improvement found

- **WHEN** измерения не подтверждают безопасного ускорения полного тестового набора
- **THEN** отчёт описывает проверенные варианты и ограничения и не объявляет тесты ускоренными

#### Scenario: Benchmark environment is unavailable

- **WHEN** ограничения окружения не позволяют выполнить сопоставимые замеры или проверки
- **THEN** отчёт явно указывает непройденные и незапущенные проверки и не заявляет улучшение без доказательств
