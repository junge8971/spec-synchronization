# surface-registration Specification

## Purpose

Обеспечить создание поверхностей по текущему API с корректными ссылками на ответственных пользователей и безопасным восстановлением после отказа либо неизвестного результата запроса.

## Requirements

### Requirement: Responsible assignments use business user identifiers

Регистрация SHALL выбирать обоих ответственных через существующий API бизнес-пользователей и отправлять их строковые ID в responsible.product и responsible.connection. Имя и email SHALL использоваться только для представления выбора. UI MUST NOT отправлять произвольное ФИО как ID, ограничивать выбор первой страницей либо восстанавливать ID старого черновика по совпадению имени. Старые текстовые назначения SHALL требовать явного перевыбора. Ошибка загрузки пользователей SHALL сохранять форму без синтетических вариантов. Назначение ответственного MUST NOT изменять permissions или сессию.

#### Scenario: Selected external user

- **WHEN** выбран пользователь с не-UUID строковым ID и заполнены остальные обязательные поля
- **THEN** POST содержит этот ID, а не ФИО; подтверждение выбора показывает серверные сведения без требования UUID

#### Scenario: Legacy draft

- **WHEN** восстановлен старый черновик с произвольными строками ответственных
- **THEN** форма сохраняет остальные данные, объясняет необходимость перевыбора и не отправляет старые строки как подтверждённые ID

### Requirement: Creation supports an atomic optional configuration

API-клиент и локальное API SHALL поддерживать configuration по текущему CreateSurfaceRequest. При передаче объекта SHALL применяться действующие правила конфигурации и атомарное создание; отсутствие или null SHALL сохранять backend defaults. UI без редактируемой конфигурации SHALL опускать поле, а не присылать вымышленные defaults. Создание MUST NOT подменяться последовательностью POST и скрытого PUT. После 201 SHALL сохраняться data.id и выполняться GET для подтверждения сохранённой карточки; ошибка GET MUST NOT приводить к повторному созданию.

#### Scenario: Configuration is provided

- **WHEN** API-клиент получает валидную конфигурацию вместе с данными создания
- **THEN** один POST передаёт configuration, последующее чтение отражает сохранённые настройки; отдельный PUT не выполняется

#### Scenario: Default configuration

- **WHEN** configuration отсутствует или равна null
- **THEN** применяется серверная конфигурация по умолчанию без локальной подстановки клиентом

#### Scenario: Detail cannot be read after creation

- **WHEN** POST вернул ID, а GET завершился ошибкой
- **THEN** ID сохраняется, доступен повтор только чтения, второй POST не выполняется

### Requirement: Rejections are distinct from unknown creation outcomes

UI SHALL различать подтверждённый отказ без создания и неизвестный исход. Документированные структурированные ошибки DOMAIN_ALREADY_IN_USE, неизвестного пользователя и конфигурации SHALL сохранять ввод, показывать серверную причину и связываться с полем, когда ответ содержит надёжный путь; исправление SHALL разрешать новую явную попытку без автоматического replay. Неизвестный формат ошибки MUST NOT разбираться по тексту message и MUST NOT считаться доказательством отсутствия созданной поверхности. Сетевой сбой после отправки SHALL сохранять блокировку слепого повторного создания.

#### Scenario: Confirmed domain conflict

- **WHEN** получен подтверждённый серверный отказ DOMAIN_ALREADY_IN_USE с указанием конфликтующего домена
- **THEN** форма показывает домен и ошибку, сохраняет ввод и позволяет исправить его; успешное создание не показывается

#### Scenario: Unknown responsible user

- **WHEN** сервер отклоняет назначение с надёжным указателем responsible.product или responsible.connection
- **THEN** ошибка отображается у соответствующего выбора, остальные поля не сбрасываются

#### Scenario: Lost response

- **WHEN** ответ на отправленный POST потерян
- **THEN** UI сообщает о неизвестном результате и не повторяет POST автоматически или как гарантированно безопасную попытку

### Requirement: Empty production catalog explains registration blocking and recovery

Если полный успешно загруженный продовый каталог пуст, шаг сценариев регистрации SHALL явно объяснять, что для продолжения нужен хотя бы один навык со статусом prod и что отсутствие таких навыков не означает отсутствие всех навыков. Причина SHALL быть видима без hover и программно связана с недоступным переходом «Далее». Шаг SHALL предоставлять явное обновление каталога без сброса анкеты, ответственных и введённых параметров. Обновление SHALL использовать существующие правила полного чтения и проверки каталога; pending/error/empty SHALL различаться. UI MUST NOT автоматически публиковать навыки, подставлять non-prod записи или разрешать пустой состав для обхода блокировки. Действующее разрешение пустого состава в карточке существующей поверхности SHALL сохраняться.

#### Scenario: No production skills

- **WHEN** полный запрос status=prod успешно возвращает пустой список
- **THEN** «Далее» недоступна, рядом видна связанная причина и действие обновления, а запрос создания поверхности не отправляется

#### Scenario: Production skill becomes available

- **WHEN** пользователь обновляет каталог после появления prod-навыка
- **THEN** навык становится доступен для выбора, введённая анкета сохранена, а переход разрешается только после валидного выбора и проверки параметров

#### Scenario: Refresh fails

- **WHEN** обновление каталога завершается ошибкой
- **THEN** показываются ошибка и безопасный повтор, форма сохраняется, отсутствие данных не представляется успешным пустым каталогом и создание не выполняется

### Requirement: Registration uses supported fields and local domain validation

Мастер SHALL сохранять четыре шага и поддержанные поля создания: название поверхности и конфигурации, тип, домены, назначение, продуктовый контекст, владельца и команду, двух ответственных по их бизнес-ID, выбранные навыки с параметрами и `submit_for_check`. Локальная нормализация доменов, проверка наличия хотя бы одного адреса и запрет дубликатов в форме SHALL сохраняться. Мастер MUST NOT запрашивать реестр для проверки занятости, блокировать шаг на основании такого поиска или объявлять уникальность подтверждённой. Рядом с доменами и в итоговой сводке SHALL быть доступное пояснение об отсутствии предварительной проверки; оно MUST NOT выдавать моки или поиск реестра за доказательство поведения backend.

#### Scenario: Valid details without registry access

- **WHEN** заполнены обязательные сведения и введён хотя бы один нормализуемый адрес
- **THEN** переход к следующему шагу не зависит от загрузки реестра поверхностей, запросы поиска доменов не выполняются и утверждение «домен свободен» отсутствует

#### Scenario: Empty domains remain invalid

- **WHEN** после нормализации список адресов пуст
- **THEN** шаг блокируется локальной ошибкой у поля без сетевой проверки

### Requirement: Unavailable greeting and server-owned channel

До создания мастер SHALL показывать, что идентификатор канала назначается сервером, без вычисления значения из домена. После подтверждающего чтения SHALL отображаться только серверный `channel_id`; null SHALL обозначаться как «Не назначен». Пока в мастере нет редактора конфигурации, блок «Приветствие» SHALL объяснять применение серверных настроек по умолчанию и недоступность настройки при регистрации. Мастер MUST NOT требовать приветствие, показывать локальный текст как сохранённый или отправлять скрытый PUT конфигурации. Возможность передать optional configuration через контрактный API-клиент сохраняется отдельно.

#### Scenario: Registration with server defaults

- **WHEN** пользователь проходит шаг сценариев и отправляет валидную форму в существующем мастере без редактора конфигурации
- **THEN** отсутствие ввода приветствия не блокирует регистрацию, пояснение видно, POST содержит только контрактные поля и PUT configuration не выполняется

#### Scenario: Channel differs from domain

- **WHEN** подтверждающий GET возвращает канал, не связанный с именем домена, либо null
- **THEN** UI показывает соответственно полученную строку либо «Не назначен», без синтетического fallback

### Requirement: Review reflects the current outgoing draft

Итоговый шаг SHALL показывать название поверхности и конфигурации, тип, нормализованные домены, назначение, продуктовый контекст, владельца, обоих ответственных, запрошенный режим создания и выбранные навыки с названиями и значениями параметров. Пустой продуктовый контекст SHALL обозначаться как «Не указан». Сводка SHALL соответствовать нормализации запроса и текущему выбору; снятые навыки не включаются. При недоступном названии SHALL использоваться известное название или ID без выдуманной подписи. Проблемные параметры SHALL оставаться видимыми с ошибкой до исправления, отсутствие параметров SHALL отличаться от ошибки их загрузки. Сводка MUST NOT объявлять готовность к публикации или уникальность доменов на основании заполненности полей.

#### Scenario: Review after editing parameters

- **WHEN** пользователь меняет продуктовый контекст и параметры двух выбранных навыков, затем открывает итоговый шаг
- **THEN** показаны текущие значения отдельно для каждого навыка; одинаковые ключи параметров разных навыков не смешиваются, снятые навыки не показаны как отправляемые

#### Scenario: Unavailable skill metadata

- **WHEN** метаданные выбранного навыка не удалось подтвердить
- **THEN** выбранный ID и введённые значения не исчезают, причина видна, POST блокируется действующей проверкой сценариев

### Requirement: Single explicit creation attempt

От окончательного действия пользователя до завершения подготовки навыков и запроса создания SHALL действовать общая блокировка повторного запуска и редактирования всех отправляемых полей, включая режим создания. Защита SHALL действовать также при повторном событии до обновления UI. Навыки и параметры SHALL повторно проверяться непосредственно перед POST; ошибка подготовки SHALL сохранять черновик и допускать исправление без POST. Создание SHALL выполняться один раз через `POST /api/control/api/surfaces/v1/surfaces`, без неподдерживаемого Idempotency-Key и автоматического повтора. Enter вне окончательного действия итогового шага MUST NOT запускать создание.

#### Scenario: Double submit while preparing

- **WHEN** пользователь дважды запускает финальное действие во время ожидания проверки навыков
- **THEN** выполняется одна последовательность подготовки и не более одного POST, поля и переключатель отправки на проверку недоступны до завершения операции

#### Scenario: Skill no longer in production

- **WHEN** проверка перед отправкой подтверждает, что выбранный навык вышел из prod
- **THEN** POST не отправляется, причина отображается, введённые параметры остаются для исправления

### Requirement: Creation outcome controls retry

Мастер SHALL отличать подтверждённый отказ от неизвестного результата. Контрактный 422 с корректной схемой ошибки валидации SHALL позволять исправление и новую явную отправку с повторной подготовкой. Иные структурированные отказы SHALL распознаваться только после подтверждения их wire-формата согласно действующему контракту; локальная mock-конвенция не подтверждает формат backend. Сетевой сбой, отмена после начала POST, 5xx, некорректный успешный ответ, отсутствие валидного ID и иные ответы без достоверного подтверждения отказа SHALL переводить попытку в неизвестный результат.

При неизвестном результате SHALL объясняться, что поверхность могла быть создана и повтор может создать дубль; данные SHALL сохраняться, автоматическая и ручная повторная отправка в текущем мастере SHALL блокироваться. Изменение полей или режима MUST NOT снимать эту блокировку. Ссылка на реестр SHALL позволять ручную проверку без автоматического сопоставления по имени или домену и без утверждения, что отсутствие в списке доказывает неуспех.

#### Scenario: Validation rejection is correctable

- **WHEN** POST возвращает контрактный 422
- **THEN** показана ошибка, черновик сохранён и после исправления доступна новая явная отправка без автоматического retry

#### Scenario: Lost response is not a failed creation

- **WHEN** POST завершается сетевым сбоем или 503
- **THEN** UI не сообщает успех или гарантированный отказ, не очищает форму и не разрешает повтор POST в текущем мастере

#### Scenario: Malformed success cannot unlock retry

- **WHEN** POST возвращает 201 с некорректным JSON или без валидного UUID
- **THEN** результат неизвестен, GET с выдуманным ID и повторный POST не выполняются

### Requirement: Created surface is confirmed by a fresh read

Успешное создание SHALL приниматься только по HTTP 201, успешному envelope и валидному ID. Полученный ID SHALL сохраняться в состоянии текущей попытки до последующих операций. Затем SHALL выполняться новый GET карточки этого ID, начатый после POST; кэш или более ранний ответ MUST NOT заменять подтверждение. ID карточки SHALL совпадать с созданным ID. До подтверждающего чтения мастер MUST NOT сбрасывать форму или автоматически уходить в реестр.

При ошибке GET, 404, невалидном ответе или несовпадении ID SHALL объясняться, что поверхность создана, но результат не загружен; повтор SHALL выполнять только GET того же ID. Неудача обновления реестра после POST также MUST NOT разрешать новое создание. После чтения SHALL отображаться серверный статус и channel_id со ссылками на карточку и реестр. «Черновик сохранён» SHALL показываться при запрошенном черновике и status=draft; «Отправлено на проверку» — при запрошенной проверке и status=review. При другом статусе SHALL показываться фактическое состояние и отличие от запроса без повторной записи. После создания новая отправка в этом мастере SHALL оставаться недоступной.

#### Scenario: Read confirms review

- **WHEN** POST с submit_for_check=true возвращает ID, затем новый GET того же ID возвращает review
- **THEN** мастер показывает подтверждённую отправку на проверку и серверные данные, не вычисляя статус из переключателя

#### Scenario: Read fails after creation

- **WHEN** POST вернул валидный ID, а GET завершился 404 или сетевой ошибкой
- **THEN** ID и ввод сохранены, по действию повтора выполняется только GET этого ID; число POST остаётся равным одному

#### Scenario: Actual status differs

- **WHEN** после запроса отправки на проверку GET возвращает draft и channel_id=null
- **THEN** показаны фактический draft, отсутствие канала и отличие результата от запроса; сообщение об отправке на проверку и дополнительная запись отсутствуют

#### Scenario: Wrong card returned

- **WHEN** GET после создания возвращает карточку с другим ID
- **THEN** результат не считается подтверждённым, чужая карточка не отображается и доступен повтор чтения исходного ID

### Requirement: Draft preservation and accessible recovery

Переходы назад/далее и ошибки SHALL сохранять поля формы, выбор навыков и их параметры. Уход из незавершённого мастера, включая неизвестный POST и ошибку чтения результата, SHALL требовать предупреждения; отмена перехода SHALL сохранять данные и состояние попытки. Перед перезагрузкой SHALL сохраняться браузерное предупреждение. После подтверждённого результата переход к карточке или реестру SHALL выполняться без предупреждения о несохранённой форме. Ошибки и результаты SHALL быть доступны вспомогательным технологиям, кнопки восстановления SHALL иметь однозначные подписи и управление с клавиатуры.

Автоматическое восстановление после перезагрузки, защита между вкладками и глобальная гарантия отсутствия дублей не предоставляются. При уходе из неизвестного результата предупреждение SHALL пояснять риск уже созданной поверхности и дубля; UI MUST NOT предлагать перезагрузку как безопасный повтор.

#### Scenario: Leave cancelled

- **WHEN** пользователь пытается уйти после изменения параметров либо неизвестного результата POST и отменяет переход
- **THEN** поля, параметры, текущий шаг и блокировка повторного POST остаются без изменений

#### Scenario: Confirmed result can be opened

- **WHEN** подтверждающий GET завершился успешно и пользователь открывает карточку
- **THEN** открывается карточка полученного ID без предупреждения о несохранённом вводе и без нового POST
