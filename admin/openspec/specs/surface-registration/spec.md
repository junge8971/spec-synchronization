# surface-registration Specification

## Purpose

Обеспечить создание поверхностей по текущему API с корректными ссылками на ответственных пользователей и безопасным восстановлением после отказа либо неизвестного результата запроса.

## Requirements

### Requirement: Responsible assignments use business user identifiers

Регистрация SHALL выбирать обоих ответственных через существующий API бизнес-пользователей и отправлять их строковые ID в responsible.product и responsible.connection. Имя и email SHALL использоваться только для представления выбора. UI MUST NOT отправлять произвольное ФИО как ID, ограничивать выбор первой страницей либо восстанавливать ID старого черновика по совпадению имени. Старые текстовые назначения SHALL требовать явного перевыбора. Ошибка загрузки пользователей SHALL сохранять форму без синтетических вариантов. Назначение ответственного MUST NOT изменять permissions или сессию.

#### Scenario: Selected external user

- **WHEN** выбран пользователь с не-UUID строковым ID и заполнены остальные обязательные поля
- **THEN** POST содержит этот ID, а не ФИО; подтверждение выбора показывает серверные сведения без требования UUID

#### Scenario: Legacy draft

- **WHEN** восстановлен старый черновик с произвольными строками ответственных
- **THEN** форма сохраняет остальные данные, объясняет необходимость перевыбора и не отправляет старые строки как подтверждённые ID

### Requirement: Creation supports an atomic optional configuration

API-клиент и локальное API SHALL поддерживать `configuration` по текущему `CreateSurfaceRequest`. При передаче объекта SHALL применяться действующие правила конфигурации и атомарное создание. При отсутствии поля или значении `null` SHALL применяться серверные значения по умолчанию. Мастер передаёт приветствие в составе `configuration` одного POST. Создание MUST NOT подменяться последовательностью POST и скрытого PUT. После 201 SHALL сохраняться `data.id` и выполняться GET для подтверждения сохранённой карточки; ошибка GET MUST NOT приводить к повторному созданию.

#### Scenario: Configuration is provided

- **WHEN** API-клиент получает валидную конфигурацию вместе с данными создания
- **THEN** один POST передаёт configuration, последующее чтение отражает сохранённые настройки; отдельный PUT не выполняется

#### Scenario: Default configuration

- **WHEN** configuration отсутствует или равна null
- **THEN** применяется серверная конфигурация по умолчанию без локальной подстановки клиентом

#### Scenario: Detail cannot be read after creation

- **WHEN** POST вернул ID, а GET завершился ошибкой
- **THEN** ID сохраняется, доступен повтор только чтения, второй POST не выполняется

### Requirement: Rejections are distinct from unknown creation outcomes

Мастер SHALL различать подтверждённый отказ без создания и неизвестный исход. Для структурированного `409 DOMAIN_ALREADY_IN_USE` все конфликтующие адреса SHALL читаться из элемента `errors[]` с `field: "/domains"` и списка `details.domains`. Для `422 VALIDATION_ERROR` и `422 FAILED` причины из `errors[].message` SHALL связываться с полями по надёжным путям `errors[].field`, в том числе при пустом верхнеуровневом `message`. Если путь не соответствует редактируемому полю, причина SHALL оставаться видимой в общем сообщении. Структурированный `422` с `detail[]` SHALL по-прежнему обрабатываться. При подтверждённом отказе мастер SHALL сохранить ввод и разрешить явный повтор после исправления. Неизвестный формат MUST NOT распознаваться по тексту `message` или одному HTTP-статусу.

#### Scenario: Confirmed domain conflict

- **WHEN** после предварительной проверки POST создания возвращает `409 DOMAIN_ALREADY_IN_USE` со списком занятых доменов
- **THEN** форма показывает все конфликтующие адреса, сохраняет ввод и позволяет исправить его с новой предварительной проверкой перед повторным POST

#### Scenario: Unknown responsible user

- **WHEN** POST возвращает `422 FAILED` с пустым `message` и ошибкой у `/responsible/product` или `/responsible/connection`
- **THEN** причина из `errors[]` видна в общем сообщении и у соответствующего выбора при открытии шага, остальные поля сохраняются

#### Scenario: Configuration field is not editable

- **WHEN** POST возвращает `422 VALIDATION_ERROR` для настройки, которой нет в форме
- **THEN** мастер показывает причину отказа в общем сообщении и сохраняет форму

#### Scenario: Lost response

- **WHEN** ответ на отправленный POST потерян
- **THEN** мастер сообщает о неизвестном результате и блокирует автоматический и явный повтор POST в текущем мастере

### Requirement: Empty production catalog explains registration blocking and recovery

Если полный успешно загруженный продовый каталог пуст, шаг сценариев регистрации SHALL явно объяснять, что для продолжения нужен хотя бы один навык со статусом prod и что отсутствие таких навыков не означает отсутствие всех навыков. Причина SHALL быть видима без hover и программно связана с недоступным переходом «Далее». Шаг SHALL предоставлять явное обновление каталога без сброса анкеты, ответственных и введённых параметров. Обновление SHALL использовать существующие правила полного чтения и проверки каталога; pending/error/empty SHALL различаться. UI MUST NOT автоматически публиковать навыки, подставлять non-prod записи или разрешать пустой состав для обхода блокировки. Действующее разрешение пустого состава в карточке существующей поверхности SHALL сохраняться.

#### Scenario: No production skills

- **WHEN** полный запрос status=prod успешно возвращает пустой список
- **THEN** «Далее» недоступна, рядом видна связанная причина и действие обновления, а запрос создания поверхности не отправляется

#### Scenario: Production skill becomes available

- **WHEN** пользователь обновляет каталог после появления prod-навыка
- **THEN** навык становится доступен для выбора, введённая анкета сохранена, а переход разрешается только после валидного выбора и проверки параметров

#### Scenario: Refresh fails

- **WHEN** обновление каталога завершается ошибкой
- **THEN** показываются ошибка и безопасный повтор, форма сохраняется, отсутствие данных не представляется успешным пустым каталогом и создание не выполняется

### Requirement: Registration uses supported fields and local domain validation

Мастер SHALL сохранять четыре шага и поддержанные поля создания: название поверхности и конфигурации, тип, домены, назначение, необязательный продуктовый контекст, владельца и команду, двух ответственных по их бизнес-ID, выбранные навыки с параметрами, приветствие в `configuration` и `submit_for_check`.

Мастер SHALL требовать хотя бы один домен и проверять повторы внутри списка после нормализации, до удаления повторяющихся адресов. Разделителями SHALL оставаться запятая, точка с запятой и пробельные символы, включая перенос строки. Нормализация SHALL удалять окружающие пробелы, приводить адрес к нижнему регистру, удалять начальное `http://` или `https://` и завершающие `/`. Пустые элементы SHALL игнорироваться. Префикс `www.` и поддомены SHALL сохраняться: `ag.ru` и `www.ag.ru` считаются разными адресами. Проверка повторов MUST NOT вводить новые правила допустимости адресов.

При наличии повторов мастер SHALL сразу показывать под полем «Домены» доступный алерт «Домены не должны повторяться: <адреса>», помечать поле как невалидное и связывать его с ошибкой. Каждый повторяющийся нормализованный адрес SHALL отображаться один раз, несколько адресов SHALL разделяться запятой с пробелом. Исходный ввод SHALL сохраняться. Повторы SHALL блокировать «Далее» и окончательную отправку без запроса проверки или создания. После исправления алерт SHALL исчезать, а «Далее» SHALL снова стать доступной, если остальные обязательные поля валидны. Исправление и переходы SHALL сохранять остальные данные регистрации. Для валидного ввода сводка и запрос создания SHALL использовать тот же нормализованный список.

После успешной локальной валидации «Далее» на первом шаге SHALL проверять занятость текущего непустого нормализованного списка через `POST /api/control/api/surfaces/v1/surfaces/domains/check`. Переход SHALL выполняться только после ответа `200` с пустым `data.occupied_domains` для актуального ввода и при валидных полях первого шага. Мастер MUST NOT запрашивать реестр для проверки занятости или представлять результат проверки как резервирование доменов. При создании сервер повторно проверяет занятость доменов.

При непустом `occupied_domains` мастер SHALL показать все возвращённые занятые адреса в доступном сообщении у поля и сохранить ввод на первом шаге. При сбое или некорректном ответе мастер SHALL остаться на первом шаге, сообщить, что занятость неизвестна, и позволить повторить проверку. Параллельные нажатия «Далее» MUST NOT запускать дублирующие проверки. Изменение доменов SHALL сбрасывать результат, а ответ на предыдущий ввод MUST NOT менять поля, ошибку или шаг мастера, даже если пользователь успел вернуть прежний текст.

#### Scenario: Valid details without registry access

- **WHEN** пользователь нажимает «Далее» с валидными сведениями и проверка возвращает пустой `occupied_domains`
- **THEN** открывается шаг ответственных, а проверка использует нормализованный список и не запрашивает реестр

#### Scenario: Empty domains remain invalid

- **WHEN** после нормализации список адресов пуст
- **THEN** локальная ошибка связана с полем, запрос проверки не отправляется, следующий шаг не открывается и ошибка о повторах не показывается

#### Scenario: Identical domains block the next step

- **WHEN** пользователь вводит `ag.ru, ag.ru` при заполненных остальных обязательных полях
- **THEN** под полем появляется алерт «Домены не должны повторяться: ag.ru», поле невалидно, «Далее» недоступна, сетевой запрос не отправляется, следующий шаг не открывается и исходный ввод сохраняется

#### Scenario: Repeated domains remain invalid

- **WHEN** пользователь меняет ранее проверенный список доменов на список с повторами
- **THEN** прежний результат проверки сбрасывается, ошибка связана с полем и переход блокируется без нового запроса проверки

#### Scenario: Equivalent normalized addresses are duplicates

- **WHEN** пользователь вводит `ag.ru, https://AG.RU/; http://ag.ru/`
- **THEN** показан связанный с полем алерт «Домены не должны повторяться: ag.ru», запрос проверки не отправляется и переход блокируется независимо от регистра, протокола и завершающего слеша

#### Scenario: Supported separators do not hide duplicates

- **WHEN** одинаковые нормализованные адреса разделены запятой, точкой с запятой, пробелом, табуляцией или переносом строки
- **THEN** повтор обнаруживается для каждого из этих разделителей и блокирует переход с тем же алертом

#### Scenario: Empty elements are not duplicate addresses

- **WHEN** пользователь вводит `, ag.ru; ;` с повторяющимися разделителями и пустыми элементами
- **THEN** на проверку отправляется только `ag.ru`, алерт о повторах отсутствует, а переход доступен при валидных обязательных полях и успешной проверке занятости

#### Scenario: Distinct hostnames remain allowed

- **WHEN** пользователь вводит `ag.ru, www.ag.ru; api.ag.ru` при заполненных остальных обязательных полях и API не возвращает занятых доменов
- **THEN** алерт о повторах отсутствует, переход доступен и все три нормализованных адреса сохраняются в сводке и запросе создания

#### Scenario: Each conflicting address is listed once

- **WHEN** пользователь вводит `ag.ru, ag.ru, other.ru, ag.ru, other.ru`
- **THEN** алерт содержит оба повторяющихся адреса по одному разу: «Домены не должны повторяться: ag.ru, other.ru»

#### Scenario: Correcting duplicates restores navigation

- **WHEN** пользователь исправляет `ag.ru, ag.ru` на `ag.ru, other.ru`, нажимает «Далее» и получает пустой `occupied_domains`
- **THEN** алерт о повторах исчезает после исправления, открывается шаг ответственных и остальные данные формы сохраняются

#### Scenario: Final validation also rejects duplicates

- **WHEN** окончательная отправка запускается с черновиком, содержащим повторяющиеся нормализованные домены
- **THEN** локальная валидация отклоняет отправку и запрос создания поверхности не выполняется

#### Scenario: Partially occupied list can be corrected

- **WHEN** `occupied_domains` содержит часть отправленных адресов
- **THEN** мастер сохраняет весь ввод и показывает занятые адреса у поля, а после исправления проверяет новый список по «Далее»

#### Scenario: Unavailable check can be retried

- **WHEN** запрос проверки завершается сбоем или возвращает некорректный ответ
- **THEN** занятость отмечается как неизвестная, ввод сохраняется и пользователь может повторить проверку без создания поверхности

#### Scenario: Concurrent clicks and stale responses do not advance

- **WHEN** пользователь несколько раз нажимает «Далее» или меняет домены, пока проверка выполняется
- **THEN** повторные нажатия не запускают дублирующий запрос, а ответ для изменённого ввода не открывает следующий шаг и не показывает ошибку для нового ввода

### Requirement: Registration greeting and server-owned channel

На шаге сценариев мастер SHALL показывать редактируемое обязательное поле «Приветствие» с начальным текстом и пояснением о запасном приветствии для посетителей без имени. Мастер SHALL валидировать приветствие, показывать его в сводке и передавать в `configuration.greeting` атомарного POST создания. При ошибках введённый текст SHALL сохраняться. После подтверждающего GET мастер SHALL показывать сохранённое серверное приветствие и сообщать о его отличии от отправленного. Дополнительный PUT конфигурации MUST NOT выполняться.

В сводке до создания мастер SHALL показывать расчётный идентификатор канала, используя первую часть первого нормализованного домена и суффикс `-web`. `channel_id` назначается сервером и MUST NOT передаваться в POST. После подтверждающего чтения мастер SHALL показывать `channel_id` из ответа GET, а `null` обозначать как «Не назначен».

#### Scenario: Registration saves greeting in the create request

- **WHEN** пользователь отправляет валидную форму с приветствием
- **THEN** один POST передаёт приветствие в `configuration`, полученное по GET значение показывается как сохранённое, а отдельный PUT не выполняется даже при расхождении текста

#### Scenario: Channel differs from domain

- **WHEN** подтверждающий GET возвращает канал, не связанный с именем домена, либо null
- **THEN** UI показывает соответственно полученную строку либо «Не назначен», без синтетического fallback

### Requirement: Review reflects the current outgoing draft

Итоговый шаг SHALL показывать название поверхности и конфигурации, тип, нормализованные домены, назначение, продуктовый контекст, владельца, обоих ответственных, приветствие, запрошенный режим создания и выбранные навыки с названиями и значениями параметров. Пустой продуктовый контекст SHALL обозначаться как «Не указан». Сводка SHALL соответствовать нормализации запроса и текущему выбору; снятые навыки не включаются. При недоступном названии SHALL использоваться известное название или ID без выдуманной подписи. Проблемные параметры SHALL оставаться видимыми с ошибкой до исправления, отсутствие параметров SHALL отличаться от ошибки их загрузки. Сводка MUST NOT объявлять готовность к публикации, проверку сотрудников или уникальность доменов на основании заполненности полей.

#### Scenario: Review after editing parameters

- **WHEN** пользователь меняет продуктовый контекст и параметры двух выбранных навыков, затем открывает итоговый шаг
- **THEN** показаны текущие значения отдельно для каждого навыка; одинаковые ключи параметров разных навыков не смешиваются, снятые навыки не показаны как отправляемые

#### Scenario: Unavailable skill metadata

- **WHEN** метаданные выбранного навыка не удалось подтвердить
- **THEN** выбранный ID и введённые значения не исчезают, причина видна, POST блокируется действующей проверкой сценариев

### Requirement: Single explicit creation attempt

От окончательного действия пользователя до завершения подготовки навыков и запроса создания SHALL действовать общая блокировка повторного запуска и редактирования всех отправляемых полей, включая режим создания. Защита SHALL действовать также при повторном событии до обновления UI. Навыки и параметры SHALL повторно проверяться непосредственно перед POST; ошибка подготовки SHALL сохранять черновик и допускать исправление без POST. Создание SHALL выполняться один раз через `POST /api/control/api/surfaces/v1/surfaces`, без неподдерживаемого Idempotency-Key и автоматического повтора. Enter вне окончательного действия итогового шага MUST NOT запускать создание.

#### Scenario: Double submit while preparing

- **WHEN** пользователь дважды запускает финальное действие во время ожидания проверки навыков
- **THEN** выполняется одна последовательность подготовки и не более одного POST, поля и переключатель отправки на проверку недоступны до завершения операции

#### Scenario: Skill no longer in production

- **WHEN** проверка перед отправкой подтверждает, что выбранный навык вышел из prod
- **THEN** POST не отправляется, причина отображается, введённые параметры остаются для исправления

### Requirement: Creation outcome controls retry

Мастер SHALL отличать подтверждённый отказ от неизвестного результата. Распознанный ответ создания `409 DOMAIN_ALREADY_IN_USE` или `422` в согласованной структуре SHALL позволять исправление и новую явную отправку с повторной подготовкой. Локальные форматы моков MUST NOT расширять список подтверждённых отказов. Сетевой сбой, отмена после начала POST, `5xx`, некорректный успешный ответ, отсутствие валидного ID и иные ответы без достоверного подтверждения отказа SHALL переводить попытку в неизвестный результат.

При неизвестном результате SHALL объясняться, что поверхность могла быть создана и повтор может создать дубль; данные SHALL сохраняться, автоматическая и ручная повторная отправка в текущем мастере SHALL блокироваться. Изменение полей или режима MUST NOT снимать эту блокировку. Ссылка на реестр SHALL позволять ручную проверку без автоматического сопоставления по имени или домену и без утверждения, что отсутствие в списке доказывает неуспех.

#### Scenario: Validation rejection is correctable

- **WHEN** POST возвращает подтверждённый отказ и пользователь исправляет данные
- **THEN** показана ошибка, черновик сохранён и после исправления доступна новая явная отправка без автоматического повтора

#### Scenario: Malformed rejection cannot unlock retry

- **WHEN** POST возвращает `409` или `422` с неизвестным кодом и форматом либо без ожидаемых данных ошибки
- **THEN** мастер показывает неизвестный результат и сохраняет блокировку POST

#### Scenario: Lost response is not a failed creation

- **WHEN** POST завершается сетевым сбоем или 503
- **THEN** UI не сообщает успех или гарантированный отказ, не очищает форму и не разрешает повтор POST в текущем мастере

#### Scenario: Malformed success cannot unlock retry

- **WHEN** POST возвращает 201 с некорректным JSON или без валидного UUID
- **THEN** результат неизвестен, GET с выдуманным ID и повторный POST не выполняются

### Requirement: Created surface is confirmed by a fresh read

Успешное создание SHALL приниматься только по HTTP 201, успешному envelope и валидному ID. Полученный ID SHALL сохраняться в состоянии текущей попытки до последующих операций. Затем SHALL выполняться новый GET карточки этого ID, начатый после ответа POST; кэш или более ранний ответ MUST NOT заменять подтверждение. ID карточки SHALL совпадать с созданным ID. До подтверждающего чтения мастер MUST NOT сбрасывать форму или автоматически уходить в реестр.

При ошибке GET, 404, невалидном ответе или несовпадении ID SHALL объясняться, что поверхность создана, но результат не загружен; повтор SHALL выполнять только GET того же ID. Неудача обновления реестра после POST также MUST NOT разрешать новое создание. После чтения SHALL отображаться серверный статус и channel_id со ссылками на карточку и реестр. «Черновик сохранён» SHALL показываться при запрошенном черновике и status=draft; «Отправлено на проверку» — при запрошенной проверке и status=review. При другом статусе SHALL показываться фактическое состояние и отличие от запроса без повторной записи. После создания новая отправка в этом мастере SHALL оставаться недоступной.

#### Scenario: Read confirms review

- **WHEN** POST с submit_for_check=true возвращает ID, затем новый GET того же ID возвращает review
- **THEN** мастер показывает подтверждённую отправку на проверку и серверные данные, не вычисляя статус из переключателя

#### Scenario: Read fails after creation

- **WHEN** POST вернул валидный ID, а GET завершился 404 или сетевой ошибкой
- **THEN** ID и ввод сохранены, по действию повтора выполняется только GET этого ID; число POST остаётся равным одному

#### Scenario: Actual status differs

- **WHEN** после запроса отправки на проверку GET возвращает draft и channel_id=null
- **THEN** показаны фактический draft, отсутствие канала и отличие результата от запроса; сообщение об отправке на проверку и дополнительная запись отсутствуют

#### Scenario: Wrong card returned

- **WHEN** GET после создания возвращает карточку с другим ID
- **THEN** результат не считается подтверждённым, чужая карточка не отображается и доступен повтор чтения исходного ID

### Requirement: Draft preservation and accessible recovery

Переходы назад/далее и ошибки SHALL сохранять поля формы, выбор навыков и их параметры. Уход из незавершённого мастера, включая неизвестный POST и ошибку чтения результата, SHALL требовать предупреждения; отмена перехода SHALL сохранять данные и состояние попытки. Перед перезагрузкой SHALL сохраняться браузерное предупреждение. После подтверждённого результата переход к карточке или реестру SHALL выполняться без предупреждения о несохранённой форме. Ошибки и результаты SHALL быть доступны вспомогательным технологиям, кнопки восстановления SHALL иметь однозначные подписи и управление с клавиатуры.

Автоматическое восстановление после перезагрузки, защита между вкладками и глобальная гарантия отсутствия дублей не предоставляются. При уходе из неизвестного результата предупреждение SHALL пояснять риск уже созданной поверхности и дубля; UI MUST NOT предлагать перезагрузку как безопасный повтор.

#### Scenario: Leave cancelled

- **WHEN** пользователь пытается уйти после изменения параметров либо неизвестного результата POST и отменяет переход
- **THEN** поля, параметры, текущий шаг и блокировка повторного POST остаются без изменений

#### Scenario: Confirmed result can be opened

- **WHEN** подтверждающий GET завершился успешно и пользователь открывает карточку
- **THEN** открывается карточка полученного ID без предупреждения о несохранённом вводе и без нового POST
