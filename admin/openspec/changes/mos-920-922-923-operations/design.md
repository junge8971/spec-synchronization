## Context

См. `proposal.md`. React Router 8 работает в Framework SPA с basename `/tsam-panel/`; внешние вкладки `/ops` читают `tab` из URL. `app/application/ui/operations-route.tsx` передаёт в `OperationsPage` публичный `SystemStateRegistry` только для `*`. Его сохранённые ссылки используют `kind`, `stateType`, `stateSearch`, а карточка `/ops/toggles/:toggleId` возвращается к `/ops` с `kind`.

Локальный `docs/api/contracts/openapi.json` совпадает по бизнес-операциям трёх сценариев с предоставленным `/home/user/Загрузки/message.txt`; 14 операций и 57 зависимых схем сверены, security в репозитории сохраняет ранее согласованную нормализацию. Отдельное согласование статуса draft-контракта MOS-920 и фактической интеграции backend этим не заменяется. Активный `mos-1026-skill-operations-info` читает окно мониторинга навыка из другого GET и не является владельцем этого редактора.

## Goals / Non-Goals

**Goals:** сохранить MOS-1570 и старые ссылки, обеспечить три самостоятельных серверных сценария с корректной изоляцией и безопасным восстановлением, воспроизвести визуальную структуру прототипа без подмены данных.

**Non-Goals:** новая система auth/permissions, API, scheduler или frontend-движок приоритетов; объединение моделей `system-state-toggles` и глобальных модулей; новая заглушка для неизвестной цели; атомарное создание draft; неподтверждённая эксплуатационная сводка навыков/поверхностей или изменение MOS-1026.

## Decisions

### 1. Композиция и совместимость URL

Оставить внешние `modules`, `stubs`, `maintenance` и существующие совместимые редиректы. Внутри `modules` добавить выбор глобальных модулей и прежних рубильников через отдельный query-параметр, например `opsView=assistant|toggles`; не использовать `tab` или `kind` для этого выбора. По умолчанию показывать глобальные модули. При отсутствии нового параметра наличие `kind`, `stateType` или `stateSearch` распознаёт старую ссылку на рубильники; возврат из `/ops/toggles/:toggleId` остаётся совместимым. Явный новый параметр имеет приоритет; запрещённый `toggles` показывает отказ без запроса. Прежний общий `/ops` без параметров теперь открывает глобальные модули — это согласованное изменение начального содержимого, а ссылки с сохранённым отбором и карточки не теряются.

Композиция приложения подключает публичный `SystemStateRegistry` только для `*` и отдельное содержимое модулей по `TSAM.Module:view`. Новые предметные клиенты, виджеты и действия размещаются в обычных `entities`/`features`/`widgets`/`pages` по их владельцу; optional-модуль и другие бизнес-слайсы не импортируют друг друга. Новое адресное исключение FSD или plugin framework не нужны. Альтернатива замены MOS-1570 нарушает действующую спецификацию; размещение обеих разных моделей в одном реестре скрывает их несовпадение.

### 2. Данные, ошибки и права

Переиспользовать общий `apiRequest`, TanStack Query, Zod, React Hook Form и существующие UI-компоненты. DTO брать из репозиторного OpenAPI, runtime-проверять используемые ответы и сохранять nullable/optional поля. Не импортировать runtime fixtures в клиент и не добавлять заголовки или idempotency-поля, отсутствующие в этих операциях. `apiRequest` сейчас сериализует scalar query; при необходимости сортировки списка модулей передавать один поддерживаемый критерий как один параметр и не превращать массив в ошибочную строку через запятую. Мультисортировка не требуется прототипом и не добавляется без корректной согласованной сериализации.

Использовать существующую policy: `Module:view/enable/disable` для глобальных модулей, явный `*` для заглушек, окон и managed-рубильников. UI скрывает неразрешённые действия; состояние и бизнес-валидация дополнительно ограничивают разрешённые. Backend остаётся источником object scopes и авторизации, transport не получает ACL. Запросы работают только после готовности текущей сессии; отмена и guards поколения/владельца предотвращают поздние ответы прежнего контекста. При ошибках показывать серверные 403/404/409/422, сеть и ошибки формата, не маскируя их под пустой список.

Список, summary и preview модулей имеют независимые query keys и состояния. Успешная мутация инвалидирует связанные чтения; если последующий GET не удался, подтверждённый успех и ошибка обновления показываются отдельно. Тот же принцип применяется к заглушке, preview и окнам. Инвалидация связанных публичных запросов координируется их ближайшим общим владельцем/композицией, без импортов внутренних файлов соседних FSD-слайсов. Никакая мутация не повторяется автоматически после 401, timeout или неизвестного исхода; сохранённый ввод остаётся доступен прежнему подтверждённому пользователю.

Для незавершённых операций `/ops` хранить только ввод пользователя и состояние защиты/сверки отдельно по владельцам в памяти текущей вкладки, за пределами пересоздаваемого дерева сессии. Это не пользовательский query-кэш, не хранилище credentials и не новая auth-модель: существующая очистка запросов при изменении контекста и backend-авторизация сохраняются. При проверке сессии или потере прав содержимое и бизнес-запросы скрыты; при возвращении того же подтверждённого владельца с нужными правами его ввод и защита восстанавливаются. Другой владелец не видит чужой ввод и не блокируется чужой операцией. Перед новой записью при неподтверждённом исходе требуется явная успешная серверная сверка только чтением; поздние ответы прежнего контекста не изменяют текущий. При обновлении страницы или закрытии вкладки память исчезает; долговременное восстановление и сохранение credentials не обещаются.

### 3. Отключение глобального модуля

Использовать `disable_allowed` и реальные права, а не фиксированный список имён ядра. Диалог всегда показывает глобальный характер последствий и, при наличии, `disable_impact_message`; после явного подтверждения и непустого сообщения отправляет `expected_version`, `confirm_impact=true`, `user_message`. Enable отправляет только обязательную версию. Запрос без обязательного подтверждения невозможен из UI, хотя существующий локальный mock намеренно допускает более слабые случаи: изменение этой принятой mock-конвенции не входит в scope.

Отказ 409 и неопределённый исход не меняют подтверждённую строку; пользователь может перечитать данные и явно принять новое решение. Server `summary` описывает модули, а не все навыки и поверхности. Отключение в демо или наличие backend API не подтверждает применение на всех поверхностях; MOS-920 сохраняет отдельный gate подтверждения статуса контракта и реальной интеграции.

### 4. Заглушка и два значения preview

Каталог представляет одну серверную запись на цель; три поля отображаются отдельными строками внутри этой цели, а `is_applied` — одним контролом. Inline-редактор отправляет обязательный флаг и изменённое поле, сохраняя остальные; null, отсутствие поля и непустая строка различаются. Стирание текста в пустую строку не интерпретируется автоматически как null. Отдельного создания и выдуманных строк каталога нет.

Для фактического результата читать `/stubs/{target_type}/{target_id}/preview`: успешный PUT возвращает summary, не preview. После записи обновлять оба источника; не использовать введённые данные или `is_applied` как доказательство приоритета. При ошибке preview не отменять подтверждённый PUT и не показывать старое значение как новое. Для формы техработ согласованы два отдельных визуальных образца введённых текстов с маркировкой «без учёта приоритетов»; они не отправляют запрос и не называются серверным будущим preview.

### 5. Форма окна, выбор целей и время

Форма использует явные title, IANA timezone, начало/конец, warning, priority и выбранные цели; три текста могут быть null. Списки модулей, навыков и поверхностей читаются через существующие server-scoped реестры и их публичные API; поиск и пагинация не ограничиваются первой страницей. Ассистент использует согласованный стабильный target `assistant`. Не подменять каталоги объектами из локального seed, не выбирать всё автоматически и не фильтровать только `prod`. Списки дают кандидатов, а не подтверждение допустимости для техработ; отказ backend остаётся видимым и не теряет форму.

Преобразование даты должно использовать выбранный именованный пояс и правила временных зон, а не `new Date(datetimeLocal)` в часовом поясе браузера. Передавать RFC3339 с явным смещением, проверять порядок и корректность зоны; несуществующее время и неоднозначное без явного выбора не отправлять. Покрыть DST и отличающийся от браузера пояс. Готового установленного преобразователя зон в проекте не найдено: сначала использовать надёжные штатные возможности, а новую поддерживаемую зависимость рассматривать только при доказанной необходимости, с отдельным обоснованием размера и поддержки; не писать непроверенный самодельный календарь.

Кнопка «Запланировать» выполняет ровно один POST; не строить создание draft как POST + PUT. Возвращённый ID позволяет повторить только GET после подтверждённого POST. При потерянном ответе POST нет безопасного ID: не выполнять повтор автоматически, предложить сверить список. Существующий draft можно читать и редактировать; его явная публикация использует описанный в аналитике PUT `is_currently_applied=true`, при этом ответное `false` не означает неуспешную публикацию будущего окна. Активные окна блокируют изменение начала, timezone и целей; разрешённые поля и завершённые/отменённые состояния следуют спецификации и серверному ответу. Отмене требуется reason, результат пересечений и гонок определяет backend.

### 6. Локальные моки и проверка

Доработать существующие `mocks/maintenance.mjs` и `mocks/stubs.mjs`, не добавляя новый сервер. Для проверяемого прямого совпадения цели обеспечить воспроизводимое влияние активного окна на preview, а также ограниченные round-trip сценарии состояний и terminal-ошибок. Время можно оценивать при чтении по управляемым тестовым часам, не вводя фоновый scheduler. Иерархию разных целей и непрояснённые правила конфликтов не объявлять реализованными; конкретные mock-правила и источник результата описать в `mocks/README.md`. Существующий module mock и его нормативная более слабая конвенция остаются без изменений.

Компонентные тесты используют контролируемые ответы и проверяют UI-валидацию, разделение preview, состояния и защиту от несвежих результатов; HTTP-тесты непосредственно проверяют mock round trips, ошибки и отсутствие мутации. Конфигурация Vitest запускает только `app/**/*.test.{ts,tsx}`, поэтому новые Node HTTP-тесты надо запускать явно и указать фактическую команду, не утверждая, что их автоматически запускает `yarn test`. Mock-финализация не является интеграционной приёмкой backend.

## Risks / Trade-offs

- [Wiki и локальный OpenAPI различаются namespace и полнотой бизнес-правил] → URL и DTO брать из репозиторного снимка, сохранять требования аналитики, расхождения и подтверждение backend как release gates; не добавлять fallback на другой путь.
- [Старые ссылки MOS-1570 потеряют вид или фильтр] → явный internal selector и восстановление legacy `kind/stateType/stateSearch`; протестировать возврат карточки, повторы query и разные права. Общий пустой `/ops` намеренно меняет начальный экран.
- [Флаг применения и preview трактуются как эквиваленты] → показывать общий флаг отдельно от ответа preview; неподтверждённое сохранение и ошибка последующего чтения не смешиваются.
- [Нет подтверждённого каталога допустимых целей и атомарного draft POST] → показывать только кандидатов из серверных реестров, сохранять ошибки backend; отдельное создание draft не предлагать.
- [DST/несовпадение зон создают неверный интервал] → явная зона и смещение, проверка обратного преобразования и переходов DST, блокировка неоднозначного ввода без разрешения.
- [Mock даёт ложное ощущение полной приоритетной модели] → ограничить прямой цельный пример, документировать его и не считать mock подтверждением backend; иерархическое применение остаётся integration gate.
- [Разрешение на локальное UI-тестирование отсутствует] → unit/component/HTTP остаются обязательными; интерактивный Playwright MCP и любые E2E/browser suites выполняются только после отдельного явного разрешения, иначе отмечаются непроверенными.

## Открытые интеграционные gates

- Статус draft-контракта MOS-920 и доступность опубликованных путей backend не подтверждены владельцами.
- Совместимость `assistant-ops/v1` и `maintenance/v1`, реальное применение изменений и серверные приоритеты не подтверждены. Локальные моки не являются интеграционной приёмкой.

## Migration Plan

1. Подключить независимые клиенты и композицию, сохранив существующие маршруты, selected filters и session policy; добавить адресные mock-сценарии без изменения других операций.
2. Реализовать согласованные экраны и recovery, проверить UI, HTTP-моки, FSD, production isolation и quality gates. Сверить mock-ограничения и документацию.
3. До интеграционной приёмки получить подтверждение актуальных путей/бизнес-семантики, статуса контракта MOS-920 и реального эффекта backend; схема и моки не закрывают эти gates.
4. Откатить новый bundle/композицию без удаления сохранённых данных на сервере и без изменения существующих рубильников, сессии или контрактов.
