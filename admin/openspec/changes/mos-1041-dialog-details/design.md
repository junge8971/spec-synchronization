## Context

См. proposal.md. Карточка — заглушка; `app/shared/api/http-client.ts` читает только JSON. Базовый HTTP URL уже отделён от UI basename. Существующий detail навыка адресуется UUID, тогда как PDF диалогов передаёт service_id. Shell spec требует заглушку для незавершённых карточек и статичную подпись «Диалог»; соответствующая delta входит только в этот change.

## Goals / Non-Goals

**Goals:** один согласованный detail snapshot, безопасные вложения, независимая прямая ссылка и основа для дочерних задач.

**Non-Goals:** восемь загрузок по вкладкам, real-time переписка, редактирование сообщений, role highlighting, auth lifecycle, клиентская генерация audit events.

## Decisions

1. **Contract gate:** принять 2.3/3.5/3.7 PDF и подтвердить chat_id, источники и режимы вложений. Опубликовать бизнес-схемы и generated DTO в координации с MOS-1037. Противоречие «без адресата» решается следованием новому PDF: нет поля — нет синтетического счётчика. Если владелец требует третий вид, сначала расширяется контракт.
2. **Один detail query:** публичный API `entities/dialog`, ключ по chat_id, route param dialogId трактуется как этот ID, без UUID-валидации навыка. Прямая ссылка выполняет detail независимо от списка. Владелец карточки передаёт один snapshot приватным вкладкам; навигация по ним не запускает дополнительные чтения. Повтор ошибки явный, без фонового polling ради продолжающегося диалога. Audit формирует сервер; технические refetch не считать клиентскими событиями.
3. **Композиция:** page/при необходимости widget карточки содержит переписку и вкладки. MOS-1042 добавляет оценки/основания, MOS-1043 — route, MOS-1044 — feature категории. Внутри владельца прямые импорты приватных модулей, снаружи публичные API. Не создавать feature на каждый read-only блок.
4. **Представление:** RFC3339 UTC форматируется в согласованном поясе. duration_sec — серверный снимок, при ended_at null подпись «и идёт», без локального таймера. Участники и операторы в порядке ответа, доли/message_count не пересчитываются. Знаменатель участника — step_count по принятому предположению 8.5. Nullable тема/поля отличаются от нуля/пустого списка. Тексты сообщений и имена файлов рендерятся текстом, не HTML.
5. **Ошибки:** NOT_FOUND даёт «Диалог не найден»; 503 ESK_CORE_UNAVAILABLE и ATTACHMENT_SOURCE_UNAVAILABLE не превращаются в 404/пустую переписку. route.available=false не блокирует карточку. Ошибка binary-чтения не стирает уже загруженную карточку. 401/403 остаются бизнес-ошибками без входа/refresh.
6. **Вложения:** status=unprocessed не опрашивается и не открывается; ready допускает download, view определяется серверным viewable. Получать содержимое только после действия сотрудника, не preload. Для browser view предпочтителен прямой серверный ответ с CSP sandbox, nosniff, no-store и корректным Content-Disposition; нельзя считать эти заголовки автоматически перенесёнными на blob URL. Если окружению нужен fetch/Blob, до включения просмотра подтвердить равноценную изоляцию, обработку JSON-ошибок, освобождение object URL и отсутствие обхода CSP. Ни один путь не добавляет токен в URL. Binary-обработка добавляется узко к общему transport только при необходимости, без второго независимого JSON-клиента. Ошибку view не заменять автоматическим download.
7. **Ссылки:** использовать безопасные http/https для внешних источников; app:// страницы обращения показывать текстом до отдельной политики. Код навыка не является UUID: до согласованного resolver показывать название/код без фиктивного перехода. Не загружать весь каталог ради случайного совпадения названий.
8. **Крошки:** reuse существующего механизма с данными того же snapshot; topic либо «Диалог <chat_id>». При loading/error допускается нейтральная «Диалог», а не заголовок прошлого ID.

## Risks / Trade-offs

- Один большой ответ → в PDF нет message pagination/лимита; оценить размер с backend до подключения, не выдумывать пагинацию.
- PDF считает nosniff защитой от ложного MIME → не полагаться только на MIME; сохранить sandbox и запрет исполнения активного содержимого.
- Маршрут недоступен, вложения недоступны → разные контрактные состояния, тестировать отдельно.
- Нет message_id → использовать порядок snapshot для read-only представлений, не объявлять локальные ключи серверными IDs.

## Migration Plan

После gate добавить detail/attachment схемы и HTTP fixtures, заменить заглушку и внести shell delta при sync. Дочерние вкладки принимаются отдельными changes. Откат возвращает честную недоступность карточки; безопасность binary-чтения проверяется unit/component/server-тестами без браузера, неподтверждённая изоляция остаётся gate просмотра.
