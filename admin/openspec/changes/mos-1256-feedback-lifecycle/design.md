Моки не доказывают доступность реального стенда.

## Decisions

### Dependencies and ownership

[MOS-1250](../archive/2026-10-20-mos-1250-feedback-registry/proposal.md); [MOS-1251](../archive/2026-10-23-mos-1251-feedback-editor/proposal.md)

Весь раздел «Обратная связь» принадлежит `app/optional/feedback`, по образцу `app/optional/knowledge-base`: API-клиенты, runtime-схемы, модель, ключи запросов, предметные типы, константы, UI и их тесты находятся внутри модуля. MOS-1249 поставляет только CRUD/search/lookup/metadata foundation; UI, клиенты saved-filters и CSV добавляются своими changes в этот же модуль. Приватные редакторы вопросов, правил, меток и preview остаются у владельца draft. Общая модель отбора обслуживает реестр, conditions, сохранённые фильтры и экспорт через прямые внутренние импорты. Раздел не раскладывается на внешние `entities/feedback`, `features`, `widgets` и `pages`.

Граница адресная, по существующим `scripts/eslint-fsd-config.mjs` и проверкам knowledge base. Модуль может использовать `shared` и публичные `index.ts` существующих entities; зависимости от application, providers, root, route configuration, pages/widgets/features и других optional-модулей запрещены. Слои shared/entities/features/widgets/pages не импортируют optional. Внешние потребители используют только `app/optional/feedback/index.ts`; внутри модуля запрещён импорт собственного index, используются прямые импорты. Штатные framework route entrypoints регистрируются отдельно и могут импортировать приватный UI, как в knowledge base; это точка подключения React Router, не разрешение deep imports из бизнес-слоёв. Новые широкие ESLint-исключения и отключение проверок не вводятся; direction FSD и публичные API существующих слайсов сохраняются.

Composition владеет `app/application/constants/application-routes.constants.ts`: MOS-1250 подключает публичные route/tab descriptors feedback к существующему registry; descriptors не импортируют runtime UI. `app/routes.ts` использует объединённый registry и отдельные route entrypoints, shell получает ту же конфигурацию. MOS-1249 не подключает UI-маршруты. Подключение Express-моков и адресных архитектурных проверок документируется отдельно; удаление раздела снимает его composition/route/mock/test registrations и адресные проверки, затем удаляет модуль, без удаления серверных данных и общего transport/session.

Именованные types/constants/handlers размещаются в технических сегментах ближайшего владельца по AGENTS.md; локальные вычисления не выносятся ради синтаксиса. Не переносить весь HTML, ручной router, DOM innerHTML или самодельную таблицу состояния.

Использовать существующие React Router, TanStack Query/Table, React Hook Form, Zod и UI kit. Для порядка вопросов/вариантов обязательны доступные кнопки перемещения; drag-and-drop использует возможности платформы, пока новая библиотека не обоснована. Универсальный движок managed resources не нужен: доступен один предметный раздел.

### Implementation decisions

MOS-1256: PUT status из lookup — draft/active/paused/disabled. «Приостановить», «Возобновить», «Выключить» относятся к сохранённой карточке; disabled не удаляет её. Перед выключением и удалением — подтверждение. При dirty draft сначала явное сохранение либо отмена действия, без скрытого discard. DELETE — soft-delete: GET/повторный DELETE/export затем 404; код остаётся занят. Реестр и detail обновляются только по подтверждённому исходу, отдельной клиентской машины переходов нет.

### Disable confirmation boundary

Единый механизм подтверждения перехода существующей карточки в disabled используется кнопкой выключения и submit формы со сменой статуса. MOS-1251 подключает его в общий submit, MOS-1256 — в отдельное действие; реализация находится у владельца редактора, внутри feedback, без внешних feature-слайсов. Отмена сохраняет draft и не отправляет запрос. Submit после подтверждения отправляет один PUT всех изменений; уже disabled без смены статуса не требует повторного подтверждения. Для отдельного lifecycle-действия сохраняется правило dirty draft: сначала явное сохранение либо отмена действия; если сохранение уже установило целевой статус, второй PUT не нужен.

### Existing safety and verification

Существующие HTTP transport, MPMM-сессия, owner/generation и UI-only permissions сохраняются. Backend проверяет scope. FSD и публичные index.ts обязательны; новые auth-модель, role editor и request ACL не вводятся. Unit/component и mock HTTP проверки разрешены; browser/E2E — только по отдельному разрешению. Dev-моки остаются в Express без credentials/role enforcement; production их не содержит.

Новая UI-policy, mappings permissions и новые ограничения интерфейса по пользователю исключены из текущей поставки всех feedback changes. Существующие защитные механизмы сохраняются; общий transport обрабатывает фактические серверные ошибки, включая 401/403, без собственной auth/session/RBAC-логики. Доступность клавиатуры, ошибок и фокуса проверяется у владельца соответствующего UI. Данные редакторов проходят через владельца draft и внутреннюю модель feedback.

## Risks / Trade-offs

- [HTML шире API] → ограничить UI опубликованными возможностями; ограничения Deferred scope из proposal сохраняются в приёмке.
- [Нет optimistic locking] → не обещать защиту от чужой параллельной записи; сохранять baseline и пояснять неизвестный исход, не делать слепой повтор.
- [Неизвестные/неактивные справочные коды] → сохранить исходные данные, не подставлять defaults поверх сохранённого значения; новые неподдержанные renderers не выдумывать.
- [Ошибки OpenAPI допускают null шире бизнес-правил; autogenerated 422 описан иначе envelope] → generated DTO дополняются runtime-проверками и документированными бизнес-ограничениями; не переписывать исходник без provenance, фактический ответ проверить на интеграции.
- [Версии источников могут измениться] → использовать локальные HTML/PDF из Downloads и опубликованные API-контракты; новая PDF-выгрузка имеет собственный hash, исторические hashes не переписываются. При дальнейшей реализации сверять относящийся к задаче материал без расширения согласованного scope.

## Migration Plan

Реализовать только tasks этой подзадачи после указанных prerequisites. Моки не подтверждают доступность реального API. Перед выпуском проверить операции этой задачи на стенде; rollback — предыдущий frontend bundle без удаления серверных данных. Backend schema migration не входит.

## Open Questions

Блокирующих продуктовых решений в согласованном первом этапе нет. Перед выпуском остаётся подтверждение фактических endpoint/errors/CORS и действующих серверных ограничений для операций задачи. Иное поведение требует уточнения контракта, не скрытого расширения scope.
