## Purpose

Обеспечить подтверждённое сервером добавление одной категории диалога без удаления существующих значений или затирания конкурентных изменений.

## ADDED Requirements

### Requirement: Category action requires an accepted write contract

Форма SHALL становиться рабочей только после принятия метода записи категории в ЕСК. До этого UI MUST NOT показывать ложное сохранение. После gate операция SHALL использовать POST `/api/control/api/dialogs/v1/dialogs/{chat_id}/categories` с единственным name; справочник SHALL поступать из dictionaries.categories. UI MUST NOT вводить category_id, expected_version, отдельные permissions или клиентские audit events без соответствующего контракта.

#### Scenario: Write API unavailable

- **WHEN** запись категории ещё не согласована
- **THEN** действие не меняет локально категории как будто они сохранены и не отправляет запрос на предположительный endpoint

### Requirement: Form selects one dictionary category

Форма SHALL предлагать одну категорию из серверного списка строк, без произвольного создания, удаления или замены состава. Name SHALL обрезаться по краям и сопоставляться без регистра согласно контракту. Категории карточки, отсутствующие в текущем справочнике, SHALL оставаться видимыми. Ошибка загрузки справочника SHALL отличаться от пустого справочника; все поля/ошибки SHALL быть доступны с клавиатуры.

#### Scenario: Dictionary no longer contains an existing category

- **WHEN** карточка содержит категорию, которой нет в новом справочнике
- **THEN** категория не удаляется и не подменяется; новая выбирается только из актуального списка

#### Scenario: Unknown category rejected

- **WHEN** сервер возвращает 422 с field=/name
- **THEN** ошибка показана у поля, выбранное значение доступно для исправления, прежние категории сохранены

### Requirement: Success replaces categories with the server result

UI SHALL показывать успех только после HTTP 200 с полным categories и обновлять поле этим серверным составом без повторного чтения всей карточки. Повторное добавление существующего имени SHALL не создавать дубликат. Во время запроса повторная отправка SHALL предотвращаться. Ответ для прежнего chat_id MUST NOT обновлять открытую карточку другого диалога.

#### Scenario: Repeated addition

- **WHEN** та же категория добавлена повторно и сервер возвращает прежний состав
- **THEN** UI показывает категорию один раз, без локального дубликата и без вымышленного конфликта версии

#### Scenario: Concurrent additions

- **WHEN** другой сотрудник добавил категорию и ответ текущего POST содержит обе
- **THEN** показаны обе серверные категории, не только локально выбранная

#### Scenario: Stale detail response

- **WHEN** detail-запрос начат до успешного добавления и его ответ приходит позже
- **THEN** старый состав не затирает подтверждённый результат текущей мутации

### Requirement: Write failures preserve state and allow explicit retry

Ошибка записи SHALL сохранять ранее подтверждённые категории и введённое значение. 503 SHALL показывать отказ записи, 404 — отсутствие диалога, 401/403 — ошибку бизнес-запроса без auth-последовательности. Повтор после неоднозначного сетевого сбоя SHALL быть явным, а не автоматическим бесконечным retry; его безопасность SHALL следовать идемпотентности добавления.

#### Scenario: Network or source failure

- **WHEN** POST завершается сетевой ошибкой или ESK_CORE_UNAVAILABLE
- **THEN** нет сообщения об успешном добавлении, прежние категории сохранены и доступен осознанный повтор
