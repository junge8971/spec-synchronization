## Context

См. proposal.md. HTML-кнопка «+» демонстрационная; новый PDF 3.6 определяет добавление имени из dictionaries.categories. В отличие от общего рассуждения 8.15 об устойчивых IDs справочников, конкретный wire-контракт категорий использует строки; не заменять их вымышленными category_id.

## Goals / Non-Goals

**Goals:** серверно подтверждённое добавление без потери чужих категорий и без повторного чтения всей карточки.

**Non-Goals:** replace/delete, создание категорий, expected_version/409, клиентский аудит и новые permissions.

## Decisions

1. **Gate закрыт:** пользователь подтвердил принятие бизнес-контракта PDF §3.6, §8.16/8.24/8.30 при реализации MOS-1044. POST принимает `{ name }` из строкового справочника и возвращает полный `{ categories }`; backend отвечает за запись в ЕСК, идемпотентность, сохранение конкурентных добавлений и аудит. Это принятие интерфейса интеграции, не проверка доступности развёрнутого ЕСК. UI не реализует storage категории локально: иначе серверный поиск по категории её не увидит. Auth/session/RBAC и клиентские audit-запросы не добавляются.
2. **Feature мутации:** `features/dialog-category-addition` принимает chat_id и текущие категории; использует публичный `entities/dialog`, не импортирует page/card. Обратный результат передаётся владельцу карточки. Общий dictionary-клиент MOS-1037 не копируется.
3. **Форма:** выбрать одну строку из справочника; сохранить только после валидного выбора. Trim и case-insensitive принадлежность следуют серверу. Существующие категории, исчезнувшие из справочника, показываются как история и не удаляются. Пустой справочник и ошибка чтения различаются; нет ввода произвольного нового имени.
4. **Добавление, не замена:** POST содержит только name. Во время запроса повторное нажатие блокируется; никакого optimistic success. Ответ categories заменяет поле карточки целиком как серверный снимок, без локального объединения, которое могло бы скрыть нарушение контракта. Полный detail refetch не нужен и породил бы лишнее чтение/аудит.
5. **Повтор и конкурентность:** повтор того же имени получает 200 без дубликата; expected_version не вводится. Последовательные мутации одного клиента не должны применить старый ответ после нового. Если параллельный запрос detail начат до добавления, его старые categories не должны затереть результат мутации; использовать существующие средства отмены/обновления query cache по chat_id, а не глобальный mutex.
6. **Ошибки:** 422 /name показывается у выбора, 503 — как отказ записи с сохранением формы; 404 и 401/403 сохраняют смысл бизнес-ошибки без auth-последовательности. Повтор после неоднозначного сетевого сбоя предлагается явно и безопасен по контракту. Серверный аудит не дублируется клиентской записью.

## Risks / Trade-offs

- Два сотрудника добавляют разные категории → backend гарантирует множество; проверка через HTTP mock/server-сценарий, не клиентская имитация версии.
- Устаревший справочник → показать 422 и предложить обновить, не объявлять категорию сохранённой.
- Старый detail-ответ после POST → отмена/изоляция запроса и обновление только текущего chat_id.

## Migration Plan

После gate добавить метод в общий контракт/DTO, mutation и форму карточки MOS-1041. Приёмка включает повторную/конкурентную запись, отказ и гонку с detail. Откат убирает действие, уже записанные категории остаются видимыми.
