## MODIFIED Requirements

### Requirement: Publish requires confirmation and truthful success

Перед публикацией UI SHALL требовать отсутствие несохранённых изменений конфигурации и сценариев в обеих точках запуска; при dirty SHALL объяснять необходимость отдельного сохранения. Незавершённое обязательное чтение после успешной записи SHALL блокировать публикацию. Для доступной публикации UI SHALL показать подтверждающее модальное окно. Отмена SHALL закрывать его без сохранения и без publish-запроса, возвращая фокус к кнопке. После подтверждения UI SHALL повторно проверить отсутствие обоих dirty-черновиков и блокировок, затем проверить текущий сохранённый состав сценариев и параметры, сохранить их через существующий `PUT /enabled-skills`, получить свежую карточку и только затем отправить bodyless `POST /surfaces/v1/surfaces/{surface_id}/publish`. Для публикации SHALL требоваться хотя бы один сценарий в отправляемом и подтверждённом сервером составе, допустимый статус и успешные проверки параметров. Пустое приветствие SHALL NOT вводиться как самостоятельный новый блокер публикации; действующие проверки контрактов сохраняются.

Ошибка подготовки, сохранения или чтения перед публикацией SHALL останавливать цепочку без POST publish. UI SHALL сохранить пользовательские данные и показать этап ошибки. Успешное сохранение перед неуспешной публикацией MUST NOT откатываться фиктивно: последнее подтверждённое серверное состояние остаётся видимым. Новый явный запуск публикации SHALL заново проверять и сохранять актуальный чистый состав, а не обходить этап подготовки прямым POST. Существующий подготовительный PUT enabled-skills сохраняется и для чистого состава; PUT configuration при публикации MUST NOT выполняться. Если подготовительный PUT успешен, а его GET неуспешен, recovery SHALL повторять только GET, не PUT и не POST; успешное recovery не продолжает публикацию автоматически, новый запуск требует нового подтверждения.

Успех публикации SHALL показываться только после подтверждённого `status = prod` и успешного обновления detail с `prod`. При ошибке команды, неожиданном статусе или ошибке обновления UI MUST NOT показывать окно подтверждённой публикации. Успешная команда с неудачным refresh SHALL предлагать повтор чтения, а не повторную запись.

Обязательное чтение перед публикацией SHALL начинаться после успешного PUT; ответ запроса, начатого до сохранения, MUST NOT считаться его подтверждением или перезаписывать результат более позднего чтения. Решение о публикации SHALL использовать полученную свежую карточку. При 409 SHALL применяться ручное обновление и новый запуск действия по требованию `Accessible errors, retry and scope boundaries`.

#### Scenario: Publish is cancelled

- **WHEN** пользователь отменяет подтверждение
- **THEN** PUT и POST не отправляются, черновик и статус сохраняются, фокус возвращается к кнопке публикации

#### Scenario: Publish succeeds

- **WHEN** подтверждена публикация допустимой поверхности с валидным непустым составом
- **THEN** текущие параметры сохраняются перед POST publish, свежая карточка подтверждает prod, появляется доступное окно успеха без обещания нового embed-кода

#### Scenario: Empty current draft prevents publication

- **WHEN** на сервере есть сценарии, но пользователь снял все в текущем черновике
- **THEN** обе точки публикации недоступны; отдельное сохранение пустого состава по-прежнему разрешено для неархивной поверхности

#### Scenario: Save failure prevents publication

- **WHEN** подготовка параметров или PUT enabled-skills завершается ошибкой
- **THEN** publish не вызывается, ошибка сохранения видна, черновик остаётся для исправления и повтора

#### Scenario: Preparation refresh changes eligibility

- **WHEN** после успешного сохранения свежая карточка имеет archived, disabled, draft, prod либо пустой состав
- **THEN** POST publish не отправляется и пользователю объясняется актуальное состояние

#### Scenario: Publish failure follows a successful save

- **WHEN** состав успешно сохранён, но publish отклонён
- **THEN** сохранённый состав не объявляется несохранённым, статус не заменяется prod, повтор проходит полную проверку доступности и подготовку

#### Scenario: Refresh cannot confirm publication

- **WHEN** publish ответил успешно, но detail не загрузился или не подтвердил prod
- **THEN** отображается отдельное сообщение о невозможности подтвердить итог, доступно повторное чтение и окно успеха не открывается

#### Scenario: Earlier read cannot authorize publication

- **WHEN** до сохранения начался GET карточки, а PUT завершился успешно
- **THEN** UI ждёт нового чтения, начатого после PUT, и не отправляет publish на основании старого ответа; старый ответ не заменяет более свежие сведения

#### Scenario: Either draft is dirty

- **WHEN** конфигурация или состав сценариев имеют несохранённые изменения, включая замену элемента без изменения количества
- **THEN** обе точки публикации заблокированы с пояснением отдельного сохранения; обход disabled или изменение состояния во время подтверждения не отправляет PUT или POST

#### Scenario: Clean preparation readback fails

- **WHEN** после подтверждения публикации чистый состав успешно записан подготовительным PUT, но свежий GET завершился ошибкой
- **THEN** повтор восстановления выполняет только GET, не повторяет PUT и не отправляет publish; после восстановления публикация возможна лишь как новое явно подтверждённое действие

### Requirement: MVP editing and deferred functionality boundaries

Перед публикацией SHALL быть отдельно сохранены все редактируемые данные: конфигурация через явное действие конфигуратора и сценарии с параметрами через существующее сохранение состава. При несохранённых изменениях любого из этих черновиков публикация SHALL быть недоступна. Конфигуратор SHALL использовать существующий PUT configuration только для явного сохранения редактируемой конфигурации; фиктивный PUT неизменённой конфигурации, defaults из прототипа, скрытый PUT ради перевода draft в configured и объединение enabled_skills с configuration MUST NOT выполняться. Существующий подготовительный PUT чистого состава перед подтверждённой публикацией SHALL сохраняться согласно Publish requires confirmation and truthful success. Это заменяет только отсрочку конфигуратора, не активирует sandbox или аудит. UI MUST NOT представлять history-заглушку как реальную историю или обращаться к выдуманному API аудита.

#### Scenario: Configuration editor saves explicitly

- **WHEN** пользователь отдельно сохраняет изменения конфигурации, а затем публикует допустимую поверхность без dirty-черновиков
- **THEN** конфигурация записывается только явным сохранением и подтверждается свежим GET; публикация сохраняет существующую подготовку чистого состава без PUT configuration, sandbox и аудита

#### Scenario: Configuration editor is not available

- **WHEN** редактор конфигурации недоступен, а пользователь публикует configured-поверхность без несохранённых изменений
- **THEN** существующая подготовка сохраняет чистый состав сценариев; отсутствие редактора не заменяется фиктивным PUT configuration, defaults или скрытым переводом статуса, sandbox и аудит не вызываются

#### Scenario: Draft remains a draft after saving skills

- **WHEN** сохранение состава не перевело draft в configured на сервере
- **THEN** карточка сохраняет draft и недоступность публикации, не выполняя скрытый PUT configuration ради смены статуса

#### Scenario: Server confirms configured after saving skills

- **WHEN** пользователь отдельно сохранил валидный непустой состав draft-поверхности и серверный ответ с последующим свежим GET подтвердили configured
- **THEN** при чистой конфигурации и отсутствии блокировок публикация становится доступной в обеих точках без автоматического POST publish и без PUT configuration; локального присваивания статуса нет
