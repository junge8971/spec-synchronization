# Design

## Context

Мотивация и четыре Jira-источника приведены в [proposal.md](proposal.md). Требования принадлежат [регистрации](specs/surface-registration/spec.md) и [общему редактору сценариев](specs/surface-skill-selection/spec.md).

Сверка выполнена по исходникам на `bba8b14` и ранее прочитанным вложениям Jira. Текущие пользовательские сценарии в браузере не воспроизводились. Наблюдения по коду:

| Задача   | Текущее состояние                                                                                                                                                      | Точка изменения                                                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| MOS-1164 | `SurfaceDetailsStep` выводит вычисленный канал с `break-words`, без ellipsis; внешний fieldset в `SurfaceRegistrationForm` не имеет `min-w-0`                          | `app/features/surface-registration/ui/steps/surface-details-step.tsx`, `app/features/surface-registration/ui/surface-registration-form.tsx` |
| MOS-1165 | `OwnerTeamField` использует общий `SelectContent` без overrides; default `alignItemWithTrigger=true` совмещает пункт с trigger при открытии мышью                      | `app/features/surface-registration/ui/steps/owner-team-field.tsx`                                                                           |
| MOS-1166 | `SkillSelectionItem` показывает полный `skill.purpose` без локального ограничения; родительский Card скрывает overflow, но сам по себе не задаёт обрезку текста        | `app/features/surface-skill-selection/ui/surface-skill-selection-editor/skill-selection-item.tsx`                                           |
| MOS-1907 | Распознанный `422 FAILED` уже переводит попытку в `rejected` и снимает блокировку; `SurfaceRegistrationResult` не включает `rejected` в состояния со ссылкой на реестр | `app/features/surface-registration/ui/surface-registration-result.tsx`                                                                      |

Историческая причина MOS-1907 — поддержка только `detail[]` при фактическом `errors[]` — устранена коммитом `4bf74ba` от 13.11.2026. Это поведение закреплено в архивном change `2026-11-16-mos-958-registration-api-followup` и `docs/api/contracts/surface-error-provenance.md`. Старые `JOIN-MOS-1164/1165/1166` из audit-пакета описывают более раннюю версию кода; их выводы не заменяют текущие исходники и не подтверждают deployment.

## Goals / Non-Goals

**Goals:** локальное ограничение длинного текста с доступом к полному значению, предсказуемая привязка списка владельца и завершение восстановления после подтверждённого отказа без изменения правил повторной отправки.

**Non-Goals:** пересмотр алгоритма предпросмотра канала, перенос назначения `channel_id` на клиент, замена `purpose` на detail-поле `description`, новый лимит длины, общий редизайн Select/Tooltip, изменения бизнес-API, auth/session/RBAC или автоматическое снятие блокировки неизвестного POST. Соседние поля и экраны не перепроектируются; второй потребитель общего редактора проверяется на регрессию.

## Decisions

### 1. Сокращать представление, сохраняя полные данные

Для предпросмотра канала и описательного текста навыка используется одна строка с многоточием. Это выбранная для данного плана политика представления: Jira требует обрезку, но не задаёт число строк. Альтернатива с переносом не обеспечивает ожидаемую обрезку, а `slice()` меняет данные и не учитывает ширину контейнера.

Переиспользуются Tailwind `truncate` и `min-w-0`. Ограничение ширины проводится по цепочке контейнеров до текста, включая fieldset мастера и нужные grid/flex-элементы. Простое скрытие overflow всей страницы не используется: оно может скрыть элементы управления. Расчёт канала, ввод доменов, `aria-live` предпросмотра адресов и request payload сохраняются. Итоговый шаг использует тот же расчёт; его значения должны оставаться в пределах контейнеров после изменения общей обёртки, без редизайна сводки.

Полное значение остаётся текстом в DOM. Для чтения глазами переиспользуется `~/shared/ui/tooltip`: текстовый trigger доступен с клавиатуры, popup переносит длинные непрерывные строки через `wrap-anywhere` и ограничен шириной экрана. Native `title` не является единственным способом раскрытия, поскольку не обеспечивает требуемое чтение по фокусу. Escape закрывает подсказку; trigger не выполняет submit и не меняет выбор. Обёртка не должна разрушать семантику `dl/dd` или существующее доступное описание переключателя навыка.

Описание навыка по-прежнему берётся из каталожного `purpose`; полное значение сохраняется в элементе, на который ссылается `aria-describedby`. Для длинного имени ограничивается текстовая область рядом с переключателем, сохраняя полную доступную подпись. Правка выполняется в общем `SkillSelectionItem`, поэтому применяется также в `SurfaceDetailsScenarios`. Новый detail-запрос не нужен.

### 2. Настроить позиционирование только списка владельца

В `OwnerTeamField` передать `SelectContent` параметры `alignItemWithTrigger={false}` и `align="start"`. Сохранить существующие `side="bottom"`, отступ, Portal, привязку ширины к anchor и встроенную адаптацию Base UI к границам экрана. Длинное название ограничить внутри локальных текстовых областей trigger/option, не меняя значение команды.

Штатный контракт установленной Base UI описывает `alignItemWithTrigger` как перекрытие trigger для совмещения текста выбранного пункта. Это объясняет наблюдаемое на вложении поведение, но не является измерением геометрии текущего стенда. Изменение глобального default затронуло бы все Select; ручное вычисление координат и новые обработчики resize/scroll дублировали бы библиотеку. Оба варианта исключены из выбранного решения.

### 3. Завершить восстановление, переиспользуя существующую модель попытки

Добавить `rejected` к состояниям, в которых `SurfaceRegistrationResult` показывает существующую ссылку «К реестру поверхностей». Ссылка остаётся обычным переходом React Router, поэтому проходит через уже действующие `useBlocker` и `SurfaceRegistrationLeaveDialog`.

`getRegistrationRejection`, `useSurfaceRegistrationAttempt`, синхронные locks и политика повторов остаются владельцами классификации ответа. Переписывать парсер или разблокировать по одному HTTP-статусу не требуется. Состояния сохраняют смысл:

| Исход                                       | Редактирование и «Назад»          | Повтор POST                                              | Переход в реестр                                     |
| ------------------------------------------- | --------------------------------- | -------------------------------------------------------- | ---------------------------------------------------- |
| Распознанный отказ, `rejected`              | Доступны, ввод и ошибки сохранены | Только новое явное действие после валидации и подготовки | Доступен с предупреждением об уходе                  |
| Неизвестный результат, `unknown`            | Заблокированы                     | Заблокирован                                             | Доступен с действующим предупреждением о риске дубля |
| ID получен, чтение не удалось, `read-error` | Заблокированы                     | Заблокирован; повторяется только GET того же ID          | Сохраняется текущее поведение предупреждения         |

Отмена ухода сохраняет текущее состояние, подтверждение открывает реестр без записи. Возврат по шагам после отказа не требует предупреждения об уходе и не сбрасывает навыки, их параметры или режим отправки на проверку.

### 4. Проверять поведение, отдельно обозначая пределы jsdom

- MOS-1164: расширить `surface-details-step.test.tsx` коротким, пустым и длинным непрерывным вводом; проверить неизменность значения, полный предпросмотр и раскрытие подсказки по hover/focus с закрытием Escape. Проверить сохранение длинного домена в сводке/запросе без отправки `channel_id` средствами component/model-тестов.
- MOS-1165: компонентный сценарий `OwnerTeamField` — открытие указателем и клавиатурой, первый/последний выбранный пункт, длинное имя, Escape без изменения выбора. Не подменять эту проверку тестом соседних ответственных пользователей.
- MOS-1166: компонентный сценарий общего редактора — короткий текст, около 200 символов с пробелами, непрерывная строка длиннее 200, длинное имя, полное `aria-describedby`, hover/focus и сохранение выбора/параметров. Проверить интеграцию в регистрации и карточке поверхности.
- MOS-1907: расширить widget component-тест и API fixture точным `422 FAILED` из бага. Проверить обе навигации, ошибку у доменов, сохранение формы, явный повтор после исправления, отмену/подтверждение ухода. Для границ использовать существующие сценарии неизвестного ответа и ошибки GET; добавить только недостающие существенные утверждения.

Тесты не должны зеркалировать набор CSS-классов или проверять только передачу props в mock библиотеки. В jsdom отсутствует полноценная раскладка: эти проверки подтверждают доступность и поведение, но не отсутствие горизонтальной прокрутки или пиксельное положение popup. Browser/E2E-тесты и запуск приложения в браузере не входят в исполнение этого плана без отдельного явного разрешения. Визуальную приёмку фиксировать как непроверенную до такого разрешения и фактической проверки.

## Risks / Trade-offs

- Длинный текст может растягивать предка даже при `truncate` у потомка → проверить всю локальную цепочку сжатия; не маскировать ошибку глобальным `overflow-x-hidden`.
- Подсказки добавляют точки фокуса → ограничить их двумя целевыми видами текста, сохранить видимый focus и доступность полного содержимого; не вводить копию Tooltip.
- Изменение общего элемента навыка затрагивает карточку поверхности → проверить второго потребителя и сохранение состава, не менять его политику мутаций.
- Слишком широкая трактовка `422` может разрешить дубль → сохранить строгую классификацию и отрицательные сценарии, включая неизвестный формат и потерю ответа.
- Наличие локального исправления MOS-1907 не доказывает его наличие на T → при последующей разрешённой проверке стенда отдельно сверить версию сборки; это не основание дублировать парсер сейчас.

## Migration Plan

Миграция данных и изменение серверного контракта не требуются. После реализации выполнить проверки из tasks и выпускать обычным frontend-релизом. Откат ограничивается UI и соответствующими тестами; существующую обработку подтверждённых отказов MOS-958 и защиту от повторного POST сохранять.
