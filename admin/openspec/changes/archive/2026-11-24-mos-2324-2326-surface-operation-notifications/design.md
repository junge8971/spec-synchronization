# Design

## Context

Мотивация и согласованный объём — в [proposal.md](proposal.md). Проверены координатор `use-surface-details-operations.ts`, обе точки запуска, `surface-details-publish-action.tsx`, lifecycle-диалог, локальный toast provider, существующие тесты сценариев и общий `shared/ui/notifications`.

- `SurfaceDetailsPublishAction` хранит одновременно `dialogMode` и `feedback`: после успешного `onPublish` создаёт краткий успех и открывает модалку результата. `onPublish` используется обеими реальными точками запуска.
- Старый success остаётся в `feedback` после удаления toast по таймеру. Сохранение сценариев включает `hasPendingReadback`, который через `isBlocked` меняет `isConflict` и `retryLabel` даже у успеха. Зависимый от `retryLabel` эффект `SurfaceDetailsFeedback` снова регистрирует старый toast. Запрос публикации при этом не нужен.
- `useSurfaceDetailsOperations` уже владеет общим lock, dirty/readback-проверками, раздельными мутациями и окончательным GET. Он может сформировать результат без чтения устаревших props.
- Общий `NotificationProvider` подключён в `application-root.tsx`. `useOperationNotification` уже публикует успех событием, заменяет предыдущее уведомление и проверяет контекст/время жизни владельца. `Notification` поддерживает `Toast.Description`, но hook пока принимает только заголовок и необязательный таймер.
- Предметная спецификация требует подтверждающий диалог и окно результата, а общий `operation-feedback` требует событийный неблокирующий успех. Пользователь выбрал замену обеих модалок нотификатором, отдельно подтвердил сохранение текущего порядка записи и исключил MOS-2322.

## Goals / Non-Goals

**Goals:** один владелец краткого успеха публикации и сохранения сценариев, достоверный серверный счётчик, отсутствие зависимости уведомлений от рендера, одинаковый запуск из шапки и «Подключения».

**Non-Goals:** перестройка сохранения и query-кэша, миграция всех уведомлений поверхности, переписывание ошибок и предупреждений, новые транспортные операции или общий workflow/event bus. Существующие данные успешной записи не должны теряться вместе с кратким уведомлением.

## Decisions

### 1. Сохранить координатор и заменить только вход и представление результата

`SurfaceDetailsPublishAction` становится запуском существующего `onPublish` по нажатию кнопки, с прежними проверками доступности и локальным представлением ошибки. Удалить состояния confirmation/success и использование `SurfaceDetailsLifecycleDialog`; после проверки всех импортов удалить оставшиеся без потребителей компонент и типы. Повтор после ошибки команды вызывает ту же полную последовательность без модального подтверждения. После успешной записи с ошибкой GET повтор остаётся только чтением.

Все реальные потребители уже передают `onPublish`: использовать этот обязательный путь вместо запасной прямой публикации из UI-компонента, чтобы обе точки всегда проходили подготовку. Допустимость в обработчике и общий синхронный lock координатора сохраняются; двух быстрых кликов и кликов по разным кнопкам недостаточно для второй операции.

```text
Publish click --> validate clean drafts --> prepare --> PUT enabled-skills
              --> fresh GET --> recheck --> POST publish --> fresh GET(prod)
              --> one publication notification

Save skills   --> prepare --> PUT enabled-skills --> existing readback
              --> one skills-save notification
```

Это сохраняет текущий порядок запросов, включая подготовительный PUT неизменённого состава. Автоматический PUT configuration не добавляется. Альтернатива — заменить только текст модалки — не выполняет выбранное поведение и оставляет два представления успеха.

### 2. Публиковать успех из координатора, а не из JSX и эффектов

Использовать один экземпляр общего `useOperationNotification` в координаторе карточки для двух затронутых операций. Привязать его к `surfaceId`; сохранить существующие проверки актуального владельца ответа. Уведомление принадлежит карточке, а не переключаемой вкладке или каждой из двух кнопок.

На старте принятой операции очищать предыдущее краткое уведомление этого координатора. После подтверждённой публикации вызывать уведомление один раз; после успешного ручного сохранения сценариев — один раз для этого сохранения. Подготовительный PUT публикации не вызывает ручной success. Общий hook заменяет предыдущее уведомление, в том числе если сохранение началось до исчезновения публикационного результата.

Удалить затронутые success-ветки `feedback`/`saveSucceeded` и их success-JSX, проверив все места использования. Данные ошибки, сообщения неполного чтения и признаки сохранённого состояния, необходимые для восстановления, сохранять. Не менять `SurfaceDetailsFeedback` для остальных потребителей ради этой миграции.

Альтернатива — стабилизировать `retryLabel` для успеха — устраняет конкретный триггер, но сохраняет повтор старого успеха при перемонтировании. Глобальная подписка на все mutations создаёт ложный успех на подготовительном PUT и усложняет связь с конкретной операцией.

### 3. Взять число из результата окончательного GET

В `publishAndConfirm` использовать `published.detail`, уже полученный `runAndRefresh`, после действующих проверок результата и `status = prod`. Сформировать описание с `published.detail.enabled_skills.length`; не использовать `controller.draft`, `surface` из замыкания или промежуточный GET до POST. Не добавлять новый GET ради уведомления и не менять контракт POST, возвращающего только статус и время.

Для публикации передать заголовок «Поверхность опубликована» и описание «Ассистент доступен пользователям, включено сценариев: N». Для ручного сохранения — «Состав сценариев сохранен» согласно MOS-2326. Если PUT сценариев успешен, а GET завершился ошибкой, сохранить существующий факт записи и отдельное предупреждение; сообщение о сохранении не утверждает, что чтение подтверждено. Повтор такого GET не создаёт новый успех сохранения или публикации.

Альтернатива — передать число выбранных сценариев из кнопки — может сообщить локальное или устаревшее значение и теряет серверную нормализацию.

### 4. Совместимо дополнить существующий общий нотификатор

Добавить необязательное описание к `useOperationNotification.notifySuccess`, сохранив действующие вызовы `(title, timeout?)` и их поведение. Использовать уже имеющийся `Toast.Description`, provider, закрытие, паузу таймера и контекстные guards. Конкретная совместимая сигнатура может добавить описание третьим необязательным параметром; новый виджет или менеджер уведомлений не нужен. Расширение проверить тестами существующего hook без ослабления прежних утверждений.

Локальный toast provider поверхности остаётся у остальных сообщений. Проверить совместное отображение общего успеха и действующего предупреждения о неудачном чтении: оба сообщения и действия восстановления должны оставаться доступными. Не переносить смешанные error/warning состояния целиком в общий success-hook и не отключать доступность ради расположения уведомлений.

### 5. Обновить только затронутые предметные контракты

Delta `surface-lifecycle-publication` явно удаляет прежнее требование публикации с причиной и миграцией и добавляет замещающее требование без модалок. Удаляется только ставший неприменимым сценарий отмены подтверждающего окна; все сценарии подготовки, частичного успеха, dirty, свежего GET и отсутствия sandbox сохраняются. Подтверждения заменяются на явный запуск также в retry/conflict-recovery и ссылке из границ MVP. Delta `surface-overview-connection` согласует публикацию второй точки и отсутствие старого успеха при открытии вкладки. `operation-feedback` и `surface-skill-selection` используются как действующие контракты без новых дублирующих capability.

## Risks / Trade-offs

- [После удаления диалога проще отправить две команды] → сохранить общий lock и pending во всех точках; component-тест с отложенными ответами и двумя быстрыми кликами проверяет одну последовательность.
- [Старый success остаётся у одной кнопки или вкладки] → один владелец уведомления в координаторе; тестировать оба запуска, истечение таймера, повторное сохранение и переключение вкладок.
- [Общий hook используется другими разделами] → расширение описания совместимо со строкой и таймером; прежние проверки повторных вызовов и позднего завершения сохраняются.
- [Факт записи смешан с успешным чтением] → не менять существующие границы частичного успеха; при неудачном GET сохраняются данные записи, предупреждение и повтор только GET.
- [Два механизма уведомлений могут перекрыть важное предупреждение] → проверить доступность успеха, предупреждения и retry в составном сценарии; ограничить корректировку затронутым представлением, без миграции соседних операций.
- [Удаление подтверждения оставляет старые требования в связанных specs] → delta включает полный изменённый requirement и ссылки на него; перед завершением проверить отсутствие активных предписаний модалки публикации в итоговом объединении specs.

## Migration Plan

Миграция данных, backend и API-типов не требуется. После отдельного запуска реализации изменить точки уведомлений и запуск кнопок, добавить unit/component-регрессии, затем выполнить проверки проекта. Поставка — обычное обновление фронтенда; технический откат возвращает прежнее представление без миграции данных. На стадии propose создаются только planning artifacts; sync основных specs и архивирование в этот этап не входят.
