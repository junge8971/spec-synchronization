## Context

Мотивация и границы — в `proposal.md`. Design необходим из-за нескольких затронутых модулей, безопасности скачивания и зависимости от внешнего развёртывания.

## Goals / Non-Goals

**Goals:** минимальные изменения в существующих владельцах поведения, подтверждение уже внесённой совместимости, понятная диагностика и воспроизводимые критерии приёмки именно развёрнутого приложения.

**Non-Goals:** tolerant-parser для несовместимых DTO, общий новый metadata framework, изменения session/permissions, отключение CSV-защит, автоматическая публикация тестовых навыков, новый CRUD удаления навыков, вмешательство в чужие сущности. Не расширять соседние changes отчётов, мониторинга или истории.

## Decisions

### 1. Use current contract support instead of reimplementing it

Сохранить существующие Zod-схемы поверхности и typed metadata в каждом optional-модуле. Добавить/дополнить адресные тесты обезличенными формами реально наблюдавшихся ответов: объект ответственного с nullable сведениями, `links_count` и `groups_count` с числовыми операторами. Проверять не только parser, но загрузку реестра/карточки после успешного ответа.

Граничные случаи: строка вместо объекта ответственного, неизвестный оператор и ошибочный тип metadata должны по-прежнему отклоняться, не становиться пустой успешной выдачей. Существующие эквивалентные тесты использовать, а не дублировать. Альтернатива с union старого/нового DTO отклонена: скрывает несовместимую выкладку и противоречит текущему контракту. Generated API не редактируется вручную.

### 2. Repair export delivery at its source, keep client validation

Общий клиент `app/entities/dialog/api/dialog-export-client.ts` обслуживает POST отбора/отмеченных и GET карточки. Уточнить там ошибки отсутствующего/неверного обязательного заголовка, сохранив текущую последовательность проверок, байты, session boundary и отсутствие автоматического replay.

Отсутствующий в Fetch заголовок не позволяет определить, отсутствует ли он на проводе или скрыт CORS. При интеграционной проверке сопоставить безопасно извлечённые response headers сети и доступные Fetch headers; не сохранять request credentials. Для двух origin обязательные заголовки должны быть реально корректны, а заголовки вне CORS safelist — доступны JS через явный `Access-Control-Expose-Headers` (в частности X-Content-Type-Options и Content-Disposition). Wildcard не считать достаточным при credentials. Проверить все обязательные заголовки, а не только первый отказ.

Если причина на backend/ingress, описать точное требуемое исправление и передать владельцу; данный репозиторий его не реализует. UI-диагностика не считается исправленной выгрузкой до успешного реального скачивания всех трёх scope. Альтернативы снять nosniff/no-store, дописать отсутствующие заголовки клиентом, использовать no-cors или локально пересобрать CSV отклонены.

### 3. Keep explicit filter application, make it discoverable

В существующей React Hook Form оставить submit и добавить видимый текст «Найти» с пояснением, что он применяет все быстрые фильтры. Состояние неприменённых изменений вычислять из значений формы относительно применённых q/period/channel_ids/skill_ids, не создавать второй самостоятельный store и не включать condition_group в сравнение быстрых полей. Списки сравнивать по смыслу выбора, не по случайному порядку; учитывать одинаковое значение отсутствующего/пустого поля по действующим правилам нормализации.

Использовать существующий сброс/remount страницы при применении сохранённого отбора и текущий query flow. Проверить Enter, ошибки дат, общий сброс, применение сохранённого фильтра, сохранение condition_group и отсутствие устаревших страниц. Не переходить на auto-apply: это меняет принятую модель draft/applied, частоту запросов и семантику экспорта.

### 4. Explain the catalog prerequisite without relaxing it

В регистрации связать недоступный переход с видимым пояснением о минимуме одного prod-навыка. На пустом каталоге предложить существующий механизм повторного чтения; он должен сохранять заполненную анкету и параметры. Использовать имеющийся controller.retryCatalog и полную серверную пагинацию, не новый загрузчик. Причина регистрации принадлежит регистрации, а общий empty/retry каталога может оставаться у feature выбора сценариев; не переносить регистрацию в shared.

Не менять правило карточки, где пустой enabled_skills разрешён. Не превращать пустой prod-каталог в ошибку всего реестра. Для проверки успешной регистрации владелец тестового контура должен предоставить подходящий prod-навык с валидной схемой; создание/публикация произвольного навыка автоматически не выполняется. Если prerequisite отсутствует, позитивная интеграционная проверка отмечается blocked, а не passed.

### 5. Separate implementation completion from contour acceptance

Добавить компактный `docs/test-contour-scenarios-checklist.md`, а не новое CI/версионное API. Для каждого прогона фиксировать ревизию исходников, идентификатор сборки/артефакта из доступных средств релиза, фактический manifest/bundle, время и результаты сценариев. Наличие локального исправления или зелёных mock-тестов не доказывает его доставку пользователю. Исходные ошибки сверяются с новым bundle после согласованной выкладки владельцем контура.

При повторной проверке не создавать новые навыки без плана очистки; использовать выделенный аудитный объект только по назначению, отмечать оставшиеся сущности. Не удалять существующие пользовательские данные и не выдумывать cleanup API.

## Risks / Trade-offs

- [Новая сборка не выложена] → локальные задачи могут быть выполнены, но contour acceptance остаётся незавершённой до проверки manifest и поведения.
- [Заголовки исправляются вне репозитория] → явно блокировать приёмку CSV, приложить обезличенный перечень header presence/values и получить подтверждение владельца; не обходить защиту.
- [Нестабильная авторизация/503] → зафиксировать исходную операцию и повтор чтения; auth-модель не менять, запись автоматически не повторять.
- [Отсутствует prod-навык] → проверить объяснение/сохранение формы локально; успешную регистрацию на контуре не объявлять проверенной без prerequisite.
- [Form dirty state расходится с applied selection] → тесты возврата к исходным значениям, сброса и смены сохранённого отбора; не полагаться только на touched/dirty флаг.
- [Frontend-only rollback снова ломает контракт] → возвращать только совместимую с текущим backend сборку; не откатывать к строковым ответственным.
- [Аудит не исчерпывает все роли/состояния] → матрица явно разделяет passed/failed/blocked/not-run и не обещает «проверены все сценарии».

## Migration Plan

1. Добавить недостающие регрессионные проверки существующих схем и выполнить локальные исправления UX/диагностики.
2. Запустить typecheck, lint без предупреждений, test, format:check, api:check и build. Сохранять production без моков; никаких обновлений зависимостей ради задачи.
3. Заполнить release-checklist доступными идентификаторами артефактов и внешними prerequisites CSV/prod-каталога. Самостоятельная выкладка не входит в разрешение на планирование/аудит.
4. После согласованной выкладки проверить карточку поверхности, оба контентных реестра/существующие формы, три CSV scope, быстрые фильтры, регистрацию и работающие регрессионные сценарии. Использовать только разрешённые сценарии браузерного аудита; новые/изменённые E2E-файлы требуют отдельного разрешения.
5. Закрывать change только после проверки реального контура либо оставлять соответствующие задачи незавершёнными с блокирующей причиной. При необходимости отката согласовать совместимость backend/frontend, не выполнять слепой откат только фронта.

## Open Questions

- На каком уровне теряется/скрывается X-Content-Type-Options и кто владеет требуемой настройкой backend/ingress? Это уточняется сравнением response headers без изменения выбранной fail-closed модели.
- Какая сборка будет выложена владельцем контура и когда будет доступен выделенный prod-навык для позитивной регистрации? Это prerequisites интеграционной приёмки, не основание менять контракт.

## Authorized follow-up: local search draft and surface validation

Причина потери текста KB/A/B подтверждена owner component-тестами с реальным createMemoryRouter и посимвольным userEvent: draft был связан с будущим URL, тогда как срочный рендер ещё видел старый URL и восстанавливал прежний applied query. Один символ нормализуется в отсутствие API query; задержанные commits также могли обрезать более новый ввод.

В каждом optional-модуле независимо хранить raw draft, committed `location.key`, `useId` владельца и возрастающую ревизию ввода. Только query edits передают owner/revision через существующий setSearchParams в собственный namespaced navigation state, сохраняя посторонний location state. На смене committed key собственный non-POP commit с ревизией не новее draft сохраняет raw text; POP, внешняя навигация, сброс и применение сохранённого отбора восстанавливают applied query, в том числе при том же URL. Категории/статусы не получают query ownership. Metadata остаётся в history state, не URL/API. Не использовать очередь ожидаемых URL: одинаковые нормализованные query и промежуточные commits требуют идентичности навигации и ревизии, а не предсказанного URL.

Проверки владельцев покрывают один символ, непрерывный ввод, вручную задержанный loader, повторные нормализованные targets, очистку до commit, Back/Forward, внешнюю навигацию, same-URL saved filter, сброс, сохранность прочих фильтров/state и offset=0. A/B сохраняет `.min(1)` с сообщением «Выберите хотя бы одну поверхность»; schema и editor tests проверяют отказ пустому составу, доступное описание/alert и успешное сохранение после выбора поверхности. Правила и API не меняются. Историческая 6.1 относится к прежнему артефакту; доставка этого follow-up требует отдельного сопоставления новой сборки и повторной проверки.
