## Context

Мотивация и scope описаны в proposal.md. На момент исследования HEAD содержит 28 операций / 93 схемы; рабочий OpenAPI с незакоммиченным intents — 29 / 102; выгрузка — 33 / 115. Все прежние paths/schemas HEAD структурно совпадают с выгрузкой: её добавления ограничены Assistant modules. Пользователь подтвердил сохранение intents.

`mocks/app.mjs` регистрирует операции из полного OpenAPI и падает при отсутствии handler, кроме явно исключённого Access `/me`. AJV валидирует входы и успешные ответы, `state.mjs` создаёт изолированное состояние, `list.mjs` предоставляет page/sort. `scripts/generate-api-types.mjs` уже поддерживает генерацию и проверку типов. Клиент карточки требует intents, редактор использует PUT intents; их контракт нельзя удалить.

Основная спецификация `control-center-mock-server` уже содержит семантику модулей. Архив `2026-09-28-update-assistant-modules-contract` описывает подход и отмечен завершённым, но реализации модулей в текущем дереве нет. Он используется как контекст решений, а не как свидетельство выполненных задач. Все задачи нового change проверяются по фактическим файлам.

## Goals / Non-Goals

**Goals:** единый совместимый контракт, актуальные самостоятельные разделы и типы, работоспособный mock API модулей вместе с intents, воспроизводимые проверки без внешнего файла после импорта.

**Non-Goals:** новый механизм слияния контрактов на каждый запуск, новый генератор разделов, ручные DTO, UI модулей, изменения редактора фраз, auth/session/RBAC, новые зависимости, отдельный storage или реальное дообучение.

## Decisions

### 1. Аддитивное объединение, не замена источника

В текущий `docs/api/contracts/openapi.json` добавить только пять paths/operations и 22 схемы Assistant modules из выгрузки без семантических правок. Сохранить целиком прежний контракт, включая PUT intents, девять его схем, свойство intents и его обязательность в SkillResponse. Проверить структурным сравнением отсутствие изменений прежних paths/schemas и точность переноса модулей. Итог — 34 операции / 124 схемы; счётчики дополняют сравнение, а не заменяют его.

Это минимальнее и безопаснее полной замены с последующим восстановлением удалённых определений. При неожиданном конфликте одноимённых схем не выбирать источник молча: остановиться и согласовать конфликт. В изученных источниках такого конфликта для добавляемых модулей нет.

`docs/api/contracts/README.md` явно описывает объединённое происхождение: выгрузка message.txt плюс уже согласованный intents MOS-809. Обновить Assistant modules Markdown и добавить самостоятельный OpenAPI с транзитивными схемами/security; обновить Skills/Domains JSON и Markdown до девяти операций. Индекс содержит 34 операции, пять заполненных и шесть отсутствующих разделов. Остальные самостоятельные контракты не менять без обнаруженного расхождения, относящегося к этому change. Генерация типов — только `yarn api:generate`; CI использует файлы репозитория, а не Downloads.

### 2. Один источник состояния модулей в существующем сервере

Добавить `mocks/assistant-modules.mjs` и подключить operationId map в `app.mjs`; fail-fast сохранить. Seed содержит включённый разрешённый модуль, отключённый разрешённый модуль и включённый модуль с запретом отключения; предусмотреть непустое предупреждение о последствиях. UUID, nullable/required-поля и fixed business actor `by` соответствуют схемам. `by` не описывает посетителя и не вводит сессию.

Summary и preview вычисляются из коллекции modules на чтении, а не хранятся отдельными snapshots. Сохраняются основные требования: totals по всей коллекции, degraded/warning при наличии disabled, иначе healthy/success; по одной fallback-карточке на disabled. Для пустого user_message использовать документированный mock-текст «Модуль временно недоступен». Caption, banner и sample_user_message — детерминированные mock-тексты.

### 3. Мутации по уже принятой mock-конвенции

После schema-validation: поиск модуля (404), проверка версии (409), для disable проверка disable_allowed и необходимого confirm_impact (409), затем единственная мутация. Отказ не меняет состояние. Успех, включая повтор целевого статуса с актуальной версией, увеличивает version, обновляет updated_at/by и status. Disable сохраняет user_message с default пустой строкой; enable сбрасывает его в null. Для модулей Idempotency-Key не добавляется: источник его не требует.

Использовать существующие sendSuccess/sendError. Недокументированные исходником 404/409 и правила производных представлений фиксируются в mock README, а не добавляются в OpenAPI как якобы backend-гарантии.

### 4. Исправления на общей границе query и sort

Нормализовать одиночное значение query-параметра с array-схемой в массив до AJV; повторённые значения уже представлены массивом. Не менять scalar-параметры или расширять нормализацию на body/header/path. Это устраняет причину отклонения `?sort=name`, не обходя общую валидацию в handler.

Переиспользовать page/sort: фильтровать до пагинации, применять стабильные сортировки от последнего критерия к первому. Локальные defaults и семантика соответствуют основной спецификации: name при отсутствии sort, регистронезависимый query по code/name/description, точный status и пустой результат для неизвестного status.

В текущем `list.mjs` default accessor обращается к исходному field (`-name`), игнорируя вычисленный key (`name`). Исправить общий accessor, сохранив custom accessor API, неизменность входного массива и стабильность. Это необходимо для контрактной descending-сортировки модулей и устраняет ту же причину у прежних потребителей; не вводить отдельный sorter модулей. Перед изменением проверить все вызовы helper, покрыть строки, даты, числа, nullable и одинаковые значения.

### 5. Сохранение текущей работы и исполняемые проверки

Не сбрасывать и не перезаписывать staged/unstaged изменения intents. Сохранить регистрацию PUT intents и его участие в idempotency, начальные intents в состоянии, существующие server/component-тесты и runtime-валидацию карточки. Недостающие граничные проверки добавить в существующий node:test подход: запись/GET/повтор/очистка, устаревшая версия, невалидная группа, отсутствующий ключ и отсутствие мутации при отказе.

Контрактный тест сравнивает множество реально выполненных method/path или operationId со всеми 33 бизнес-операциями, не только число handlers. Отдельно проверяются 404 Access, соответствие двух самостоятельных разделов полному контракту и разрешимость их ссылок, актуальность generated-типов. Для модулей нужны успешные и ошибочные HTTP-сценарии, согласованность всех views и изоляция состояния. UI совместимость подтверждается существующими unit/component-тестами; браузер не нужен.

## Risks / Trade-offs

- Утрата незакоммиченного intents при импорте → аддитивное объединение, структурная проверка прежних определений и регрессия PUT/GET.
- Архив создаёт ложное впечатление готовности → реализация проверяется по текущему дереву, новый task list начинается полностью невыполненным.
- OpenAPI не описывает все бизнес-правила → применять ранее согласованные mock-конвенции, отдельно документировать их статус.
- Изменение общих query/sort затрагивает прежние списки → проверить всех потребителей, scalar/integer параметры и descending-регрессии.
- JSON обновлён без handlers → поставлять контракты, типы, seed и handlers совместно; оставить fail-fast.
- Личный путь источника недоступен в CI → все runtime/генерация/тесты используют только версионируемые контракты.

## Migration Plan

1. Сверить исходное рабочее дерево, импортировать только добавления модулей, обновить документацию и самостоятельные разделы, сгенерировать типы.
2. Добавить seed/handlers модулей и необходимые исправления общей валидации/сортировки; сохранить intents.
3. Расширить contract/server-тесты и mock README. Запустить typecheck, lint без предупреждений, test, format:check, api:check и build для регрессии production isolation; E2E/browser-тесты не менять и не запускать.
4. Проверить diff относительно исходного рабочего дерева, отдельно указать прежние падения проверок. Rollback ограничивается добавлениями этого change, не уничтожает ранее существовавшие изменения intents; постоянной миграции данных нет.
