# Spec Delta

## Purpose

Позволить выбирать навыки и задавать их параметры при регистрации и редактировании поверхности, сохраняя корректную привязку значений к навыку и явно показывая ограничения актуального API.

## ADDED Requirements

### Requirement: Contract-backed skill catalog

Оба экрана SHALL получать полный список из `GET /api/control/api/skills/v1/skills` с учётом пагинации и схемы из `GET /api/control/api/skills/v1/skills/{skill_id}`. UI MUST NOT обращаться к отсутствующему `available-skills`, выводить prod-статус или доступность для поверхности из косвенных полей. Источник выбора SHALL обозначаться как общий реестр без обещания фильтрации по prod. Loading, empty и error/retry SHALL различаться; ошибка страницы реестра MUST NOT превращать частичный список в полный.

#### Scenario: Catalog spans multiple pages

- **WHEN** нужный навык находится за пределами первой страницы
- **THEN** он доступен в выборе после загрузки полного реестра и находится в своём домене

#### Scenario: Catalog request fails

- **WHEN** одна из страниц реестра не загружена
- **THEN** интерфейс показывает ошибку и повтор; отсутствие записи в неполной выборке не трактуется как удаление, сохранение блокируется до успешной проверки

### Requirement: Domain and bulk selection

Редактор SHALL группировать навыки по доменам, предоставлять индивидуальный выбор, включение/снятие домена, «Включить все», «Снять все» и количество выбранных навыков. Частичный выбор домена SHALL быть видимым и доступным для вспомогательных технологий; включение частично выбранного домена SHALL выбирать все его навыки. Массовое включение SHALL дополнять выбор без удаления ранее выбранных отсутствующих записей. Элементы SHALL иметь доступные подписи и управление с клавиатуры.

#### Scenario: Partially selected domain

- **WHEN** выбран один из трёх навыков домена и пользователь включает домен
- **THEN** выбраны все три, дубликатов нет, выбор других доменов сохранён, счётчики обновлены

#### Scenario: Clear selection

- **WHEN** пользователь нажимает «Снять все»
- **THEN** выбор очищается, включая явно показанные отсутствующие навыки, а параметры остаются в черновике до завершения редактирования

### Requirement: Schema-driven parameters

Редактор SHALL строить параметры выбранного навыка из `connection.parameters` по `key/title/type/required/default/options`. Для актуального `select` SHALL использоваться строковые options; обязательное значение должно быть непустым и принадлежать options. Необязательный незаполненный параметр SHALL опускаться в payload. Default SHALL применяться только к ещё не инициализированному значению, числовой default преобразуется в строку и принимается только при наличии в options. Пустая схема, отсутствующий parameters или connection=null SHALL означать отсутствие параметров. Неизвестный тип, неоднозначные ключи или некорректная схема MUST NOT молча приводить к сохранению пустых параметров.

#### Scenario: Required select and valid default

- **WHEN** выбран навык с обязательным select и default, соответствующим options
- **THEN** поле получает default; очистка или значение вне options блокирует сохранение с ошибкой у поля

#### Scenario: No parameters

- **WHEN** выбран навык без схемы параметров
- **THEN** дополнительные поля не показываются и для него отправляется `parameters: {}`

#### Scenario: Unusable schema

- **WHEN** выбран навык с неизвестным типом, повторяющимися ключами либо обязательным select без вариантов
- **THEN** редактор объясняет проблему и блокирует сохранение этого выбора, позволяя повторить загрузку или снять навык

### Requirement: Parameter ownership and draft preservation

Значения SHALL принадлежать паре skill_id/key. Переключение навыка, домена, массового выбора и шагов регистрации MUST NOT сбрасывать параметры других навыков. Повторное включение навыка в той же сессии редактирования SHALL восстанавливать введённые значения; фоновые ответы MUST NOT перезаписывать черновик defaults или сохранённой конфигурацией. В запрос SHALL входить только выбранные навыки, каждый ровно один раз.

#### Scenario: Same key in different skills

- **WHEN** два навыка имеют параметр с одинаковым key и пользователь меняет значение одного
- **THEN** значение другого сохраняется и оба отправляются под соответствующими skill_id

#### Scenario: Toggle and return to registration step

- **WHEN** пользователь снимает и повторно включает навык или возвращается с проверки на шаг сценариев
- **THEN** введённые значения сохранены и не заменены defaults

### Requirement: Revalidation and missing skills

Перед созданием или сохранением поверхности UI SHALL обновить полный реестр и схемы выбранных навыков, проверить актуальный черновик и заблокировать повторную отправку на время проверки и мутации. Отсутствующий в успешно загруженном полном реестре выбранный навык SHALL оставаться видимым с названием, если оно известно, иначе с ID; сохранение SHALL блокироваться до явного снятия. Ошибка чтения схемы SHALL давать retry без потери данных. Устаревшее значение options или сохранённый ключ, отсутствующий в новой схеме, SHALL требовать явного исправления/удаления пользователем, а не молчаливого отбрасывания. Ошибки сервера после проверки SHALL сохранять черновик. UI MUST NOT обещать выявление prod/доступности, которых нет в API.

#### Scenario: Skill disappears after selection

- **WHEN** навык исчез из реестра между выбором и финальной отправкой
- **THEN** запрос записи не выполняется, проблемная запись видна и может быть явно снята

#### Scenario: Schema changes while editing

- **WHEN** обновлённая схема больше не допускает введённый option или сохранённый ключ
- **THEN** старое значение видно как проблема, не удаляется автоматически, сохранение ожидает явного исправления

#### Scenario: Detail cannot be loaded

- **WHEN** схема выбранного навыка не загружена из-за ошибки
- **THEN** показаны ошибка и повтор, остальные значения сохранены, запрос записи не отправляется

### Requirement: Registration and existing surface persistence

Регистрация SHALL включать проверенный `enabled_skills` в существующий POST создания поверхности и сохранять действующее требование хотя бы одного сценария. Карточка SHALL инициализировать редактор из GET поверхности и сохранять состав отдельным `PUT /api/control/api/surfaces/v1/surfaces/{surface_id}/enabled-skills`; пустой состав при редактировании SHALL допускаться по контракту. Запрос MUST NOT менять оформление через `/configuration`. Успех SHALL отображаться только после успешного ответа; повторное открытие SHALL показывать сохранённые данные. Сетевые ошибки, включая 422, SHALL отображаться без сброса черновика и без фиктивного успеха.

#### Scenario: Create surface with configured skills

- **WHEN** завершена валидная регистрация с двумя навыками
- **THEN** POST создания содержит оба skill_id с их параметрами, а остальные поля регистрации сохраняют прежнее поведение

#### Scenario: Edit and clear existing surface

- **WHEN** пользователь снимает все навыки существующей поверхности и сохраняет
- **THEN** PUT enabled-skills содержит пустой массив, оформление не отправляется и после успешного ответа повторное открытие показывает пустой состав

#### Scenario: Save rejected

- **WHEN** сервер отклоняет сохранение
- **THEN** пользователь видит ошибку, введённые параметры остаются и доступен повтор без двойной параллельной отправки
