# Design

## Context

Мотивация — в proposal.md. `useRegistrationSkillsQuery` уже использует полный пагинированный реестр; `ScenariosStep` группирует его и меняет `skillIds`, но `toCreateSurfaceRequest` всегда отправляет пустые параметры. `SurfaceDetails` показывает только базовые сведения, а его DTO выбран через Pick без enabled_skills. `getSkillDetails` уже валидирует connection.parameters, поэтому новый клиент схем не нужен. Mock server уже обслуживает PUT enabled-skills и хранит параметры.

Приложенный api-29:09.txt — единственный актуальный контракт. В нём select, строковый словарь параметров, nullable connection и отдельный enabled-skills endpoint. Схема не предоставляет lifecycle или surface eligibility. Существующая спецификация control-center-api-integration запрещает синтез таких данных; новый change её не меняет. Наличие zones или auth_required не является признаком допустимости выбора.

## Goals / Non-Goals

**Goals:** единый редактор и валидатор для двух владельцев сохранения; корректные границы FSD; проверка актуальности без перезаписи черновика; повторное использование установленных React Hook Form, Zod и TanStack Query.

**Non-Goals:** универсальный конструктор форм для неизвестных типов, изменение API, перенос всех новых методов приложенного API в проект, реализация оформления/публикации и перенос ролевых ограничений прототипа.

## Decisions

### 1. Общая feature и композиция выше features

Создать `features/surface-skill-selection` с контролируемым редактором, hook управления черновиком, валидацией и подготовкой enabled_skills через публичный index.ts. Владельцы состояния живут на время всей формы, а не только смонтированного шага.

Добавить `widgets/surface-registration` как точку композиции существующей регистрации и новой feature. Регистрация получает слот редактора и контракт подготовки навыков перед submit через props; она не импортирует соседнюю feature. Общие wire-типы остаются в entities/surface, типы слотов — у владельца props. `widgets/surface-details` подключает ту же feature непосредственно. Это сохраняет направление зависимостей и не переносит предметный UI в shared. Копирование редактора или импорт feature из feature отвергнуты.

Один компонент — один файл; типы, константы и обработчики размещаются в соответствующих сегментах ближайшего владельца. Внешние импорты — только через index.ts. Не создавать обёртки сверх необходимых точек композиции.

### 2. Получение данных и query-кэш

Переиспользовать getAllSkills и getSkillDetails. Обобщить registration-specific query на уровне entities/skill, проверив все вызовы. Полный реестр нужен для группировки и массового выбора, details загружаются для выбранных навыков через query-кэш; не загружать карточки всего реестра заранее. Дедупликация и отмена запросов — штатными средствами Query и AbortSignal, без отдельного самописного кэша.

В entities/surface расширить DTO и runtime-схему detail полем enabled_skills, добавить клиент и mutation существующего PUT с проверкой ответа. Типы брать из generated-контракта; если требуется актуализация локального snapshot, переносить только релевантный подтверждённый контракт штатным генератором, не редактировать schema.d.ts вручную. Не импортировать несвязанные API-изменения из приложения к задаче.

### 3. Черновик и правила значений

Хранить выбранные ID и параметры по skill_id раздельно: снятие флага исключает навык из payload, но оставляет его значения в черновике. Инициализировать серверные значения один раз на surfaceId; фоновые refetch не сбрасывают dirty state. Переключение surfaceId создаёт независимый черновик.

Defaults применять однократно для нового поля, сохраняя информацию об инициализации, в том числе при явной очистке. Числовой default нормализовать String(default), null/отсутствие трактовать как отсутствие default. Invalid default не подставлять; обязательность валидировать отдельно. Select допускает только перечисленные строки; необязательное незаполненное поле не сериализовать. Отсутствующие options — отсутствие вариантов: обязательный select блокирует сохранение, необязательный можно оставить пустым. Пустые/повторные ключи и неподдержанный тип дают ошибку схемы.

Сохранённые неизвестные ключи показывать отдельной проблемой с явным удалением; исчезнувший option — ошибкой поля. Не чистить их при сериализации автоматически. Для навыка действительно без параметров после устранения устаревших данных отправлять {}. Предлагаемые правила нормализации — frontend-поведение этого change, а не дополнительные гарантии backend.

Сохраняется существующее требование регистрации выбрать минимум один навык. Редактирование допускает пустой список, поскольку PUT его разрешает; это записано явно, чтобы не распространить ограничение мастера на карточку.

### 4. Финальная проверка и сохранение

Общий prepare/validate перед POST и PUT повторно получает полный реестр и схемы выбранных навыков. На время этой операции и мутации блокировать изменение редактора и повторную отправку, чтобы проверяемый снимок совпадал с payload. Если список неполон или запрос завершился ошибкой, запись запрещена, черновик сохраняется. Существующие проверки остальных полей регистрации остаются действующими.

Найденные в полном реестре навыки доступны для выбора без выдуманного prod-фильтра. Отсутствующий выбранный ID показывается отдельно и блокирует запись до явного снятия. Массовое включение объединяет выбор с реестром; массовое снятие является явным удалением всех выбранных записей.

Успешный PUT возвращает enabled_skills: принять серверный результат как новую базу, обновить detail и инвалидировать затронутые surface queries. Не выполнять оптимистичный успех. Ошибки транспорта и 422 показывать на форме, field errors связывать с полями там, где серверный путь однозначен. Ошибка повторного чтения после успешной записи не должна выдаваться за неуспешную запись. Общий transport и его error conventions переиспользуются.

### 5. Проверки и fixtures

Использовать unit-тесты модели и component-тесты двух интеграций. Существенные случаи: два навыка с одинаковым key; defaults и очистка; toggle/domain/all; возврат между шагами; исчезновение после выбора; смена схемы; неполная пагинация; ошибка detail; отказ PUT; пустой список; повторное открытие; refetch без сброса dirty state. Серверные тесты подтверждают round-trip параметров через POST/PUT/GET и сохранение оформления.

Fixtures должны включать несколько навыков с различными схемами, без параметров и повторяющимся key между навыками. Недоступность/гонки имитируются в тестах, а не выдуманными runtime API-полями. Новые ограничения backend не добавлять в mock handlers как якобы контрактные правила. Browser/E2E не нужны и не запускаются.

## Risks / Trade-offs

- API не сообщает prod/доступность для поверхности → использовать общий реестр и явно зафиксировать ограничение приёмки; новый eligibility API потребует отдельного согласования.
- Между preflight и записью возможна гонка, в PUT нет expected_version → обработать серверный отказ без потери данных; не обещать атомарную проверку или защиту от перезаписи другим редактором.
- Массовый выбор приводит к множеству detail-запросов → загружать только выбранные, использовать Query cache и показывать прогресс; стоимость следует из отсутствия batch/schema endpoint.
- Схема parameters расположена в connection → использовать ровно предоставленные поля, не выводить дополнительные правила из endpoint/auth-полей.
- Поведение очистки устаревших значений требует дополнительного UI → дать явные действия удаления, чтобы не скрывать потерю данных за успешным сохранением.

## Migration Plan

Изменений хранилища и backend-миграции нет. Внедрить общую модель и API-адаптеры, затем две интеграции и fixtures. Старый локальный skillIds-only draft миграции не требует: постоянного хранения у него нет. Проверить существующие DTO fixtures после расширения detail-схемы. Откат — возврат frontend-изменений; уже сохранённые контрактные параметры остаются на сервере и не должны очищаться отдельной миграцией.
