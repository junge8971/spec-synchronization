## Bounded lifecycle and physical-delete implementation record

The subsequent lifecycle stage extends the same editor controller's synchronous pending lock and authoritative current-state reference. It does not create another draft or mutation lock. Informational/user cards offer draft → active, active → paused and paused → active; system is readonly and unknown statuses have no guessed transition. PUT contains only status and accepts success only for the matching UUID and requested target. The returned card supplies status/date/settings metadata without replacing value drafts. Status remains stored configuration, not readiness or downstream propagation.

Lifecycle intent resolves dirty work through Save/Discard/Stay first. Save must return a fully confirmed clean result; partial/rejected/unresolved/cancelled saves stop continuation. Stay also cancels continuation while a save is pending. The latest authoritative state/group/status is checked again at dispatch. User deletion then requires a separate irreversible confirmation naming the dictionary/code and all its values; cancelling that dialog sends no DELETE and does not undo earlier saves.

Matching DELETE 200 identity alone authorizes automatic terminal exit. The exact editor's native blocker is released synchronously, matching owner/card reads are cancelled and removed, the registry is invalidated, and Router replaces the current detail entry. Other-card caches and generic resources are not removed. Status/delete uncertainty is separate from row/settings uncertainty: writes remain blocked, errors remain visible, explicit UUID readback displays observed status/date or observed 404 absence, and nothing is replayed automatically. Accepting a present observation requires acknowledgement that completion was separately established; readback itself cannot establish abandoned-request finality. Observed 404 never announces deletion success or auto-navigates; it offers an explicit safe return only.

Specialized mock DELETE overrides enforce nonuser card 405 and nonuser row 409 without mutating shared consumer arrays. User card deletion physically removes its own card/values and frees the code; row deletion addresses current code and updates parent count/server timestamp. A WeakSet initialization sentinel prevents recomposition from restoring a deleted user seed or duplicating shared registrations. Generic managed-resource handlers and lookup ownership remain unchanged. Focused model/API/component/local HTTP evidence is recorded in tasks and the stage handoff; deployment, journal and independent acceptance review remain separate.
