## Purpose

Реализовать конструктор вопросов и вариантов в разделе обратной связи ЦАМ по опубликованному API, с отдельной приёмкой и сохранением ограничений первого этапа.

## ADDED Requirements

### Requirement: Isolated feedback integration

Возможности этой задачи SHALL поставляться внутри обособленного модуля раздела «Обратная связь», с общим foundation MOS-1249 и ограниченными точками подключения приложения по образцу базы знаний. Внешние потребители SHALL обращаться через публичный API модуля; framework route entrypoints SHALL подключаться отдельно. Бизнес-слои приложения MUST NOT зависеть от внутренних модулей feedback. Существующие transport, обработка ошибок и механизмы сессии SHALL сохраняться. Новая UI-policy, mappings permissions и новые ограничения интерфейса по пользователю MUST NOT добавляться в текущую поставку.

#### Scenario: Integrate the task without expanding module boundaries

- **WHEN** реализация задачи подключается к приложению и общей модели feedback
- **THEN** предметная логика и тесты остаются у владельца раздела, composition использует публичный API и отдельные route entrypoints; действующие защитные механизмы сохраняются без новых permission mappings

### Requirement: Stable questions and options

Конструктор SHALL поддерживать stars, tags, text, boolean, scale, nps, emoji, изменение заголовка/типа/required, добавление, удаление и порядок вопросов/вариантов. Порядок SHALL изменяться перетаскиванием и доступными клавиатурными действиями. Лимиты SHALL быть 100 вопросов, 100 вариантов на вопрос, title 1–500, option.text 1–255. tags SHALL иметь минимум один вариант; остальные типы MUST NOT отправлять непустые options. Смена типа, удаляющая варианты, SHALL требовать подтверждения.

PUT questions SHALL содержать полный итоговый массив с сохранёнными UUID существующих элементов и без ID новых. sort_order MUST NOT отправляться. Existing inactive type SHALL допускать изменение/перестановку без смены типа, новые вопросы с ним MUST NOT создаваться. Неизвестный type SHALL сохраняться без подмены и иметь явное ограничение preview.

#### Scenario: Reorder without identity loss

- **WHEN** сохранённые вопросы и варианты переставлены, один удалён и один добавлен
- **THEN** PUT содержит полный итоговый порядок, старые UUID сохранены, у нового элемента ID отсутствует; повторный GET воспроизводит результат

#### Scenario: Empty tag options

- **WHEN** у вопроса tags удалён последний вариант
- **THEN** сохранение не объявляется успешным, ошибка доступна рядом с вопросом и введённый текст остаётся

### Requirement: Accessible questions interactions

Область этой задачи — вопросы, варианты и их перестановка — SHALL поддерживать клавиатуру, доступные названия/ошибки, предсказуемый фокус и узкую компоновку. Приёмка SHALL проверять собственные элементы; реализация и приёмка соседних UI-возможностей MUST NOT требоваться для закрытия этой задачи сверх явно указанных зависимостей интеграции. Недоступные API MUST NOT имитироваться успешными заглушками.

#### Scenario: Keyboard and narrow layout within this task

- **WHEN** пользователь работает с элементами этой задачи клавиатурой на узком экране
- **THEN** действия и ошибки доступны, содержимое не перекрывает управляющие элементы, закрытие имеющихся диалогов возвращает фокус

### Requirement: Questions share the existing survey save

Конструктор SHALL подключаться к готовому общему черновику карточки MOS-1251 и её единому сохранению внутри обособленного feedback. Изменение вопросов MUST NOT создавать отдельное сохранение, очищать метки/поверхности или сбрасывать правила. После успешного PUT/GET SHALL приниматься серверные UUID и новый baseline; ошибка вопроса на скрытой вкладке SHALL раскрывать эту вкладку с фокусом и сохранять остальной ввод. Итоговая совместная приёмка с метками после готовности MOS-1254/MOS-1257 SHALL выполняться в MOS-1257 с сохранением самостоятельной приёмки базового MOS-1251.

#### Scenario: Save questions together with basic fields and rules

- **WHEN** пользователь изменяет вопрос, название и правило показа и сохраняет карточку
- **THEN** один PUT передаёт согласованный payload; повторный GET сохраняет UUID вопросов/вариантов, метки, поверхности и все неизменённые правила
