## Purpose

Показывать актуальный серверный этап проверки, обучения и автотестов навыка посредством автоматического чтения открытой карточки без имитации результатов процесса.

## ADDED Requirements

### Requirement: Server-owned current processing status

UI SHALL показывать текущий этап из опубликованного SkillResponse.status и объяснять, что результаты отдельных проверок недоступны. Статусы checking/training/autotest SHALL отображаться как проверка, обучение и автотесты с теми же подписями, что в существующей карточке. Этап SHALL различаться текстом, а не только цветом. Локальное время MUST NOT менять статус, объявлять предыдущие этапы успешными или создавать проценты, ETA, run ID, логи и ошибки процесса.

#### Scenario: Server changes processing stage

- **WHEN** очередное чтение возвращает training вместо checking
- **THEN** карточка показывает обучение без объявления проверки успешной и без выдуманных результатов пропущенных этапов

#### Scenario: Server status does not change

- **WHEN** повторные чтения продолжают возвращать training
- **THEN** UI сохраняет этот этап без локального завершения, процентов, ETA или ошибки по истечении времени

### Requirement: Conditional automatic observation

Пока открытая видимая карточка имеет последний успешно прочитанный status checking, training или autotest, UI SHALL периодически перечитывать её. Периодическое чтение SHALL прекращаться при получении любого другого опубликованного статуса и при уходе со страницы; скрытая вкладка браузера MUST NOT продолжать polling. Переключение вкладок внутри карточки MUST NOT создавать дополнительные независимые циклы. Повторное открытие SHALL получать серверное состояние и определять необходимость автообновления заново. Ручное обновление SHALL сохраняться для любого статуса.

Наблюдение SHALL выполнять только чтение, без POST status или команд запуска/повтора. Автообновление MUST NOT сбрасывать несохранённые изменения существующих редакторов карточки. Данные другого skill ID MUST NOT подменять состояние открытого навыка.

#### Scenario: Observe processing until status changes

- **WHEN** сервер возвращает checking, затем training, autotest и sandbox
- **THEN** UI автоматически перечитывает карточку во время первых трёх статусов, отражает серверные ответы и прекращает периодические запросы после sandbox, не отправляя мутаций

#### Scenario: Open a non-processing skill

- **WHEN** карточка открыта с draft, sandbox, review, whitelist или prod
- **THEN** статус загружается обычным чтением, периодические запросы не запускаются, ручное обновление остаётся доступным

#### Scenario: Leave and reopen

- **WHEN** пользователь уходит со страницы во время training и позже возвращается
- **THEN** после ухода периодические запросы прекращаются, при возвращении читается актуальная карточка без создания локального запуска

#### Scenario: Preserve an editing draft

- **WHEN** пользователь редактирует данные карточки и приходит автоматическое обновление
- **THEN** несохранённый ввод сохраняется, а существующая проверка версии при сохранении не обходится

### Requirement: Read failure is not process failure

Ошибка получения обновлений SHALL отображаться как ошибка чтения, а не обучения или автотестов. При наличии ранее загруженной карточки UI SHALL помечать показанный этап как последние загруженные данные, приостанавливать периодическое чтение и предоставлять ручной повтор. Успешное чтение SHALL возобновлять наблюдение только при checking/training/autotest. Без ранее полученных данных SHALL сохраняться штатное состояние ошибки загрузки.

#### Scenario: Update request failure

- **WHEN** чтение очередного обновления завершается ошибкой после ранее полученного training
- **THEN** UI показывает последние данные с ошибкой обновления и повтором, не объявляет обучение проваленным и приостанавливает polling

#### Scenario: Successful retry

- **WHEN** ручной повтор успешно возвращает training либо sandbox
- **THEN** ошибка чтения снимается; для training автообновление возобновляется, для sandbox остаётся выключенным

### Requirement: Status observation does not establish readiness

MVP SHALL ограничиваться наблюдением за status. UI MUST NOT считать его подтверждением результатов отдельных проверок, обработки текущей версии фраз или доступности песочницы. Полноценные результаты, ошибки процесса, повторный запуск и готовность SHALL оставаться недоступными до отдельного согласования API; существующие команды MOS-909 сохраняются без расширения.

#### Scenario: Sandbox status without readiness API

- **WHEN** сервер возвращает sandbox без данных о проверках и обработанной версии
- **THEN** UI показывает этот текущий статус и прекращает polling, но не объявляет все проверки успешными, не разрешает песочницу на основании одного status и не создаёт токен
