## Context

См. proposal.md. `overview-tab.tsx` уже выводит DTO, `skill-details-client.ts` валидирует GET через Zod, `use-skill-details-query.ts` использует TanStack Query. Формы и HTTP transport уже существуют в проекте. Визуальный ориентир — `/home/user/Загрузки/Прототип. Центр управления.html`, не его локальное хранилище/роли.

## Goals / Non-Goals

**Goals:** дополнить существующий read-flow одной формой анкеты и общей skill mutation.

**Non-Goals:** новый универсальный CRUD-конструктор, создание навыка, редактирование connection, lifecycle и auth-контекст.

## Decisions

- UI формы принадлежит `features/skill-editing`, сборка — `widgets/skill-details`, PATCH и cache invalidation — `entities/skill` через публичный index. Альтернатива копировать транспорт в widget создаст второй протокол сохранения.
- Использовать существующие средства форм/валидации и UI-компоненты; форма открывается отдельно от read-only обзора. Ввод и ошибки принадлежат форме, серверная карточка — Query cache.
- PATCH отправляет только изменённые поля анкеты и исходный expected_version. Не отправлять connection, чтобы не затереть MOS-1022. Одна логическая попытка и её сетевой повтор используют один Idempotency-Key; изменённое тело — новый ключ. Успех валидировать тем же контрактом карточки.
- Обновить detail и связанные списки, не сбрасывая фильтры реестра. Не переносить черновик на другую skill ID. Dirty-форму не перезаписывать фоновым refetch.
- Ссылки related_materials отображать безопасно, без HTML-инъекций и исполняемых URL. Не выводить серверные строки через raw HTML.

## Contract gate

Перед соответствующей интеграцией зафиксировать с владельцем API: источник выбора contact_user_id (members команды не доказанный полный справочник), очистку nullable полей/массивов, ответ на expected_version conflict. Backend описывает только 200/422; не считать mock 409 согласованной схемой. До решения не ограничивать контакты самовольно и не закрывать полную приёмку.

## Согласованный частичный объём реализации

Пользователь разрешил пропустить вопросы согласования и реализовать доступную функциональность. Это разрешение не заменяет backend-контракт:

- Можно изменять текстовые поля, type, domain_id, team_id, непустые zones и related_materials. Используются существующие полные справочники доменов и команд.
- Контакт показывается только для чтения; новый источник контактов не придумывается.
- Неизменённые поля не отправляются. Очистка изменённых строк/массивов блокируется с пояснением до согласования null/пустых значений. Существующие null и пустые массивы не препятствуют изменению других полей.
- Любая ошибка PATCH сохраняет draft и исходный expected_version. Пользователь получает предложение перечитать данные перед новой попыткой; автоматического PATCH с новой версией нет. Тест защитной обработки HTTP 409 не объявляет его согласованным backend-ответом.
- related_materials в обзоре остаются обычным текстом, без исполняемых ссылок.
- Полная приёмка, выбор контакта и контрактный сценарий конфликта остаются открытыми. Задачи с частично реализованным объёмом не отмечаются завершёнными.

## Risks / Trade-offs

- Параллельное редактирование → сохранить draft, показать ошибку конфликта, предложить перечитать карточку без автоматического повторного PATCH новой версии.
- Неизвестная связь domain/team/contact → использовать контрактные ID, ошибки связи показывать у формы; не выводить бизнес-ограничения из UI прототипа.
- Общий файл карточки меняют несколько задач → MOS-944 не трогает содержимое остальных вкладок.

## Migration Plan

Добавить форму без миграции данных, проверить существующий GET и новые component/API-сценарии. Откат UI возвращает read-only карточку, не отменяет уже сохранённые серверные изменения.
