# Design

## Context

Мотивация описана в [proposal.md](proposal.md), поведение — в [delta spec](specs/surface-registration/spec.md).

`model/parse-domains.ts` разделяет строку по запятым, точкам с запятой и пробельным символам, нормализует адреса и возвращает уникальные непустые значения через `Set`. Его результат используют первый шаг, сводка и `toCreateSurfaceRequest`; unit-тест уже закрепляет удаление дублей. Поэтому проверять повторы по готовому результату этой функции поздно.

`surfaceRegistrationSchema.shape.domains` проверяет только непустой результат. Эта же схема подключена к React Hook Form через `zodResolver` в режиме `onChange`, используется в `areSurfaceRegistrationFieldsValid`, при `form.trigger` в `goNext` и через `handleSubmit` перед подготовкой/созданием. Кнопка «Далее» зависит от `isStepReady`.

`SurfaceDetailsStep` передаёт сообщение поля в `SurfaceRegistrationField`, который размещает текст ошибки внутри `label`. Для доменов пока нет `role="alert"` и связи поля с отдельным описанием ошибки. Дизайн нужен, чтобы согласовать сохранение существующего разбора с новой проверкой и доступным сообщением без второго состояния валидации.

## Goals / Non-Goals

**Goals:** сохранить один набор правил нормализации и одну схему валидности для кнопки, обработчика перехода и отправки; оставить контракт `parseDomains` для потребителей; предоставить алерт, связанный с полем.

**Non-Goals:** перенос логики в другой FSD-слой, замена библиотек формы, новая модель состояния, изменение сетевой последовательности регистрации, проверка занятости через реестр, расширение синтаксической проверки адресов и исправление остальных сценариев регистрации.

## Decisions

### 1. Искать повторы до удаления одинаковых значений

Внутри `model/parse-domains.ts` выделить общую операцию разбора нормализованных непустых элементов с сохранением повторов. `parseDomains` продолжит возвращать уникальные адреса в прежнем порядке. Добавить предметную функцию получения повторяющихся адресов, переиспользующую тот же разбор; каждый повторяющийся адрес возвращается один раз. Для поиска достаточно стандартных `Set`, без зависимости и отдельного сервиса.

Новая функция нужна только внутри feature и импортируется схемой напрямую; публичный `index.ts` расширять не требуется. Связанная логика остаётся в существующем модуле.

Альтернатива с изменением результата `parseDomains` затрагивает сводку, запрос и существующих потребителей. Независимая нормализация в схеме создаёт риск расхождения. Сравнение числа исходных токенов с числом уникальных адресов ошибочно считает пустые элементы повтором.

### 2. Вся блокировка остаётся в Zod-схеме поля

Расширить валидацию `domains` в `surface-registration.schema.ts`: сначала проверять наличие непустых нормализованных адресов, затем повторы. Для пустого списка оставлять прежнее сообщение «Укажите хотя бы один домен»; для повторов формировать одно сообщение с адресами из функции поиска. Использовать штатную проверку поля Zod, например `superRefine`, сохраняя доступ через `surfaceRegistrationSchema.shape.domains`.

Схема автоматически влияет на существующие `isStepReady`, `form.trigger` и `handleSubmit`. В `goNext` и контроллер отправки не добавляется самостоятельное правило или отдельный флаг. `onChange` обеспечивает появление и снятие ошибки при редактировании; исходная строка формы не преобразуется и не переписывается.

Альтернатива с проверкой только в `onNext` оставляет отсутствие алерта при уже отключённой кнопке и не защищает окончательную отправку. Дополнительный React state дублирует результат схемы.

### 3. Алерт принадлежит полю доменов

В `ui/steps/surface-details-step.tsx` вывести сообщение доменов под полем отдельным элементом за пределами `label`, со стабильным ID через React `useId` и `role="alert"`. Передавать его ID в `aria-describedby` textarea при наличии ошибки и сохранять `aria-invalid` из ошибок формы. Выводить серверные и локальные сообщения как обычный текст. Остальные ошибки `SurfaceRegistrationField` сохраняют текущий вывод.

Это сохраняет доступное имя «Домены» при появлении сообщения и позволяет вспомогательным технологиям объявить ошибку. Пояснение о непроверенной занятости остаётся рядом. Отдельный toast или `window.alert` потребовал бы дополнительного канала уведомлений и управления повторными показами при каждом изменении; сообщение у поля использует существующий сценарий исправления.

### 4. Приёмка через unit/component-тесты

- В `model/tests/surface-registration.test.ts` проверить точные и нормализованные повторы, все поддержанные разделители, несколько конфликтов, игнорирование пустых элементов и допустимость разных поддоменов. Сохранить тест прежнего результата `parseDomains` и нормализованного request mapping.
- В тех же unit-тестах проверить отклонение полного draft общей схемой и `isStepReady` через `areSurfaceRegistrationFieldsValid`. Отдельный тест обработчика должен подтвердить, что отрицательный результат `form.trigger` не меняет шаг: disabled-кнопка не заменяет проверку обработчика.
- В component-тестах widget заполнить остальные поля, ввести дубль, проверить алерт, доступное имя/описание textarea, `aria-invalid`, недоступность «Далее» и отсутствие перехода. Затем исправить список, проверить снятие ошибки, переход и сохранение остальных данных. Повторить существенный сценарий для эквивалентных адресов после нормализации; проверить отсутствие запросов поиска доменов и создания при ошибке.
- Перед окончательной отправкой unit/component-тестом подтвердить отклонение невалидного draft до подготовки навыков и вызова создания, используя существующий контроллер и поддержанные моки.

## Risks / Trade-offs

- Расхождение нормализации и поиска повторов → общий разбор в существующем модуле и проверки эквивалентных записей.
- «Далее» отключается до клика → алерт выводится в режиме `onChange`, независимо от попытки перехода.
- Текст ошибки внутри `label` меняет доступное имя → сообщение доменов выносится за пределы метки и связывается через `aria-describedby`; это проверяется component-тестом.
- Уникальность внутри поля может восприниматься как проверка занятости → сохраняется прежнее пояснение; сетевые проверки не добавляются.
- Baseline `surface-registration` ещё находится в `mos-958-registration-mvp` → delta содержит полный изменённый requirement из этого change. Перед синхронизацией этой delta сначала перенести baseline MVP; никаких правок соседнего change или основных specs в рамках подготовки/реализации 1571 не требуется.

## Migration Plan

Миграция данных и API не требуется. Изменение поставляется с фронтом и unit/component-тестами; валидные уникальные списки сохраняют прежний формат запроса. Откат возвращает прежнее принятие дублей и молчаливое удаление повторов без изменения серверных данных.
