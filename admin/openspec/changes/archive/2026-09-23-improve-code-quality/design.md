## Context

Мотивация и область — в `proposal.md`. Рабочее дерево содержит незакоммиченную интеграцию `connect-control-center-http-client`, включая новые файлы, которые не видны в обычном `git diff`. Её design уже предусматривает разделение mock handlers по разделам контрактов.

Наблюдения при подготовке:

- `AGENTS.md` задаёт базовые требования, но не фиксирует запрет обхода проверок и критерии полезной декомпозиции достаточно явно.
- `yarn lint` запускает `eslint .` и проходит с 8 предупреждениями: HTTP-клиент (complexity 32), три функции URL-параметров, шапка и три участка mock-сервера. Порог уже равен 10.
- `lint-staged.config.ts` запускает `eslint --fix`, поэтому оставшиеся warnings не блокируют commit.
- `mocks/app.mjs` содержит 819 строк: Ajv-валидацию, контекст запроса, формат ответов, идемпотентность, обработчики и изменения связанного состояния.
- HTTP-клиент содержит подготовку URL/заголовков, fetch, обработку транспортных ошибок, JSON/envelope и проверку данных. Его тесты уже проверяют 204, Bearer, идемпотентность, 422/401, сетевые ошибки и abort.
- Моки используют `node:test`, приложение — Vitest; контрактные и lifecycle-тесты уже существуют. Переезд на другой runner не нужен.

## Goals / Non-Goals

**Goals:**

- Сделать границы ответственности очевидными без роста числа абстракций ради самого роста.
- Использовать существующие инструменты и тесты для контроля изменений.
- Проверить весь согласованный рабочий набор, сохранив простые участки без изменений.

**Non-Goals:**

- Переписывать API, вводить SDK, repository/service-слои или универсальный framework для mock CRUD.
- Менять пользовательские сценарии, модель авторизации, политику retry, значения seed или OpenAPI.
- Вводить лимиты длины каждого файла/функции, новые lint-плагины, новые зависимости или переделывать CI/deployment.
- Редактировать установленные skills или глобальные инструкции агента: требования проекта живут в корневом `AGENTS.md`.

## Decisions

### 1. Правила проекта и механическая проверка дополняют друг друга

Расширить существующий `AGENTS.md`, не дублировать его новым руководством. Описать критерии: одна ответственность, один уровень абстракции, предметное имя выделенной операции, минимум переходов между файлами, явные условия вместо сжатых выражений. Перед изменением общей функции проверить её вызовы. Сохранить требования к валидации границ, безопасности, доступности и обработке ошибок.

В `package.json` использовать `eslint .`, применить ту же политику к `lint:fix` и ESLint-команде в `lint-staged.config.ts`. Сохранить complexity 10 и существующие исключения сгенерированных файлов. Проверить согласованность staged-glob с поддерживаемыми расширениями JS/TS, включая модульные варианты. Не включать дополнительные правила без обнаруженной необходимости.

Альтернатива — только поменять severity complexity на error — не блокирует остальные warnings. Строгие лимиты строк отклонены: длина не доказывает смешение ответственностей.

### 2. Mock-сервер разделяется по предметным границам

`mocks/app.mjs` остаётся точкой сборки Express-приложения и контрактных маршрутов. Выделить обработчики Access, Domains/Skills, Surfaces, Teams в предметные модули. Вместе с обработчиками держать специфичные для них преобразования и изменения отношений. Общие операции выделять только при реальном использовании несколькими группами.

В инфраструктурных модулях разместить контрактную валидацию/контекст/ответы и middleware идемпотентности. Направление зависимостей — сборка импортирует handlers и инфраструктуру, handlers используют инфраструктуру, инфраструктура не импортирует handlers или app. Не создавать общий `utils` для несвязанных функций.

Сохранить `createMockApp`, изоляцию состояния при создании приложения, проверку наличия всех operationId, HTTP-маршруты, статусы, ошибки, порядок auth/validation/idempotency и lifecycle. Существующую передачу request context не заменять одновременно другим механизмом без конкретной необходимости: структурный перенос не должен менять HTTP-семантику.

Альтернатива — один файл на endpoint — увеличивает навигацию и повторение; универсальный CRUD-конструктор скрывает различия контрактов.

### 3. HTTP-клиент остаётся маленьким транспортом

Сохранить публичные `apiRequest`, `ApiError` и token provider. Выделить внутренние именованные операции подготовки запроса и чтения/проверки ответа; начать с функций в том же файле, а не отдельного файла для каждого шага. Упростить повторные условия после успешного разбора envelope.

Сохранить query 0/false и исключение null/undefined, пользовательские заголовки и ключ идемпотентности, AbortSignal, 204, ошибки non-JSON, произвольный успешный code, ошибки envelope и проверку data. Не превращать ошибку протокола в пустые данные, не ослаблять runtime-validation ради снижения complexity.

Альтернатива — обёртка над fetch в виде класса — не нужна для единственного транспорта.

### 4. URL-state и UI упрощаются локально

В двух `registry-search-params.ts` сделать ветвление нормализации и обновления параметров понятнее; сохранить отличия фильтров, defaults, сброс страницы, удаление устаревших значений и посторонние query-параметры. Общий helper допустим только для совпадающего поведения с понятным контрактом, не для конфигурируемого движка URL-state.

В шапке проверить и выделить вычисление представления пользователя, если это делает loading/error/success ветки понятнее. Для остальных изменённых clients, providers, widgets, тестов и конфигурации применять те же критерии. Не менять уже связные небольшие функции: например, генератор API-типов сам по себе не требует декомпозиции.

### 5. Поведение проверяется через существующие границы

Использовать публичные HTTP-клиенты, HTTP mock-server и UI-сценарии, не закреплять тестами имена внутренних helper-функций. Для изменяемой логики переиспользовать подходящие тесты и добавить только недостающие существенные/граничные случаи. Большие последовательные тесты разделять по сценариям только с сохранением проверок mutation→read и покрытия операций; приложения и состояние изолировать.

Проверить новый lint gate небольшим воспроизводимым smoke-тестом через ESLint CLI: чистый ввод даёт 0, warning-only ввод с complexity выше 10 даёт ненулевой код с ``. Fixture можно передавать через stdin; не оставлять намеренно плохой исходник среди lint-целей. Отдельно проверить использование флага обеими командами и staged-конфигурацией.

Обнаруженные функциональные ошибки не исправлять молча в структурном diff: описать воспроизводимый случай и вынести в отдельное согласование/изменение. Несовпадения существующего поведения и требований интеграции также не разрешать неявно.

## Risks / Trade-offs

- [Потеря исходных незакоммиченных правок] → перед apply зафиксировать состав working tree и baseline проверок; не выполнять reset/checkout/stash или commit без запроса; сверять правки с исходным рабочим состоянием, а не только HEAD.
- [Циклические импорты после разделения моков] → однонаправленные зависимости и HTTP-контрактные тесты после каждого переноса.
- [Метрика улучшается, читаемость ухудшается] → оценивать названия и поток управления на review; не прятать ветвление в случайных callbacks и конфигурации.
- [Строгий lint обнаружит старые проблемы вне рабочего набора] → зафиксировать исходные ошибки, минимально расширять область лишь при необходимости для gate и объяснять каждое такое изменение.
- [Генерация или форматирование затронут посторонние файлы] → генерируемые файлы проверять через `api:check`, форматировать адресно, просматривать tracked и untracked файлы.
- [Тесты проходят за счёт ослабления утверждений] → сохранять контрактные assertions и отрицательные сценарии, не заменять их snapshots структуры реализации.

## Migration Plan

1. Зафиксировать рабочий набор и результаты исходных проверок; уточнить только выявленные ограничения среды.
2. Обновить `AGENTS.md` и lint-команды; проверить отрицательный и положительный сценарии gate. До устранения warnings lint ожидаемо красный.
3. Последовательно рефакторить транспорт, mock-инфраструктуру/предметные обработчики, URL-state и UI, затем остальные участки рабочего набора при наличии причины. После каждой группы запускать целевые тесты.
4. Выполнить `yarn typecheck`, `yarn lint`, `yarn test`, `yarn format:check`, `yarn api:check`, `yarn build`, `yarn test:e2e`. Проверить сохранение dev-only моков и отсутствие их попадания в production.
5. Просмотреть полный diff и новые файлы; отдельно перечислить непроверенное и причины. Не отмечать выполнение по одному отсутствию lint-ошибок.

Миграции данных и API нет. При необходимости отменять только собственные изменения этого рефакторинга относительно сохранённого исходного рабочего состояния, не откатывать интеграцию пользователя целиком.
