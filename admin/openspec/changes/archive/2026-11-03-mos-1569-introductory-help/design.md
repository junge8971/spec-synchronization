## Context

Мотивация — в `proposal.md`; проверяемое поведение — в `specs/control-center-shell/spec.md`.

`ApplicationRoot` размещает `ApplicationLayout` и общую шапку внутри существующей `SessionBoundary`. В шапке уже есть кнопка и `IntroductoryHelpDialog`; hook управляет открытием и отметкой, а локальный массив содержит в точности три текста аналитики. Диалог использует существующий `Dialog` на Base UI. Отдельный API не нужен. Текущий hook читает отметку при монтировании и изменении версии, но не при переходе внутри SPA; его `sessionSeenKeys` запоминает все закрытия, даже при успешной записи. Поэтому после удаления сохранённого ключа автопоказ на следующем переходе в другой раздел сам по себе не восстанавливается.

После согласованного сокращения тестового набора от прежнего компонентного теста шапки остался unit/hook-тест смены версии. Исторические отчёты о прежних компонентных тестах не являются свидетельством текущего покрытия.

## Goals / Non-Goals

**Goals:** сохранить существующие компоненты и границу сессии, выполнить точные критерии справки, сделать хранение и отказы наблюдаемыми в unit/hook-тестах и отдельно предусмотреть проверку доступности реального UI.

**Non-Goals:** новые механизмы входа, сессии, permissions, маршрутов, API или моков; реализация песочницы; новая библиотека onboarding; повторное создание удалённого набора компонентных или автоматических E2E-тестов.

## Decisions

### 1. Использовать общую шапку после существующего session boundary

Оставить управление справкой у `ApplicationHeader`, который уже монтируется общей оболочкой, в том числе на экранах отказа в разделе после подтверждения principal. Не переносить справку до `SessionBoundary`, не делать дополнительный запрос `/me` ради отметки и не менять разрешения. Формулировка прежнего сценария «без сессии» заменена на подтверждённый контекст в соответствии с аналитикой и ответом пользователя. В mock mode тот же путь использует подтверждённый mock principal, а не реальные credentials.

Альтернатива — отдельный глобальный onboarding provider или копии диалога по страницам — не нужна: оболочка уже общая, а дополнительные владельцы усложняют единое состояние и фокус.

### 2. Сохранять версию и учитывать открытие раздела

Сохранить существующий ключ `control-center-help-seen:1` и значение `"1"`, не вводить миграцию или привязку к пользователю. Сохранить поведение для доступной отметки и новую версию ключа при изменении версии справки. Аналитика определяет отсутствующий ключ и значение `"1"`; значение других записей не расширять новыми требованиями.

При открытии другого раздела, включая переход без перезагрузки, проверять текущую отметку снова: критерий MOS-1569 связывает автопоказ с отсутствием ключа при открытии раздела. Использовать существующий pathname из `ApplicationLayout` через штатную маршрутизацию и передать в управление справкой; не создавать свой роутер, не слушать каждый query-параметр и не менять историю. Пока диалог открыт, переход не должен сбрасывать открытый шаг. Немедленный показ только из-за самого события удаления ключа без последующего открытия раздела не требуется.

Различать успешную запись, последующее намеренное удаление сохранённой отметки и недоступность чтения/записи: после успешно сохранённой, но затем удалённой отметки следующий переход снова запускает справку. При отказе storage удерживать отметку в памяти текущего сеанса оболочки, чтобы навигация не открывала её бесконечно; после полной перезагрузки повтор допустим. При доступном storage эта временная защита не должна постоянно перекрывать фактическое удаление ранее успешно сохранённого ключа. Реализовать это минимальным расширением существующих storage helper/hook, не добавляя сервер, глобальный store или межвкладочный протокол.

Альтернатива — считать отметку только при первом монтировании — дешевле, но не покрывает повторную доступность автопоказа после очистки ключа при переходе внутри открытого приложения. Мгновенная синхронизация открытых вкладок и обработка произвольных нештатных значений не предусмотрены аналитикой.

### 3. Оставить единый путь закрытия и существующий доступный диалог

Переиспользовать установленный `Dialog`: все пять способов закрытия должны сходиться на сохранении отметки и одном закрытии, а повторный запуск сбрасывать шаг, не удаляя отметку. Сохранить modal/focus-trap, семантические title/description, явно доступное имя крестика и возврат фокуса на кнопку шапки как при ручном, так и при автоматическом открытии. Ограничение ширины и вертикальная прокрутка остаются локальными для этого диалога; не менять общий primitive ради одной справки без доказанной необходимости.

Текущий второй шаг дословно называет песочницу, хотя её маршрут пока показывает заглушку и может быть скрыт по правам. Сохраняем одинаковый текст аналитики; он указывает расположение разделов и не расширяет их функции или доступ. Если требуется иная редакция, её нужно согласовать отдельно, а не менять текст молча.

### 4. Проверять логику и UI раздельно

Расширить существующие unit/hook-проверки: отсутствие/наличие отметки, запись и повторное открытие, новая версия, повторная проверка при переходе после удаления сохранённого ключа, а также ошибки чтения и записи с подавлением автоповтора в текущем сеансе. Проверять штатные и граничные случаи без подмены пользовательских сценариев проверкой одного implementation detail.

Фокус, Escape, крестик, фон, доступность всех шагов и прокрутку невозможно доказать одним hook-тестом. Для них предусмотреть интерактивную проверку через Playwright MCP в локальном приложении с моками, включая клавиатуру, низкий viewport и отказ storage, **после отдельного явного разрешения пользователя на browser-проверку**. При отсутствии разрешения, приложения или MCP зафиксировать конкретный blocker и непроверенные сценарии, не утверждать успешную приёмку. Это не разрешение на автоматические E2E, внешний стенд или операции с внешними данными; локальные моки не доказывают реальную интеграцию.

## Risks / Trade-offs

- [Временная отметка в памяти подавляет автопоказ после успешной записи и последующего удаления ключа] → различать недоступный storage и удаление ранее сохранённой отметки; проверять оба пути на переходе между разделами.
- [После ошибки записи чтение остаётся доступным, но ключ отсутствует] → для такого случая сохранять fallback текущей оболочки, а не повторно показывать справку на каждом переходе.
- [Примитив диалога есть, но фактические focus-trap, overlay и прокрутка не доказаны] → отдельные сценарии локальной интерактивной проверки при разрешении; до неё фиксировать ограничение.
- [Текст про песочницу может создать ожидания готовой функции] → сохранить согласованный текст без выдачи новых прав или имитации работающей песочницы; содержательные изменения вынести на отдельное согласование.

## Migration Plan

Сохранить существующий ключ и контент; пользователи с отметкой `"1"` не получают повторный автопоказ из-за выпуска этого изменения. При откате вернуть только изменения справки, не удаляя localStorage, пользовательские данные или настройки сессии. Синхронизация delta в основную спецификацию и проверка развёрнутого приложения выполняются отдельными согласованными действиями.
