## Context

Мотивация и границы — в [proposal.md](proposal.md), наблюдаемое поведение — в [feedback-export/spec.md](specs/feedback-export/spec.md). Реестр, редактор, применённый поиск и metadata уже реализованы в `app/optional/feedback/`. Отдельных CSV-клиентов и UI экспорта в модуле пока нет. Обе операции присутствуют в generated API; общий binary transport, session protection и UI-компонент результата уже существуют.

### Sources and precedence

- [MOS-1260](https://task.mos-team.ru/browse/MOS-1260) определяет пользовательский сценарий, включая окна настройки и результата.
- `docs/api/contracts/openapi.json` и `managed-resources.openapi.json` определяют DTO и binary `text/csv`; обе операции и request-схемы сверены между aggregate и split. `app/shared/api/schema.d.ts` — generated-представление, не самостоятельный источник.
- `docs/api/contracts/crud-api.md`, §10, дополняет OpenAPI: весь отбор, сохранённая карточка, BOM, `;`, Content-Disposition, лимит и ошибки. Происхождение снимков описано в `docs/api/contracts/README.md`.
- [Аналитика «Обратная связь»](https://wiki.mos-team.ru/spaces/KR/pages/247734813) описывает более широкий прототип. Выбор вложенных разделов и ответы пользователей из него не переносятся в эту поставку.

Локальный контракт не публикует отдельного счётчика записей экспорта. Оговорка в `managed-resources.md` о неопределённом success content устарела относительно текущего OpenAPI: успешный ответ обеих операций явно CSV binary. Эта ревизия не редактирует контрактные документы и не подтверждает доступность API на стенде.

## Goals / Non-Goals

**Goals:** встроить экспорт в существующий feedback owner, переиспользовать transport/session и UI kit, получить достоверный результат из фактически полученного файла без его пересборки.

**Non-Goals:** перенос раздела в entities/features, универсальный движок managed resources, новый backend API, изменения auth-модели, исполнение правил опросника, реализация соседних редакторов или экспорт вложенных сущностей. Полная приёмка остальных задач MOS-1246 не становится условием закрытия этой подзадачи.

## Decisions

### Ownership and integration

API-клиенты, runtime-проверки, типы, модель экспорта, UI и тесты остаются в `app/optional/feedback/`. Реестр передаёт применённый search из существующей модели; карточка — сохранённый ID, сохранённый код и признак dirty. Экспорт не читает редактируемые поля как источник серверной записи и не сохраняет draft автоматически.

Использовать существующие shared transport/session, UI и публичные API entities. Внешняя композиция обращается к feedback через его публичный index; optional-модули не импортируют друг друга. Примеры экспорта соседних разделов служат ориентирами, но не источником private imports. Декларации и компоненты размещаются по соглашениям владельца. Альтернатива со старым `entities/feedback` и отдельными features отвергнута: она противоречит текущей обособленной архитектуре и требует ненужного переноса раздела.

### Requests and metadata

Два клиента используют существующий binary transport:

- список: POST `/feedback/surveys/export`, тело `{ fields, search }`;
- карточка: POST `/feedback/surveys/{id}/export`, тело `{ fields }`.

Префикс managed-resources берётся из существующей конфигурации клиента. Проверять UUID и поля на границе. Поля/подписи берутся из `metadata.surveys.export_fields`; текущий DTO допускает name/code/type_code/audience_type/status, от 1 до 100 полей. Уникальность проверяется дополнительно: текстовый контракт требует её, хотя OpenAPI не публикует uniqueItems. Пустой export_fields означает недоступность экспорта, а не разрешение подставить фиксированный набор.

Для списка фиксировать снимок применённого search в момент отправки, включая сортировку и conditions; не включать черновик условий. limit/offset не нужны для экспорта и исключаются из тела: контракт допускает их, но не ограничивает ими файл. Нельзя строить CSV из загруженной страницы или блокировать экспорт по потенциально устаревшему total. Лимит из metadata (default 10000) объясняется в UI, окончательное решение о превышении принимает backend через EXPORT_LIMIT_EXCEEDED.

### Settings and result interactions

Использовать существующие диалоговые примитивы и shared UI результата там, где их API покрывает спецификацию, не вводить собственную модальную инфраструктуру. По дополнительному запросу пользователя порядок выбранных колонок меняется нативным drag-and-drop за ручку. Кнопки выше/ниже сохраняются как доступная альтернатива для клавиатуры и сенсорного экрана; новая зависимость не нужна. Drop принимает только локально начатое перетаскивание выбранного поля на выбранное поле; внешние, отменённые, self-drop и pending не изменяют порядок.

Модель различает закрытое окно, настройку, pending и результат. Одновременно активно одно окно. Ошибка возвращает возможность явного повтора в настройке без потери полей. «Вернуться к параметрам» закрывает результат и открывает настройку без запроса. Повторные нажатия не создают дублей запросов или окон.

Последний выбор и порядок сохраняются на время текущей сессии в памяти владельца, а не в постоянном storage. Смена пользователя очищает выбор и результат; техническое обновление той же подтверждённой сессии не должно произвольно терять настройки. Перед отправкой выбор сверяется с актуальной metadata; исчезнувшее поле не отправляется молча как валидное. При закрытии pending отменить запрос и исключить публикацию позднего ответа. Esc, кнопки и клик вне используют единый путь закрытия; фокус возвращается к исходной кнопке «Экспорт».

Результат карточки показывает сохранённый код либо ID, а не code из dirty draft. Предупреждение о сохранённых данных присутствует в настройке и результате dirty карточки. Новая карточка без ID не предлагает работающий экспорт.

### File validation and exact record count

Сохранять исходные байты полученного файла. Проверить Content-Type CSV UTF-8, безопасное CSV-имя из Content-Disposition, UTF-8 BOM и содержимое; JSON/HTML, пустой или синтаксически повреждённый CSV не скачивать. Корректный файл только с заголовками не считать пустым ответом.

`app/shared/api/read-csv-file.ts` нельзя использовать напрямую: он требует Content-Length, Cache-Control и X-Content-Type-Options, которых feedback-контракт не гарантирует. Не ослаблять этот reader для существующих потребителей. Использовать общий binary transport и существующий разбор имени, а проверку feedback CSV держать у владельца до появления доказанной потребности в общей абстракции.

Декодирование разрешено для проверки и подсчёта записей; пересериализация запрещена. Счётчик — число логических CSV-записей после заголовка, не число физических строк. Разбор учитывает разделитель `;`, кавычки, удвоенные кавычки, переносы внутри значений, CRLF/LF и завершающий перевод строки. Проверять завершённость quoted-полей и согласованность количества ячеек с заголовком/выбранными колонками. Ошибку декодирования UTF-8 не маскировать replacement-символами. Не нужны объекты для всех строк: достаточно проверить структуру и посчитать записи за линейный проход. Перед реализацией использовать подходящий уже установленный CSV API, если он есть; новая зависимость требует отдельного обоснования, универсальный CSV-фреймворк не нужен.

Альтернативы: total реестра неверен при изменении данных между поиском и экспортом; повторный search тоже не обеспечивает один снимок; новый response header требует изменения backend, которого нет в scope. Подсчёт полученного CSV даёт точное количество именно скачиваемых записей. Для header-only результат равен 0. CSV escaping, справочные display_name и защита формул остаются ответственностью backend; frontend не меняет ячейки.

### Cancellation, errors and download

Существующие apiBinaryRequest, ApiError и owner/generation-механизмы сохраняются. Проверить отмену и принадлежность ответа после асинхронного чтения, перед скачиванием и перед публикацией результата. Запросы не повторять автоматически; при смене карточки/размонтировании отменить незавершённую операцию. Старый результат не должен появиться в другом контексте.

Ошибки 403/404/422/5xx, сеть, неверный файл или имя показываются отдельно от успеха. EXPORT_LIMIT_EXCEEDED предлагает уточнить отбор. Отмена и смена пользователя не дают файла или окна результата. Object URL освобождается по завершении использования; скачивание и показ результата выполняются только после всех проверок. Сообщение подтверждает получение файла и запуск скачивания, но не сохранение на диск, которое браузер не подтверждает приложению.

### Permission agreement boundary

Новая UI-политика read + export не утверждена: это явный пункт согласования из proposal, а не незначительная техническая неизвестность. Действующие specs feedback исключают новые mappings; Jira требует read + export, §1 CRUD публикует отдельный export, §10.2 противоречиво приравнивает права к чтению. Ни отсутствие описания прав в аналитике, ни эта неоднозначность не разрешают обход существующих ограничений.

Сохранить текущую защиту и обработку серверного 403. Не добавлять mappings или новую auth-модель в рамках этого решения. Полная приёмка критерия Jira о UI-правах остаётся заблокированной до отдельного согласования и отражения решения в плановых артефактах; прежнее утверждение design о готовой матрице прав отменяется.

### Verification

Unit-тесты проверяют DTO, CSV-разбор/счётчик и неизменность байтов; component/mock HTTP — окна, applied search, dirty/new карточку, pending, ошибки и session isolation. Существенные границы: отбор больше страницы; header-only; quoted-переносы, `;` и `""`; повреждённый CSV; JSON/HTML; некорректное имя; 403/404/422/5xx; отмена во время чтения; смена owner перед скачиванием.

Планировать интерактивную проверку этих UI-сценариев на локальных моках через Playwright MCP, включая клавиатуру, узкую компоновку и возврат фокуса. По проектным ограничениям получить отдельное явное разрешение перед browser-проверкой; при отсутствии разрешения/инструмента/приложения оставить проверку невыполненной с причиной. Автоматизированные E2E не создавать и не запускать без отдельного разрешения. Моки остаются в Express без credentials и role enforcement, production их не содержит. Проверки с внешними данными согласуются отдельно; моки не доказывают реальную интеграцию.

## Risks / Trade-offs

- [Данные меняются после поиска] → считать полученные CSV-записи, не обещать снимок ранее отображённой таблицы.
- [CSV допускает переносы и кавычки внутри значений] → тестировать логические записи и malformed input, сохранять исходные байты.
- [Нет опубликованной длины/контрольной суммы] → проверка структуры не доказывает отсутствие обрыва ровно на границе корректной записи; не обещать такую гарантию и не придумывать обязательные headers.
- [Лимит записей не задаёт лимит байтов] → избегать хранения разобранных объектов всех строк; учитывать память для исходных байтов и декодированного текста, не вводить произвольный новый пользовательский лимит.
- [Формальная OpenAPI 422 отличается от бизнес-envelope] → сохранять реальные status/code/message/errors общим transport, проверить фактический ответ при согласованной интеграционной приёмке.
- [Требование UI permissions не согласовано] → не объявлять полную готовность Jira-критериев и не вводить скрытую новую policy.
- [Источники изменяются] → новая версия контракта требует отдельной сверки; не расширять scope автоматически вслед за прототипом.

## Migration Plan

Реализовать экспорт внутри существующего раздела без backend migration и переноса данных. Сначала выполнить локальные проверки, затем отдельно согласованные проверки реальных CSV, ошибок, лимита и доступности Content-Disposition через CORS. Для полного закрытия Jira согласовать UI-права. Rollback — предыдущий frontend bundle без удаления серверных данных. Задачи соседних возможностей не закрываются этой поставкой.
