# Design

## Context

Мотивация и границы продукта описаны в proposal.md. Текущая архитектура — FSD, React Router, React Query, общий HTTP client с распаковкой `data` и Zod-валидацией. `getSurfaceRegistry` уже отправляет контрактные параметры, принимает `items` и использует `total_items`. URL хранит `query/status/type/sort/page`, размер страницы фиксирован на 10; offset вычисляется из страницы. Переподключать эту цепочку с нуля не требуется.

Найденные пробелы: обязательный объект stats в валидаторе и прямой доступ к нему в таблице; отсутствие detail-маршрута и ссылок; отсутствие ограничения самой страницы регистрации; один текст для разных пустых выдач. Существуют тесты пагинации, поиска, сортировки и части ролевых сценариев, но нет полного покрытия критериев MOS-910.

В рабочем дереве уже есть чужие незакоммиченные изменения реестра: проверка ролей кнопки, исправление aria-sort и соответствующие тесты. Они являются исходным состоянием для продолжения и должны быть сохранены.

## Goals / Non-Goals

**Goals:** локализовать совместимость с API в сущности surface, сохранить URL-контракт, переиспользовать transport и запрос текущего пользователя; закрыть критерии приёмки без переписывания существующих features.

**Non-Goals:** новые библиотеки, новый auth-протокол, ручное редактирование сгенерированных типов, скрытая клиентская фильтрация по ролям, полная карточка с операциями изменения состояния.

## Decisions

### 1. Сохранить существующий запрос и URL

Оставить `getSurfaceRegistry`, React Query key с параметрами запроса, AbortSignal и существующие функции URL. Основным форматом ответа считать `data.items`; общий клиент уже снимает envelope, поэтому повторная распаковка не нужна. `data.surfaces` не поддерживать без подтверждения бэкенда: автоматическая поддержка двух форматов скрывает расхождение. `sort` остаётся значением OpenAPI (`-updated_at`, а не `updated:desc`). Размер страницы 10 допустим при API default 20, поскольку передаётся явно.

Счётчик и число страниц рассчитывать по серверному total и limit. Сохранить существующее явное восстановление при выходе за пределы страниц. Не переносить локальный поиск и скрытие draft из демонстрационного прототипа: клиент не знает всей доступной выборки.

### 2. Изолировать nullable stats без изменения исходного OpenAPI

В модели surface ввести явное расширение сгенерированного типа через `Omit<..., 'stats'>` и поле `stats: ContractStats | null`. Валидатор разрешает null, отображение использует безопасный доступ; 0 не преобразуется в отсутствие данных. Проверить потребителей Surface, включая проверку дубликатов доменов и тестовые сортировщики.

Альтернативы: менять опубликованный OpenAPI или вручную править `schema.d.ts`. До ответа бэкенда обе неприемлемы: первая выдаёт предположение за контракт, вторая ломает генерацию. После получения обновлённого контракта регенерировать типы и убрать ненужное расширение. Отсутствующее поле stats не разрешать автоматически: это отдельное неподтверждённое поведение.

Мок, проверяемый строгим OpenAPI, сохраняет контрактную форму объекта. `stats: null` проверять отдельным совместимостным ответом в тестах клиента/UI или E2E-перехватом, не ослабляя общую валидацию моков.

### 3. Навигация с минимальным detail-маршрутом

Добавить обычный Link для имени и переход по свободной области строки. Не перехватывать стандартные модификаторы и события вложенной ссылки; клавиатурная навигация обеспечивается ссылкой. Добавить `/surfaces/:surfaceId` в application-routes по образцу skill details. Detail API и query разместить в entities/surface, отображение — в отдельном widget, page оставить тонкой.

Маршрут читает данные по UUID из URL, не зависит от наличия списка в кэше, показывает название, тип, статус, домены и владельца. Обработать загрузку, повтор сетевой ошибки, 403/404. Полный редактор и действия прототипа исключены. Если к моменту применения появится готовый detail widget, интегрировать его вместо второго. Ссылка на несуществующий маршрут не считается выполнением критерия приёмки.

### 4. Общая политика создания

Вынести проверку `client_service`/`surface_owner` в переиспользуемую модель доступа без зависимости entity surface от entity user. Виджет и страница регистрации используют одну проверку, получая roles из существующего principal query. Guard располагается перед монтированием формы, чтобы запрещённый прямой вход не запускал связанные запросы формы. Пока principal загружается, показывать загрузку; при ошибке — повтор; при отсутствии роли — отказ в доступе. Сама политика UI не заменяет серверную авторизацию.

Альтернатива — только скрыть кнопку — оставляет прямой путь к форме и не покрывает критерий задачи. Самостоятельно сопоставлять все демонстрационные роли прототипа с API не требуется: для создания сохраняется уже используемое в проекте правило, отмеченное как предположение.

### 5. Отображение и состояния

Заголовок «Диалогов» сопровождается доступным пояснением «За последние 30 дней». Русские справочники уже соответствуют прототипу; сохраняем `review` как API-значение. Подсветка совпадений не обязательна для приёмки MOS-910 и не включена в задачи.

Пустую выдачу определять только после успешного ответа. Разделить отсутствие поверхностей и отсутствие совпадений по наличию query/status/type; сортировка сама по себе не делает выдачу поисковой. Ошибка с повтором не должна одновременно выглядеть как успешный пустой результат. Сохранить URL при повторе и браузерном возврате из карточки.

### 6. Уточнения и интеграционная проверка

Пользователь разрешил уточнять вопросы по ходу разработки. Единственный журнал для передачи бэкенду — `docs/MOS-910-backend-questions.txt`: сохранять вопрос, источник расхождения, рабочее предположение и полученный ответ. Не заменять его перечнем фронтенд-задач.

Продолжать локальную реализацию на текущих предположениях без ожидания всех ответов. При подтверждённом изменении формата или ролей согласованно обновить контракт, адаптер, эту спецификацию и тесты; не объявлять предположения подтверждёнными. Проверка на реальном контуре требует URL, способа авторизации и тестовых данных; отсутствие доступа фиксируется отдельно от результатов мок-тестов. Разработка SSO в эту задачу не входит.

## Risks / Trade-offs

- [Фактический API отличается от документации] → явные предположения, журнал вопросов, финальная проверка на доступном контуре.
- [Расширение Surface влияет на регистрацию] → проверить обход всех страниц и поиск дубликатов доменов после nullable-изменения.
- [Карточка разрастается в отдельный проект] → только чтение идентифицирующих полей и состояния загрузки; без редактора и lifecycle-операций.
- [Ролевая матрица не подтверждена] → одна заменяемая политика, сервер остаётся источником решения о доступе.
- [Потеря существующих правок] → учитывать текущий diff при применении, не откатывать изменения реестра и тестов.

## Migration Plan

Изменений хранилища нет. Сохранить существующие URL и параметры окружения. Проверить клиент/UI и целевой E2E, затем typecheck, lint, format:check, api:check, тесты и build. Проверить реальный GET при наличии предоставленного доступа; зафиксировать ограничения, если его нет. Откат — возврат только изменений MOS-910 без удаления ранее существовавших правок. Никаких deploy или изменений удалённого сервиса в рамках планирования.

## Open Questions

Где доступен тестовый контур и как подключить существующую сессию; какие тестовые записи доступны для проверки отсутствующей статистики и ролей. Эти сведения влияют на проведение внешней проверки, но не блокируют выбранную реализацию. Расхождения items/stats/ролей уже разрешены рабочими предположениями выше и отслеживаются в отдельном текстовом файле.
