## Why

Раздел «Навыки» уже использует бизнес-HTTP, но его композиция расходится с предоставленным прототипом, а домены и регистрация остаются заглушками. Нужен единый план реализации MOS-907, MOS-929, MOS-933, MOS-935, MOS-942 и видимой части MOS-909, который обеспечивает визуальное сходство без повторной разработки готовой основы и без вымышленных серверных состояний.

## What Changes

- Зафиксировать визуальный эталон по `/home/user/Загрузки/Прототип. Центр управления.html`: плотность, типографику, карточки, таблицы, формы, состояния и допустимые контрактные отличия. Включить визуальную приёмку в каждый экран, а не оставлять её финальной косметической задачей.
- MOS-907: убрать устаревшее сообщение о просмотре, доработать шапку, действия, справку и пустые состояния; сохранить существующие URL-вкладки. Ревью подключать из MOS-1020, не реализовывать повторно. До подключения API сохранять вкладку с видимым пояснением рядом, без фиктивного счётчика и решений.
- MOS-929/MOS-933: привести таблицу и фильтры к прототипу, сохранить серверную пагинацию и поиск; до расширения API убрать колонки статуса/готовности/числа диалогов, статусный фильтр и предупреждения вместе с заглушками их недоступности. Возвращать их только после согласования и подключения API; отсутствие расширения не блокирует поставку поддерживаемого каталога.
- MOS-935: реализовать реестр, создание и редактирование предметных доменов через существующие GET/POST/PATCH, включая `skills_count`, выбор команды, зоны и конкурентную версию. Дополнительные неопубликованные ограничения доменов отложены; текущий CRUD использует опубликованную валидацию и обработку серверных ошибок без обещаний уникальности.
- MOS-942: заменить `/skills/new` четырёхшаговым мастером; переиспользовать логику фраз и подключения, собрать обязательные команду и контакт из её участников через опубликованный members API, реализовать согласованный неатомарный сценарий POST анкеты → GET карточки/версии → PUT фраз. При подтверждённом создании и ошибке следующего шага сохранять ID и повторять только незавершённую операцию без второго POST. По уточнённому решению пользователя POST отправляется один раз с защитой от повторного нажатия. При потерянном ответе сохраняется ввод и показывается «Результат неизвестен» без автоматического или ручного повтора создания в этой попытке. Backend-гарантия безопасного повтора больше не является условием включения сохранения; отсутствие дублей при новом самостоятельном создании после неизвестного исхода не гарантируется.
- MOS-909: после согласования lifecycle API показать серверные этапы и подключить одиночные команды отправки/выката. До этого скрыть шкалу, блок и заглушку lifecycle, неподдерживаемые команды обучения/проверки/выката, а в мастере — серверный черновик и отправку на проверку без disabled-кнопок. Создание анкеты остаётся отдельным сценарием G4. Lifecycle отложен и не блокирует поддерживаемую часть UI.
- Разделить 20 пакетов работ на доступные сейчас, требующие контрактного решения и зависящие от профильных changes. Полная интеграционная и визуальная готовность не следует из существования planning artifacts.

## Capabilities

### New Capabilities

- `skill-catalog-experience`: визуальная согласованность раздела, композиция каталога, фильтры, предупреждения и состояния с правдивыми источниками данных.
- `skill-domain-management`: серверный реестр доменов и безопасные формы создания/редактирования.
- `skill-registration`: четырёхшаговая регистрация, обязательные связи, группы фраз, итоговая проверка и восстановление после частичного сохранения.
- `skill-lifecycle`: серверная шкала этапов и одиночные переходы навыка после согласования API.

### Modified Capabilities

- `control-center-shell`: снять обязательность заглушек для доменов и создания навыка, сохранив маршрутизацию и остальные точки входа; совместить это с условным подключением ревью из MOS-1020.
- `control-center-api-integration`: актуализировать требование правдивого отображения: intents уже поддерживаются, дополнительные поля разрешены только по согласованным контрактам; отсутствие данных и ноль остаются разными состояниями.

## Impact

- Доработки `app/pages/skills`, `app/pages/skill-creation`, `app/widgets/skills-registry`, `app/widgets/skill-details`, `app/features/skill-registry-filter`, `app/entities/skill` и существующего HTTP/Query слоя; новые владельцы доменного CRUD и мастера в FSD. Точечная корректировка `app/app.css`/существующих UI-примитивов с проверкой других потребителей.
- Источник wire-схем: `docs/api/contracts/skills-domains.openapi.json`, объединённый `openapi.json`, generated `app/shared/api/schema.d.ts`. Справочник команд существует; источником контактов согласованы участники выбранной команды по опубликованному members API. Расширенный список и lifecycle отложены до расширения API; G4 уточнён: сохранение разрешено без backend-гарантии replay, с однократным POST и запретом повтора при неизвестном исходе. Новые endpoints, enum и ошибки не предполагаются.
- Используются установленные React Router, TanStack Query, React Hook Form/Zod, shared/ui и существующие тестовые средства; новые зависимости не требуются.
- MOS-1018/1019/1020/1021/1022/1023/1025/1026/1027/1030 сохраняют владение конфликтами, проверками, ревью, массовым выкатом, настройками подключения, токенами, мониторингом, инцидентами, глобальным отключением и аналитикой. Этот change задаёт точки композиции, а не дублирует их реализацию. По решению G6 блоки проверок конфликтов, готовности и мониторинга в карточке/мастере сохраняются с видимым пояснением рядом о неподключённом API или невыполненной проверке; рабочие редакторы и локальная валидация сохраняются. Это не возвращает скрытые элементы каталога G1 и lifecycle G5.
- Существующие changes и пользовательские изменения кода не меняются при подготовке плана. При последующей синхронизации потребуется объединить пересекающиеся delta-требования shell с MOS-1020, не восстановив старые заглушки.
- Приёмка логики — unit/component и необходимые server-тесты. Браузерная визуальная проверка требует отдельного разрешения; до неё визуальное совпадение отмечается непроверенным. Демороли и фиктивные пользователи из HTML не переносятся.
