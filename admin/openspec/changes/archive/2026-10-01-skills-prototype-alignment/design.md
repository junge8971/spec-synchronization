## Goals / Non-Goals

**Goals:** один серверный источник состояния; визуальный эталон до вёрстки; последовательные формы без потери ввода; независимая поставка доступных работ при явных API-gates; проверяемая трассировка 20 пакетов работ к шести Jira-задачам.

**Non-Goals:** копирование bundle, редизайн всего приложения, замена установленных библиотек, собственный workflow engine, runtime-фикстуры, локальное обучение/семантический поиск, атомарность нескольких HTTP-запросов, долговременное хранение мастера, реализация профильных changes вместо их владельцев. Ролевой demo-контекст не служит источником team/contact и не переносится.

### 2. Сохранить существующий поток данных и FSD

- Страницы собирают widgets/features; route-модули остаются адаптерами существующего Framework SPA. URL-состояние — React Router/useSectionTab/существующие helpers, серверное состояние — установленный TanStack Query и apiRequest. Нет второй системы загрузки через ad hoc effects.
- Доменный CRUD получает владельца `entities/skill-domain` (не `entities/surface`), формы — `features/skill-domain-editing`, реестр — `widgets/skill-domains-registry`. Существующие domain options навыков сверять с новым владельцем через композицию верхнего слоя/общую техническую инвалидизацию, без импорта entity-слайса из соседнего entity.
- Мастер — `features/skill-registration`, собранный страницей создания. Draft принадлежит одной форме RHF, шаги — приватные компоненты, а не глобальное хранилище или набор самостоятельных маршрутов. Dirty-навигация использует useBlocker и штатное предупреждение закрытия документа; после успешного сохранения блокировка снимается.
- UI существующей `SkillTrainingPhrases` привязан к сохранённой карточке и публично экспортирует только этот компонент. Не импортировать её внутренности из новой feature. Повторно используемые чистые схемы/преобразования фраз и подключения поднимать к `entities/skill` через публичный API, если они действительно нужны двум потребителям. Редактируемую draft-часть можно переиспользовать на нижнем слое без переноса HTTP-оркестрации; не делать универсальный form framework.
- Именованные types/constants/handlers размещать у владельца; не менять generated schema вручную. Новые зависимости и FSD-исключения не нужны.

### 4. Реестр и формы доменов

Переиспользовать текущие фильтры и сброс page, limit/offset и AbortSignal. Имена query-параметров сохранять текущие (`query`, `domain_id`, `team_id`); не копировать q/domain из HTML. Подпись поиска до решения G1 — нейтральная «Поиск навыков» без обещания конкретных полей. Статусный фильтр и пояснение его недоступности отсутствуют до согласования и подключения API; фильтр команды сохраняется.

Реестр доменов запрашивает страницы, а не все навыки для подсчёта. Ссылка skills_count ведёт на первую страницу `/skills?domain_id=<id>` без tab=domains и без случайного старого фильтра команды. Формы используют Domain detail, POST/PATCH; после успешной записи инвалидировать реестр доменов, его options и затронутые данные навыков. Ошибка refetch после подтверждённой записи не является поводом повторно отправлять мутацию.

По решению пользователя G1 до расширения API из каталога убираются колонки статуса, готовности и числа диалогов, статусный фильтр и предупреждения, включая заглушки «Нет данных API» и пояснения недоступности. Сохраняются навык/назначение/ID/версия, домен/команда, даты, переход в карточку, поиск, domain/team-фильтры и серверная пагинация. Неподдерживаемый sort в URL по-прежнему нормализуется к поддерживаемому. Отсутствие блока предупреждений не означает «Проблем нет»; после подключения источника его ошибка должна отображаться отдельно от отсутствия контракта. G1 остаётся условием будущего расширения, но не блокирует текущий сокращённый каталог. Решение G1 не определяет поведение карточки и мастера. Решения G2–G6 приведены ниже. Отвергнута загрузка карточки на каждую строку и локальный расчёт total/metrics. Выделение строк и массовая панель принадлежат MOS-1021.

**Решение пользователя по G2:** дополнительные ограничения доменов (нормализация, уникальность имени/API-адреса и неопубликованные правила) отложены до отдельного согласования. Они не блокируют текущую поставку CRUD. Сохраняются опубликованная валидация, обработка `422 HTTPValidationError` через `loc`/`msg`, сохранение ввода при любом отказе, `expected_version`, ключи идемпотентности и запрет автоматической перезаписи. Не добавляются demo-ограничения, клиентская гарантия уникальности или preflight. Специальные backend-коды конфликтов не выводятся из mock: до опубликованного контракта сохраняется безопасная общая обработка отказа. Отложенная задача 10.3 не отмечается выполненной.

### 5. Мастер и восстановление частичной записи

**Решение пользователя по G3:** допустимые контакты — участники выбранной команды. Источник: `GET /api/control/api/teams/v1/teams/{team_id}/members` в `docs/api/contracts/openapi.json` и `teams.openapi.json`, параметры пагинации `limit`/`offset` (limit до 100). `contact_user_id` берётся из `TeamMemberResponse.id`, подпись — имя и email. Дополнительный отбор по `roles`/`membership_role` не вводится; auth/session/RBAC не добавляются. Выбор явный, без первого участника по умолчанию, с доступностью участников за первой страницей. При смене команды контакт сбрасывается; запросы и кэш привязаны к team_id, запоздалый ответ старой команды не подменяет новые варианты. Loading/empty/error различаются, при ошибке доступен повтор; остальной draft сохраняется. Исчезновение участника из подтверждённого актуального состава требует нового выбора, но отсутствие на одной странице не считается доказательством удаления. В сводке показывается выбранный контакт, а не сообщение о несогласованном источнике. G3 как решение снят, выбор контакта 13.2 и сводка 15.2 реализованы и проверены component/client-тестами; отправка ожидает реализации уточнённого G4, а не подтверждения backend replay.

**Решение пользователя по G4:** принят неатомарный порядок POST анкеты → GET карточки и актуальной версии → PUT фраз. При подтверждённом POST ID и draft сохраняются; ошибка GET или PUT показывает частичный результат и позволяет повторить только незавершённый шаг. Подтверждённый POST не повторяется, общий успех не объявляется до подтверждения необходимых записей.

**Уточнение G4, подтверждённое пользователем:** backend-гарантия replay больше не блокирует включение сохранения. POST отправляется один раз за попытку, с контрактным Idempotency-Key, блокировкой повторных нажатий и без автоматического retry. При потере ответа либо невозможности достоверно определить исход сохраняется draft; UI показывает «Результат неизвестен» и сообщает, что навык мог быть создан. Автоматический и ручной повтор создания в этой попытке запрещены независимо от ключа. Можно перейти в реестр для проверки, но UI не угадывает созданный ID по имени или другим признакам.

Гарантированного восстановления неизвестного исхода нет. Новое самостоятельное создание после ухода/перезагрузки может создать дубль — это принятый риск, о котором UI предупреждает. Долговременное хранение попытки не добавляется. Наличие Idempotency-Key не доказывает гарантий backend. При подтверждённом ID продолжается GET → PUT, повторяется только незавершённая операция. Неполный серверный черновик и отправка на проверку решением не разрешены.

Согласованный поток (production-включение после реализации уточнённого сценария и его component/client-проверок):

```text
Draft --> POST skill --confirmed ID--> GET detail/version --> PUT intents --> Detail
              |                            |                    |
              v                            v                    v
        Unknown outcome               Read error           Save error/conflict
        no POST retry                 retry GET            preserve ID + phrases
```

- POST возвращает EntityCreatedResponse с ID, не полную карточку; поэтому версию для PUT нельзя угадывать как 1.
- `zones` — массив рабочих зон. `connection.auth_required` — отдельное требование подключения. При отсутствии connection передавать разрешённое отсутствие; при заданном connection использовать явное значение auth_required, не брать его из zones. Базовый шаг endpoint не дублирует полный редактор параметров MOS-1022.
- После подтверждённого POST фиксировать созданный ID и не позволять повторному нажатию создать новый объект. При ошибке GET повторять GET; при ошибке PUT сохранять фразы и повторять PUT с правилами версии/ключа. Не откатывать создание удалением: такого согласованного метода нет.
- Изменённая анкета после создания не превращается во второй POST: уже созданные поля редактируются в существующей карточке. В мастере восстановления пользователь видит сохранённую анкету, несохранённые группы и ссылку на карточку. Уход предупреждает о потере несохранённых групп.
- При конфликте PUT не менять expected_version автоматически. Потребовать явное сопоставление с новой серверной версией; до него сохранять draft. Пока исход POST неизвестен, не предоставлять повтор создания в текущей попытке, в том числе с изменённым телом или новым ключом.
- Полное восстановление локального draft/ключей после закрытия браузера не обещается. Предупреждение об уходе и серверная карточка дают путь продолжения после подтверждённого ID; долговременный draft потребует отдельного требования. Это не серверный неполный черновик из демо.

Альтернатива атомарного create с intents предпочтительна только если появится согласованный контракт; сейчас такого поля нет. Локальный «успех» или помещение intents в PATCH анкеты отвергнуты.

**Решение пользователя по G5:** до согласования и подключения API скрыть самостоятельный блок lifecycle и его заглушку, шкалу этапов и неподдерживаемые команды обучения, отправки на проверку и выката; disabled-кнопки вместо них не оставлять. В мастере также скрыть «Сохранить черновик» для неполных серверных данных и «Отправить на проверку» вместе с пояснениями их недоступности. Сохранить локальный draft/dirty-guard, анкету, фразы и подключение. Создание полной анкеты по уточнённому G4 остаётся отдельным сценарием без ожидания backend-гарантии replay: отсрочка lifecycle не должна его блокировать после выполнения G4. Пакеты 17, 18.2 и 19 отложены до расширения API, не считаются реализованными. Вкладка ревью, блоки проверок/готовности/мониторинга и сообщение о непроверенных пересечениях остаются видимыми с пояснением рядом по отдельному решению G6, без фиктивной очереди. После подключения API неизвестное состояние или ошибка чтения не должны молча скрываться как отсутствие контракта.

**Решение пользователя по G6:** не скрывать вкладку ревью и блоки проверки конфликтов, готовности и мониторинга в карточке/мастере. Сохранять короткий видимый комментарий рядом с соответствующим заголовком, полем или действием: например, «API ревью ещё не подключён», «Данные готовности недоступны: API ещё не подключён», «Пересечения не проверены: API проверки ещё не подключён». Это пользовательское пояснение в UI, не комментарий исходного кода и не только tooltip. Пояснение доступно с клавиатуры/скринридером и переносится без перекрытия действий на узком экране. Для ревью пояснение видно рядом с вкладкой и в её содержимом. Не показывать фиктивные очередь, счётчики, инциденты, готовность или успешные проверки; представленные неподдерживаемые команды disabled с доступно связанным пояснением, без запросов к вымышленным endpoints. Редактор фраз, его счётчики и локальная валидация остаются рабочими. После подключения согласованного источника показываются реальные данные; ошибка такого источника отличается от отсутствия интеграции. Решение G6 не отменяет скрытие колонок/фильтра/предупреждений каталога G1 и lifecycle/команд G5. Интеграция профильных источников остаётся зависимостью, но не блокирует поставку UI с пояснениями.

### 7. Проверки и критерий завершения

Каждый пакет UI имеет functional check и визуальные критерии; component snapshots сами по себе не заменяют визуальную приёмку. Расширить существующие Vitest/RTL/MemoryRouter/fetch doubles; серверные проверки переиспользуют mocks. Проверять существенный сценарий и границу: длинные данные, null/0, два предупреждения, 101-й элемент справочника, ошибка/отмена, конфликт версии, потерянный ответ и частичная запись.

Перед завершением реализации: `yarn typecheck`, `yarn lint` без предупреждений, `yarn test`, `yarn format:check`; при API-типах — `yarn api:check`, при изменениях сборки — `yarn build`. E2E/browser-файлы не менять и не запускать без отдельного разрешения. При согласованном визуальном просмотре проверить матрицу экранов/состояний и контрольные ширины. Если разрешения нет, оставить соответствующую приёмку незавершённой, а не отмечать весь change готовым.

## Risks / Trade-offs

- [API беднее прототипа] → сохранить общую схожесть каталога без неподдерживаемых элементов и не принимать отложенное расширение как завершённую интеграцию.
- [Общие токены меняют другие экраны] → минимальные правки с перечнем потребителей; проверка оболочки, поверхностей и карточки, не смена preset.
- [Контракт и демо расходятся по зонам/контакту/обязательности фраз] → контракт и существующие specs определяют сохранение; отличия включены в визуальную приёмку.
- [Неатомарная регистрация оставила объект без фраз] → сохранённый ID, раздельный результат, повтор только незавершённой операции; нет вымышленного rollback.
- [Неизвестный исход и потеря локального состояния] → предупреждение об уходе, стабильный ключ в рамках логической операции, gate восстановления; не обещать устойчивость draft после закрытия браузера.
- [Параллельные changes перезаписывают shell/spec или код] → объединение актуальных требований перед sync; пользовательские staged/untracked изменения не переписывать.
- [Нет разрешения браузера] → честно непроверенное визуальное совпадение при независимой функциональной приёмке.

## Migration Plan

1. Пакеты 1–2 фиксируют визуальную базу; 3–5, 7, 9–12 и доступные части 14–15 реализуются без lifecycle. G2 не блокирует опубликованный CRUD, но неподтверждённые правила отдельно отмечаются.
2. UI мастера собирается без фиктивных справочников; production-сохранение включается только после реализации выбора контакта 13.2 и уточнённого потока G4 с запретом повторного POST при неизвестном исходе. Протокол тестируется независимо через существующие test doubles.
3. Пакеты 6, 8 и 17–19 включаются после согласования нужных gates; профильные изменения подключаются по публичным API, а не переписываются.
4. Пакет 20 фиксирует матрицу приёмки и оставшиеся блокеры. Planning-ready не означает, что все 20 пакетов исполнимы прямо сейчас.
5. Откат UI не отменяет серверно созданные домены/навыки или выкат. Сохранять действующие detail URL и данные; запрещено компенсировать откат удалением ресурсов или возвратом runtime fixtures.
