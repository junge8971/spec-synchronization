# Spec Delta

## MODIFIED Requirements

### Requirement: Contract-backed eligible rollout

Реестр SHALL предлагать `whitelist → prod` и, по решению пользователя для MOS-1772, `approved → whitelist` через опубликованный POST status с expected_version и UUID Idempotency-Key для каждого навыка. UI MUST NOT считать `review` согласованным или автоматически принимать решение ревью. `approved` SHALL обозначать только фактически полученный статус. Эти варианты MUST NOT объявляться гарантией принятия конкретного перехода backend.

Оба действия SHALL использовать общий выбор видимых строк. Пустой выбор, наличие неподходящего для выбранного действия статуса или ошибка обновления данных SHALL блокировать перевод с пояснением. Неподходящие строки MUST NOT молча пропускаться. Если данные доступны и обработка группы не выполняется, кнопка «В белые списки» SHALL принимать нажатие для непустого выбора без навыков в `approved`. По нажатию реестр SHALL показать доступное всплывающее уведомление «Подходящих навыков нет» с описанием «В белые списки переводятся только согласованные навыки», без пояснения над таблицей для этой причины, и снять все отметки. Диалог подтверждения MUST NOT открываться, запросы на перевод MUST NOT отправляться.

Перед отправкой UI SHALL показывать имена, ID, версии и число выбранных навыков, переход и предупреждение о частичном успехе в одном подтверждении. Для выката в prod SHALL явно указываться продуктивный контур. Отмена MUST NOT отправлять запросы. Известное изменение status/version выбранных записей до отправки SHALL требовать нового подтверждения. Во время выполнения группы SHALL предотвращаться повторный запуск любого массового действия и изменение подтверждённого состава.

#### Scenario: Confirm production rollout

- **WHEN** пользователь выбирает навыки в whitelist и подтверждает выкат в продуктивный контур
- **THEN** команды используют только подтверждённые ID и версии, целью каждого перехода является prod

#### Scenario: Confirm whitelist transition

- **WHEN** пользователь выбирает два или более навыка в approved и подтверждает перевод
- **THEN** окно перечисляет их ID и версии, предупреждает о частичном результате, а каждая команда использует соответствующую версию и цель whitelist

#### Scenario: Ineligible selection

- **WHEN** выбор пуст, содержит навыки в несовместимых с выкатом в prod статусах или смешивает `approved` с другими статусами для перевода в белые списки
- **THEN** соответствующая кнопка недоступна с пояснением, отметки сохраняются, неподходящие строки не пропускаются молча и не объявляются успешно переведёнными

#### Scenario: No approved skills in the selection

- **WHEN** реестр готов, обработка группы не выполняется, пользователь отмечает один или несколько навыков вне `approved` и нажимает «В белые списки»
- **THEN** появляется уведомление с заголовком «Подходящих навыков нет» и описанием «В белые списки переводятся только согласованные навыки», все отметки снимаются и счётчик показывает 0
- **AND** окно подтверждения не открывается и POST status не отправляется

#### Scenario: Cancel or stale confirmation

- **WHEN** пользователь отменяет подтверждение либо до отправки стало известно об изменении status/version выбранного навыка
- **THEN** команды по этому подтверждению не отправляются; для изменившихся данных требуется новое подтверждение
