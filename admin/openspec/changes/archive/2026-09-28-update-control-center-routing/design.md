## Context

Мотивация и объём — в `proposal.md`. React Router работает в Framework SPA mode (`ssr: false`, `prerender: false`), basename уже задан в `react-router.config.ts`. `app/routes.ts` строит маршруты по существующему каталогу `applicationRoutes`; навигация использует тот же каталог. Крошки сейчас ищут точное совпадение пути, но любой `/skills/...` считают карточкой навыка. Это ошибочно для будущего `/skills/new`.

`SkillsPage` использует неконтролируемые Tabs с `defaultValue="registry"`; URL не управляет вкладкой. `/surfaces/new` уже содержит работающий мастер, `/skills/:skillId` — карточку и существующую загрузку имени для крошек. `/ops` сейчас представлен недоступным пунктом. Тесты меню, крошек и конфигурации проверяют старые адреса и недоступную эксплуатацию.

Источник примера — `/home/user/Загрузки/Прототип. Центр управления.html`, исследованный как исходный текст без браузера. В нём функции `Vne`, `$9`, `Rne`, `zne`, `Bne`, `BS` подтверждают маршруты, приоритет вкладки старого пути и набор вкладок. Прототип использует replace для переключения вкладок; это намеренно не переносится, поскольку согласовано восстановление вкладок через назад/вперёд. Роли, профиль и бизнес-экраны прототипа не копируются.

Текущая спецификация оболочки требует `/documentation` и недоступный `/ops`: delta-spec явно заменяет эти требования, сохраняя совместимость старого адреса.

## Goals / Non-Goals

**Goals:**

- Один каталог маршрутов и метаданных для оболочки; URL — единственный источник выбранной вкладки.
- Минимальное расширение существующих route-модулей, Tabs, меню и BreadcrumbTrail без нового роутера или универсального движка страниц.
- Сохранять working screens, доступность и существующую обработку ошибок.

**Non-Goals:**

- CRUD, формы создания навыков, содержимое команд/эксплуатации, новые карточки и API-интеграции.
- Перевод всех фильтров реестра или вкладок карточки навыка на новый механизм: согласованный контракт вкладок ограничен `/skills`, `/teams`, `/ops`. Существующие query фильтров не теряются; новые фильтры не изобретаются.
- Изменение deployment-конфигурации, модели авторизации, SSR или инфраструктуры. Новые зависимости не требуются.

## Decisions

### 1. Канонические маршруты и штатная навигация React Router

Расширить существующий каталог в `shared/config`, сохраняя route-модули тонкими адаптерами. `/metrics` и `/docs` используют существующие страницы дашборда и документации; имена файлов страниц необязательно переименовывать. Совместимые адреса регистрируются как маршруты редиректа, но не как отдельные пункты меню.

Для SPA использовать штатный `Navigate` с `replace` в тонком route-адаптере совместимости; целевой путь задаётся только локальной таблицей, не пользовательским query. `URLSearchParams` копирует query и меняет только `tab` для соответствующих старых путей. Ссылки и цели задаются без ручного добавления basename: им управляет Router. Сохранять fragment при перенаправлении как безопасное дополнение к query-совместимости. Проверить это под `/tsam-panel/` компонентным тестом.

Альтернативы: дублирование страниц на обоих адресах оставляет два основных URL; ручной `window.location` обходит маршрутизатор и делает лишнюю перезагрузку; серверные loaders не подходят текущему SPA-режиму. Не создавать общий redirect framework: достаточно таблицы и минимального адаптера для повторяющихся совместимых переходов.

### 2. Метаданные вкладок и управление через search params

Наборы вкладок и подписи, используемые одновременно страницами и крошками, принадлежат техническому сегменту `shared/config`, рядом с маршрутами, а не одному из page-слайсов. React Router `useSearchParams` управляет контролируемыми Tabs; небольшой общий hook допустим в `shared/lib`, поскольку есть три реальных потребителя. Не вводить отдельное хранилище выбранной вкладки.

Внешний ключ реестра навыков — `list` вместо локального `registry`. Неизвестное или пустое значение читается как default без обязательной автоматической перезаписи URL; при следующем выборе URL становится каноническим. При выборе default удаляется `tab`, при выборе другой вкладки — устанавливается; остальные пары query, включая повторяющиеся, сохраняются. Выбор другой вкладки использует push, редиректы — replace; повторный выбор текущей вкладки не должен засорять историю.

Альтернатива локального state с эффектами синхронизации добавляет два источника истины. Копирование `BS` из прототипа нарушает согласованное поведение истории и не валидирует неизвестную вкладку.

### 3. Точки входа вместо бизнес-реализации

Добавить минимальные страницы создания навыка, карточек поверхности/диалога, команд и эксплуатации. Общая простая презентационная заглушка допустима в `shared/ui`, если используется несколькими страницами; предметные названия, вкладки и композиция остаются у владельцев. Сообщение «Раздел в разработке» не означает найденную сущность или успешную операцию. Новые карточки не загружают данные и не различают существующие и отсутствующие ID: такая проверка принадлежит последующей реализации.

Команды имеют две вкладки, эксплуатация — три, с заглушками содержимого. Домены и ревью сохраняются как незавершённые вкладки. Реестр навыков, карточка навыка и регистрация поверхности сохраняют текущую реализацию. Не добавлять фиктивные формы, данные, permissions или API-запросы ради крошек.

Альтернатива копирования полного прототипа расширяет MOS-905 до реализации отдельных бизнес-разделов и поэтому отвергнута.

### 4. Расширение существующих крошек и навигации

Использовать штатное сопоставление маршрутов React Router, учитывающее статические и параметризованные пути, вместо `startsWith('/skills/')`. Статические экраны создания должны определяться до динамических карточек. Сохранить `BreadcrumbTrail` и существующую загрузку названия только для реальной карточки навыка.

Для новых карточек использовать статические подписи «Поверхность»/«Диалог»; для `/skills/new` — «Добавление навыка». Для вкладок не по умолчанию добавить подпись из того же набора метаданных, что использует страница. Родительская ссылка ведёт на корень раздела, без переноса `tab` дочернего экрана. Элемент «Главная» не отображается: крошки начинаются с текущего раздела. На `/` до перенаправления в навыки крошки отсутствуют.

Пункт «Команды» добавить в «Эксплуатацию» рядом с «Состоянием системы». Заголовок и крошки команд используют «Команды и доступ»; краткая подпись меню не должна случайно подменять заголовок страницы. Обновить документационное меню и все найденные внутренние ссылки, включая `surfaces-registry` и `surface-registration-form`, на `/docs`.

Полная миграция крошек на новый route-handle framework не нужна: текущую композицию можно расширить с корректным matching. Глобальный catch-all редирект из прототипа не переносится: он скрывал бы реальные ошибочные URL.

### 5. Проверки без браузера

Существующие Vitest/Testing Library и memory router покрывают таблицу редиректов, basename, query, выбор вкладок и историю через действия router. Компонентные тесты проверяют крошки и отсутствие запроса ID `new`, заглушки без fetch карточек, канонические ссылки, закрытие мобильной навигации и клавиатурную доступность вкладок.

Дополнительно `yarn typecheck` и `yarn build` проверяют конфигурацию и route typegen; `yarn lint`, `yarn test`, `yarn format:check` — остальные gates. API-контракт не меняется, `yarn api:check` не требуется. E2E/browser-тесты не создаются, не редактируются и не запускаются.

## Risks / Trade-offs

- [Перехват `/skills/new` динамической логикой крошек] → маршрутный matching и тест отсутствия запроса карточки с ID `new`.
- [Потеря фильтров или повторяющихся query] → копировать `URLSearchParams`, а не преобразовывать query в обычный объект; проверять повторяющиеся значения.
- [Различие метаданных вкладок страницы и крошек] → один набор метаданных; тестировать неизвестный tab и историю.
- [Бизнес-раздел выглядит готовым после включения ссылки] → явное сообщение о разработке, без работающих на вид действий и вымышленных данных.
- [Прямое обновление вложенного URL возвращает серверный 404] → приложение остаётся SPA; production-хост должен обслуживать `/tsam-panel/*` через index. Unit/component-тесты и сборка не подтверждают конфигурацию внешнего хоста; это явно указать при завершении реализации.
- [Старые ссылки остаются в соседних компонентах] → проверить все употребления `/dashboard` и `/documentation`; оставлять их только как входы совместимости и тестовые примеры.

## Migration Plan

Изменение поставляется одной frontend-сборкой: новые основные маршруты, редиректы и ссылки включаются одновременно. Миграция данных не нужна; внешние закладки старых адресов продолжают работать. При откате достаточно вернуть предыдущую frontend-сборку; новые адреса `/metrics`, `/docs` и новые точки входа в ней могут отсутствовать, что следует учитывать при распространении новых ссылок.
