## MODIFIED Requirements

### Requirement: Registration uses supported fields and local domain validation

Мастер SHALL сохранять четыре шага и поддержанные поля создания: название поверхности и конфигурации, тип, домены, назначение, необязательный продуктовый контекст, владельца и команду, двух ответственных по их бизнес-ID, выбранные навыки с параметрами и `submit_for_check`. Локальная нормализация доменов, проверка наличия хотя бы одного адреса и запрет дубликатов в форме SHALL сохраняться. После успешной локальной валидации действие «Далее» на первом шаге SHALL проверять занятость текущего нормализованного списка через `POST /api/control/api/surfaces/v1/surfaces/domains/check`. Переход SHALL выполняться после ответа `200` с пустым `data.occupied_domains` для актуального ввода. Мастер MUST NOT запрашивать реестр для проверки или представлять результат проверки как резервирование доменов.

При непустом `occupied_domains` мастер SHALL показать все возвращённые занятые адреса в доступном сообщении у поля и сохранить ввод на первом шаге. При сбое или некорректном ответе мастер SHALL остаться на первом шаге, показать, что занятость неизвестна, и позволить повторить проверку. Параллельные действия «Далее» MUST NOT запускать дублирующие проверки. Изменение доменов SHALL сбрасывать результат, а ответ на предыдущий ввод MUST NOT менять поля, ошибку или шаг мастера, даже если пользователь успел вернуть прежний текст.

#### Scenario: Valid details without registry access

- **WHEN** пользователь нажимает «Далее» с валидными сведениями и проверка возвращает пустой `occupied_domains`
- **THEN** открывается шаг ответственных, а проверка использует нормализованный список и не запрашивает реестр

#### Scenario: Empty domains remain invalid

- **WHEN** после нормализации список адресов пуст
- **THEN** локальная ошибка связана с полем, сетевой запрос не отправляется и следующий шаг не открывается

#### Scenario: Repeated domains remain invalid

- **WHEN** нормализованный список содержит повторы, включая адреса, отличающиеся регистром, протоколом или завершающим слешем
- **THEN** локальная ошибка связана с полем, сетевой запрос не отправляется и следующий шаг не открывается

#### Scenario: Partially occupied list can be corrected

- **WHEN** `occupied_domains` содержит часть отправленных адресов
- **THEN** мастер сохраняет весь ввод и показывает занятые адреса у поля, а после исправления проверяет новый список по «Далее»

#### Scenario: Unavailable check can be retried

- **WHEN** запрос проверки завершается сбоем или возвращает некорректный ответ
- **THEN** занятость отмечается как неизвестная, ввод сохраняется и пользователь может повторить проверку без создания поверхности

#### Scenario: Concurrent clicks and stale responses do not advance

- **WHEN** пользователь несколько раз нажимает «Далее» или меняет домены, пока проверка выполняется
- **THEN** повторные нажатия не запускают дублирующий запрос, а ответ для изменённого ввода не открывает следующий шаг и не показывает ошибку для нового ввода

### Requirement: Rejections are distinct from unknown creation outcomes

Мастер SHALL различать подтверждённый отказ без создания и неизвестный исход. Подтверждённые ответы POST создания `409 DOMAIN_ALREADY_IN_USE`, `422 VALIDATION_ERROR` и `422 FAILED` SHALL распознаваться по структуре, согласованной в proposal. Для `409` все конфликтующие адреса SHALL читаться из `errors[]` по `/domains` и `details.domains`. Для `422` ошибки SHALL отображаться по надёжным путям `errors[].field` с причинами из `errors[].message`, в том числе при пустом верхнеуровневом `message`. Ошибка для поля, которое нельзя исправить в мастере, SHALL оставаться видимой в общем сообщении. Структурированный `422` с `detail[]` SHALL сохранять прежнее поведение. При подтверждённом отказе мастер SHALL сохранить ввод и разрешить явный повтор после исправления. Неизвестный формат MUST NOT распознаваться по тексту `message` или одному HTTP-статусу.

#### Scenario: Confirmed domain conflict

- **WHEN** после предварительной проверки POST создания возвращает `409 DOMAIN_ALREADY_IN_USE` со списком занятых доменов
- **THEN** форма показывает все конфликтующие адреса, сохраняет ввод и позволяет исправить их с новой предварительной проверкой перед повторным POST

#### Scenario: Unknown responsible user

- **WHEN** POST возвращает `422 FAILED` с пустым `message` и ошибкой у `/responsible/product` или `/responsible/connection`
- **THEN** причина из `errors[]` видна в общем сообщении и у соответствующего выбора при открытии шага, остальные поля сохраняются

#### Scenario: Configuration field is not editable

- **WHEN** POST возвращает `422 VALIDATION_ERROR` для настройки, которой нет в форме
- **THEN** мастер показывает причину отказа в общем сообщении и сохраняет форму

#### Scenario: Lost response

- **WHEN** ответ на отправленный POST потерян
- **THEN** UI сообщает о неизвестном результате и блокирует автоматический и явный повтор POST в текущем мастере

### Requirement: Creation outcome controls retry

Мастер SHALL отличать подтверждённый отказ от неизвестного результата. Распознанный ответ создания `409 DOMAIN_ALREADY_IN_USE` либо `422` в согласованной структуре SHALL позволять исправление и новую явную отправку с повторной подготовкой. Локальные mock-форматы MUST NOT расширять список подтверждённых отказов. Сетевой сбой, отмена после начала POST, `5xx`, некорректный успешный ответ, отсутствие валидного ID и иные ответы без достоверного подтверждения отказа SHALL переводить попытку в неизвестный результат.

При неизвестном результате SHALL объясняться, что поверхность могла быть создана и повтор может создать дубль. Данные SHALL сохраняться, автоматическая и ручная повторная отправка в текущем мастере SHALL блокироваться. Изменение полей или режима MUST NOT снимать эту блокировку. Ссылка на реестр SHALL позволять ручную проверку без автоматического сопоставления по имени или домену и без утверждения, что отсутствие в списке доказывает неуспех.

#### Scenario: Validation rejection is correctable

- **WHEN** POST возвращает подтверждённый отказ и пользователь исправляет данные
- **THEN** сохранённый черновик можно отправить явно, запрос не повторяется автоматически

#### Scenario: Malformed rejection cannot unlock retry

- **WHEN** POST возвращает `409` или `422` с неизвестным кодом и форматом либо без ожидаемых данных ошибки
- **THEN** UI показывает неизвестный результат и сохраняет блокировку POST

#### Scenario: Lost response is not a failed creation

- **WHEN** POST завершается сетевым сбоем или `503`
- **THEN** UI сохраняет форму и блокирует повтор POST в текущем мастере

#### Scenario: Malformed success cannot unlock retry

- **WHEN** POST возвращает `201` с некорректным JSON или без валидного UUID
- **THEN** результат неизвестен, запрос карточки и повторный POST не выполняются
