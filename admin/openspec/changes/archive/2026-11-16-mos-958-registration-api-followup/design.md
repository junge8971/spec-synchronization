# Design

## Context

Сценарий опирается на опубликованные DTO проверки доменов и ответы создания, подтверждённые backend-командой. Примеры и гарантия отсутствия записи зафиксированы в [proposal](proposal.md).

## Decisions

- Проверка по «Далее» использует тот же нормализованный список, который уйдёт в POST создания. Мастер остаётся на первом шаге, пока не получит успешный ответ без занятых доменов. Это даёт пользователю явное действие для повтора после сбоя и позволяет исправить занятый адрес до выбора ответственных.
- Синхронная защита от параллельных переходов действует до первого асинхронного шага проверки. Результат привязан к версии ввода, поэтому смена адресов, включая возврат прежнего текста, делает предыдущий ответ неактуальным. Pending и ошибки доступны у поля, ввод сохраняется.
- API-клиент проверки использует существующий транспорт и валидирует `occupied_domains` при чтении ответа. Mock читает тот же источник поверхностей, что и создание. Обе операции сравнивают домены без учёта регистра. Mock-обработчики возвращают подтверждённые форматы `409` и `422` для создания поверхности, сохраняя обработку других операций.
- Общий HTTP-клиент уже передаёт код и `errors[]` в `ApiError`. Обработчик регистрации распознаёт только согласованные сочетания HTTP-статуса, кода и структуры. Поля сопоставляются по пути, список конфликтов берётся из `details.domains`. Подтверждённый отказ возвращает управление пользователю с сохранённым вводом. Перед новым явным POST повторяются валидация и подготовка навыков. После получения ID сохраняется повтор только GET при ошибке чтения.

## Проверка интеграции

Локальные unit/component-тесты и тесты мок-сервера проверяют запросы, повтор и отсутствие записи при отказе. Доступность проверки доменов и правки `product_context` на целевом контуре проверяется отдельно от локальной реализации.
