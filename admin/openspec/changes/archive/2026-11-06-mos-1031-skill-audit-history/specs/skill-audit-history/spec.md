## Purpose

Предоставить серверную историю изменений конкретного навыка без смешения одноимённых сущностей и потери записей при переименовании.

## ADDED Requirements

### Requirement: Audit entity identity

История SHALL читаться из Query API аудита с `object_type=skill` и `object_id`, равным устойчивому skill ID. Название MUST NOT использоваться как идентификатор или замена серверного фильтра. Локальный dev SHALL использовать серверный mock по контракту без credentials. В real mode до подтверждения безопасного транспорта и адреса аудита SHALL показываться unavailable без отправки credentials сервису аудита и без подмены результата моками; работа общей сессии не меняется.

#### Scenario: Renamed skill

- **WHEN** навык переименован и пользователь открывает его историю за период, содержащий сохранённые доступные записи до переименования
- **THEN** запрос использует прежний устойчивый ID и показывает эти записи независимо от прежнего названия

#### Scenario: Same names

- **WHEN** два навыка имеют одинаковое название
- **THEN** история каждого содержит только записи его типа и ID

#### Scenario: Real integration is not confirmed

- **WHEN** приложение работает в real mode, но транспорт или разрешённый адрес аудита не подтверждены
- **THEN** история показывает unavailable, credentials сервису аудита не отправляются и локальный mock не используется

### Requirement: History period and cursor

Каждый запрос SHALL содержать корректный обязательный период: `occurred_from` включительно и `occurred_to` исключительно, в UTC. UI SHALL позволять выбрать период и проверять его до отправки. Используется серверная курсорная пагинация; при переходе на следующую страницу SHALL сохраняться тип сущности, skill ID, границы периода и сортировка исходного запроса. Изменение периода SHALL начинать новое чтение, не смешивая результаты разных отборов. Неизвестные максимальная длина периода, retention и доступность старых записей MUST NOT выдумываться клиентом; отказ сервера по периоду SHALL показываться как ошибка, а не пустая история.

#### Scenario: Next page

- **WHEN** пользователь запрашивает следующую страницу истории
- **THEN** запрос использует курсор сервера с теми же типом, skill ID, периодом и сортировкой, не заменяя их фильтрацией загруженной страницы или offset

#### Scenario: Period changes during loading

- **WHEN** период меняется до завершения предыдущего запроса
- **THEN** новый отбор начинается без прежнего курсора, а запоздавшие записи старого периода не показываются как результат нового

#### Scenario: Empty period and unavailable history

- **WHEN** сервер возвращает пустой результат за применённый период либо старые записи недоступны из-за ограничений источника
- **THEN** UI не утверждает, что у навыка никогда не было изменений, и не объявляет неподтверждённую полноту истории

### Requirement: Server audit presentation

UI SHALL показывать серверные записи по времени действия `occurred_at` от новых к старым, запрашивая сортировку `occurred_at:desc`: время, автора, действие и доступные безопасные подробности. В целевой состав входят создание навыка, изменения карточки, содержания и подключения, действия с токенами без раскрытия секретов, переходы статусов с основаниями, проверки в песочнице, решения ревью с причинами и комментариями, отключения и включения. Неподтверждённая полнота публикации и хранения MUST NOT объявляться подтверждённой, но не блокирует reader и UI; отсутствие записи MUST NOT восполняться локальными событиями или выдаваться за доказательство отсутствия действия. Подробности MUST NOT исполнять HTML/скрипты, раскрывать секреты или несогласованные чувствительные поля. Автор MUST NOT подменяться текущим пользователем; подтверждённое системное действие SHALL отличаться от неизвестного автора.

#### Scenario: Previous review decisions

- **WHEN** согласованный серверный ответ за применённый период содержит прежнее и новое решения ревью
- **THEN** UI показывает обе записи с доступными причинами и комментариями, не скрывая прежнее решение из-за повторного ревью

#### Scenario: Employee and unknown authors

- **WHEN** ответ содержит запись сотрудника и запись с неизвестным автором
- **THEN** UI показывает доступный employee ID и обозначает неизвестного автора, не приписывая запись текущему пользователю или системе

#### Scenario: Accessible history

- **WHEN** пользователь просматривает таблицу и запрашивает следующую страницу или повтор клавиатурой
- **THEN** данные и действия имеют доступные подписи и остаются доступны без зависимости от цвета

### Requirement: Honest history refresh and states

UI SHALL различать loading, успешный empty за период и error/retry. Отказ доступа и недоступность проверки доступа MUST NOT показываться как пустая история; существующие правила сессии и обработки 401/403 SHALL сохраняться. Обновление после мутации SHALL читать аудит, а не добавлять локальную запись об успехе. Поздний ответ другого навыка, периода или пользовательского контекста MUST NOT заменять текущую историю.

#### Scenario: Audit event not yet visible

- **WHEN** мутация навыка успешна, но Query API ещё не возвращает событие
- **THEN** UI не создаёт вымышленную запись; повторное чтение начинает обход с первой страницы

#### Scenario: Failed history request

- **WHEN** запрос завершился ошибкой
- **THEN** показаны ошибка и повтор, не пустая история

#### Scenario: Skill or session changed during request

- **WHEN** после выбора другого навыка или смены пользовательского контекста приходит прежний ответ истории
- **THEN** прежние записи не отображаются в новом контексте
