## Context

Мотивация — proposal.md. Исследованы целиком HTML и текст PDF из proposal, schemas KnowledgeBase*, kb_entryCondition и export DTO, раздел 19 CRUD-документа, общие search/saved-filters/error правила. Реальный backend и браузер не запускались: это анализ контракта, не подтверждение интеграции со стендом.

Приложение использует React Router Framework в SPA-режиме с basename `/tsam-panel/`, TanStack Query, React Hook Form, Zod и существующие shadcn/Base UI-компоненты. `app/routes.ts` строится из общего реестра маршрутов; его используют меню, крошки и route-access. HTTP transport уже владеет сессией. Все KB DTO уже сгенерированы. Публичный `useSkillsCatalogQuery` загружает все страницы навыков. Поиск пользователей опубликован, отдельного GET пользователя по ID нет. Универсальный managed mock существует, но metadata использует `kb_entry` вместо `entries`, bindings пусты, lookup не фильтрует section, display names заменены ID/кодами. Основная mock-spec всё ещё описывает 501 для импортированных операций: delta адресно принимает KB, не утверждая корректность остальных managed mocks.

## Goals / Non-Goals

**Goals:** обособленный удаляемый модуль; соответствие структуре и сценариям прототипа/PDF; реальные поддержанные операции; видимые локальные ограничения вместо скрытого урезания; подключение без отдельного флага и проверяемая production isolation.

**Non-Goals:** backend-расширения, редактор категорий, загрузка документов/видео, HTML/rich-text редактор статей, поисковый/RAG движок, исполнение правил в чате, новая auth-модель, точные ManagedResource UI-grants, универсальная платформа плагинов. DELETE материала опубликован, но кнопки удаления записи в прототипе нет — в UI не добавлять. Удаление ссылки и сохранённого фильтра входит в scope.

## Decisions

### 1. Один change с отдельными проверяемыми блоками

Реестр, редактор, экспорт и optional-интеграция реализуются одним change, поскольку используют один контракт и единую границу удаления. Backend-пробелы не блокируют план: пользователь явно согласовал видимые недоступные функции с пояснениями. Альтернатива — changes по каждой вкладке — добавляет координацию без независимого релизного результата.

### 2. Адресное архитектурное исключение

Новый предметный код размещается только в `app/optional/knowledge-base/`: `routes/`, `ui/`, `api/`, `model/`, `types/`, `constants/`, `handlers/`, colocated tests или `tests/`. Не создавать пустые сегменты заранее. Route modules — framework entrypoints; остальные внешние подключения используют публичный `index.ts` модуля. Отдельный минимальный descriptor для build/навигации не импортирует runtime UI.

Модуль может использовать shared и публичные API entities. Он не импортирует pages/widgets/features других разделов или application internals. Остальные бизнес-слайсы не импортируют KB. Application является единственным потребителем публичного entrypoint; framework route config отдельно ссылается на route files. Server-only KB seed/handlers/tests лежат в `mocks/knowledge-base/`, не в browser-графе. Общие managed handlers переиспользуются, их адресные исправления не копируются в новый mock-server.

Это исключение из глобального размещения FSD, а не отказ от качества: один компонент на файл, типы/константы/handlers у владельца, проверки относительных/type-only/re-export зависимостей сохраняются. Delta code-quality-gates фиксирует исключение; при реализации кратко согласовать с ним AGENTS.md. Не исключать optional из lint.

Альтернативы: глобальные FSD-слайсы затрудняют удаление; отдельный workspace/микрофронтенд требует лишней инфраструктуры; копирование shared создаёт вторую систему компонентов.

### 3. Подключение без флагов и композиция на уровне приложения

По согласованному уточнению пользователя KB всегда зарегистрирована при обычном запуске, typegen и сборке. Отдельного переключателя раздела, парсера или Vite define нет. `CONTROL_API_MOCKS` и настройки сессии не меняются: KB работает с mock или real API согласно существующему режиму.

Общий application-level реестр содержит базовые маршруты и публичный KB descriptor; его используют Node route config и browser navigation. Проверка анализирует route manifest и output graph: три маршрута и runtime-модули KB присутствуют, production fixtures отсутствуют. Общие generated DTO и существующие упоминания KB в диалогах сохраняются.

Маршруты: `/knowledge-base`, `/knowledge-base/new`, `/knowledge-base/:entryId`; вкладки карточки `tab=main|links|skills|rules`, default main. Сохраняется basename. Новый пункт «База знаний» — группа «Контент», видимость по прежним permissions. Реестр/карточка/создание подсвечивают один пункт. Статический `new` не запрашивается как ID.

Существующий реестр shared не должен импортировать optional-модуль. Собрать итоговую конфигурацию в application и передать её потребителям оболочки через существующую композицию или узкий технический context. Чистые helpers shared могут принимать конфигурацию параметром. Переносить только необходимую композицию, не перестраивать всю оболочку. Node route config и browser navigation используют один реестр и descriptor без UI-импортов. Существующие route-access проверки остаются; для KB действует прежний fallback непокрытых операций `*`. Новых permission constants/ACL в transport нет.

Удаление: удалить две KB-папки и перечисленные подключения; снять специальные архитектурные проверки; остальным бизнес-разделам изменения не нужны. Минимальный host config и проверки сборки допускаются снаружи папки и перечисляются в инструкции удаления.

### Визуальное уточнение контента

По пяти скриншотам пользователя контент приближается к прототипу без pixel-perfect требования. Общая шапка приложения не меняется. По последующему адресному запросу пользователя верхний блок карточки KB оформляется по существующему page-intro паттерну: заголовок text-2xl, приглушённые метаданные, локализованные даты, отступы и Separator. Header с действиями находится вне формы редактора: Save связан с ней штатным HTML-атрибутом form, экспорт сохраняет независимую форму. Используются существующие Card, line Tabs, Popover, Badge и Bubble: компактные раскрываемые фильтры, светлая таблица с чипсами, формы в две колонки с адаптивным переходом в одну, компактные действия ссылок с доступными именами и тёмный локальный предпросмотр чата. Выбранные ссылки/навыки и активная вкладка получают акцент. Dialog условий сохраняет draft/apply/cancel; ограничения API и пояснения остаются видимыми у соответствующих действий. Новые глобальные стили, зависимости и изменения shared-компонентов не требуются. После отдельного разрешения пользователя визуальное уточнение дополнительно проверяется в Chromium с локальными mock-данными на desktop/mobile, без доступа к реальному backend. Контент получает адаптивные отступы; полные ID известных навыков доступны в tooltip и accessible name, неизвестные ID остаются видимыми. Scroll-контейнер таблицы задаёт containing block для sr-only заголовков, чтобы они не расширяли страницу на mobile.

Выявленный при браузерной проверке сброс черновика в demo исправляется в существующем `useRouteAccess`: как и в real mode, временный checking не считается подтверждённым отказом доступа. SessionBoundary скрывает/блокирует дерево; после ready политика пересчитывается, в том числе при отзыве прав. Новая session-модель, grants и обход bootstrap не вводятся.

По последующему запросу пользователя убраны технические подписи о минимуме поиска, сортировке статуса, объединении быстрых фильтров с условиями и локальном макете preview. Дублирующие недоступные блоки «Ссылок / Навыки» под условиями удалены; недоступные пункты с пояснениями остаются в выборе поля. Поведение поиска, лимит 50 условий и безопасность preview не меняются.

### 5. API, данные и ошибки

Все KB-клиенты локальны модулю, DTO ссылаются на generated types; runtime validation следует принятому стилю соседних клиентов. Общий transport, Query Client, отмена/защита от поздних результатов и session-owner semantics переиспользуются. Не строить второй transport или generic managed-resource framework. Query keys имеют KB namespace и участвуют в штатном сбросе пользовательского кэша.

Metadata: `data.entries`, catalog_bindings, condition_fields, export_fields, export_max_rows. Lookup: шесть kb_* наборов; сохранить inactive values для отображения/неизменённого сохранения, запретить новый выбор. Неподдержанное значение не подменяется первым option. Ошибка lookup не превращается в статический демо-справочник.

Поиск: POST `/managed-resources/knowledge-base/entries/search`, query/status/category_code/conditions/sort/limit/offset. Limits 1–100, default 20. Фильтры объединяются AND, группа conditions имеет одну логику, не более 50 условий. Операторы camelCase прототипа не выходят на wire: используются contains/not_contains/eq/ne/is_empty/is_not_empty/in/not_in и только реально разрешённые metadata. eq регистрозависим в отличие от демо; пустой enum selection нельзя отправлять как in:[] — убрать условие или показать ошибку до Apply. Неполные условия не игнорируются молча.

URL — источник применённого отбора, draft условий отдельно. Кодек валидирует JSON/размеры/лимиты/поля/операторы; неподдержанное состояние из URL или saved filter объясняется и не применяется частично без ведома пользователя. Воспроизводятся query, multi-filters, conditions, sort, pagination; смена фильтров сбрасывает offset. Clipboard failure — ошибка, не «Скопировано». Saved filters имеют собственную серверную пагинацию; одинаковые имена не означают upsert/замену существующего ID.

Ошибки envelope и HTTPValidationError преобразуются в полевые/общие сообщения, включая `/links/{index}/url`, `/skill_ids/{index}`, `/display_rules/max_links`. Ошибка на скрытой вкладке открывает соответствующую вкладку и фокусирует поле. После перестановки ошибка относится к snapshot отправленного массива, не к другой ссылке. Ошибка не сбрасывает форму; невалидный ответ не считается успехом.

### 6. Редактор и команды

Одна React Hook Form на карточку и все вкладки, Zod для ограничений, useFieldArray для ссылок. Локальный key строки не подменяет server link id. Серверный snapshot отделён от черновика; фоновая refetch не затирает dirty values. Создание POST возвращает id, затем GET и переход replace на detail; если GET упал после успешного POST, повторять чтение известного ID, не создавать вторую запись.

PUT отправляет изменённые верхнеуровневые поля; при изменении links/skill_ids — полный итоговый список; при изменении правил — полный display_rules. Для nullable полей очистка даёт null, для списков []; не отправлять null для остальных полей, даже если permissive patch schema это допускает вопреки CRUD-документу. Пустой diff не отправлять. created_at/updated_at берутся с сервера, не из часов браузера.

Пауза/возобновление доступна для сохранённой чистой карточки: paused -> active, остальные поддержанные неархивные статусы -> paused как в прототипе; подпись меняется на «Возобновить» для paused. Перед командой dirty-карточка показывает «Сохраните или отмените изменения перед сменой статуса» и не отправляет запрос. Для новой карточки — «Сначала сохраните запись». Успех только после PUT; серверный отказ сохраняет прежний статус. Архив всегда недоступен в текущем контракте. Отдельную кнопку активации черновика сверх прототипа не добавлять.

Защита несохранённых изменений — существующие router blocker/beforeunload паттерны: закрытие, крошки, sidebar, Back, переход на другой ID; смена вкладки сохраняет черновик и не блокируется. Чистая карточка закрывается без подтверждения. Same-user refresh сохраняет draft без автоматической отправки; замена пользователя исключает старые данные по существующей сессионной границе.

HTTP mutation retry выключен: pending защищает от двойного клика; сеть после отправки не доказывает отмену backend. Пояснить неопределённый результат и предложить сверить сохранённые данные. Не придумывать version/idempotency протокол. Подтверждённый POST с id рассматривается отдельно от неизвестного исхода.

Ссылки переставляются drag-and-drop за ручку плюс доступные кнопки вверх/вниз. Preview выбора не сбрасывается при reorder, при удалении выбирается оставшаяся ссылка либо пустое состояние. URL валидируется через URL + allowlist http/https; отображается текстом, без iframe/fetch внешней страницы. При открытии новой вкладки используются безопасные rel.

Ответственный: GET `/users/v1/search` с query 1–200, limit/offset, data.items/total. Пользователь — бизнес-ссылка, не principal. Сохранённый ID, не найденный в поиске, виден как ID и остаётся в draft, не назначается другой пользователь. Новые варианты ограничены активными пользователями; отсутствующее имя не выдумывать. Навыки используют полный публичный каталог; пагинация/ошибка не удаляет текущие связи.

### 7. Экспорт

Использовать общий file-response/download механизм. Список передаёт fields и полный применённый search, выгружается весь отбор, а не текущая страница; metadata limit по умолчанию 10000. Поддержанные поля: name, code, category_code, skill_names, links_count, status, description, owner, tags, material_type, language, valid_until. Порядок выбора полей сохраняется. Ошибка/лимит — без ложного готового файла и скрытого усечения.

Карточка экспортирует только сохранённую запись, не draft. Для новой кнопка disabled с пояснением; при dirty — явное предупреждение «Выгружаются сохранённые данные». В modal сохранить разделы прототипа: «Основное» содержит поддержанные поля; «Материалы», «Навыки (связи)», «Правила показа» disabled с пояснениями об отсутствии вложенного экспорта. Плоское поле skill_names при этом доступно и не объявляется экспортом kb_entry_skill.

### 8. Локальная среда и проверки

KB fixtures/handlers и tests размещаются в `mocks/knowledge-base/`, подключаются к существующему Express. Test script должен явно запускать вложенные tests: нынешний `mocks/*.test.mjs` их не подхватывает. Не менять чужие mock conventions без необходимости, не ослаблять contract assertions.

Исправить `entries` metadata/bindings, KB lookup section, display names, порядок/ID вложенных ссылок, массивы replacement, полный rules defaulting, field conflicts, HTTP/HTTPS, ссылки на навыки, inactive references, search/sort до pagination и CSV. Seed содержит только контрактные статусы; archived — отдельный UI test double для read compatibility, не фиктивно доступная backend-команда. Неподдержанные числовые условия отклоняются, вложенный экспорт не моделируется успешным.

До mock-работ прочитать proposal/design/specs archive changes integrate-mpmm-auth-permissions и add-local-session-demo; существующая сессия/профили не меняются. Контрактные фикстуры пользователей/навыков согласованы с seed, локальные бизнес-запросы без credentials и role enforcement. Production не содержит моки.

Unit/component: кодеки URL, DTO mapping, defaults, errors, dirty/save/status, reorder с server IDs, keyboard controls, clipboard/export failures, session boundary reuse. Server: HTTP round trips с проверкой контрактов, лимитов, конфликтов и отсутствия мутации при ошибке. Build: обычные typegen/typecheck и сборка без дополнительных настроек KB, manifest/output graph с тремя маршрутами и без production fixtures; lint без warnings. E2E/browser не создавать/не запускать.

## Risks / Trade-offs

- [PDF и API расходятся] -> UI сохраняет требуемые функции с точными локальными labels; неизвестное не заменяется похожим endpoint.
- [Модуль требует точек подключения] -> один descriptor и документированный перечень host changes; не обещать удаление только одной папки без снятия регистрации.
- [Shared сейчас владеет route registry] -> композиция переносится только на уровень application, UI-конфигурация не создаёт reverse imports.
- [OpenAPI допускает больше, чем текстовый бизнес-контракт] -> runtime ограничения учитывают оба источника; mocks не используются как источник разрешения функции.
- [Нет подтверждённой уникальности name и конкурентной версии] -> видимые ограничения, ошибки сервера и отсутствие автоповтора; локальная неполная выборка не выдаётся за гарантию.
- [Полный каталог навыков может вырасти] -> переиспользовать существующую пагинированную загрузку, не обрезать первую страницу; не добавлять новый индекс без измеренной необходимости.
- [Defaults прототипа отсутствуют в реальном lookup] -> явный выбор обязательных значений вместо молчаливой подмены или отправки неактивных кодов.

## Migration Plan

1. Добавить адресные границы и безусловное application-level подключение; подтвердить неизменность существующих маршрутов.
2. Реализовать модуль и его локальные контрактные сценарии, последовательно закрывая задачи.
3. Проверить обычные typegen и build без настроек включения KB. Реальную интеграцию проверять отдельно от mocks с разрешённой конфигурацией стенда, без запроса/вывода credentials.
4. Для удаления выполнить документированный список отсоединения и пересобрать приложение, сохранив серверные данные, общие API-контракты и связанные данные других разделов.
