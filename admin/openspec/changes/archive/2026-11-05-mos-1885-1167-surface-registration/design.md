## Context

Мотивация и границы — в [proposal.md](proposal.md), пользовательские гарантии — в двух delta-спецификациях. Текущий `SurfaceDetailsStep` уже выводит нормализованные адреса, но скрывает весь блок при отсутствии вычисленного `channelId`. React Hook Form в `use-surface-registration.ts` владеет остальным вводом; приветствия в draft и запросе нет. `useSurfaceRegistrationAttempt` уже сохраняет snapshot, различает отказ и неизвестный POST, а после известного ID выполняет fresh GET.

`docs/api/contracts/surfaces.openapi.json` описывает optional `configuration` создания с полной схемой конфигурации и документированными defaults. Контуры недоступны; локальный контракт и моки не доказывают актуальное развёртывание. Существующий API-клиент уже принимает `configuration`, а mock handler сохраняет переданную конфигурацию; тестовый `surface-registration-api-mock.ts` пока возвращает фиксированное приветствие вместо отправленного.

## Goals / Non-Goals

**Goals:** единый источник текущего ввода, отсутствие лишних записей и правдоподобная диагностика результата при переходах, отказах и повторном чтении.

**Non-Goals:** новый endpoint, предварительная проверка занятости, редактирование оформления или fallback в мастере, изменение правил выбора навыков, новые права, изменение API-типов, полная реализация MOS-958 или подтверждение работы backend на контуре.

## Decisions

### 1. Превью — представление ввода

Использовать существующий `parseDomains` и выводить его результат отдельной строкой «Адреса» по непустому списку, независимо от наличия локально вычисленного `channelId`. Не добавлять второй parser, сетевую проверку, новую модель или доменные syntax rules. Изменение и очистка поля сразу обновляют превью; существующая ошибка повторов не превращается в молчаливое исправление формы. Текст и длинные адреса отображаются безопасно; подпись и ошибка доступны вспомогательным технологиям.

Альтернатива — показывать результат поиска в реестре — не подтверждает глобальную доступность и не нужна для отражения ввода. Существующее отдельное расхождение: код рассчитывает канал, основная `surface-registration` запрещает клиентский расчёт, а MOS-1697 и описание локального POST приводят формулу. Здесь не меняется правило канала и не декларируется устранение расхождения; после создания подтверждённым остаётся серверный `channel_id`. Исправление или согласование этого вопроса требует отдельного объёма.

### 2. Приветствие принадлежит draft и одной попытке

Добавить `greeting` в текущие defaults/schema полей регистрации и список полей шага «Сценарии». Начальное значение — точный текст MOS-1885; пользовательский ввод сохраняется при переходах, ошибках и блокировке попытки. Обязательность, 500 символов и допустимые подстановки соответствуют локальному контракту; ошибки связать с полем и проверять до подготовки/POST.

Правила приветствия уже есть во внутренней схеме `features/surface-configurator`; feature-слайсы не импортируют внутренности друг друга. При необходимости общего использования адресно выделить схему приветствия в публичный API `entities/surface`, сохранив поведение существующего конфигуратора и его тесты; не переносить туда весь редактор. Не вводить собственную форму или второе состояние. Итоговый шаг показывает текст как черновик; старое сообщение о недоступности настройки удаляется.

### 3. Полная конфигурация в существующем POST

Расширить `toCreateSurfaceRequest`: каждый POST мастера содержит `configuration.greeting` из текущего draft, в том числе неизменённый начальный текст. Остальные поля — задокументированные локальным POST defaults: `#B3121B`, `round`, `moscow_sans`, `greeting_fallback: "Здравствуйте! Чем помочь?"`, `suggestions: []`, `cards: []`. Для отсутствующего имени fallback остаётся отдельным согласованным текстом; его можно редактировать после создания в конфигураторе. Это явные значения запроса по локальному снимку, а не утверждение, что текст уже сохранён или что текущий backend использует именно эти defaults.

Входящий массив навыков остаётся результатом существующей проверки перед созданием и передаётся в том же POST. Сохранить общую блокировку snapshot, проверку владельца, запрет автоматического replay и `Idempotency-Key`. Извлекать ошибку поля `/configuration/greeting` только из уже надёжно распознаваемого контрактного отказа. Если отказ получен на итоговом шаге, показать общую ошибку и сохранить возможность вернуться к полю с его ошибкой; ошибки неизменяемых в мастере настроек показывать общим сообщением, не обещая их исправления здесь. Иные неизвестные envelopes не классифицировать по тексту и не ослаблять правила unknown.

Оставить server defaults через отсутствие `configuration` нельзя: локальное значение приветствия сервера отличается от начального текста Jira. POST, за которым незаметно выполняется PUT, отклонён: он создаёт промежуточное состояние и усложняет восстановление.

### 4. Подтверждение прочитанной конфигурации

После принятого 201 сохранить ID и snapshot запроса, затем использовать существующий fresh GET с проверкой того же ID. Сопоставить `configuration.greeting` из ответа с отправленным значением с учётом описанного контрактом trimming. Если оно совпадает, можно подтвердить фактический текст; если отличается — показать созданную поверхность, серверный текст и отличие, не объявляя пользовательский текст сохранённым. Невалидный ответ без читаемого приветствия остаётся ошибкой чтения; повторяется только GET. Известный ID, несоответствие или ошибка чтения не запускают POST/PUT повторно. Не изменять правила отображения фактического статуса и серверного канала.

Тестовый API-fixture должен отражать отправленное приветствие для успешного случая и уметь вернуть отличающееся значение для негативного. Существующий Express handler уже принимает переданную конфигурацию; менять его defaults без отдельной необходимости этой задачи не требуется.

## Risks / Trade-offs

- [Значения в локальном контракте отличаются от реально развёрнутых] → показывать серверные отказы и readback без фиктивного успеха; после восстановления доступа отдельно подтвердить интеграцию. Моки не являются доказательством backend.
- [Создание подтвердилось, приветствие отличается или GET не прочитан] → сохранять ID и snapshot, показывать различие либо ошибку чтения; не повторять запись.
- [Контрактные значения оформления становятся недоступными в справочниках] → показать отказ без сброса формы и без выдуманной замены; менять справочники и правила выбора здесь не предполагается.
- [Существующее противоречие по каналу остаётся] → явно фиксировать его отдельно и не засчитывать эту работу как подтверждение всей прежней спецификации канала.
- [Локальный mock без `configuration` применяет другие defaults] → этот сценарий не использовать как подтверждение отправленной конфигурации и не расширять задачу исправлением всех mock defaults.

## Migration Plan

Добавить field/валидацию, отображение превью и конфигурацию в POST, затем дополнить подтверждение и адресные unit/component-тесты; существующие типы контракта не меняются. Текущие поверхности не мигрируются. Откат клиента не изменяет уже сохранённые конфигурации и возвращает прежнее ограничение мастера. Интерактивную проверку локального UI через Playwright MCP выполнять только после отдельного явного разрешения; без него или при недоступной среде оставить её непроверенной. Тестовые контуры и автоматизированные E2E/browser-тесты требуют отдельного разрешения.
