## Context

См. proposal.md. Карточка — заглушка; `app/shared/api/http-client.ts` читает только JSON. Базовый HTTP URL уже отделён от UI basename. Существующий detail навыка адресуется UUID, тогда как PDF диалогов передаёт service_id. Shell spec требует заглушку для незавершённых карточек и статичную подпись «Диалог»; соответствующая delta входит только в этот change.

## Goals / Non-Goals

**Goals:** один согласованный detail snapshot, безопасные вложения, независимая прямая ссылка и основа для дочерних задач.

**Non-Goals:** восемь загрузок по вкладкам, real-time переписка, редактирование сообщений, role highlighting, auth lifecycle, клиентская генерация audit events.

## Decisions

1. **Contract gate:** пользователь подтвердил принятие бизнес-контракта 2.3/3.5/3.7 PDF, включая chat_id, источники и режимы вложений. Принятие зафиксировано в `docs/api/contracts/dialogs.md`; бизнес-схемы и generated DTO опубликованы в общей схеме вместе с MOS-1037, `yarn api:check` проходит. Пользователь запросил полную функциональность, включая preview; binary-путь описан ниже. Для PDF подключён установленный пользователем `pdfjs-dist` 6.4.299; gate безопасного способа закрыт проверками canvas-renderer и binary-пути. Противоречие «без адресата» решается следованием новому PDF: нет поля — нет синтетического счётчика. Если владелец требует третий вид, сначала расширяется контракт.
2. **Один detail query:** публичный API `entities/dialog`, ключ по chat_id, route param dialogId трактуется как этот ID, без UUID-валидации навыка. Прямая ссылка выполняет detail независимо от списка. Владелец карточки передаёт один snapshot приватным вкладкам; навигация по ним не запускает дополнительные чтения. Повтор ошибки явный, без фонового polling ради продолжающегося диалога. Audit формирует сервер; технические refetch не считать клиентскими событиями.
3. **Композиция:** page/при необходимости widget карточки содержит переписку и вкладки. MOS-1042 добавляет оценки/основания, MOS-1043 — route, MOS-1044 — feature категории. Внутри владельца прямые импорты приватных модулей, снаружи публичные API. Не создавать feature на каждый read-only блок. По согласованным скриншотам карточка оформлена компактной сводкой сверху и двумя колонками (переписка шире); на узком экране колонки складываются. Общая информация содержит отдельные карточки диалога, участников, пользователя и операторов без дополнительной вкладки участников. Сообщения жителя выровнены вправо, ответы — влево, роли сотрудников не влияют на оформление или доступ. Вложение — компактная строка с размером и подписанными для screen reader действиями. Нереализованные экспорт, оценки ответов, маршрут и изменение категорий из прототипа не имитируются.
4. **Представление:** RFC3339 UTC форматируется в согласованном поясе. duration_sec — серверный снимок, при ended_at null подпись «и идёт», без локального таймера. Участники и операторы в порядке ответа, доли/message_count не пересчитываются. Знаменатель участника — step_count по принятому предположению 8.5. Nullable тема/поля отличаются от нуля/пустого списка. Тексты сообщений и имена файлов рендерятся текстом, не HTML. Пятибалльная оценка оператора в реестре, сводке и блоке операторов отображается единым read-only компонентом `entities/dialog`: пять звёзд с доступной числовой подписью. Null остаётся «Нет оценки» (в сводке элемент отсутствует), не превращается в нулевой рейтинг. Числовые фильтры/сортировка и бинарные оценки ответов good/poor не меняются.
5. **Ошибки:** NOT_FOUND даёт «Диалог не найден»; 503 ESK_CORE_UNAVAILABLE и ATTACHMENT_SOURCE_UNAVAILABLE не превращаются в 404/пустую переписку. route.available=false не блокирует карточку. Ошибка binary-чтения не стирает уже загруженную карточку. 401/403 остаются бизнес-ошибками без входа/refresh.
6. **Вложения:** status=unprocessed не опрашивается и не открывается; ready допускает download, view определяется серверным viewable. Получать содержимое только после действия сотрудника, не preload. Выбран fetch/Blob, поскольку прямое открытие не позволяет карточке обработать JSON-envelope ошибки и проверить ответ до показа. Общий transport использует `cache: no-store`, разбирает JSON-ошибки, не запускает retry/download. Клиент проверяет CSP `sandbox` без разрешений, `nosniff`, `no-store`, режим Content-Disposition, UTF-8 filename*, совпадение MIME и размера с метаданными. Cross-origin API должен открыть эти заголовки через CORS, иначе действие отклоняется. Изображения показываются в iframe с пустым `sandbox` и `referrerPolicy=no-referrer`: запрещены scripts, same-origin, формы, навигация верхнего уровня, popups и download. Защиту задаёт контейнер, а не унаследованные заголовки Blob. PDF не передаётся встроенному browser viewer: PDF.js получает только уже проверенные байты, разбирает их в bundled worker и отображает текущую страницу в canvas. Viewer/scripting manager, XFA, annotation/link layers и QuickJS assets не подключаются; извлечённый доступный текст выводится React как текст. Переходы между страницами не перечитывают бизнес-API. Через штатный BinaryDataFactory разрешены только Vite-emitted ресурсы установленной версии (шрифты, CMap, image-decoder WASM), а не произвольные URL из документа. Рендер ограничен 1600 пикселями по длинной стороне; при закрытии render task отменяется, page очищается, loading task/worker уничтожается. Object URL освобождается при закрытии/размонтировании; незавершённое чтение отменяется, поздний ответ игнорируется. Download создаёт отдельный URL только по явному действию и освобождает его после передачи браузеру либо при размонтировании. Проверки покрыты unit/component/server-тестами, включая реальный разбор и canvas-rendering двухстраничного PDF в Node и проверку неисполнения PDF OpenAction JavaScript. Browser/E2E и внешняя CSP окружения не проверялись; production-сборка проверяет выпуск worker и локальных assets под basename. Ни один путь не добавляет токен в URL. Binary-обработка добавляется узко к общему transport только при необходимости, без второго независимого JSON-клиента. Ошибку view не заменять автоматическим download.
7. **Ссылки:** использовать безопасные http/https для внешних источников; app:// страницы обращения показывать текстом до отдельной политики. Код навыка не является UUID: пользователь подтвердил отображение названия/кода текстом до согласованного resolver, без фиктивного перехода. Не загружать весь каталог ради случайного совпадения названий.
8. **Крошки:** reuse существующего механизма с данными того же snapshot; topic либо «Диалог <chat_id>». При loading/error допускается нейтральная «Диалог», а не заголовок прошлого ID.

## Risks / Trade-offs

- PDF.js добавляет вес worker/decoder/font assets; библиотека загружается динамически только при PDF-preview. Vite предупреждает о размере отдельного PDF chunk; порог не повышается. Зависимость необходима: встроенный PDF viewer может блокироваться пустым sandbox, ослаблять sandbox ради просмотра нельзя. Прежний package-registry blocker снят пользователем установкой `pdfjs-dist` 6.4.299. Парольные/повреждённые PDF и ошибки рендера показываются как ошибка просмотра, не заменяются скачиванием. Обновление PDF.js требует повторной проверки worker/assets и security-тестов.
- Один большой ответ → в PDF нет message pagination/лимита; оценить размер с backend до подключения, не выдумывать пагинацию.
- PDF считает nosniff защитой от ложного MIME → не полагаться только на MIME; сохранить sandbox и запрет исполнения активного содержимого.
- Маршрут недоступен, вложения недоступны → разные контрактные состояния, тестировать отдельно.
- Нет message_id → использовать порядок snapshot для read-only представлений, не объявлять локальные ключи серверными IDs.

## Development fixtures

По запросу пользователя расширены локальные сценарии: 58 независимых snapshots с проекцией в реестр, первые 15 IDs покрывают основные успешные/ошибочные состояния. Матрица и прямые пути находятся в `mocks/README.md`. Ошибки фиксируются по mock ID, не по посетителю или новым API-параметрам. Binary fixtures общие, но IDs вложений уникальны для диалогов; принадлежность проверяется до выбора локального содержимого. Демо-PNG показывает синтетический счётчик; PDF/TXT, необработанное вложение, отказ binary-источника и повреждённый PDF доступны отдельными сценариями. Production-контракт и auth-scope не расширяются.

## Migration Plan

После gate добавить detail/attachment схемы и HTTP fixtures, заменить заглушку и внести shell delta при sync. Дочерние вкладки принимаются отдельными changes. Откат возвращает честную недоступность карточки; безопасность binary-чтения проверяется unit/component/server-тестами без браузера, неподтверждённая изоляция остаётся gate просмотра.
