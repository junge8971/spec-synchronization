## Context

См. proposal.md. Реестр уже имеет серверную пагинацию, status-фильтр и отображение статуса. SkillListItemResponse и SkillResponse содержат status и version; клиент changeSkillStatus валидирует запрос и ответ опубликованного POST status. MOS-909 уже использует `whitelist → prod` для одиночного навыка. Пользователь согласовал тот же переход для массового MVP с последовательными запросами.

HTML-прототип дополнительно содержит approved и переход в белые списки. В опубликованном SkillStatus approved отсутствует; этот сценарий отложен без блокирования MVP.

## Goals / Non-Goals

**Goals:** минимальный массовый выкат текущей страницы с одним подтверждением и понятным результатом каждого запроса.

**Non-Goals:** переход в whitelist, решение ревью, выкат всего серверного реестра, batch API, параллельные команды, фоновая очередь, автоматические повторы и восстановление очереди после reload. Не обещать атомарность группы или развёртывание отдельного runtime.

## Decisions

- **API-gate для MVP снят продуктовым согласованием.** Использовать только `whitelist → prod`; окончательное принятие перехода остаётся за backend. Не добавлять approved и не трактовать review как согласование. Отложенный переход потребует отдельного согласования по контракту.
- **Переиспользовать существующий клиент.** Чтение и смена статуса остаются в entities/skill, выбор и последовательная отправка — в feature массового выката, сборка — в widgets/skills-registry. Не импортировать соседнюю feature skill-lifecycle; использовать публичный entity API и существующие соглашения обновления detail/реестра. Новый клиент, зависимость или scheduler не нужны.
- **Выбор ограничен показанными строками.** Смена страницы, фильтра или сортировки сбрасывает выбор. Пустой выбор или наличие статуса, отличного от whitelist, блокирует действие с пояснением; не пропускать неподходящие строки молча. Не отправлять команды по данным реестра с ошибкой обновления.
- **Одно подтверждение.** Показать продуктивный контур, количество и выбранные навыки. Зафиксировать ID, status и version; известное изменение выбранных записей до отправки требует нового подтверждения. Отмена не отправляет запросов. Во время выполнения нельзя запустить вторую группу или менять её состав; обновление таблицы не добавляет строки в уже подтверждённую группу.
- **Обычный последовательный цикл вместо batch/fan-out.** Для каждого навыка вызвать changeSkillStatus с `status=prod`, подтверждённым expected_version и отдельным UUID Idempotency-Key, дождавшись завершения предыдущего вызова. Ошибка одного элемента не скрывает его результат и не мешает обработать остальные. Не перечитывать версию для автоматической повторной команды при конфликте.
- **Отчёт по ID, отдельно от строк таблицы.** Валидный ответ с prod означает подтверждённый успех; другой status показывается как фактическое состояние с предупреждением. Серверный отказ показывается как ошибка элемента. Timeout, сетевая ошибка, 5xx и невалидный успешный ответ означают неизвестный исход, а не гарантированный отказ. После обработки обновить реестр и затронутые detail; refetch не стирает отчёт.
- **Переключение вкладок страницы навыков не теряет операцию.** Панель реестра сохраняется штатным `TabsContent.keepMounted`; активность передаётся отдельно. Уход на «Домены» или «Ревью» останавливает неотправленную часть текущего запуска даже при возврате до ответа. Отчёт содержит состояния очереди, отправленного запроса и неотправленных элементов; блокировка сохраняется до завершения запроса. Полный уход со страницы по-прежнему не сохраняет очередь между посещениями.
- **Без механизма replay.** Для неизвестного исхода предложить чтение актуальной карточки. Ошибка чтения сохраняет неопределённость. Успешное чтение показывает текущий status, но не доказывает, какая команда его установила. Новая попытка возможна только по актуальному whitelist после нового выбора/подтверждения, с актуальной версией и новым ключом; подтверждённо успешные элементы не повторяются. Отдельную кнопку «повторить всю группу» не добавлять.

## Risks / Trade-offs

- [Состояние изменилось после подтверждения] → expected_version, ошибка конкретного элемента и перечитывание без автоматического POST с новой версией.
- [Ответ потерян после принятия команды] → явно неизвестный исход и ручное чтение состояния; Idempotency-Key не объявляется гарантией replay.
- [Последовательная отправка медленнее параллельной] → допустимо для одной страницы; нет необходимости в настройках параллелизма и batch-протоколе.
- [Пользователь закрыл страницу во время выполнения] → не отправлять оставшиеся команды после ухода, уже отправленная команда не считается отменённой; при следующем открытии читать серверное состояние. Сохранение очереди и отчёта между посещениями не требуется.

## Migration Plan

Расширить существующий реестр без изменения API и одиночного lifecycle. Проверить основной выкат, неподходящий выбор, частичный успех и неизвестный исход unit/component-тестами; браузерные проверки не входят в работу. Приёмка относится только к MVP `whitelist → prod`. Откат UI убирает массовое действие, но не отменяет принятые сервером переходы.
