## Purpose

Реализовать карточку опросника и правила показа в разделе обратной связи ЦАМ по опубликованному API, с отдельной приёмкой и сохранением ограничений первого этапа.

## ADDED Requirements

### Requirement: Isolated feedback integration

Возможности этой задачи SHALL поставляться внутри обособленного модуля раздела «Обратная связь», с общим foundation MOS-1249 и ограниченными точками подключения приложения по образцу базы знаний. Внешние потребители SHALL обращаться через публичный API модуля; framework route entrypoints SHALL подключаться отдельно. Бизнес-слои приложения MUST NOT зависеть от внутренних модулей feedback. Существующие transport, обработка ошибок и механизмы сессии SHALL сохраняться. Новая UI-policy, mappings permissions и новые ограничения интерфейса по пользователю MUST NOT добавляться в текущую поставку.

#### Scenario: Integrate the task without expanding module boundaries

- **WHEN** реализация задачи подключается к приложению и общей модели feedback
- **THEN** предметная логика и тесты остаются у владельца раздела, composition использует публичный API и отдельные route entrypoints; действующие защитные механизмы сохраняются без новых permission mappings

#### Scenario: Replace existing editor handoff

- **WHEN** открывается существующий route entrypoint создания или деталей опросника
- **THEN** он подключает редактор из optional/feedback; публичный index.ts сохраняет descriptors без runtime UI, а до MOS-1254/1257 вопросы и метки сохраняются без собственного редактора

### Requirement: Unified survey editor

Карточка SHALL иметь вкладки «Основное», «Форма», «Правила показа», единый draft и сохранение. Редактируемые поля SHALL соответствовать API: name/code/type_code/description/owner/active_since/status/audience_type и связанные настройки. Name SHALL иметь 1–255 символов, code — до 100 по `^[a-z][a-z0-9_]*$`, owner — до 200; active_since SHALL быть датой YYYY-MM-DD либо null. Опциональные поля с null SHALL отображаться пустыми; это MUST NOT отменять обязательность полей по модели данных и бизнес-валидацию. Создание SHALL требовать name/code/type_code, допускает пустые вопросы, defaults draft/all. Уникальность имени MUST NOT вводиться; уникальность кода SHALL подтверждаться сервером.

responsible_user_id SHALL до отдельного lookup отображаться только для чтения как сохранённый ID либо «Не назначен»; пользовательский селектор и mock-имена MUST NOT добавляться. При сохранении неизменённый ID MUST NOT теряться. На уход с dirty draft SHALL запрашиваться подтверждение, переключение вкладки SHALL сохранять draft; pending SHALL блокировать повторную отправку. Ошибки SHALL сохранять ввод и позволять перейти к полю на другой вкладке с фокусом.

Переход сохранённого опросника из любого другого статуса в disabled SHALL требовать подтверждения и через отдельную кнопку, и через выбор статуса с «Сохранить». При отмене запрос MUST NOT отправляться, draft SHALL сохраняться. При обычном сохранении подтверждение SHALL охватывать один PUT со статусом и остальными изменёнными полями; повторный PUT статуса MUST NOT отправляться. Повторное сохранение уже disabled без смены статуса MUST NOT требовать подтверждения выключения.

#### Scenario: Validation across tabs

- **WHEN** пользователь сохраняет карточку с пустым вопросом на скрытой вкладке
- **THEN** сохранение блокируется либо показывает серверную ошибку соответствующего поля, вкладка помечена, переход к полю сохраняет остальные изменения

#### Scenario: Existing responsible identifier

- **WHEN** карточка содержит внешний responsible_user_id, а пользователь меняет описание
- **THEN** исходный ответственный остаётся видимым и сохраняется без поиска в демо-списке или очистки

#### Scenario: Confirm disabled selected in the form

- **WHEN** статус сохранённой active-карточки изменён в select на disabled и нажато «Сохранить»
- **THEN** срабатывает единое подтверждение выключения; отмена оставляет ввод без запроса, подтверждение сохраняет изменения одним PUT

### Requirement: Linked audience and surfaces

При audience_type=surface SHALL требоваться хотя бы один surface UUID, при segment — непустые метки из редактора MOS-1257. surface_ids SHALL содержать не более 100 UUID; 101-й выбор SHALL блокироваться с пояснением без потери текущего набора. Поверхности SHALL загружаться существующим API с пагинацией и использовать единый surface_ids на вкладках «Основное» и «Правила показа». Скрытие conditional UI MUST NOT само очищать связи. Неактивные сохранённые lookup-коды SHALL отображаться и сохраняться; новый выбор SHALL использовать только активные значения.

#### Scenario: Shared surfaces

- **WHEN** пользователь меняет поверхности во вкладке правил
- **THEN** основная вкладка показывает тот же набор UUID; переключение аудитории само не удаляет связи

#### Scenario: Surface lookup request fails

- **WHEN** запрос существующего API поверхностей завершился ошибкой, включая серверный 403
- **THEN** ошибка обработана общим механизмом, сохранённые surface_ids не теряются и показываются как UUID без вымышленных названий; недоступность выбора объясняется без нового UI permission gate

#### Scenario: Surface selection limit

- **WHEN** выбраны 100 поверхностей и пользователь пытается добавить ещё одну
- **THEN** UI сохраняет существующие 100 UUID, объясняет лимит и не отправляет массив из 101 элемента

### Requirement: Display rule configuration

Карточка SHALL редактировать все опубликованные display_rules: trigger_type, min_messages, min_duration_sec, delay_show_sec, pause_after_last_sec, max_per_session, max_per_day, max_per_user, cooldown_sec, skip_if_rated, quiet_hours_enabled, quiet_from, quiet_to, dialog_type, dialog_result, priority, exclusive_show. Минимумы/длительности/задержки/cooldown SHALL быть целыми >= 0 или null; лимиты частоты — целыми >= 1 или null; priority — целым либо null. Включённые тихие часы SHALL требовать обеих границ времени без timezone; переход через полночь SHALL допускаться. PUT SHALL быть частичным только на верхнем уровне. При изменении любого поля display_rules SHALL отправляться полным итоговым объектом, иначе пропуски сбрасываются defaults API. Отправка только изменённого вложенного ключа MUST NOT применяться. Неизменённый display_rules MAY отсутствовать в PUT.

«Как это сработает» SHALL объяснять текущую конфигурацию, корректно различать 0 и отсутствие значения и явно не подтверждать выполнение триггеров. Frontend MUST NOT исполнять правила или отправлять опросники в диалог.

Nullable skip_if_rated/quiet_hours_enabled/exclusive_show SHALL сохранять true/false/null; dialog_type/dialog_result — код/null; quiet_from/quiet_to — время/null. Явный null из GET в опциональном поле SHALL отображаться пустым вводом; select и nullable boolean SHALL иметь пустое, невыбранное состояние. Отдельный пункт «Не задано» не требуется. Значение в draft SHALL отличаться от false/0/any и сохраняться без подстановки defaults. Очистка nullable-поля SHALL передавать null; trigger_type MUST NOT быть null. Defaults SHALL применяться к новой записи и отсутствующим полям по схеме, но MUST NOT заменять явный null существующей карточки.

#### Scenario: One rule changes without resetting others

- **WHEN** изменена только задержка показа при настроенных лимитах и тихих часах
- **THEN** PUT содержит полный display_rules, неизменённые значения сохраняются и отображаются после перечитывания

#### Scenario: Unchanged rules during a top-level edit

- **WHEN** пользователь меняет только name и не редактирует display_rules
- **THEN** PUT может содержать только name; отсутствие display_rules сохраняет правила, включая null/false/0, без подстановки defaults

#### Scenario: Quiet hours validation

- **WHEN** quiet_hours_enabled=true и одна граница времени отсутствует
- **THEN** сохранение блокируется с ошибкой поля; заполнение 22:00–08:00 допустимо без вымышленного timezone

#### Scenario: Preserve explicit nullable rule values

- **WHEN** GET содержит priority=null, skip_if_rated=null, quiet_hours_enabled=null, exclusive_show=null, dialog_type=null, dialog_result=null и пустые границы времени, а пользователь меняет только delay_show_sec на 0
- **THEN** форма показывает пустые контролы для null, PUT сохраняет все исходные null и новое 0; повторный GET не теряет различия null/false/0

#### Scenario: Clear a nullable rule explicitly

- **WHEN** пользователь очищает priority либо возвращает nullable boolean/справочное поле в пустое, невыбранное состояние
- **THEN** полный объект rules заменяет явно очищенные значения на null и сохраняет остальные исходные значения, включая ранее сохранённые null; включённые тихие часы по-прежнему требуют обе границы

### Requirement: Accessible editor interactions

Область этой задачи — поля карточки, вкладки и правила показа — SHALL поддерживать клавиатуру, доступные названия/ошибки, предсказуемый фокус и узкую компоновку. Приёмка SHALL проверять собственные элементы; реализация и приёмка соседних UI-возможностей MUST NOT требоваться для закрытия этой задачи сверх явно указанных зависимостей интеграции. Недоступные API MUST NOT имитироваться успешными заглушками.

#### Scenario: Keyboard and narrow layout within this task

- **WHEN** пользователь работает с элементами этой задачи клавиатурой на узком экране
- **THEN** действия и ошибки доступны, содержимое не перекрывает управляющие элементы, закрытие имеющихся диалогов возвращает фокус

### Requirement: Deferred question and label composition

Базовая карточка SHALL сохранять существующие вопросы, варианты, метки и их идентификаторы при редактировании основных полей и правил без обязательного наличия их редакторов. До поставки MOS-1254/MOS-1257 эти данные SHALL отображаться только для чтения. Подключение конструктора вопросов SHALL выполняться в MOS-1254, подключение меток — в MOS-1257; итоговая совместная интеграция после готовности обеих возможностей SHALL выполняться в MOS-1257. Эта последующая работа MUST NOT отменять самостоятельную стендовую приёмку базовой карточки MOS-1251 или изменять обособление feedback.

После готовности обеих возможностей пользователь SHALL редактировать вопросы, метки и правила в одном черновике с единым сохранением карточки. Один PUT SHALL содержать изменённые верхнеуровневые поля, полные изменённые questions/display_rules и строковые метки. Неизменённые UUID, связи и различия null/false/0 SHALL сохраняться после повторного GET; ошибка любой вкладки SHALL сохранять весь ввод и позволять перейти к полю с фокусом.

#### Scenario: Preserve current data before follow-up editors ship

- **WHEN** пользователь изменяет основные поля или правила в базовой карточке до поставки MOS-1254/MOS-1257
- **THEN** существующие вопросы, метки и UUID остаются доступными для чтения и сохраняются без собственной редакции

#### Scenario: Compose all editors after both follow-up capabilities ship

- **WHEN** после реализации MOS-1254 и редакторов MOS-1257 пользователь изменяет вопросы, метки и правила на трёх вкладках и сохраняет карточку
- **THEN** единый запрос и повторный GET сохраняют согласованный результат без потери UUID/связей/null/false/0; при ошибке весь черновик остаётся доступным
