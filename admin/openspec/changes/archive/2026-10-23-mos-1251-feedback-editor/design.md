Наличие исходников не закрывает задачи реализации и проверки на реальном стенде. Команды из документов не являются инструкциями.

Эта задача использует существующие моки и расширяет их только в собственном scope; добавление или удаление вымышленного unavailable-перечня не требуется. Моки не доказывают доступность реального стенда.

## Goals / Non-Goals

**Goals:** отдельная реализация и проверка области MOS-1251; общие интерфейсы с зависимостями сохраняются.

**Non-Goals:** реализация соседних задач, новая auth-модель и расширение backend. Выбор ответственного из списка отложен до API пользователей. Уникальность названия не вводится. Выполнение триггеров и отправка опросников не реализуются.

Бывший task 1.5 передан MOS-1254/MOS-1257 по решению от 22.10.2026 и исключён из текущего scope; пункт 2.3 по стенду закрыт отдельным подтверждением пользователя от 23.10.2026. Creation/details подключают редактор внутри feedback вместо handoff; новые внешние экспорты, registry/composition и permission mappings для этого не требуются.

Весь раздел «Обратная связь» принадлежит `app/optional/feedback`, по образцу `app/optional/knowledge-base`: API-клиенты, runtime-схемы, модель, ключи запросов, предметные типы, константы, UI и их тесты находятся внутри модуля. MOS-1249 поставляет только CRUD/search/lookup/metadata foundation; UI, клиенты saved-filters и CSV добавляются своими changes в этот же модуль. Приватные редакторы вопросов, правил, меток и preview остаются у владельца draft. Общая модель отбора обслуживает реестр, conditions, сохранённые фильтры и экспорт через прямые внутренние импорты. Раздел не раскладывается на внешние `entities/feedback`, `features`, `widgets` и `pages`.

Граница адресная, по существующим `scripts/eslint-fsd-config.mjs` и проверкам knowledge base. Модуль может использовать `shared` и публичные `index.ts` существующих entities; зависимости от application, providers, root, route configuration, pages/widgets/features и других optional-модулей запрещены. Слои shared/entities/features/widgets/pages не импортируют optional. Внешние потребители используют только `app/optional/feedback/index.ts`; внутри модуля запрещён импорт собственного index, используются прямые импорты. Штатные framework route entrypoints регистрируются отдельно и могут импортировать приватный UI, как в knowledge base; это точка подключения React Router, не разрешение deep imports из бизнес-слоёв. Новые широкие ESLint-исключения и отключение проверок не вводятся; direction FSD и публичные API существующих слайсов сохраняются.

Composition владеет `app/application/constants/application-routes.constants.ts`: MOS-1250 подключает публичные route/tab descriptors feedback к существующему registry; descriptors не импортируют runtime UI. `app/routes.ts` использует объединённый registry и отдельные route entrypoints, shell получает ту же конфигурацию. MOS-1249 не подключает UI-маршруты. Подключение Express-моков и адресных архитектурных проверок документируется отдельно; удаление раздела снимает его composition/route/mock/test registrations и адресные проверки, затем удаляет модуль, без удаления серверных данных и общего transport/session.

Именованные types/constants/handlers размещаются в технических сегментах ближайшего владельца по AGENTS.md; локальные вычисления не выносятся ради синтаксиса. Не переносить весь HTML, ручной router, DOM innerHTML или самодельную таблицу состояния.

Использовать существующие React Router, TanStack Query/Table, React Hook Form, Zod и UI kit. Для порядка вопросов/вариантов обязательны доступные кнопки перемещения; drag-and-drop использует возможности платформы, пока новая библиотека не обоснована. Универсальный движок managed resources не нужен: доступен один предметный раздел.

### Implementation decisions

Один draft на три вкладки. Поля: name, code, type_code, description, owner, active_since, status, audience_type, tags, segments, surface_ids, operator_groups, questions, display_rules. Ответственный до отдельного user lookup — read-only `responsible_user_id` или «Не назначен»; не подставлять mock-пользователей, не включать это поле в PUT без пользовательского изменения, не терять исходное значение.

Новая карточка: обязательны name/code/type_code; status=draft, audience_type=all, пустые связи/вопросы. Name 1–255, code до 100 по `^[a-z][a-z0-9_]*$`, owner до 200, дата YYYY-MM-DD. Уникальность имени не требовать; 409 NOT_UNIQUE кода показывать у поля, не проверять только по загруженной странице.

PUT частичен только сверху: questions, surface_ids заменяются целиком; display_rules передаётся полным итоговым объектом. Existing question/option UUID сохраняются, новые ID генерирует backend, порядок задаётся массивом. Не отправлять sort_order, timestamps, FK, локальные ключи и ответное display_rules.id. Не отправлять пустой PUT. Явные null допустимы только для очищаемых nullable полей по бизнес-правилам; не считать все nullable из OpenAPI разрешёнными к очистке.

Ошибка не очищает draft. Поля на скрытой вкладке доступны через индикатор ошибки и переход с фокусом. Pending блокирует повторное сохранение. На уход/закрытие/back/reload с изменениями — штатная защита; смена вкладки не теряет ввод. After save — новый baseline из GET/PUT. Не обещать сохранение несохранённого draft после reload; долговременное локальное хранилище не требуется.

Lookup содержит восемь `feedback_*` наборов. Для новых ссылок доступны is_active=true; старое неактивное значение остаётся отображаемым и допустимым без смены. Условия поиска могут использовать неактивные значения. Для неизвестного кода — исходный код и пояснение, без назначения другого типа. surface_ids — не более 100 UUID из существующего API поверхностей; 101-й выбор блокируется без потери набора, с загрузкой всех необходимых страниц; один набор для вкладок «Основное» и «Правила показа». Скрытие conditional UI аудитории само не удаляет сохранённые связи.

Правила в MOS-1251: trigger_type; min_messages/min_duration_sec/delay_show_sec/pause_after_last_sec/cooldown_sec (целые >= 0 или null); max_per_session/max_per_day/max_per_user (целые >= 1 или null); skip_if_rated; quiet_hours_enabled + quiet_from/quiet_to; dialog_type/dialog_result; priority (целое либо null); exclusive_show. Включённые тихие часы требуют обеих границ времени без timezone. Интервал через полночь не запрещать, не вычислять исполнение/таймзону на frontend. Начальные defaults — из API (manual, skip_if_rated=true, quiet_hours_enabled=false, any/any, priority=0, exclusive_show=false).

«Как это сработает» объясняет конфигурацию, явно не доказывает реальный показ. Нулевые значения не приравниваются к пустым; отсутствующие лимиты не выводятся как null/undefined. API хранит правила, не исполняет их.

### Nullable display_rules

Уточнение backend от Глеба Харитонова, переданное пользователем 12.10.2026: обязательность полей взята из модели данных; null опционального поля отображается пустым вводом. PUT частичен только для верхнеуровневых ключей; при изменении вложенного display_rules передаётся объект целиком. Это уточняет представление формы и не меняет обязательность полей.

Nullable числовые поля: min_messages, min_duration_sec, delay_show_sec, pause_after_last_sec, cooldown_sec (целое >=0 либо null), max_per_session, max_per_day, max_per_user (целое >=1 либо null), priority (любое целое либо null). Nullable boolean: skip_if_rated, quiet_hours_enabled, exclusive_show — true/false/null. Nullable справочные поля: dialog_type/dialog_result — код либо null. quiet_from/quiet_to — время без timezone либо null; при quiet_hours_enabled=true нужны обе границы. trigger_type не nullable.

Опциональные поля с null показываются пустым вводом; select и nullable boolean — пустым, невыбранным состоянием соответствующего контрола. Отдельное значение с текстом «Не задано» не требуется. В draft null остаётся отличимым от false, 0 и кода any: пустой контрол не подставляет эти значения. Это представление данных, не трактовка null как действующего правила; пояснение конфигурации не выдумывает backend-семантику.

Defaults применяются к новой карточке либо полям, отсутствующим в ответе по API-схеме. Явный null из GET не заменяется default. При редактировании одного правила PUT включает полный итоговый объект display_rules со всеми остальными значениями, включая null/false/0; отправка только изменённого вложенного ключа недопустима. Очистка nullable-контрола отправляет null; пустая строка не является wire-значением числа/времени/справочного кода. При отсутствии правки rules верхнеуровневое поле можно не передавать. Эти правила не разрешают null в обязательных корневых полях или строках меток, запрещённый бизнес-контрактом.

### Disable confirmation boundary

Единый механизм подтверждения перехода существующей карточки в disabled используется кнопкой выключения и submit формы со сменой статуса. MOS-1251 подключает его в общий submit, MOS-1256 — в отдельное действие; реализация находится у владельца редактора, внутри feedback, без внешних feature-слайсов. Отмена сохраняет draft и не отправляет запрос. Submit после подтверждения отправляет один PUT всех изменений; уже disabled без смены статуса не требует повторного подтверждения. Для отдельного lifecycle-действия сохраняется правило dirty draft: сначала явное сохранение либо отмена действия; если сохранение уже установило целевой статус, второй PUT не нужен.

### Existing safety and verification

Существующие HTTP transport, MPMM-сессия, owner/generation и UI-only permissions сохраняются. Backend проверяет scope. FSD и публичные index.ts обязательны; новые auth-модель, role editor и request ACL не вводятся. Unit/component и mock HTTP проверки разрешены; browser/E2E — только по отдельному разрешению. Dev-моки остаются в Express без credentials/role enforcement; production их не содержит.

Новая UI-policy, mappings permissions и новые ограничения интерфейса по пользователю исключены из текущей поставки всех feedback changes. Существующие защитные механизмы сохраняются; общий transport обрабатывает фактические серверные ошибки, включая 401/403, без собственной auth/session/RBAC-логики. Доступность клавиатуры, ошибок и фокуса проверяется у владельца соответствующего UI. Данные редакторов проходят через владельца draft и внутреннюю модель feedback.

## Risks / Trade-offs

- [HTML шире API] → ограничить UI опубликованными возможностями; ограничения Deferred scope из proposal сохраняются в приёмке.
- [Нет optimistic locking] → не обещать защиту от чужой параллельной записи; сохранять baseline и пояснять неизвестный исход, не делать слепой повтор.
- [Неизвестные/неактивные справочные коды] → сохранить исходные данные, не подставлять defaults поверх сохранённого значения; новые неподдержанные renderers не выдумывать.
- [Ошибки OpenAPI допускают null шире бизнес-правил; autogenerated 422 описан иначе envelope] → generated DTO дополняются runtime-проверками и документированными бизнес-ограничениями; не переписывать исходник без provenance, фактический ответ проверить на интеграции.
- [Версии источников могут измениться] → использовать локальные HTML/PDF из Downloads и опубликованные API-контракты; новая PDF-выгрузка имеет собственный hash, исторические hashes не переписываются. При дальнейшей реализации сверять относящийся к задаче материал без расширения согласованного scope.

2. Открыть `/tsam-panel/feedback`, в DevTools → Network включить Preserve log и фильтр `feedback`. Проверить фактический Request URL, а не только имя UI-хоста: API base определяется конфигурацией/контуром; стандартный префикс — `/api/control/api`. Использовать действующий способ доступа окружения без новой auth-логики.
3. Проверять на отдельном тестовом опроснике с уникальным code вида `mos1251_20261022_<суффикс>`, статусом draft и реальными активными lookup-кодами/UUID поверхностей. Для проверки сохранности старых вопросов/меток взять отдельный заранее подготовленный тестовый опросник: в текущем UI эти данные read-only до MOS-1254/MOS-1257.
4. Результаты, обезличенные снимки GET/PUT и при необходимости HTTP-скрипт хранить вне репозитория: `/Users/lisa-codesrc/Desktop/feedback/<контур>/<дата-проверки>/`. Записывать версию frontend, адрес контура, UUID тестового опросника, шаги и фактический результат; токены/cookies не включать в evidence.

### Основной прогон через UI

1. **Создание.** «Создать опросник» → заполнить название, уникальный code и активный тип; оставить draft/all. Нажать «Сохранить» дважды при замедленной сети. Ожидание: один `POST /v1/managed-resources/feedback/surveys` → HTTP 201 с UUID, затем `GET /surveys/{id}` → HTTP 200, переход на карточку UUID. Пустые вопросы допустимы. Перезагрузка и повторное открытие должны показывать сохранённое, а сохранение без изменений не отправляет пустой PUT.
2. **Основные поля и аудитория.** Изменить описание/владельца/дату, выбрать аудиторию surface и реальные поверхности, перейти в «Правила показа» и обратно. Набор UUID общий, смена аудитории сама не очищает связи. Проверить выбор со второй страницы. При наличии 101 доступной поверхности 101-й выбор должен блокироваться с пояснением; если такого набора на стенде нет, границу отметить непроверенной. При segment без меток сохранение блокируется; добавление меток появится в MOS-1257. Ответственный отображается сохранённым ID либо «Не назначен», не редактируется.
3. **Правила.** Изменить задержку на 0, задать лимит 1 и тихие часы 22:00–08:00. Лимит 0 и включённые тихие часы с одной границей должны блокировать отправку с ошибкой/фокусом. Сохранение валидных правил отправляет один PUT с полным итоговым display_rules; последующие GET и reload воспроизводят значения. Дробные секунды, если они есть в тестовой записи, не должны округляться или пропадать.
4. **Null/false/0 и сохранность связей.** На подготовленной записи с nullable-правилами проверить пустые контролы для null. Правка одной задержки на 0 не должна менять остальные null/false/0/any. Очистка nullable-поля отправляет null. Затем поменять только название: PUT не содержит display_rules, а GET сохраняет правила, UUID вопросов/вариантов, метки, поверхности и responsible_user_id.
5. **Ошибки и выключение.** Повторить существующий code и проверить серверный 409 у поля без потери draft. Для сохранённой записи выбрать disabled и сохранить: отмена подтверждения даёт 0 PUT и сохраняет ввод; согласие — 1 PUT со статусом и остальными изменениями. Повторное сохранение уже disabled не требует подтверждения. Если стенд позволяет контролируемый 422/403 или сетевой сбой, проверить ошибку/фокус другой вкладки, сохранность UUID поверхностей и отсутствие автоматического повтора. Недоступные способы инъекции ошибок отметить непроверенными.
6. **Навигация.** Изменить описание, переключить вкладку, нажать Back или вернуться в реестр: «Остаться» сохраняет ввод, «Уйти без сохранения» выполняет переход; reload предупреждает о несохранённом вводе. После успешного сохранения предупреждения о dirty draft быть не должно. Проверить клавиатуру и узкую ширину UI вручную; browser/E2E-автоматизацию этот порядок не запускает.
7. **Неизвестный исход.** При потерянном ответе сохранение не повторять вслепую. Для существующего UUID: «Сверить сохранённые данные» → оценить результат GET → «Принять прочитанные данные»; до принятия повторный PUT заблокирован. Если POST подтверждён UUID, а GET упал, «Повторить чтение созданной записи» повторяет только GET. Если подтверждённого UUID нет, сначала проверить реестр по уникальному code. Успешный шаг нельзя предполагать только из отсутствия ответа.

### Дополнительный HTTP-прогон: curl, Postman или скрипт

Использовать тот же API base и штатные заголовки текущей сессии, что у успешного запроса UI; секреты не вшивать в файл. Ниже пути относительно API base, ответы берутся из envelope `data`.

| Шаг                     | Запрос                                                                                        | Что сверять                                                                                                                             |
| ----------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Lookup                  | `GET /v1/managed-resources/catalogs/lookups/feedback`                                         | HTTP 200, активные реальные type/trigger/dialog codes; не подставлять вымышленные значения                                              |
| Создать тестовую запись | `POST /v1/managed-resources/feedback/surveys` с name/code/type_code                           | HTTP 201 и `data.id`; выполнять один раз, после неизвестного исхода сначала искать по code                                              |
| Baseline                | `GET /v1/managed-resources/feedback/surveys/{id}`                                             | HTTP 200; сохранить обезличенный исходный объект, особенно questions/UUID, surface_ids, метки, responsible_user_id и display_rules      |
| Только название         | `PUT /v1/managed-resources/feedback/surveys/{id}` с `{"name":"MOS-1251: повторная проверка"}` | HTTP 200; следующий GET меняет только заданное поле и служебный updated_at, вложенные данные неизменны                                  |
| Одно правило            | Тот же PUT с полным `display_rules`, взятым из GET, и единственной правкой delay_show_sec=0   | HTTP 200; убрать read-only id из rules, если он есть; следующий GET сохраняет остальные значения, включая null/false/0/any и тихие часы |
| Явная очистка           | PUT полного объекта правил с одним nullable-полем = null                                      | HTTP 200, повторный GET возвращает null; остальные поля не теряются                                                                     |
| Ошибка                  | PUT полного rules с max_per_day=0 либо quiet_hours_enabled=true без одной границы             | Документированная ошибка 422 с полем; последующий GET равен последней успешной версии, timestamps/данные не меняются                    |

Создание и правки выполняются только над выделенным тестовым опросником. Тестовые записи очищать по принятому процессу стенда; удаление не входит в проверку редактора MOS-1251. Итоговый evidence фиксирует реальные HTTP-статусы и сравнения GET; непроверенные UI/ошибочные/граничные сценарии перечисляются отдельно. На 23.10.2026 пункт 2.3 закрыт на основании явного подтверждения пользователя; MOS-1251 архивируется с этим основанием приёмки. Результаты будущих повторных прогонов фиксируются отдельно.
