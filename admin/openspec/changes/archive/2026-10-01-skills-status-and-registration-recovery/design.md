## Context

См. proposal.md. Изучены текущие клиенты skills, URL-фильтры, мастер и сохранение, обработка 422 редактора карточки, генератор типов, contract/server-тесты и контрактные документы.

- В новом файле добавлены SkillStatus (`draft`, `checking`, `training`, `autotest`, `sandbox`, `review`, `whitelist`, `prod`), обязательный status в list/detail, status query, POST изменения статуса, пять операций Analytics и 32 новые схемы. Исчезновение PUT intents и девяти схем пользователь явно запретил переносить в объединённый контракт.
- `registry-search-params.ts` сейчас удаляет status; list/detail runtime-схемы и fixtures его не требуют. Запрос/ключ Query и сброс page должны изменяться вместе с фильтром.
- `use-registration-save.ts` держит попытку только в ref. При PUT 422 состояние write-error блокирует все шаги, а повтор использует прежнее тело. Схожая обработка loc/msg уже есть в редакторе фраз карточки.
- RHF уже владеет одним draft; установлены Query, Router и Zod. Persist/store-библиотеки нет. В проекте есть только простое защищённое localStorage-чтение/запись отметки справки, не переносимый механизм черновиков.
- Mock router и тесты требуют реализации всех бизнес-операций объединённого документа. Простой импорт Analytics/status без обновления mock нарушит эту гарантию; расширение тестового сервера включено как совместимость, не как UI аналитики.

## Goals / Non-Goals

**Goals:** сохранить прежние API и публичные FSD-границы; восстановить даже невалидный незавершённый ввод; не превращать восстановление в повтор POST; исправлять фразы после доказанного отказа без потери версии/ID.

**Non-Goals:** глобальный store формы, синхронизация между устройствами, авторизация, серверный draft, браузерные тесты, новая lifecycle-машина, сортировка по статусу, UI Analytics. Архив не переоткрывается.

## Decisions

### 1. Объединённый контракт, а не замена файла

Новая выгрузка задаёт обновлённые paths/schemas; поверх неё сохраняются ровно согласованные ранее PUT intents, SkillResponse.intents (properties и required), девять зависимых схем. Не выполнять универсальный deep merge массивов required/parameters: сравнить предметные различия и проверить каждое сохранённое расширение. Итог 40 операций, 156 схем; 39 бизнес-операций. Обновить README, Skills/Domains standalone, добавить Analytics standalone со всей транзитивной зависимостью схем; прочие standalone проверить на совпадение. Документировать происхождение в репозитории, не оставлять генерацию зависимой от Downloads. Генератор запускается штатно, generated-файл вручную не правится.

Согласованное уточнение при реализации: при расхождении описаний Analytics и формальных responses приоритет имеют JSON-схемы. Валидационные 422 используют HTTPValidationError.detail, несмотря на prose code/errors; формально не описанные 400/409 остаются документированными mock-конвенциями. Исходный OpenAPI не исправляется.

Mock: сохранить HTTP transport, router, schema validation, idempotency и seed ownership. Добавить серверные status/filter и контрактно валидные Analytics fixtures/операции; состояние board сохраняется между запросами и сбрасывается при restart. Семантика изменения статуса и демо-аналитики, не определённая схемой, остаётся явно mock-конвенцией. Не выводить из неё допустимые production-переходы и не ослаблять исчерпывающую проверку покрытия.

### 2. Серверный статус и URL

Публичный SkillStatus выводится из generated-схемы; runtime enum и русские подписи принадлежат entities/skill. Колонка показывает текст (не только цвет). `draft` — «Черновик», `checking` — «Проверка», `training` — «Обучение», `autotest` — «Автотесты», `sandbox` — «Песочница», `review` — «Ревью», `whitelist` — «Белые списки», `prod` — «Прод».

Передавать status на сервер, включать его в Query key, поддержать сочетания query/domain/team/sort/page. Неизвестный status в URL удалять, пустой выбор означает все статусы; изменение фильтра сбрасывает page. Поддерживаемый sort остаётся прежним: произвольная строка схемы не подтверждает сортировку по status. По согласованному замечанию ревью неизвестное строковое значение status в списке не отклоняет весь ответ: read-model Skill расширяет только это поле до string, сохраняет исходное значение, а строка каталога показывает «Неизвестный статус» без подмены draft/prod и без потери остальных навыков, total или пагинации. Отсутствующий и нестроковый status списка остаются ошибками контракта. SkillStatus для запросов/фильтра, generated/OpenAPI и строгая проверка status в карточке не меняются; новые значения ответа не добавляются в фильтр. Не выводить lifecycle-команды по одному status.

### 3. Один versioned localStorage snapshot у владельца мастера

Использовать штатный localStorage и небольшую Zod-схему чтения в `features/skill-registration/model`, не добавлять Zustand/persist-пакет и второй источник draft. RHF остаётся живым состоянием формы. Один snapshot на браузерный origin + deployment/API context содержит версию формата, сырой draft, шаг и attempt (ID, этап, версия, неизменяемое тело/ключ PUT). Неполный draft проверять по структурной схеме, не по бизнес-валидности финального submit; иначе восстановление пустого обязательного поля теряется.

Читать лениво один раз, затем восстанавливать RHF и шаг; не перезаписывать snapshot defaults до завершения чтения. Сохранять при изменении полей/шага штатной подпиской RHF, не через polling. Данные формы не отправляются в URL. При возврате справочники читаются заново, выбранный contact проверяется только после загрузки полного состава команды. Не сохранять server options, токены, заголовки auth или Query cache.

Перед POST синхронно фиксировать create-pending; после reload этот этап трактуется как unknown, без повторного POST. Подтверждённый ID фиксировать до GET, версию/тело/ключ PUT — до отправки PUT. При восстановлении незавершённого GET/PUT предлагать явное продолжение; автоматически запрос записи не отправлять. PUT после сетевой неопределённости повторять только с сохранённым телом/ключом/версией. Не восстанавливать network Promise или Error object.

Успех: записать terminal marker с ID, убрать draft и перейти в карточку. Если очистка не удалась, terminal marker запрещает повторное создание при следующем открытии. Ошибки хранения показываются пользователю; если невозможно записать защитное состояние перед мутацией, не начинать эту мутацию, чтобы после reload старый редактируемый draft не стал вторым POST. Текущий ввод и dirty-guard остаются доступны. Повреждённый/неподдерживаемый snapshot не исполняется и не затирается молча: показать ошибку и явное удаление локальной записи с предупреждением о возможной серверной записи.

Дать отдельное подтверждаемое удаление локального draft. Оно не удаляет серверный навык и не доказывает, что неизвестный POST не создал ресурс. Предупредить об общем браузерном профиле и риске дубля после сброса unknown. Автоматического срока истечения нет; одна локальная запись не обещает слияния параллельных мастеров. Не перетирать обнаруженное внешнее обновление в другой вкладке молча: предложить перечитать локальную запись до следующего сохранения.

Альтернатива sessionStorage отвергнута: не покрывает повторное открытие после закрытия вкладки. Серверный черновик не выбран: обязательная анкета не является API сохранения неполного draft. Persist-библиотека для одной формы не уменьшает предметную логику восстановления.

### 4. Различить rejected PUT и неизвестный исход

При подтверждённом 422 PUT сохранить ID и expected_version, разрешить редактировать только группы/фразы. Поля уже созданной анкеты и подключения остаются заблокированными; их изменение выполняется в карточке. Ошибки `HTTPValidationError.detail` сопоставлять через loc с названием/текстом группы, несколько msg объединять, неизвестный путь показывать общей ошибкой. Чистый mapping вынести из соседней feature в нижележащего предметного владельца, если его можно переиспользовать без формы/HTTP; обе формы применяют результат сами.

После исправления применить общую локальную схему фраз, построить PUT из нового draft с прежней версией. Изменившееся тело получает новый Idempotency-Key; одинаковый запрос сохраняет прежний ключ. Новый POST не вызывается. Новое тело и ключ persist до отправки. Сетевой отказ/невалидный ответ/204 не доказывает отклонение: сохраняется неизменённая попытка, до подтверждённого отказа её тело не редактируется. Конфликт версии не снимается автоматически GET+новой expected_version. После повторного GET ошибка не сбрасывает сохранённый ID.

## Risks / Trade-offs

- [Общий браузерный профиль] → видимое пояснение и явное удаление локальной записи, без фиктивной изоляции по пользователю.
- [Закрытие после server commit до записи ID] → unknown сохранён до POST, повтор создания запрещён; backend replay по-прежнему не гарантируется.
- [Quota/disabled storage/повреждение] → явная ошибка, сохранение живого ввода, запрет неподтверждённой долговременной защиты перед записью; не обещать восстановление, которого нет.
- [Две вкладки] → внешние изменения не сливаются и не затираются молча; полноценная многопользовательская синхронизация не обещается.
- [Полный импорт расширяет mock-покрытие] → отдельные контрактные server-проверки status/Analytics, без новых UI-сценариев и без исключений новых бизнес-операций из coverage.
- [Новый required status] → обновить всех потребителей Skill/SkillDetails и fixtures, включая регистрацию поверхностей, а не только таблицу.

## Migration Plan

1. Добавить контракт/документы, сгенерировать типы, обновить mocks и все затронутые fixtures; подтвердить сохранение intents и исчерпывающее покрытие.
2. Подключить статус и URL-фильтр без остальных отложенных колонок/команд.
3. Разделить rejected PUT и unknown; добавить исправление фраз и persist-снимок согласованной модели попытки.
4. Проверить reload/remount, утрату ответа, частичную запись, ошибки хранения, смену контакта и переход в карточку unit/component/server-тестами. Browser не запускать.
5. Откат UI не удаляет созданные ресурсы. Версия localStorage позволяет распознать несовместимый snapshot без его автоматического исполнения или создания дубликата.
