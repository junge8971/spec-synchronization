## Context

См. proposal.md — Why. На момент анализа общий контракт содержит 64 операции и 262 схемы; новая выгрузка — 109 операций и 347 схем. Разница: четыре PUT-алиаса, 43 managed-resource операции, отсутствие двух локально принятых экспортных методов и переименование DTO saved filters из-за коллизии имён. Остальные существующие операции отличаются security; POST saved filters также меняет ссылку на ответ.

OpenAPI определяет wire DTO; CRUD-документ — семантику managed resources. Скриншоты объясняют миграцию с PATCH из-за WAF, но не доказывают доступность конкретного стенда. Принятые исключения перечислены в `docs/api/contracts/README.md`.

`scripts/generate-api-types.mjs` читает общий контракт. `mocks/app.mjs` регистрирует все его операции по operationId и падает при отсутствии handler. Idempotency для навыков/доменов включается по точному списку operationId, пока только PATCH. Это делает простое добавление JSON несовместимым с запуском dev.

## Goals / Non-Goals

**Goals:** атомарная совместимость контрактов, типов, работающих редакторов и локального сервера; проверяемая граница между опубликованным API и реализованными моками.

**Non-Goals:** универсальный CRUD UI, исполнение правил вложений, A/B runtime, изменение MPMM, миграции backend, удаление PATCH из транспортных типов или из опубликованного контракта. Полноценные managed-resource handlers и новые клиенты остаются в отдельных changes.

## Decisions

### 1. Объединение с узкими сохранёнными дополнениями

Взять новую выгрузку целиком и сохранить только документированные отличия: POST `/dialogs/v1/dialogs/export`, GET `/dialogs/v1/dialogs/{chat_id}/export` и четыре схемы `DialogExportRequest`, `DialogExportField`, `DialogErrorEnvelope`, `DialogValidationDetail`; нормализовать security к уже принятому AND двух X-токенов. Полные пути сохраняют `/api/control/api`. Не переносить все старые schemas вслепую и не менять отдельный `mpmm-auth.openapi.json`.

Ожидаемый результат — 111 операций и 351 схема. Проверять также точное множество method/path, замкнутость ссылок и сохранность бизнес-схем: одних счётчиков недостаточно. Новые длинные имена двух SavedFilterResponse сохранить как выдал backend; существующему UI дать ссылку на dialog DTO через его нынешний локальный тип. Wire-поля dialog DTO не изменились.

Альтернатива прямой замены удаляет действующий экспорт; слияние всех старых схем сохраняет устаревшие неоднозначные имена.

### 2. Секционные документы и источник CRUD

Пересобрать существующие секционные JSON как точные подмножества общего с транзитивным замыканием schemas. Добавить `managed-resources.openapi.json` для всего `/api/control/api/v1/managed-resources/` (43 операции), обзор `managed-resources.md` и локальную копию `crud-api.md` в `docs/api/contracts/`. Один общий раздел соответствует общим metadata, catalogs и saved filters; дробление на пять дублирующих контрактов пока не требуется.

Исходный CRUD-документ сохранять без смысловой редакции. Зафиксировать исходный hash; если форматирование меняет байты, различать hash входного файла и копии. README и аудит должны отличать присутствие контракта от реализации UI/моков. Новый исходник в корне не удалять и не использовать как обязательный runtime/typegen input.

### 3. PUT в предметных клиентах

Менять метод в `skill-details-client.ts` и `skill-domain-client.ts`, включая общую запись параметров подключения навыка. Сохранить body, expected_version, Idempotency-Key, Zod-валидацию, UI ошибки и ручной retry. Не вводить глобальную замену PATCH внутри transport и fallback PUT → PATCH: это скрывает реальный метод и рискует повторить мутацию.

Четыре PUT-операции в новой выгрузке используют те же request/response schemas, что PATCH. Для managed resources PUT тоже частичный сверху, но вложенные списки и объекты заменяются согласно CRUD; имя схемы `*Patch` и код `EMPTY_PATCH` не переименовывать. Новые managed-resource запросы в этой поставке не создаются.

### 4. Моки: алиасы и явно ограниченная недоступность

Четыре PUT operationId направить к существующей логике domains/skills/teams/member без копирования обработчиков. При реализации обнаружено, что прежние handlers домена и анкеты навыка не проверяли expected_version. Общая логика PUT/PATCH дополнена проверкой 409 до записи; все ссылки навыка также проверяются до изменения состояния, чтобы ошибочный запрос не сохранял часть связей. Это обеспечивает сценарии версии и атомарности из delta-spec. PATCH остаётся рабочим. Для PUT навыков и доменов явно подключить существующий idempotency middleware; ключ остаётся scoped по method/path/key, межметодный replay не обещается.

Для ровно 43 новых managed-resource method/path создать явный реестр unavailable-операций с ответом 501 и обычным error envelope. Сохранить входную контрактную валидацию и demo scenarios. Этот ответ — документированная dev-конвенция, не дополнение backend OpenAPI. Не добавлять общий fallback для любого неизвестного operationId и не пропускать весь префикс: случайно потерянный handler старого API или новая неучтённая операция должны по-прежнему ломать проверку покрытия.

Проверить, что импорт новых schemas не ломает Ajv compilation, demo-каталог и existing handlers. При будущем подключении полноценной CRUD-операции удалить именно её из unavailable-реестра. Сохранить особый режим `/me`, credential-free бизнес-моки и production isolation.

### 5. Совместимость действующих specs и feedback planning

Действующие specs skill-card-editing, skill-connection-settings и skill-domain-management явно требуют PATCH. Их полные затронутые requirements включены в delta этого change с единственной заменой HTTP-метода на PUT; остальные сценарии сохранены. Основные specs обновляются штатной синхронизацией после реализации.

Во время реализации обновить существующие planning artifacts пяти changes из proposal: источники на локальные актуальные документы, HTTP PATCH на PUT. Обновлять формулировки сценариев и tasks согласованно, но не переименовывать backend `*Patch`/`EMPTY_PATCH`, не менять бизнес-правила и не отмечать чужие задачи выполненными. `mos-1249-feedback-api` должен использовать уже обновлённый контракт и заменить соответствующие unavailable handlers полноценными; это не выполнение его клиентов/UI в текущем change.

В текущем propose создаются только документы этого change. Изменения соседних plans перечислены как задачи будущего apply.

## Risks / Trade-offs

- [Потеря экспортного дополнения или auth-нормализации] → точные regression assertions и документация происхождения исключений.
- [PUT обходит idempotency] → повтор того же запроса и конфликт тела с тем же ключом проверяются через HTTP.
- [Новые schemas ломают dev startup] → запуск test app и компиляция валидаторов входят в проверки; общий fallback запрещён.
- [501 воспринимается как backend-контракт] → документировать исключительно как mock convention; успешные CRUD fixtures не выдавать.
- [Старый fingerprint DTO ломается из-за rename] → обновить осмысленный эталон с проверкой сохранности полей, не удалять утверждения ради зелёного теста.
- [Стенд отличается от файла] → локальная проверка не закрывает gate реального API/WAF; доступность подтверждать отдельно перед выпуском.

## Migration Plan

1. Обновить документы/контракты и DTO с сохранёнными исключениями.
2. В той же поставке переключить клиентов, подключить mock aliases и ограниченные unavailable handlers.
3. Согласовать feedback planning и tests. Выполнить `yarn api:check`, `yarn typecheck`, `yarn lint`, `yarn test`, `yarn format:check`, `yarn build`; browser/E2E не запускать.
4. До выпуска отдельно подтвердить PUT на целевом стенде; не считать локальные тесты доказательством отсутствия WAF-блокировки.
5. Rollback — предыдущий frontend bundle и согласованный набор контрактов/моков. Серверные данные не удаляются; прежний PATCH bundle может снова столкнуться с WAF.
