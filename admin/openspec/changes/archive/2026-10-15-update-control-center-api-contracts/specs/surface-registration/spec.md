## Purpose

Обеспечить создание поверхностей по текущему API с корректными ссылками на ответственных пользователей и безопасным восстановлением после отказа либо неизвестного результата запроса.

## ADDED Requirements

### Requirement: Responsible assignments use business user identifiers

Регистрация SHALL выбирать обоих ответственных через существующий API бизнес-пользователей и отправлять их строковые ID в responsible.product и responsible.connection. Имя и email SHALL использоваться только для представления выбора. UI MUST NOT отправлять произвольное ФИО как ID, ограничивать выбор первой страницей либо восстанавливать ID старого черновика по совпадению имени. Старые текстовые назначения SHALL требовать явного перевыбора. Ошибка загрузки пользователей SHALL сохранять форму без синтетических вариантов. Назначение ответственного MUST NOT изменять permissions или сессию.

#### Scenario: Selected external user

- **WHEN** выбран пользователь с не-UUID строковым ID и заполнены остальные обязательные поля
- **THEN** POST содержит этот ID, а не ФИО; подтверждение выбора показывает серверные сведения без требования UUID

#### Scenario: Legacy draft

- **WHEN** восстановлен старый черновик с произвольными строками ответственных
- **THEN** форма сохраняет остальные данные, объясняет необходимость перевыбора и не отправляет старые строки как подтверждённые ID

### Requirement: Creation supports an atomic optional configuration

API-клиент и локальное API SHALL поддерживать configuration по текущему CreateSurfaceRequest. При передаче объекта SHALL применяться действующие правила конфигурации и атомарное создание; отсутствие или null SHALL сохранять backend defaults. UI без редактируемой конфигурации SHALL опускать поле, а не присылать вымышленные defaults. Создание MUST NOT подменяться последовательностью POST и скрытого PUT. После 201 SHALL сохраняться data.id и выполняться GET для подтверждения сохранённой карточки; ошибка GET MUST NOT приводить к повторному созданию.

#### Scenario: Configuration is provided

- **WHEN** API-клиент получает валидную конфигурацию вместе с данными создания
- **THEN** один POST передаёт configuration, последующее чтение отражает сохранённые настройки; отдельный PUT не выполняется

#### Scenario: Default configuration

- **WHEN** configuration отсутствует или равна null
- **THEN** применяется серверная конфигурация по умолчанию без локальной подстановки клиентом

#### Scenario: Detail cannot be read after creation

- **WHEN** POST вернул ID, а GET завершился ошибкой
- **THEN** ID сохраняется, доступен повтор только чтения, второй POST не выполняется

### Requirement: Rejections are distinct from unknown creation outcomes

UI SHALL различать подтверждённый отказ без создания и неизвестный исход. Документированные структурированные ошибки DOMAIN_ALREADY_IN_USE, неизвестного пользователя и конфигурации SHALL сохранять ввод, показывать серверную причину и связываться с полем, когда ответ содержит надёжный путь; исправление SHALL разрешать новую явную попытку без автоматического replay. Неизвестный формат ошибки MUST NOT разбираться по тексту message и MUST NOT считаться доказательством отсутствия созданной поверхности. Сетевой сбой после отправки SHALL сохранять блокировку слепого повторного создания.

#### Scenario: Confirmed domain conflict

- **WHEN** получен подтверждённый серверный отказ DOMAIN_ALREADY_IN_USE с указанием конфликтующего домена
- **THEN** форма показывает домен и ошибку, сохраняет ввод и позволяет исправить его; успешное создание не показывается

#### Scenario: Unknown responsible user

- **WHEN** сервер отклоняет назначение с надёжным указателем responsible.product или responsible.connection
- **THEN** ошибка отображается у соответствующего выбора, остальные поля не сбрасываются

#### Scenario: Lost response

- **WHEN** ответ на отправленный POST потерян
- **THEN** UI сообщает о неизвестном результате и не повторяет POST автоматически или как гарантированно безопасную попытку
