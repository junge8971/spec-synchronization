## Context

См. `proposal.md`. Текущий `/ops` имеет URL-вкладки `modules`, `stubs`, `maintenance`; все отображают «Раздел в разработке». `modules` доступна по `TSAM.Module:view`, две другие — по явному `*`. Общий application registry строит React Router Framework routes, меню, крошки и access boundary. Прямая ссылка и отказ должны по-прежнему проходить эту границу.

Снимок `docs/api/contracts/` от 26.10.2026 публикует system-state CRUD/search/summary/metadata/export, section lookups и `system-state-toggles` для saved-filters. DTO содержит `enabled`, `critical`, `is_custom`, `updated_at`, nullable `updated_by` и optional `updated_by_user`; `PUT` не описывает version/expected_version или idempotency protocol. Локальные девять операций system-state пока возвращают 501. Прежний `assistant-modules/v1` описывает другую модель с version/disable_allowed и не является заменой этому API.

Jira и аналитика описывают реальное влияние рубильников на все пользовательские сеансы, но рассматриваемый снимок не подтверждает источник состояния для каждого пользователя, отображение кодов на маршруты, propagation или server enforcement. Пользователь включил эту интеграцию в результат с явной блокировкой до подтверждения контракта, не разрешая изобретать новый API.

## Goals / Non-Goals

**Goals:** минимальная композиция независимо удаляемого модуля; серверное состояние без фиктивных успехов; совместимость `/ops`; раздельная проверка UI, локальных моков и реального применения; доступные состояния ошибок и подтверждений.

**Non-Goals:** новый auth/RBAC, роль по имени, backend-реализация рубильников или аудита, управление навыками через другой API, новый framework плагинов, автоматическое выключение по расписанию/мониторингу, pixel-perfect копирование, новый push/polling protocol или неподтверждённый API для общего меню.

## Decisions

### 1. Ownership и маршрутизация

Предметные клиенты, модели, обработчики, компоненты и тесты принадлежат `app/optional/system-state/`; server fixtures/handlers/tests — `mocks/system-state/`. Модуль использует только свой код, shared и публичные API entities; другие optional и бизнес-слайсы, shared и приложение снизу не зависят от внутренних файлов модуля. Только application composition подключает его публичный descriptor; framework route entrypoints остаются штатными. Для этого change требуется адресное расширение `code-quality-gates`, правил проекта и lint с позитивными и негативными проверками, без отключения структурных правил. Инструкция удаления перечисляет маршруты, host-подключение, mocks, test glob и адресные проверки; общие DTO и чужие разделы остаются.

Реестр находится внутри существующей вкладки `/ops?tab=modules`. Внешний `tab` сохраняет старую семантику; внутренний `kind=module|function` выбирает одну из двух новых вкладок, не перезаписывая `tab`. Карточка имеет отдельный адрес `/ops/toggles/:toggleId`, независимо загружает DTO и подсвечивает `/ops`. Создание — диалог, не маршрут `new`. При переходе назад сохраняется корректное состояние отбора; существующие `/ops/stubs`, `/ops/maintenance`, их redirect/query и остальные вкладки не меняются. Композиция на уровне приложения, а не импорт optional из `pages/operations`, связывает прежние вкладки с новым содержимым. Удаление модуля восстанавливает прежнюю заглушку. Альтернативы с новым пунктом меню или заменой всей страницы нарушают согласованную совместимость; общий plugin framework избыточен.

### 2. Разграничение управления и доступа к работе разделов

Новый реестр, карточка и все их действия остаются за существующим fallback `*`; `Module:view` не расширяет права на managed system-state. Посетитель с одним `Module:view` видит прежнюю вкладку-заглушку без запросов нового раздела. Карточка по прямому URL без `*` показывает отказ без бизнес-загрузки. Метка «Доступ только для администратора платформы» воспроизводит требование, но UI не выводит роль из `*` и не обещает доказанного backend enforcement. Проверка реального администратора и granular mapping — отдельный release gate, не новая клиентская ACL или задача добавления permissions.

После согласования отдельного источника доступности **каждый** пользователь получает разрешённый ему актуальный snapshot состояний без требования `*` на административный экран. Приложение сопоставляет только подтверждённые backend/продуктом коды с маршрутами; произвольная пользовательская запись и строка `impact` не создают новых маршрутов или runtime capability. Application composition передаёт узкий результат состояния оболочке, не заставляя другие разделы импортировать optional-модуль. Backend независимо блокирует недоступные операции и остаётся окончательным источником доступа.

В инициировавшей вкладке после подтверждённого PUT инвалидируются данные панели и запрашивается подтверждённый snapshot доступности. Другие клиенты обновляют его на следующем переходе и при возврате фокуса; прямая ссылка проверяется по свежему подтверждённому состоянию до монтирования соответствующей страницы. Постоянный polling/WebSocket и численный SLA не вводятся. Уже открытая чужая вкладка может визуально устареть до этого события; это не отменяет немедленного серверного применения. При недоступном/невалидном snapshot не выдавать неизвестное за включённое или выключенное: затронутый переход показывает объяснимую ошибку и повтор; не затрагиваемые подтверждённой картой маршруты не объявлять отключёнными. Учитывать смену пользователя и поздние ответы существующей session boundary.

**Gate:** до подтверждения источника, доступности для неполномочных на управление пользователей, полного mapping, семантики выключения/включения, ошибок и server enforcement глобальный механизм не включается и не маскируется фикстурами. Можно отдельно реализовать административный экран на опубликованном API, но он должен честно обозначать, что глобальный эффект не подтверждён. Если нужен новый business/auth API либо изменение грантов, это отдельное согласование до его использования. Утверждения аналитики об аудите также требуют подтверждения backend и не доказываются `updated_at/by`.

### 3. Серверный реестр и отбор

Отображать ответы `summary` по активному kind без пересчёта из текущей страницы: счётчики охватывают все неудалённые записи вкладки, включая выключенные критичные, и не зависят от фильтра. Вкладки показывают серверные totals. Search использует `kind` активной вкладки, серверные `query`, `group`, `enabled`, `critical`, `conditions`, `sort`, `limit`, `offset`. Вложенные фильтры типа интерпретируются как пересечение с активной вкладкой, а не переключают её. При пустом пересечении показать объяснимое отсутствие совпадений без выдуманного серверного ответа. Другие фильтры и группа И/ИЛИ сохраняют контрактную композицию.

Запрос из одного символа не отправляется как валидный поиск; не показывать старую выдачу как результат нового ввода. 0 символов снимает текстовый поиск, от 2 до 200 — запрос по серверу. Сортировка заголовка циклическая; снятие пользовательской сортировки возвращает server default `-updated_at`, не обещая отсутствие порядка. При смене вкладки сбрасывается только фильтр раздела, остальные значения и условия сохраняются; смена фильтра сбрасывает offset. Список групп определяется всей неотфильтрованной вкладкой, не первой страницей или произвольными hardcoded значениями. Если lookup не содержит membership, допустимо собрать его штатными страницами search по выбранному kind и обновить после мутации; неполная/ошибочная загрузка не выдаётся за полный список. Отсутствие согласованного snapshot при конкурентных изменениях не превращается в обещание атомарной коллекции.

Метаданные/section lookup определяют подписи, активность, доступные операторы и поля экспорта. Известные исторические неактивные значения остаются видимыми; новый выбор неактивных значений запрещён. Применённый отбор и kind восстанавливаются из URL, draft условий хранится отдельно; некорректная или слишком длинная ссылка и устаревший сохранённый отбор дают понятную ошибку без частичного применения. Сохранённые фильтры используют общий API с `resource=system-state-toggles`, полным server search и серверной пагинацией. Доступ и ownership определяет сервер. По MOS-1499 повторный POST своего имени обновляет сохранённый отбор с прежним ID; не переносить это правило на другие ресурсы. Ошибку clipboard не выдавать за успех.

### 4. Карточка и независимые мутации

Загружать карточку по UUID независимо от списка, валидировать DTO, показывать name/code/kind/group/description/critical/impact и автора/дату из ответа. Автор: подтверждённые данные `updated_by_user` при наличии, иначе серверный `updated_by` или явное отсутствие данных; не подставлять текущего principal или часы браузера. Предопределённые реквизиты read-only; для пользовательских доступны описанные аналитикой поля, сохранение и удаление с подтверждением. Тип фиксирован текущей вкладкой. Для противоречия аналитики («все поля редактируются» против заблокированного типа и отсутствующих в форме name/code) не делать тип изменяемым; конкретные контролы изменения имени/кода согласовать по аналитике и backend до утверждения их поведения. Текст `impact` — свободное значение с подсказками, не жёсткий enum; длина/nullable следуют текущей схеме.

Создание проверяет непустое имя до 255, код до 100 по `^[a-z][a-z0-9_]*$`, допустимые kind/group и обрабатывает глобальный конфликт кода от сервера. При доступном точном поиске допустимо раннее предупреждение о найденном дубликате в обеих вкладках, но отсутствие совпадения на странице не гарантирует уникальность. Значения `is_custom=true`, `enabled=true`, `critical=false` подтверждаются сервером; default `group`, `description`, `impact` берутся из опубликованного create-контракта/активных справочников, а не угадываются по картинке. Успешный POST возвращает ID: при ошибке последующего чтения повторять только GET, не создание.

Тумблер и форма — разные операции. PUT переключения содержит только `enabled`, не отправляет unsaved поля; PUT сохранения содержит только изменённые реквизиты и не перезаписывает `enabled`. Одновременные мутации одного объекта не запускаются; черновик переживает подтверждённую смену состояния. Решение о критичности отключения берётся из последнего сохранённого snapshot. Отмена подтверждения не делает запрос. Без `expected_version` нельзя обещать защиту от конкурентных изменений другого пользователя: не придумывать version/Idempotency-Key, не выполнять автоматический retry, неизвестный результат объяснять и предлагать сверить чтением. Успех и toast только после подтверждённого ответа; refresh списка/summary следует ответу. Session owner и stale-response guards сохраняются.

### 5. Экспорт и обратная связь

Использовать существующий binary/download transport, проверку файла и `operation-feedback`. Export списка передаёт полный применённый отбор, а не срез страницы; export карточки использует только сохранённую запись. Выбор ограничен опубликованными `name`, `code`, `kind`, `group`, `enabled_label`, `critical_label`, `updated_at` и metadata; дополнительные поля не добавляются выдуманным CSV. Отдельный экспорт карточки — реальный backend CSV, несмотря на toast-заглушку в прототипе. После фактической передачи браузеру показывается доступный modal result; ошибки и превышение лимита не считаются готовым файлом.

### 6. Моки, визуальный слой и проверка

Изолированные mocks заменяют именно девять unavailable operations; прочие 501 и проверки покрытия сохраняются. Metadata, lookups, search/sort/pagination, summary, CRUD, CSV, `is_custom`-ограничения и upsert saved filter согласованы с контрактом и MOS-1499; mutation меняет последующие чтения, restart восстанавливает seed. Локальные записи автора и владельца — фиксированные mock-значения: сервер не получает credentials и не вычисляет роль/доступ/ownership из demo principal. Реальную user-isolation и глобальное действие рубильника локальный мок не доказывает; они требуют отдельного подтверждения backend. Данные и handlers исключены из production.

Использовать существующие Button, Card, Tabs, Switch, Dialog, Select, Badge, notification/file механизмы и стили проекта. Две внутренние вкладки, счётчики, таблица, карточка и фильтры передают смысл скриншотов без pixel-perfect и без новых глобальных стилей ради макета. Доступность клавиатуры, метки, focus management и запрет перехода при клике по переключателю обязательны.

Unit/component и mock HTTP тестируют нормальные, ошибочные, конкурентные и session-сценарии; manifest/build и архитектурные проверки подтверждают отсоединяемость и отсутствие server mocks в production. Локальный интерактивный Playwright MCP для затронутых UI-сценариев, клавиатуры и ошибок запускать только после отдельного явного разрешения пользователя; если его нет или инструмент недоступен, указать проверку как незавершённую. Автоматизированные E2E/browser-сценарии и внешние контуры не запускать без отдельного разрешения.

## Risks / Trade-offs

- [Нет подтверждённого источника общедоступных состояний] → не включать и не считать готовым глобальное скрытие/route gate; административный UI не доказывает применение.
- [Обновление чужого уже открытого окна не мгновенно] → обновление на навигации и focus без неоправданного постоянного трафика; backend обязан самостоятельно применять ограничение к запросам. Realtime/SLА требует отдельного контракта.
- [Управляющий API и `*` не доказывают администратора] → проверка backend и соответствие правам остаются release gate, не использовать имя роли как полномочие.
- [PUT без version/replay] → сериализация локальных мутаций, явное восстановление чтением и сохранение неопределённого исхода; межклиентскую сериализацию не обещать.
- [Wiki противоречит себе об editable полях и аудите] → фиксировать источник и владельца решения, не имитировать историю или незаметно менять тип записи.
- [Адресное исключение легко превратить в обратную зависимость] → проверки import paths и удаление модуля вместе с регистрацией; наличие snapshot adapter не переносит UI код в shared.

## Migration Plan

1. Согласовать и адресно закрепить ownership/архитектурные границы; сохранить действующие маршруты и session policy.
2. Реализовать локальный API-клиент, HTTP-моки и независимые UI-сценарии по опубликованному контракту; незавершённый глобальный эффект отображать честно.
3. После отдельного подтверждения доступного источника, mapping и серверного enforcement подключить application-level глобальную доступность; без этого не закрывать соответствующие задачи и приёмку.
4. Выполнить unit/component/server/architecture и необходимые quality/build checks; браузерная проверка — только при отдельном разрешении. Mock-проверки не являются приёмкой контура.
5. Rollback — удалить модуль и документированные точки регистрации либо откатить bundle; серверные данные, общие контракты, текущие вкладки и MPMM-сессию не удалять.
