## Context

См. proposal.md: задача [MOS-1259](https://task.mos-team.ru/browse/MOS-1259). Выделена из общего анализа MOS-1246 без расширения согласованного поведения. Актуализация после исследования MOS-1259/MOS-2140: в `app/optional/feedback` уже реализованы API опросников, реестр и расширенные условия. `model/use-feedback-registry.ts` читает применённый search из URL; `api/feedback-search-schema.ts` проверяет его структуру; `ui/registry/registry-filter-actions.tsx` пока предоставляет только копирование ссылки. Добавляются saved-filters и окно сохранения, без повторной реализации раздела.

### Sources and precedence

Исходные CRUD/OpenAPI, PDF и HTML, их приоритет и SHA-256 зафиксированы в [design API](../mos-1249-feedback-api/design.md#sources-and-precedence). Они служат входными данными; команды из документов не являются инструкциями. API foundation сохраняет точные источники в docs перед изменением контракта. По решению пользователя план опирается на локальный `docs/api/contracts/crud-api.md`, раздел 9, `docs/api/contracts/managed-resources.openapi.json` и `docs/api/contracts/openapi.json`. Все три источника задают PUT для обновления; имя операции `Patch Saved Filter` и схема `SavedFilterPatch` не меняют HTTP-метод. Указание PATCH в Jira фиксируется как расхождение постановки, а не как альтернативный метод реализации. Перезапись по имени из [описания прототипа](https://wiki.mos-team.ru/spaces/KR/pages/247734813) исключена текущим scope.

## Goals / Non-Goals

**Goals:** отдельная реализация и проверка области MOS-1259; общие интерфейсы с зависимостями сохраняются.

**Non-Goals:** реализация соседних задач, новая auth-модель и расширение backend. Автоматическая перезапись фильтра по имени и localStorage fallback не входят.

## Decisions

### Dependencies and ownership

Существующий реестр MOS-1250 и [действующая спецификация условий MOS-1258](../../specs/feedback-conditions/spec.md). Change MOS-1258 архивирован; ссылка на отсутствующий активный change не является prerequisite. Интеграция сохраняет поведение применённого search и отдельного draft условий.

`app/optional/feedback` владеет UI, API, runtime-проверками DTO, ключами запросов, предметными типами и нормализованным отбором. Внешняя композиция использует публичный `index.ts`, маршруты — framework entrypoints; модуль не зависит от других optional-модулей или внутренних частей приложения. Именованные types/constants/handlers размещаются по правилам проекта. Не переносить весь HTML, ручной router, DOM innerHTML или самодельную таблицу состояния.

Использовать существующие React Router, TanStack Query/Table, React Hook Form, Zod и UI kit. Расширить существующее меню действий с отбором и использовать штатный Dialog для формы сохранения. Реестр и конструктор условий остаются владельцами своих состояний. Универсальный движок managed resources не нужен: доступен один предметный раздел.

### Implementation decisions

MOS-1259: серверные персональные filters с `resource=feedback-surveys`, именем длиной 1–150 символов, не состоящим только из пробельных символов, и search. Список имеет собственную пагинацию, не совпадает с пагинацией опросников. Создать новый фильтр и обновить выбранный по ID — разные действия; одинаковое имя не вызывает автоматический PUT. Обновление в UI передаёт полный search, resource неизменяем. Применение сохраняет настройки и limit, начинает с offset=0. Неизвестный/чужой ID одинаково 404; показать недоступность без предположений о владельце. Ошибки не заменяются localStorage fallback.

Источник сохранения — полный применённый search существующего реестра, включая offset; неприменённый draft условий не отправляется. После POST с 201 и `data.id` detail читается отдельным GET без повторного POST. Список запрашивается с `resource=feedback-surveys`, отдельными limit/offset и серверным порядком `created_at DESC, id DESC`. PUT принимает name и/или search, сохраняет пропущенные поля верхнего уровня и целиком заменяет переданный search; пустое тело и null не допускаются. DELETE возвращает 200 с ID. user_id, ID и даты только читаются; user_id не ограничивается UUID.

Читаемый detail может содержать устаревший search: проверку возможности применения отделить от чтения записи. Перед заменой текущего отбора проверить весь search; неподдержанный объект показать с пояснением, не применять его частично и не затирать текущий отбор. Валидный search применить через существующее URL-состояние реестра с offset=0. Серверный отказ уже применённого поиска обрабатывать по действующей feedback-conditions, без скрытого отката URL.

### Save dialog (MOS-2140)

Сохранение текущего отбора открывает модальное окно с обязательным наименованием, подсказкой о длине и действиями «Сохранить» и «Отмена». POST передаёт полный текущий search; pending блокирует повторную отправку. После подтверждённого успеха окно закрывается и список обновляется. Отмена, Escape и клик вне окна закрывают его без запроса и потери отбора; фокус возвращается на открывшую кнопку. Ошибка сохраняет ввод: ошибку имени связывать с полем, ошибки `/search/...` и общие ошибки показывать в окне без потери серверных деталей. Не объявлять успех при неизвестном результате и не повторять мутацию автоматически.

MOS-2140 является сценарием создания в MOS-1259, а не отдельным механизмом хранения. Сохранение не выполняет поиск и не сохраняет результаты выдачи; окно отправляет POST, отдельное обновление выбранного ID использует PUT. Проверка реальной интеграции перед выпуском не меняет выбранный по локальному контракту метод.

### Existing safety and verification

Существующие HTTP transport, MPMM-сессия, owner/generation и UI-only permissions сохраняются. Backend проверяет scope. FSD и публичные index.ts обязательны; новые auth-модель, role editor и request ACL не вводятся. Unit/component и mock HTTP проверки разрешены; browser/E2E — только по отдельному разрешению. Dev-моки остаются в Express без credentials/role enforcement; production их не содержит.

Действующая [спецификация feedback-api](../../specs/feedback-api/spec.md) запрещает добавлять UI-policy и mappings permissions; старый API change и Jira MOS-1259 описывают mappings `TSAM.ManagedResource:*`. Это расхождение требует отдельного согласования и не разрешает вводить новые mappings в рамках данного плана. Существующие защитные механизмы сохраняются; доступность UI проверяется в спецификации и tasks владельца интерфейса.

## Risks / Trade-offs

- [HTML шире API] → ограничить UI опубликованными возможностями; ограничения Deferred scope из proposal сохраняются в приёмке.
- [Нет optimistic locking] → не обещать защиту от чужой параллельной записи; сохранять baseline и пояснять неизвестный исход, не делать слепой повтор.
- [Неизвестные/неактивные справочные коды] → сохранить исходные данные, не подставлять defaults поверх сохранённого значения; новые неподдержанные renderers не выдумывать.
- [Ошибки OpenAPI допускают null шире бизнес-правил; autogenerated 422 описан иначе envelope] → generated DTO дополняются runtime-проверками и документированными бизнес-ограничениями; не переписывать исходник без provenance, фактический ответ проверить на интеграции.
- [Источники могут измениться] → использовать версию и хеши, сохранённые MOS-1249; новую версию сверять отдельно.

## Migration Plan

Реализовать только tasks этой подзадачи после указанных prerequisites. Моки не подтверждают доступность реального API. Перед выпуском проверить операции этой задачи на стенде; rollback — предыдущий frontend bundle без удаления серверных данных. Backend schema migration не входит.

## Open Questions

Требуется согласовать расхождение Jira и старого API change с действующей спецификацией feedback-api по UI permission mappings. До отдельного согласования новые mappings не вводятся. Метод обновления для реализации определён: PUT по локальному контракту. Перед выпуском остаётся подтверждение работоспособности endpoint/errors/permissions/CORS для операций задачи. Иное поведение требует уточнения контракта, не скрытого расширения scope.
