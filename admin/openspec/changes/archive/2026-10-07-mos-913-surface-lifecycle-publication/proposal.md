# Proposal

## Why

После MOS-913 карточка поверхности уже показывает сохранённые сведения подключения и обзора, но управление жизненным циклом остаётся заглушкой: пользователь не может отправить конфигурацию в sandbox, опубликовать её или безопасно изменить состояние поверхности. При этом OpenAPI и mock API уже предоставляют нужные бизнес-операции, поэтому UI должен подключить их без фиктивных токенов, синтетических проверок и выдуманной модели доступа.

## What Changes

- Добавить в карточку блок «Жизненный цикл конфигурации» с текущим серверным статусом и действиями `sandbox`, `publish`, `disable`, `enable`, `archive`, `restore` через существующие POST-операции.
- Добавить API-клиент и mutation/query-связку для lifecycle-операций и `PUT /surfaces/v1/surfaces/{surface_id}/configuration`; после успешной операции обновлять карточку полным серверным снимком, а не только локальным статусом.
- Для публикации показывать подтверждение перед запросом и доступное модальное сообщение об успешной публикации; ошибки не должны выглядеть как успех и должны давать повторить операцию.
- Для копирования кода подключения показывать доступный toast/status об успехе или ошибке; копировать только точную строку, полученную от сервера.
- Получать и отображать серверский `connection.embed_code`, если он возвращён `GET /surfaces/v1/surfaces/{surface_id}`; не собирать код на клиенте, не добавлять фиктивные `data-token` и не трактовать домен, channel ID или UUID как секрет.
- Явно показывать состояния loading, ошибки, блокировки во время запроса и retry; сохранять последний корректный снимок карточки при ошибке последующего чтения.
- Расширить component/unit-тесты UI, API-клиента и mock API для успешных операций, ошибок, повторов, обновления статуса и недоступного embed-кода. E2E/browser-тесты не добавлять и не запускать.
- Не добавлять auth/session/RBAC, permissions или ограничения интерфейса по пользователю. Не вводить новый endpoint для генерации кода или новый формат lifecycle-ответа.

### Неясности, которые фиксируются до реализации

- OpenAPI перечисляет статусы `draft`, `configured`, `review`, `sandbox`, `prod`, `disabled`, `archived` и целевые POST-операции, но не задаёт допустимые исходные статусы, повторяемость действий, правила `enable`/`restore` и сохранение предыдущего статуса. Mock сейчас использует конвенцию «disable/archive запоминают предыдущий статус, enable/restore возвращают его либо fallback», но это не объявлено гарантией backend. Design и implementation должны либо получить согласованную таблицу переходов, либо не скрывать действия по догадке и считать ответ/ошибку сервера источником истины.
- OpenAPI не содержит операции генерации embed-кода: `connection.embed_code` — nullable-поле detail, а `PUT /configuration` не возвращает отдельный код. До уточнения backend UI может только показать серверное значение или «код не сохранён»; генерация строки, токена или атрибутов на фронтенде запрещена. Если сервер должен генерировать код после создания/изменения конфигурации, это требует отдельного уточнения контракта, а не локального fallback.

## Capabilities

### New Capabilities

- `surface-lifecycle-publication`: публикация и управление lifecycle поверхности, подтверждение действий, серверный код размещения, truthful feedback, обновление карточки и retry.

### Modified Capabilities

Нет. Общие требования HTTP-интеграции, mock server, FSD, error handling и запрета E2E сохраняются; новая capability добавляет surface-specific требования поверх них.

## Impact

- `entities/surface`: типы и runtime-схемы detail/status/configuration, API-клиент для существующих endpoints, mutation hooks и обновление query cache.
- `widgets/surface-details`: lifecycle-блок, publish confirmation/success modal, feedback для copy/action, доступные состояния и повтор чтения; существующий read-only connection UI остаётся источником серверского embed-кода.
- `mocks/surfaces.mjs`, seed и server-тесты: воспроизводимые ответы lifecycle и server-owned embed-код без фиктивных credentials; семантика mock будет явно отделена от гарантии production backend.
- OpenAPI generated-типы используются как источник типов; ручное расширение `schema.d.ts` и добавление новой зависимости не планируется. `yarn api:check` запускается, если API-контракт или generated-типы затронуты.
- Проверки: component/unit и mock server tests, `yarn typecheck`, `yarn lint`, `yarn test`, `yarn format:check`; E2E/browser-проверки исключены.
