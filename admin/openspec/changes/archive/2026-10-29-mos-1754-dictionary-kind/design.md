## Context

Мотивация и согласованное изменение scope — в `proposal.md`; проверяемое поведение — в `specs/reference-dictionaries/spec.md`. Форма `DictionaryCreateAction` использует React Hook Form/Zod, а `useDictionaryCreateHandlers` сейчас всегда формирует `kind: list`. Дополнительная клиентская `dictionaryCreateSchema` также допускает только `list` и соответствующее хранилище. POST возвращает только ID; переход открывает карточку, которая самостоятельно читает серверные данные и выбирает редактор по возвращённому `kind`.

Локальный `docs/api/contracts/crud-api.md` §18.4–18.7 описывает оба вида, выбор хранилища по виду, ограничение значений карточкой и неизменяемость `kind`. [Swagger T](https://nchat-t-tech.mos.ru/api/control/openapi.json), прочитанный 29 октября 2026 года, публикует тот же `CatalogCreate`: `kind` — строка, `group` — `user`, `storage_table` допускает две таблицы, ответ создания — 201 с ID. Перечисление допустимых `kind` и поведение нескольких справочников в OpenAPI не доказаны. В локальном мок-сервере создание дополнительных правил уже покрыто HTTP-тестом; это не подтверждение реального backend.

## Goals / Non-Goals

**Goals:** передать выбранный формат без декоративного селекта, сохранить существующий жизненный цикл формы и использовать уже имеющийся редактор карточки. Обеспечить ясную связь формата и хранилища без новых запросов к API.

**Non-Goals:** редизайн всей формы по прототипу, изменение вида существующей карточки, новый backend-контракт, миграции данных, новый механизм проверок, подключение справочника к потребителям и применение правил к загрузкам. Изменения auth, permissions и transport не требуются.

## Decisions

### 1. Вид принадлежит форме создания

Добавить `kind` в существующие defaults и форму с замкнутым набором `list | rules-attachments`. Использовать существующий доступный Select UI и интеграцию с React Hook Form: метка «Тип справочника», варианты из задачи, начальное значение `list`, заблокированное изменение во время отправки. Разместить рядом с владельцем, как на изображении, если это совместимо с текущей адаптивной формой; остальные поля и их семантику не менять. Владелец по умолчанию остаётся «Команда ЦАМ», а не пример из изображения.

Два варианта заданы задачей и локальным контрактом, поэтому дополнительный загрузочный запрос ради самого селекта не нужен; сервер остаётся ответственным за проверку вида. Менять `group` или использовать реестровые подписи «Системный / Информационный / Пользовательский» вместо вида нельзя. Только `kind` участвует в выборе формата. Изменение выбора учитывается штатным dirty-состоянием; возврат к default считается чистым, если другие поля не менялись.

### 2. Один существующий POST, согласованные параметры

Передавать в `POST /api/control/api/v1/managed-resources/catalogs` данные формы с явными `group: user`, выбранным `kind`, `status: draft` и соответствующим `storage_table`: `list` → `ref_dictionary_user`, `rules-attachments` → `ref_attachment_rule`. Остальные преобразования формы сохраняются. Клиентская схема должна принимать только эти два вида и отвергать несоответствующую пару вида и явно переданного хранилища до запроса; сохранение существующих вызовов с опущенными необязательными полями проверить тестами.

Локальное описание допускает как автоматический выбор таблицы, так и явно переданную совпадающую таблицу. Предпочтена явная пара: Swagger указывает общий default `ref_dictionary_user`, не описывая зависимость default от `kind`. Это техническое решение по опубликованному контракту, а не утверждение, что сервер уже проверен. Альтернатива — опускать `storage_table` и полагаться на зависимый default — оставляет указанную неоднозначность невыявленной. Не запрашивать список существующих правил и не вводить клиентское ограничение единственности.

### 3. Ответ, ошибки и сохранность ввода

Сохранить подтверждение POST по 201 и UUID, инвалидацию списка, переход по возвращённому ID и независимый GET карточки. Редактор выбирается по фактически прочитанному виду; не подставлять выбранный вид, демозапись или пустую успешную карточку, если GET вернул ошибку либо другой вид. Для этого не добавлять повторный POST или отдельный предположительный endpoint.

Существующие ошибки 409/422 и общие ошибки формы должны сохранять выбранный `kind` вместе с другими полями; ошибку `/kind` нельзя терять, даже если она отображается общей ошибкой. Сохранить отмену по AbortSignal, защиту владельца сессии, запрет двойной отправки и отсутствие автоматического повтора при неизвестном исходе. Подтверждение закрытия и восстановление формы после отмены должны учитывать изменение одного только селекта.

### 4. Проверки без притворной backend-приёмки

Использовать существующие unit/component-тесты формы и клиента и контрактные тесты мока, не меняя бизнес-логику моков без выявленного расхождения. Проверять два точных тела запроса, соответствие kind/storage, неизвестное значение и несовместимую пару, клавиатуру, dirty/отмену, ошибки, pending, поздний ответ и последующее чтение карточки. Сохранить проверки обязательных полей, кода, владельца и разрешённых границ.

Локальную интерактивную проверку через Playwright MCP с моками выполнять только после отдельного явного разрешения пользователя: оба вида, ошибка, клавиатура и отмена. Без разрешения записать её как невыполненную. E2E/browser suites и внешние UI-проверки не запускать без отдельного разрешения. Проверки моков не доказывают работу серверного развёртывания.

## Risks / Trade-offs

- [OpenAPI не перечисляет допустимые kind и не гарантирует несколько независимых наборов правил] → использовать только задокументированные значения и явно показывать серверную ошибку; наличие локального мока не считать подтверждением реального backend. Проверка работы контуров или изменение внешних данных требует отдельного разрешения.
- [Вид и таблица могут разойтись] → формировать таблицу из выбранного вида, проверять пару на границе клиента и тестировать несовместимые комбинации.
- [POST вернул ID, но чтение карточки не подтверждает вид] → использовать фактический GET и его ошибку, не синтезировать данные и не повторять POST. Создание может уже состояться.
- [Пользователь примет правила за применённую политику] → сохранять существующее пояснение об отсутствии подтверждённого применения и не подключать справочник автоматически.

## Migration Plan

Развернуть frontend без изменений контрактов или миграции данных. Существующие `list`-сценарии и карточки сохраняются; новые справочники создаются только явным действием пользователя. Откат UI удалит возможность нового выбора, но не удалит уже созданные справочники или их значения; автоматического удаления и отката данных не предполагается.
