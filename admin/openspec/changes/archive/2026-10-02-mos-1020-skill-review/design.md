## Context

См. proposal.md. Вкладка review уже существует в skills-page и управляется URL. getSkillRegistry поддерживает status и серверную пагинацию; GET карточки возвращает анкету, intents, status и version в одном ответе. changeSkillStatus валидирует запрос/ответ, а useChangeSkillStatusMutation не повторяет POST автоматически и обновляет карточку/списки.

Пользователь согласовал MVP с прямым переходом review → whitelist вместо отсутствующего в API approved из прототипа. Это продуктовая договорённость; контракт не гарантирует принятие перехода backend и не хранит решение ревью, критерии или замечания.

## Goals / Non-Goals

**Goals:** очередь → материалы → ручной чек-лист → подтверждение → серверный whitelist, с понятным отказом без локального успеха.

**Non-Goals:** отдельный review endpoint/item/run ID, сохранённый протокол ревью, возврат с замечаниями, результаты автопроверок, история решений, approved, выкат в prod, клиентские роли. Не вводить требования к серверному снимку запусков, которого нет в контракте.

## Decisions

- **Очередь из существующего списка.** Запрашивать GET skills с фиксированным status=review и серверной пагинацией, независимо от фильтров основной вкладки реестра. Переиспользовать entity-клиент и ключи запросов с параметрами; не фильтровать локально страницу реестра и не загружать весь каталог. Различать loading, пустой результат и ошибку с повтором. После удаления последней записи страницы перечитать допустимую страницу.
- **Материалы из одной карточки.** Выбор строки загружает GET detail по skill ID; анкета и фразы берутся из одного ответа с его version. Для команды использовать версию просмотренной карточки, не строки очереди. Это не обещание неизменяемого review-снимка или готовности текущих фраз. Если detail уже не в review, запретить действие и обновить очередь. Не загружать фиктивные результаты проверок.
- **Чек-лист только локальный.** Пять пунктов из proposal обязательны перед подтверждением; это ручная оценка, а не автоматическая проверка. Явно объяснить, что отметки не сохраняются. Держать их только в состоянии панели выбранного навыка, без URL/storage и без PATCH comments. При смене skill ID или версии карточки сбрасывать отметки и старое подтверждение; при ошибке без смены материала сохранять ввод. Reload или уход со вкладки не восстанавливает отметки.
- **Одно явное подтверждение.** Действие называется «Согласовать и перевести в белые списки», подтверждение показывает навык и переход review → whitelist. Доступно только при успешном чтении актуальной карточки в review и всех пяти отметках. Во время POST запрещать повторную отправку. Известное изменение status/version до отправки требует повторного просмотра и подтверждения; серверный expected_version защищает от невидимых клиенту изменений.
- **Переиспользовать статусную команду.** Вызвать существующий changeSkillStatus с status=whitelist, версией просмотренной карточки и новым UUID Idempotency-Key. Чек-лист не включать в payload. Не расширять матрицу команд feature skill-lifecycle: новый переход принадлежит ревью, не обычной карточке. Валидный ответ с whitelist подтверждает переход; другой status показывать как фактический с предупреждением, без сообщения о целевом успехе. Обновлять очередь, реестр и detail по существующим соглашениям Query.
- **Ошибки без replay.** Отказ сервера не меняет status локально. Конфликт версии требует перечитать материал и заполнить чек-лист заново, без автоматического POST с новой версией. Сетевая ошибка, timeout, 5xx или невалидный успешный ответ означают неизвестный исход: предложить чтение состояния, а не повтор команды. Если актуальная карточка уже whitelist, убрать её из очереди без утверждения, какая команда установила статус; если review — новая попытка требует повторного чек-листа/подтверждения с актуальной версией и новым ключом. При ошибке перечитывания действие остаётся недоступным.
- **Композиция без нового роутинга.** Widget очереди собирает просмотр и feature подтверждения в существующей вкладке /skills?tab=review; чтение/команда остаются в entities/skill. Сохранить useSectionTab, basename, крошки и историю, убрать устаревшее общее пояснение о неподключённом ревью. Не импортировать соседние features редактирования/lifecycle ради API. Результаты проверок и возврат обозначить как недоступные в MVP без фиктивных форм, кнопок успеха и guessed endpoints.

## Risks / Trade-offs

- [Backend отклоняет продуктовый переход review → whitelist] → показать отказ и оставить фактический статус; не подменять другим переходом. Такое ограничение требует согласования с backend, а не обхода в UI.
- [Пользователь принимает локальные отметки за сохранённый протокол] → постоянное пояснение и отсутствие истории/автора решения; сервер подтверждает только status.
- [Материалы изменились во время просмотра] → сброс отметок при известной смене версии и expected_version при отправке; не объявлять проверенной новую версию автоматически.
- [Результаты обучения недоступны] → ручные критерии не выдаются за серверные проверки; отсутствие этой информации явно отмечено.

## Migration Plan

Заменить только review placeholder и его пояснения, переиспользовав существующий транспорт и UI-примитивы. Unit/component-тесты покрывают очередь, основной переход, неподходящий status, конфликт и неизвестный исход; E2E/browser не входят в работу. Приёмка независима от MOS-1019/MOS-1021. Откат UI не отменяет уже принятые сервером переходы.
