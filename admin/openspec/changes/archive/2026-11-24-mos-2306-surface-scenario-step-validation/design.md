# Design

## Context

Мотивация и границы приведены в [proposal.md](proposal.md), критерии поведения — в [delta spec регистрации](specs/surface-registration/spec.md).

Исследование исходников выполнено на `59bac2d`. В браузере ранее прочитаны описание MOS-2306 и [вложение от 18 ноября 2026 года](https://task.mos-team.ru/secure/attachment/858958/image-2026-11-18-15-29-50-669.png): один выбранный навык, обязательный select «Не выбрано», ошибка у поля и активная «Далее». Сам сценарий MOS-2306 на стенде не воспроизводился; вывод о причине основан на исходниках.

`surface-skill-selection` уже определяет обязательность, options, defaults и отсутствие настроек. Добавляемое правило принадлежит переходу регистрации; менять предметный контракт общего редактора или политику сохранения карточки не требуется. Дизайн нужен для согласования двух независимо владеемых моделей через слой widgets и единой защиты UI/обработчика.

## Goals / Non-Goals

**Goals:** связать актуальную проверку сценариев с переходом регистрации, сохранив отдельное владение формой и параметрами навыков, штатные React Hook Form/Zod и существующий контроллер каталога.

**Non-Goals:** перенос параметров в схему формы регистрации, новый валидатор навыков, общий механизм межшаговых проверок для всех мастеров, принудительная серверная проверка по каждому «Далее» и изменения схемы сохранения существующей поверхности. MOS-2303 и реализация кода в ходе подготовки этого change исключены.

## Decisions

### 1. Собирать готовность навыков в существующем widget

В `SurfaceRegistration` вычислять текущее булево `isSkillSelectionReady` из публичного `selection`: выбор непустой, `issues` пуст, отсутствуют `isCatalogLoading`, `isCatalogError`, `isDetailsLoading`, `isDetailsError` и `isPreparing`. Эти loading-флаги уже включают фоновый `isFetching`, поэтому кэшированные данные не разрешат переход во время обновления. Только выбранные навыки участвуют в проверке параметров; сохранённые параметры снятого навыка не являются ошибкой текущего выбора.

Передавать результат отдельной обязательной опцией `useSurfaceRegistration` и обновить типы ближайшего владельца. Feature регистрации получает готовность, а не контроллер соседнего feature. Внешние импорты остаются через `index.ts`; уже существующая синхронизация `skillIds` после индивидуального выбора, выбора домена и массовых операций сохраняется.

Копирование правил `required/options/default` в Zod либо импорт внутренностей соседнего feature создаст второй источник проверки. Повторный вызов `validateSkillSelection` в widget также не нужен: ошибки уже доступны через контроллер. Отдельный React state для копии готовности не нужен, это производное значение.

### 2. Одно условие для кнопки и фактического перехода

В модели регистрации объединить проверку полей текущего шага с `isSkillSelectionReady` только для `Scenarios`. Результат управляет существующим `isStepReady`, от которого `SurfaceRegistrationActions` уже выставляет `disabled`. Первый шаг сохраняет проверку доменов, второй — проверку ответственных; неготовые навыки не мешают их заполнению или переходу назад.

`goNext` проверяет ту же готовность независимо от DOM-кнопки, сохраняя `form.trigger` для полей формы. После асинхронной проверки формы, непосредственно перед сменой шага, необходимо перечитать актуальные поля и внешнюю готовность: захваченное до `await` значение не должно разрешать переход после очистки параметра или начала обновления данных. Свежий доступ к состоянию перехода держать в модели регистрации, передавая обработчику возможность читать актуальную готовность; не создавать отдельный сохранённый флаг успешной проверки. В тесте с управляемым ожиданием подтвердить, что невалидное изменение во время проверки отменяет переход.

Одна правка `disabled` недостаточна: вызов обработчика остаётся возможным из другого кода. Отдельный вызов `selection.prepare()` на «Далее» не выбран: он повторно запрашивает каталог и details, хотя локальная проверка уже доступна. `prepare()` остаётся обязательным непосредственно перед окончательным POST, поскольку каталог или схема могут измениться после открытия сводки.

### 3. Использовать существующие ошибки и сохранить ввод

Ошибки параметров продолжают поступать в `SkillParameterField` из `selection.issues`; поля сохраняют видимую ошибку и `aria-invalid`. Для причины блокировки использовать существующее пояснение шага и связь `aria-describedby` у «Далее», при необходимости уточнив текст о заполнении обязательных параметров и завершении проверки данных. Не добавлять конкурирующее общее сообщение вместо ошибки у параметра и не использовать текст старой ошибки подготовки POST как условие готовности.

Исправление значения, очистка, переключение навыка, массовая операция и возврат по шагам пересчитывают производное условие. Автоматического перехода при исчезновении ошибки нет. Defaults и значения `parametersBySkillId` обрабатываются только существующей моделью выбора; её правила инициализации, явной очистки, сохранения снятых значений и сериализации не меняются.

### 4. Проверять поведение на существующих unit/component-контурах

- `features/surface-registration/model/tests/surface-registration-handlers.test.ts`: вызов `goNext` при валидных полях формы и неготовых сценариях, повторный вызов и изменение готовности во время `form.trigger`; шаг не меняется. После исправления доступен явный переход. Проверки первого шага остаются действующими.
- `widgets/surface-registration/ui/tests/surface-registration.test.tsx` и локальные API fixtures/types: обязательный select без default, видимая ошибка и недоступная кнопка; заполнение открывает сводку без POST и сохраняет значение. Расширить fixture минимальными параметрами для нужных схем и управляемых ответов чтения, не меняя общий mock server или production API.
- Границы того же component-контура: необязательный пустой параметр, отсутствие настроек, валидный default с последующей очисткой, возврат со сводки, добавление/снятие проблемного навыка через индивидуальный и массовый выбор, пустой состав и пустое приветствие.
- Управляемая загрузка или обновление каталога/details и ошибка обновления при наличии кэша: старое валидное состояние не включает «Далее», retry сохраняет ввод и возвращает доступность после успешной проверки. Перед окончательным POST свежие невалидные данные по-прежнему останавливают создание.

Проверять доступность кнопки, связь с пояснением, видимую ошибку, текущий шаг, сохранённые значения и отсутствие POST, а не набор CSS-классов или передачу props в mock. Уже покрытые предметные правила валидатора не дублировать; новые тесты закрепляют их участие именно в регистрации. Browser/E2E-тесты не создавать, не редактировать и не запускать.

## Risks / Trade-offs

- Кэш остаётся заполненным во время обновления или после ошибки → учитывать loading/error-флаги вместе с `issues`; отдельно проверить этот случай компонентно.
- Асинхронная проверка полей удерживает прежнее разрешение на переход → читать актуальную готовность перед сменой шага и проверить изменение во время ожидания.
- Расширение проверки может ошибочно сделать любой параметр обязательным → переиспользовать существующие `issues`, проверить необязательные значения, отсутствие схемы и валидный default.
- Старый интеграционный helper сразу заполняет параметр и скрывает регрессию → выделить в тестах доступ к шагу «Сценарии» до заполнения настроек, сохранив существующий успешный проход.
- Переход по текущим данным не гарантирует их неизменность до записи → сохранить независимую финальную подготовку и действующие правила результата POST/подтверждающего GET.

## Migration Plan

Миграции данных нет. После отдельного запроса на реализацию выполнить задачи и проверки; выпускать обычным frontend-релизом. Откат ограничивается изменениями интеграции готовности и соответствующими тестами, без изменения API и схемы сохранённых данных. Unit/component-проверки не подтверждают состояние развёрнутой сборки.
