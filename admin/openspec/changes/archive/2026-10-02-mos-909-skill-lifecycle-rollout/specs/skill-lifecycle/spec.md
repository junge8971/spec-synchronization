## MODIFIED Requirements

### Requirement: Contract-gated lifecycle

Карточка SHALL показывать текущий SkillResponse.status и шкалу опубликованных этапов. На основании разрешённых пользователем продуктовых допущений MOS-909 SHALL предлагать только `draft → checking`, `sandbox → review`, `whitelist → prod` через опубликованный POST status с expected_version и Idempotency-Key. Эта матрица MUST NOT объявляться гарантией допустимости переходов backend. Для checking/training/autotest/review/prod SHALL отсутствовать команды смены состояния. UI MUST NOT синтезировать результаты процессов, дополнительные enum или endpoints; обычный PATCH анкеты MUST NOT использоваться для lifecycle. Поддерживаемые анкета, фразы, подключение и отдельный мастер регистрации SHALL сохраняться независимо от lifecycle. Неизвестный status MUST NOT сопоставляться с «Черновик» или «Прод» по умолчанию.

#### Scenario: Current skill API

- **WHEN** карточка получена с опубликованным status без истории прохождения этапов
- **THEN** показаны текущий статус и шкала без отметок успешного прохождения; предложена только команда из матрицы для данного status, открытие карточки не выполняет мутаций

#### Scenario: Unknown server state

- **WHEN** ответ карточки содержит status вне опубликованного enum
- **THEN** UI показывает штатную ошибку чтения контракта без вымышленного статуса, шкалы и предложений перехода; правило совместимости неизвестных строк в списке не расширяет валидацию карточки

#### Scenario: Background refresh fails

- **WHEN** обновление карточки завершилось ошибкой при наличии ранее загруженных данных
- **THEN** старый статус обозначен как ранее загруженный, ошибка и повтор чтения доступны, команды перехода недоступны до успешного чтения

### Requirement: Server-derived lifecycle timeline

Карточка SHALL показывать компактную шкалу «Черновик», «Проверка», «Обучение модели», «Автотесты», «Песочница», «Ревью», «Белые списки», «Прод» в соответствии с draft/checking/training/autotest/sandbox/review/whitelist/prod. Текущий этап SHALL выделяться текстом и доступным обозначением, не только цветом. Остальные этапы SHALL оставаться нейтральными, поскольку API не предоставляет историю, завершённость, ошибки и ETA; это ограничение SHALL быть объяснено рядом. UI MUST NOT объявлять предыдущие этапы успешными из-за порядка enum. Integer version MUST NOT превращаться в номер релиза. Ручное обновление SHALL перечитывать состояние; автоматический локальный переход по таймеру запрещён.

#### Scenario: Refresh during training

- **WHEN** пользователь повторно открывает или обновляет карточку с status=training
- **THEN** текущим показано обучение, предыдущие этапы не объявлены успешными, нет ETA или локального завершения

#### Scenario: Rejected or disabled skill

- **WHEN** сервер возвращает rejected, approved или disabled, отсутствующие в опубликованном enum
- **THEN** показана ошибка чтения контракта, а не выдуманное соответствие этапу, успешное завершение или команда обхода

#### Scenario: Narrow screen and keyboard

- **WHEN** шкала и подтверждение используются на узком экране или клавиатурой
- **THEN** подписи доступны без обрезки, текущий шаг обозначен семантически, действия доступны и фокус подтверждения управляется штатным диалогом

### Requirement: Safe single-skill transitions

Для draft SHALL быть доступно «Отправить на проверку», для sandbox — «Отправить на ревью», для whitelist — «Выкатить в прод». Перед POST подтверждение SHALL показывать имя/ID навыка, текущий и целевой этап; для prod SHALL явно указывать продуктивный контур. Отмена MUST NOT отправлять запрос. Подтверждение SHALL фиксировать серверную версию и статус; их изменение до отправки SHALL требовать нового подтверждения. Во время команды SHALL предотвращаться повторная отправка. UI MUST NOT оптимистически менять status или автоматически повторять POST. Валидный ответ SHALL обновлять карточку и реестр; сообщение о целевом успехе допустимо только при совпадении подтверждённого status с целью. Ошибка SHALL сохранять контекст и объяснять причину. Решения ревью, массовый выкат и глобальное отключение SHALL оставаться отдельными возможностями.

#### Scenario: Concurrent state change

- **WHEN** состояние изменилось после открытия подтверждения либо сервер отклонил запрос из-за конфликта
- **THEN** устаревшее подтверждение не используется повторно, UI сообщает об изменении и перечитывает состояние без автоматической команды с новой версией

#### Scenario: Unknown transition result

- **WHEN** команда завершилась timeout, сетевой ошибкой, 5xx или невалидным успешным ответом
- **THEN** UI показывает неизвестный исход без утверждения об успехе/отмене, предлагает только чтение состояния до получения актуальной карточки; новый запрос требует отдельного осознанного подтверждения и не объявляется гарантированным replay

#### Scenario: Confirmed rollout

- **WHEN** сервер возвращает валидный ответ со status=prod после подтверждения выката из whitelist
- **THEN** карточка и реестр отражают серверный статус, повторное нажатие во время запроса не создаёт второй POST; UI не утверждает развёртывание отдельного runtime, которого нет в контракте

#### Scenario: Cancel and rejected transition

- **WHEN** пользователь отменяет подтверждение либо сервер отклоняет переход
- **THEN** в первом случае нет POST, во втором показан отказ без локального изменения status; контекст навыка сохранён

#### Scenario: Response differs from target

- **WHEN** валидный ответ содержит status, отличный от запрошенного
- **THEN** интерфейс показывает фактическое серверное состояние и предупреждение, а не целевой успех
