## Context

См. [proposal.md](proposal.md). `SkillRegistryFilters` уже разделяет черновик ввода и `query` в URL, но записывает в URL любой непустой ввод после задержки. `registry-search-params.ts` передаёт его в `useSkillsRegistryQuery` ещё до нормализации URL, а `SkillsRegistry` при ошибке размонтирует фильтры. Клиент `app/entities/skill/api/skill-registry-client.ts` уже отправляет `query` и `team_id` раздельно. Таблица подписывает статусы простым текстом. `SkillDomainsRegistry` использует серверный `skills_count` и пагинацию; доменный клиент умеет читать и сохранять, но операция удаления в подключённой схеме не описана.

Сценарии привязаны к [дельте реестра](specs/skill-catalog-experience/spec.md) и [дельте доменов](specs/skill-domain-management/spec.md). Свидетельства из Jira, Wiki, опубликованного OpenAPI, T и моков имеют разные границы; актуальные источники, результаты и непроверенные сценарии собраны в [verification.md](verification.md).

## Goals / Non-Goals

**Goals:** сохранить управляемый поиск и общую серверную семантику пагинации; вынести отображение статусов в один источник для таблицы и фильтра; подключать подтверждённые возможности API независимо друг от друга.

**Non-Goals:** новый роутинг, отдельные клиентские поиск и сортировка, новый фреймворк моков, ручная правка generated DTO, изменение создания или редактирования домена, auth/permissions и любых переходов навыка.

## Decisions

### 1. Валидация на обеих границах (MOS-2112)

Применённый запрос остаётся в URL, черновик — в поле. Использовать одно правило длины для отправляемого значения при применении ввода и при чтении URL. Невалидный черновик не коммитить после задержки: сохранять введённый текст и текущий применённый отбор, дать доступное объяснение у поля. Очистка снимает поиск; изменение применённого запроса использует имеющееся обновление URL со сбросом страницы. Сохранять остальные параметры и не переписывать восстановленный из истории запрос устаревшим черновиком.

Не полагаться только на эффект очистки URL: parser должен исключить невалидный `query` до построения запроса, нормализация — удалить его через замену URL без нового шага истории. Панель поиска должна сохраняться при смене состояния результатов; ошибка списка или недоступность справочника не отнимает средство исправления запроса. Не показывать старый total, экспорт или массовое действие как относящиеся к не загруженной выборке. Альтернатива с `maxLength` или запретом ввода скрывает вставленный текст и не защищает вход по ссылке; общий HTTP-клиент менять не нужно.

### 2. Поиск остаётся ответственностью сервера (MOS-2124)

Проверить передачу обоих ID в запросе и ответ на известные `id` и `service_id` отдельно, с данными за пределами открытой страницы. Параметр по контракту — `query`, не `q`. В локальном `mocks/skill-selection.mjs` уже есть `service_id`, но проверка текста не включает `id`; привести локальную проверку ID к подтверждённому контракту, не использовать её как доказательство поведения T. Если запрос уходит правильно, а навык не возвращён, это результат для сверки с BE, а не причина подменять серверную выборку.

Текст по названию команды и явный фильтр `team_id` — разные операции пользователя. [PEE-10](https://wiki.mos-team.ru/pages/viewpage.action?pageId=241080062) также упоминает `purpose`, тогда как [§2.5 API](https://wiki.mos-team.ru/pages/viewpage.action?pageId=241097511) описывает `name`, `id` и `service_id`. Запросить у владельца семантику названия команды, сочетание с фильтрами и доступность; расхождение по назначению записать отдельно. До согласования сохранить честную подпись поиска без обещания лишних полей. Не преобразовывать введённое имя в один `team_id` и не обходить страницы ради клиентского поиска.

### 3. Разделить отображение статуса и его код (MOS-2144, MOS-2178)

Переиспользовать `Badge` из UI kit и единый источник подписей именно для реестра и фильтра. Три текстовые поправки — «На проверке», «Обучение модели», «На ревью». Текущий порядок в `skillStatuses` совпадает с ожидаемым в Jira; закрепить независимой проверкой порядка фильтра, не переставляя коды без причины. Цвет использовать из семантической палитры UI с читаемым текстом; неизвестная строка остаётся нейтральной. Сохранить код в URL и запросе, строгий разбор карточки и поведение других потребителей подписей. Глобальная замена всех подписей затронула бы карточку и lifecycle без требования Jira.

### 4. Одна реализация сортировки домена (MOS-2091)

Взять решение из [add-skill-domain-sorting](../add-skill-domain-sorting/design.md) в этот change. Не выполнять параллельно две реализации; если сортировка уже попадёт в ветку из того change, проверить и переиспользовать её. Wiki перечисляет `domain_name` и `-domain_name`; свободная строка в OpenAPI и статус тикета сами по себе не подтверждают направления. На T два направления подтверждены по полной отфильтрованной выборке 23.11.2026 (см. [4.1](verification.md#4-mos-2091--сортировка-по-домену)). Экспорт по опубликованному контракту использует ту же сортировку, что и список; общий перечень токенов используется для URL и проверки тела экспорта.

После этого расширить существующий список сортировок, заголовок и маршрут URL → запрос как один набор. Действие в колонке «Домен и команда» называет домен и сообщает текущее направление, не сортирует команду. Локальные fixtures могут использовать `domain.name` в серверном моке перед пагинацией; на реальном клиенте порядок и total берутся только из API. Перед будущей синхронизацией спецификаций сверить пересечение дельт, чтобы не откатить независимую правку счётчика или требований реестра.

### 5. У дополнительных колонок разные источники (MOS-2143)

`SkillListItemResponse` и декодер читают `training` и `autotest`; [Wiki PEE-4 и справочники](https://wiki.mos-team.ru/pages/viewpage.action?pageId=241080062) задают семантику полей. [Опубликованный OpenAPI T](https://nchat-t-tech.mos.ru/api/control/openapi.json) предоставляет `GET /skills/v1/catalogs` с `training_states` и `autotest_states`. Переиспользовать `useSkillCatalogsQuery` и `display_name` для обоих кодов, а не дублировать их подписи или выводить готовность из lifecycle. Неизвестному коду или пустой подписи соответствует «Нет данных» для одного результата. Без загруженного справочника не показывать колонку, но не блокировать список. «Готовность» не ждёт источник диалогов, не обращается к карточке и не заменяет `add-skill-readiness-results`.

В DTO списка нет 30-дневного поля. Внутренняя операция метрик не является согласованным источником реестра. Нужен опубликованный список или иной согласованный пакетный источник с семантикой окна в 30 дней, единицей подсчёта и правилами отсутствия. Локальная статистика, запрос карточки/метрик на каждую строку и нули по умолчанию отклонены: они меняют смысл, стоимость и доступность экрана. После подключения отдельно отображать подтверждённый ноль и отсутствие значения; ошибка дополнительного источника не должна скрывать успешно загруженные строки.

### 6. Удаление домена — отдельное подтверждаемое действие (MOS-2153/2154)

На 20.11.2026 [OpenAPI T](https://nchat-t-tech.mos.ru/api/control/openapi.json) публикует DELETE по UUIDv7 с обязательным UUID `Idempotency-Key`, без тела; подтверждение — HTTP 200 с `SUCCESS` и `data: null`. [MOS-2154](https://task.mos-team.ru/browse/MOS-2154) требует серверной проверки отсутствия навыков при операции. Точный код этого отказа не опубликован; показать сообщение сервера и перечитать реестр без зависимости от кода конфликта. Действующая [политика для непокрытых операций](https://wiki.mos-team.ru/pages/viewpage.action?pageId=261213434) ограничивает видимость явным `*` на доступной вкладке. Это не серверное разрешение, не новое permission и не привязка к праву редактирования. Исполнение DELETE и права на T остаются на отдельной приёмке.

В реестре сгруппировать корзину с редактированием, переиспользовать диалог и уведомления UI kit. Причина недоступности видна при наведении и доступна с клавиатуры, даже если сама кнопка не фокусируется. Удерживать ID и название выбранного домена до подтверждения; если свежие данные показывают навык, не отправлять запрос. Pending блокирует повтор. Клиент и мутация в `entities/skill-domain` используют существующий transport и подтверждённые ответы. Не переиспользовать сохранение домена с другим методом, не скрывать строку оптимистически и не повторять удаление автоматически при неизвестном исходе.

После подтверждения результата обновить кэши реестра и деталей домена и справочные варианты `['skills', 'filter-options']`; по свежему ответу скорректировать `domain_page`, если последняя строка страницы исчезла. Показать одно уведомление об успехе. При отказе из-за появившегося навыка перечитать серверные данные и показать причину; при неопределённом исходе предложить чтение перед дальнейшим действием. Восстановить фокус на кнопке при отмене и на доступном элементе списка при исчезновении строки.

### 7. Проверки отделяют UI от интеграции

Расширить unit/component-проверки на семантику URL, границы длины, подписи и состав фильтра, запросы и ветки мутации. В `yarn dev` с локальными моками проверить затронутые сценарии вручную через `playwright-extension`: ввод и вставка, ошибочная ссылка и восстановление при отказе, клавиатурный фильтр/сортировку, включённые колонки и отсутствие значения, отмену/подтверждение удаления и серверный отказ. Для подтверждённых контрактов можно использовать существующие Express fixtures и выбор ответа; не симулировать доступность не согласованной операции. Записать наблюдения и блокеры по каждой реально реализованной ветке, не заменять browser-проверку unit-тестом. Автоматизированные E2E не добавлять, интерактивную проверку T проводить только с отдельным разрешением.

## Risks / Trade-offs

- Невалидный URL успевает отправить запрос до очистки → проверка при разборе, не только в эффекте нормализации.
- Ограничения QA расходятся с доступными API → отдельные условия готовности для командного поиска, сортировки, двух колонок и удаления; подтверждение из моков не снимает блокеры.
- Несвежий счётчик домена или потерянный ответ → серверная проверка, перечитывание и отсутствие автоповтора; успех не выводится из состояния кнопки.
- Общие подписи или смежные дельты могут изменить другие экраны → ограничить отображение реестром, проверить значения URL/API и сверить синхронизацию OpenSpec отдельно.

## Migration Plan

Сначала выпустить независимое восстановление поиска и оформление статусов. По остальным веткам подключать интерфейс после подтверждения соответствующей возможности на T и отдельно фиксировать недоставленный объём по Jira. Миграции данных на фронте нет; не использовать адрес контура как переключатель. Откат интерфейса удаления отключает действие для будущих запросов, но не восстанавливает уже удалённые на сервере домены. Не закрывать MOS-935 целиком по локальной проверке или частичной поставке.
