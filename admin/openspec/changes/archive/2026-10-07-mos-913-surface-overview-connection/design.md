# Design

## Context

Мотивация описана в `proposal.md`. `SurfaceDetails` уже читает карточку через `useSurfaceDetailsQuery`, а `SurfaceDetailsContent` содержит вкладки с готовым редактором сценариев и заглушками подключения/обзора. Ключ кеша включает surfaceId; при ошибке обновления карточка сохраняется, а черновик сценариев инициализируется отдельно и не заменяется фоновым ответом. Существующий component-тест проверяет разделение успешной записи и ошибки следующего чтения.

`SurfaceDetails` в `entities/surface/model/types/surface.types.ts` сейчас является узким Pick generated DTO, runtime-схема в `api/surface-registry-client.ts` проверяет только используемые поля. В `docs/api/contracts/surfaces.openapi.json` полный `SurfaceDetailResponse` уже включает подключение, анкету, конфигурацию, метрики и даты. `connection` и `stats` обязательны как объекты; null допускается у `embed_code`, `authorization`, `channel_id` и отдельных метрик. Допущение `stats=null` из списка поверхностей не переносится автоматически на detail.

HTML-прототип содержит полезную компоновку карточек, но собирает код с фиктивным токеном, подменяет проверки предположениями и использует заглушку инструкции. По ответу пользователя инструкция ведёт в существующий общий `/docs`.

## Goals / Non-Goals

**Goals:** единый серверный снимок для двух новых вкладок; строгая проверка используемых полей; сохранение кеша и черновика при ошибках; тестируемое различие фактов и результатов проверок.

**Non-Goals:** независимые запросы для каждой вкладки, новый механизм кеширования, генератор кода подключения, изменение регистрации, новые статьи, перевод всех вкладок карточки в URL-state. Границы бизнес-операций перечислены в proposal.

## Decisions

### 1. Расширить существующую модель чтения

Расширить Pick от generated `SurfaceDetailResponse` полями обзора, подключения, дат, статистики и используемой частью configuration. Runtime-схема должна проверять все читаемые поля и вложенные объекты; для чек-листа достаточно валидировать `configuration.greeting`, остальные поля конфигурации сохранять через loose-схему. Не утверждать runtime-валидацию полной конфигурации, если проверено только приветствие. Отсутствие обязательного поля и неверный тип — ошибка контракта, не default и не `null`.

Сохранить текущий HTTP transport и query. Отдельные DTO с вручную повторёнными API-типами и отдельные запросы для вкладок увеличили бы риск расхождения с регистрацией и кешем, поэтому не нужны. Generated schema и опубликованный контракт не редактируются вручную.

### 2. Разместить представления у существующего владельца

Добавить приватные компоненты подключения, обзора и чек-листа в `widgets/surface-details/ui/surface-details/`, по одному компоненту на файл. Передавать им серверные данные через props, оставляя существующий query и контроллер черновика у владельца. Общий `SurfaceDetailField`, карточки, кнопки и вкладки переиспользовать там, где подходят. Props размещать в `types/*.types.ts`, именованные UI-обработчики — в `handlers/`; предметные подписи/справочники, если нужны, — в `constants/*.constants.ts`. Внешние импорты слайсов — через публичный API. Не создавать feature или shared-обёртку для единственного потребителя без самостоятельной ответственности.

Компоновка следует прототипу: сведения/код слева, нагрузка/чек-лист справа; на узком экране одна колонка. Длинный код прокручивается внутри блока, длинные поля не ломают страницу. Текущая вкладка по умолчанию «Сценарии» сохраняется.

### 3. Копировать исходный текст средствами платформы

Использовать `navigator.clipboard.writeText` по действию пользователя. Проверка trim нужна только для доступности кнопки; в буфер передавать оригинал. Отображать код через текстовый React-узел в `pre/code`, без `dangerouslySetInnerHTML`. Серверные атрибуты, включая возможный настоящий data-token, не изменять. Успех показывать после resolve; reject/отсутствие API дают ошибку и возможность ручного выделения текста. Не добавлять библиотеку или устаревший скрытый механизм копирования.

Для инструкции использовать существующий паттерн `Link to="/docs"`, который сохраняет basename; label остаётся «Инструкция по встраиванию». Нового маршрута, статьи и API URL не требуется.

### 4. Показывать ограниченные факты, а не готовность к публикации

Чек-лист вычисляет три факта исключительно по сохранённому снимку: наличие доменов, хотя бы одного enabled_skill, непустого greeting. Не привязывать его к черновику редактора. Общая проверка обязательных параметров, уникальность доменов и песочница получают нейтральное состояние «Нет подтверждения» с объяснением отсутствия результатов проверок в API. Зеленые состояния фактов не называются общей успешной проверкой. Статус поверхности не заменяет результат песочницы. Полный реестр для доказательства уникальности не загружается.

Альтернатива — перенести формулы прототипа — отвергнута: наличие данных и статус не подтверждают серверные проверки. Спецификация `control-center-api-integration` также запрещает выдавать синтетические проверки за API-данные.

### 5. Сохранить единый кеш при обновлениях

Не очищать query data при ошибке чтения и не пересоздавать черновик при переключении вкладок. Добавить повтор чтения в предупреждение для уже загруженной карточки. При успешном PUT enabled-skills обновлять в существующем снимке только возвращённые `enabled_skills`, `status`, `updated_at`, сохраняя остальные поля spread-обновлением. Сейчас дата в локальном merge не обновляется; для обзора её необходимо учитывать до завершения refetch. При ошибке refetch показывать старые сведения как последние загруженные, а не как свежие, сохраняя успешный статус записи. После успешного refetch использовать новый серверный снимок без сброса несохранённого черновика.

Не применять placeholderData от предыдущего ID. Общая ошибка detail оставляет прошлый снимок целиком; при первичной загрузке невалидного ответа показывается ошибка. Частичного протокола ошибок по блокам контракт не предоставляет, поэтому самодельное восстановление отдельных невалидных полей не вводится.

## Risks / Trade-offs

- Старые тестовые ответы содержат только узкий DTO → дополнить затронутые fixtures контрактными полями; не ослаблять валидацию ради них. Runtime mock seed уже содержит connection с null-полями; фиктивный токен в seed не добавлять.
- При отсутствии серверных результатов часть чек-листа останется неподтверждённой → явно объяснять это рядом с пунктами, не создавать общей оценки готовности.
- Clipboard API может быть недоступен → код остаётся видимым, ошибка доступна, ложного успеха нет.
- После ошибки обновления данные могут устареть → предупреждение и retry, сохранение сведений важнее обнуления.
- Критерий задачи о пользователе без права изменения нельзя проверить в текущей модели → он явно отложен; новые вкладки не добавляют запись, существующее сохранение сценариев не ограничивается вымышленными permissions.
- Общий раздел документации не является новой специализированной инструкцией → это согласованный адрес; отдельная статья не входит в приёмку этого change.

## Migration Plan

Миграции данных и API нет. Расширить модель, обновить fixtures, подключить представления и пройти unit/component и проектные проверки. Развёртывание выполняется обычным выпуском фронтенда; откат возвращает заглушки новых вкладок, не меняя серверные данные. Browser/E2E-проверки в план не входят.
