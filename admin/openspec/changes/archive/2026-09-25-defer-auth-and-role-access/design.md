## Context

Мотивация описана в `proposal.md`. Изученный поток: `app/root.tsx` создаёт `ApplicationLayout` без `navigationAccess`; navigation использует `unavailable` по умолчанию и блокирует бизнес-ссылки. Это не работающая ролевая модель: источник разрешений отсутствует. Header отдельно запрашивает current principal, отображает роли и содержит callback-заготовку logout. Справка использует user ID для автопоказа.

HTTP-клиент содержит изменяемый token provider с mock Bearer в dev; `mocks/app.mjs` проверяет его перед каждой операцией. Маршруты mock server строятся по исходному OpenAPI и требуют handler для каждой операции, поэтому удаление Access требует явного изменения покрытия, а не простого удаления файла.

Исходные спецификации требуют подтверждённых прав, current principal, выхода, 28 mock-операций и Bearer. Дельты этого change заменяют эти требования. В рабочем дереве уже есть пользовательские правки оболочки, документации и E2E; их нельзя сбрасывать. Change `enforce-fsd-code-decomposition` не объединяется с этим изменением.

## Goals / Non-Goals

**Goals:**

- Удалить auth-зависимость на всём пути shell → HTTP → local mock, а не маскировать отсутствие прав значением «всё разрешено».
- Сделать отсутствие маршрута единственным навигационным ограничением из текущих auth/route-механизмов; сохранить все бизнес-ограничения.
- Согласовать правила агента, требования и проверки, чтобы последующие изменения не возвращали преждевременную авторизацию.

**Non-Goals:**

- Не реализовывать гостевую сессию, фиктивного администратора, permissions provider, feature flag обхода авторизации или будущий auth-интерфейс.
- Не менять реальный backend, его security policy, исходные OpenAPI и производные DTO.
- Не удалять бизнес-пользователей, контакты, команды, membership_role, зоны навыков и `connection.auth_required/auth_type`: они не являются правами посетителя админки.
- Не реализовывать отсутствующие `/ops` и `/teams`; не проводить несвязанный рефакторинг.
- Не создавать, редактировать или запускать E2E/browser-тесты без отдельного разрешения.

## Decisions

### 1. Удаление модели прав вместо положительного значения по умолчанию

Удалить `NavigationPermission`, `NavigationAccess`, permission-поля маршрутов, `navigationAccess` из layout и соответствующие ветви в navigation. Сохранить статическую готовность маршрутов и обычные React Router links. Прямое открытие страницы не получает новый auth guard. `/ops` остаётся неактивным из-за отсутствия маршрута.

Альтернатива «передать все permissions=true» сохраняет неподтверждённую модель и auth-заготовки; она отклонена. Общая абстракция policy/access не нужна.

### 2. Шапка без персонального профиля, справка как самостоятельный UI

Удалить runtime-слайс current principal после проверки всех импортов, отображение пользователя/ролей/scope, profile menu и logout props/состояния из header/layout/public exports. Не заменять профиль фиктивными ФИО или вечной ошибкой загрузки. Заголовок, бренд и мобильный переключатель сохраняются. Справка открывается отдельной кнопкой шапки с корректным фокусом и клавиатурным управлением.

Принятое минимальное UI-решение: не сохранять пустое меню профиля и не переносить его пункт «Команды и доступ» в новую заготовку; маршрута команд сейчас нет. Это не удаление команд как бизнес-сущностей.

Автопоказ справки использует локальный ключ версии без user ID. Старые per-user ключи не мигрируются и не читаются: первый показ после изменения допустим. При недоступном storage сохраняется отметка в памяти текущего сеанса. Тексты шага о профиле заменить описанием реально работающего UI. Не добавлять механизм определения анонимной личности.

### 3. Удаление технической авторизации клиента и mock server одним изменением

Из HTTP-клиента удалить token provider/setter и автоматическое добавление Authorization; оставить общий `headers` API, Accept/Content-Type, Idempotency-Key, валидацию ответа и ошибки. Не вводить запрет на стандартные явно переданные заголовки и не делать обработку 401/403 успешной.

Из mock server удалить token option/константу и Bearer middleware, сохранив request context, контрактную валидацию, идемпотентность и обработчики бизнес-операций. Удалить access handler и только current-principal fixture; справочники пользователей и бизнес-ссылки на них сохранить.

При обходе OpenAPI явно исключать ровно `GET /api/control/api/auth/v1/me`, а не все неизвестные обработчики или все операции с security. Отсутствующий handler любой бизнес-операции по-прежнему вызывает ошибку. `/api/auth/v1/me` возвращает стандартный 404. Тест покрытия ожидает 27 бизнес-операций и фиксирует единственное исключение; это осознанное изменение scope, не ослабление контрактной проверки.

Удалить ставший неиспользуемым клиентский define `VITE_CONTROL_API_MOCKS` и связанные ожидания тестов, если других потребителей нет. Серверный `CONTROL_API_MOCKS`, loopback, жизненный цикл mock server, proxy rewrite и отключение в production сохраняются.

Альтернатива оставить mock-токен «только для тестов» отклонена пользователем: обе стороны удаляются согласованно. Альтернатива переписать внешние OpenAPI отклонена: неопределённость авторизации не разрешает менять поставленные контракты.

### 4. Постоянное ограничение scope вместо временной оговорки в proposal

При реализации добавить явное ограничение в `AGENTS.md` и действующие поля `context`/`rules` файла `openspec/config.yaml`. Правила proposal/design/specs/tasks должны исключать auth/session/RBAC до отдельного согласования модели и API и нового spec change. Формулировка разрешает текущую задачу удаления auth-кода и не запрещает сохранение ошибок/валидации или предметных auth-полей навыков.

В актуальных `docs/tasks/control-center/frontend-backlog.md` и `analysis.md` достаточно заметной отметки текущего scope и отложенного статуса auth-задач/зависимостей; не нужно переписывать исторический анализ и исходные API. Обновить `mocks/README.md` под token-free работу и 27 операций. Архивные OpenSpec-изменения не менять. При синхронизации дельт обновить Purpose основной shell-spec, чтобы он больше не обещал достоверный профиль.

### 5. Проверки без браузера

Переписать затронутые unit/component-тесты с проверки блокировки прав на открытые существующие маршруты; сохранить проверки отсутствующего маршрута, активного пункта, basename, мобильного закрытия и клавиатуры. Header/layout проверяют отсутствие auth-fetch и фиктивной личности; справка — первый/повторный показ, новую версию и недоступный storage.

HTTP-тесты проверяют отсутствие автоматического Authorization в dev/prod, идемпотентность и сохранение 401/403. Server-тесты выполняют 27 бизнес-операций без токена, сохраняют схемы, 422/404/409, повтор мутаций и изоляцию данных. Устаревшие тесты удалённого current-principal клиента удаляются вместе с клиентом, но бизнес-проверки не ослабляются.

## Risks / Trade-offs

- [Открытую навигацию примут за доступ к защищённому backend] → Явно документировать, что серверная авторизация не меняется и 401/403 остаются ошибками; данный этап не является production-auth решением.
- [Удаление токена только с одной стороны ломает разработку] → Выполнить клиентскую и mock-часть одной поставкой, проверить HTTP без credentials.
- [OpenAPI всё ещё содержит Access/security] → Сохранить источник неизменным, явно описать отложенный Access и узкое исключение покрытия; не пропускать другие операции.
- [Удаление principal затронет контакты и участников команд] → Удалять только session principal, сохранять users/contacts/member IDs и соответствующие тесты.
- [Старые E2E ожидают профиль и блокировки] → Не менять и не запускать их без разрешения; явно сообщить об устаревших сценариях и непроверенном browser-пути, не отключать их скрыто.
- [Предыдущие пользовательские правки пересекаются с change] → Перед реализацией перечитать текущие версии и diff; не откатывать и не заменять файлы целиком ради упрощения.
- [Вводная справка показывается повторно после миграции] → Допустимый одноразовый эффект перехода с per-user отметки на локальную отметку версии; новые посещения не требуют личности.

## Migration Plan

1. В apply обновить правила текущего scope и реализовать удаление auth-зависимостей, не синхронизируя основные спецификации раньше соответствующего поведения.
2. Одновременно перевести клиент и mock server на запросы без токена, обновить component/server-тесты и актуальную документацию.
3. Выполнить `yarn typecheck`, `yarn lint` без предупреждений, `yarn test`, `yarn format:check`, `yarn build` из-за изменения Vite-конфигурации. `yarn api:check` подтверждает неизменность производных DTO относительно исходного контракта. Не запускать browser/E2E.
4. Проверить diff и OpenSpec validation. После приёмки синхронизировать дельты штатным OpenSpec workflow, отдельно исправить Purpose shell-spec и не переписывать архив.
5. Если откат необходим, откатывать только изменения этой поставки в клиенте, mock server, правилах и тестах совместно, сохраняя исходные пользовательские правки. Возврат к разработке авторизации требует отдельного согласованного change, а не включения скрытого флага.
