## Context

Мотивация и согласованная трактовка [MOS-1702](https://task.mos-team.ru/browse/MOS-1702) — в proposal.md. В Jira слово «модалка» использовано обобщённо; в обсуждении подтверждены toast для обычного успеха, модальный результат выгрузки и две кнопки только при наличии формы параметров.

Дополнительный скриншот переписки с менеджером, предоставленный пользователем, показывает inline-сообщение после кнопки «Выгрузить диалог» в карточке. Это прямой экспорт без параметров: подтверждённый сценарий требует модального результата только с «Закрыть», без подписи под кнопкой. Уточнение не расширяет согласованную границу на ошибки и валидацию.

## Goals / Non-Goals

**Goals:**

- Общая доступная UI-инфраструктура без знания бизнес-сущностей и optional-модулей.
- Событийное подтверждение ровно одной завершённой операции, без эффекта, повторяющего cached success при монтировании.
- Сохранение формы при переходе к результату и обратно, без вмешательства в транспорт.

**Non-Goals:**

- Глобальный обработчик всех mutation-success, система истории уведомлений или новый event bus.
- Перенос ошибок в toast, переписывание существующих toast поверхностей, изменение auth/session, API, моков или незавершённых бизнес-фич.
- Механическая замена `role="status"`, `message` или текста со словом «сохранён»: это затронуло бы прогресс, восстановление и предупреждения.

## Decisions

### 1. Использовать установленный Toast API, а не копировать provider поверхностей

Предусмотреть небольшой публичный UI-сегмент `app/shared/ui/notifications/` на основе Base UI Toast. Его provider подключается в композиции приложения внутри существующей границы бизнес-UI; сегмент предоставляет уведомление об успехе, но не знает запросов или сущностей. Разметка, доступность, пауза таймера и жизненный цикл опираются на API библиотеки, а не новый самописный менеджер.

Предлагаемый визуальный default: правый нижний угол, автоматическое закрытие через 5 секунд, явная кнопка закрытия. Взаимодействие приостанавливает таймер. Это технический default, а не утверждение о точных размерах макета Jira. Toast внутри открытого Dialog должен оставаться видимым и объявляемым; проверить совместимость portal/модального слоя, не лечить её произвольными z-index и отключением модальности.

Альтернативы: Sonner добавляет ненужную зависимость; импорт provider из widget нарушает границы слоёв; самостоятельный менеджер повторяет существующее API. Адресные исключения lint для нового compound-файла не добавлять: отдельные компоненты и декларации размещаются по правилам проекта.

### 2. Владельцем успешного события остаётся бизнес-операция

Уведомление вызывается в существующем обработчике подтверждённого завершения, после обязательных предметных проверок. React Query callbacks и существующие async-handlers сохраняют ответственность за invalidation, чтение и guard устаревшего результата. Не подписываться глобально на MutationCache и не запускать уведомления через effect от `isSuccess`: иначе появятся дубли и ложный успех на промежуточных шагах.

В handlers со смешанным `message` отделить успешную ветку от ошибок и объяснений, не классифицировать по поиску слов в строке. Для справочников учитывать частичное сохранение: сообщение о неполном результате/необходимом чтении остаётся на экране, а не превращается в безусловное «всё сохранено». «Нет изменений» не считается выполненной серверной операцией. Ссылки созданной записи, recovery-действия, предупреждения и содержательные финальные экраны регистрации сохраняются; удаляется только дублирующий краткий статус.

Альтернатива — общий success-компонент поверх `isSuccess` — проще внешне, но связывает показ с рендером, а не событием.

### 3. Общий результат выгрузки, локальное управление формой

Предусмотреть переиспользуемое представление результата в `app/shared/ui/export-result/`: заголовок, безопасное текстовое имя при наличии, сообщение о передаче браузеру, действия закрытия и необязательного возврата. Компонент не загружает файлы и не владеет полями формы. Он встраивается в существующий Dialog; для прямых выгрузок владелец действия открывает Dialog только после успешной передачи файла.

```text
With parameters:
FORM --> PENDING --> RESULT --> CLOSED
             |          |
             v          v
        FORM + ERROR   FORM (same values)

Without parameters:
ACTION --> PENDING --> RESULT --> CLOSED
              |
              v
         INLINE ERROR
```

Form state должен жить дольше переключаемого содержимого: поднять уже существующее состояние/экземпляр формы к ближайшему владельцу диалога либо сохранять форму штатным механизмом React, не вводя отдельное хранилище черновиков. Скрытая форма не участвует в tab order и accessibility tree. «Назад к параметрам» очищает завершённый mutation/result state, но не значения формы. Автоматический export при reset/return запрещён. Существующие информационные запросы формы, например счётчик, остаются штатными и не считаются повторным экспортом.

При закрытии сбрасывается результат; правила defaults при новом открытии не унифицируются между разделами. У прямого экспорта навыков и экспорта карточки/отмеченных диалогов нет формы — поэтому только «Закрыть». Если обработчик сейчас теряет безопасное имя файла, можно передать уже доступное имя в UI без изменения transport/контракта; выдуманное имя не показывается.

Альтернативы: второй Dialog создаёт вложенный focus trap; общий «мастер экспорта» переносит предметные поля в shared и чрезмерно расширяет change.

### 4. Добавить сквозную capability без переписывания предметных контрактов

`operation-feedback` определяет новый presentation-контракт. `dialog-export`, `dialog-saved-filters`, `knowledge-base-export`, `ab-testing-export`, `response-templates-export` сохраняют правила запроса, достоверности и ошибок. Требование «показать успех» выполняется новым представлением; менять схемы payload или дублировать все предметные требования не нужно.

### 5. Проверять результат и сохранение поведения

Общие component-тесты проверяют toast, таймер/паузу, клавиатуру, повтор действия и отсутствие повторного показа на rerender. Тесты интеграции каждого владельца проверяют правильный момент успеха, отсутствие успеха при отказе и сохранение ошибок. Экспорты проверяются для форм и прямых действий: один Dialog, возврат с точными значениями, отсутствие повторного export/download, новое открытие, Escape и возврат фокуса.

Для реализации запланировать интерактивные сценарии Playwright MCP на локальных моках, включая ошибку, клавиатуру и toast внутри Dialog. В config.yaml записана общая авторизация таких проверок, но AGENTS.md требует отдельного явного разрешения; планирование не трактуется как это разрешение. Перед запуском запросить его, при отсутствии разрешения/инструмента/приложения отметить проверку как незавершённую. Автоматические E2E и внешний UI не входят в разрешённый план проверок. В текущем planning workflow браузер приложения не запускается.

## Risks / Trade-offs

- Смешанные success/error сообщения → мигрировать успешные ветки, сохраняя объяснения частичных результатов и recovery на странице.
- Потеря настроек при unmount формы → тесты возврата для каждого семейства форм, хранение состояния у ближайшего владельца.
- Дубли при rerender или повторное открытие старого результата → событие завершения вместо наблюдения cached success, reset на возврате/закрытии.
- Toast скрыт модальным слоем → использовать штатную совместимость примитивов и проверять доступность внутри открытого Dialog.
- Асинхронный результат от старого объекта/контекста → сохранить существующие guards; уведомления не получают собственную auth-модель.
- Широкий scope «все разделы» → миграционная матрица выше и финальная проверка оставшихся кратких успешных сообщений; не превращать эту проверку в реализацию недостающих фич.
- Параллельный `add-skill-csv-export` и будущие export changes → менять только текущее представление, не помечать чужие задачи завершёнными; новая capability задаёт правило для последующих реализаций.

## Migration Plan

1. Ввести общий UI для toast и результата выгрузки, подключить provider и тестовые wrappers.
2. Перевести краткие подтверждения существующих бизнес-операций по матрице; сохранить объяснения, ошибки и навигационные элементы.
3. Перевести экспорты на результат в одном диалоге и проверить сохранение параметров.
4. Выполнить unit/component и статические проверки; интерактивные локальные проверки — после отдельного разрешения, записать результаты/блокеры.

Изменений данных, backend и конфигурации запуска нет. Откат — возврат UI-изменений без миграции данных; существующие запросы и безопасная передача файлов остаются прежними.
