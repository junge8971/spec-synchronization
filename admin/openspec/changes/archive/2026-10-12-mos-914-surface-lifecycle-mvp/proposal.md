# Proposal

## Why

MOS-914 нужно привести к согласованному MVP: песочница и история отложены, а доступность действий определяется правилами аналитика, не permissive-поведением сервера. Сейчас публикация доступна из отключённой и архивной карточки, действия не сохраняют черновик сценариев, а архив допускает редактирование.

## What Changes

- Убрать запуск песочницы и требование проверки в ней из UI поверхности; сохранить чтение существующих статусов `review` и `sandbox` и совместимость API-клиента.
- Применить единые правила к обеим точкам публикации: `configured`, `review`, `sandbox`, хотя бы один выбранный сценарий и успешная валидация/сохранение текущих изменений. Из `draft` сначала требуется сохранение и полученный от сервера `configured`; из `disabled` — возврат в работу, из `archived` — восстановление. Из `prod` повторная публикация не нужна.
- Сохранить действия отключения (`prod`), возврата и архивирования (`disabled`), восстановления (`archived`). Архив закрыть для записи.
- Перед подтверждённой публикацией сохранять текущий состав сценариев с параметрами; ошибки подготовки, записи и обновления данных останавливают последовательность. Общая блокировка исключает конкурирующие записи и lifecycle-команды.
- Показывать фактический серверный статус, обновлять карточку и реестр, различать ошибку команды и ошибку последующего чтения. Восстановление само по себе не запускать как публикацию.
- Принять текущий мок без изменений и без дополнительных вопросов бэку. Не исправлять его переходы локальной подменой статуса.
- Сохранить публикацию в «Подключении» и lifecycle-действия в «Обзоре» по единым правилам карточки; сами сведения вкладок остаются только для чтения. Удалить отображаемую неподтверждённую проверку песочницы.
- После `409` предлагать «Обновить карточку»: только GET без автоматического повторения записи. После успешного чтения пользователь заново запускает доступное действие; публикация требует нового подтверждения.

Граница: существующий конфигуратор — заглушка. Этот change не создаёт редактор приветствия, оформления, карточек и саджестов и не имитирует сохранение отсутствующего черновика. Требование аналитика о сохранении всей карточки реализуется для доступных редактируемых данных; подключение полноценного конфигуратора остаётся отдельной работой. История, sandbox, auth/session/RBAC и изменения mock-сервера не входят в объём.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `surface-lifecycle-publication`: MVP-доступность действий, сохранение перед публикацией, общий запрет конкурирующих операций, read-only архив и достоверная обратная связь с учётом принятого мока.
- `surface-overview-connection`: согласование действий вкладок с lifecycle, checklist без песочницы и разделение сохранённых фактов и текущего черновика.

## Impact

- `app/widgets/surface-details`: обе кнопки публикации, checklist, lifecycle, редактор сценариев, сообщения и orchestration сохранения.
- `app/entities/surface`: переиспользование существующих mutation/query API; при необходимости уточнение результата refresh без потери факта успешной записи.
- Существующий `features/surface-skill-selection` используется через публичный API с сохранением проверки параметров и черновика.
- HTTP-контракт: существующие `PUT /enabled-skills`, `PUT /configuration`, bodyless POST lifecycle и GET detail. Новые endpoint, зависимости и ручная правка generated-типов не требуются.
- Unit/component-тесты изменённого поведения. E2E/browser-тесты не создаются и не запускаются.
- Заменяется прежнее требование основной спецификации о шести доступных UI-командах и об отсутствии согласованных клиентских ограничений. Правила аналитика теперь являются основанием бизнес-ограничений; они не являются RBAC.
