# Design

## Context

Мотивация и объём — в `proposal.md`. Проверены текущие карточка, lifecycle-компоненты, mutation hooks, API-тесты и основная спецификация.

- `surface-details-content.tsx` владеет черновиком сценариев и отдельной мутацией сохранения. Конфигуратор и история — заглушки.
- Header разрешает публикацию по `status !== draft`, checklist дополнительно смотрит сохранённые, а не редактируемые сценарии. В итоге две точки расходятся.
- `SurfaceDetailsPublishAction` непосредственно отправляет publish и открывает success для любого непустого ответа.
- `useSurfaceMutationController` обновляет cache и реестр, но ошибка refresh сохраняется отдельно и не отклоняет `run`. Нельзя считать resolved promise доказательством успешного refresh.
- `useUpdateSurfaceEnabledSkillsMutation` обновляет cache и запускает invalidation без ожидания свежего detail. Его `mutateAsync` недостаточно для перехода к публикации.
- Архивирование, отключение, возврат и восстановление уже вызывают существующие команды. API-клиент поддерживает bodyless POST и отдельные PUT, новые ручки не нужны.

Источники решений: правила аналитика определяют доступность действий; последняя выгрузка OpenAPI — формат запросов; решение пользователя «пока принимаем как есть» оставляет runtime-мок неизменным. Старый PDF, прототип и permissive-мок не расширяют бизнес-доступность.

## Goals / Non-Goals

**Goals:** единая orchestration текущей карточки, сохранение черновика перед publish, обработка частичного успеха и общий lock. Сохранить validation, accessibility, cache-поведение и чтение всех существующих статусов.

**Non-Goals:** полноценный конфигуратор, фиктивный PUT configuration для смены статуса, транзакция на сервере, версия конфигурации, исправление мока, auth/RBAC, sandbox и аудит. Не создавать универсальный workflow framework для одного сценария.

## Decisions

### 1. Единая политика действий и координатор карточки

Владельцем координации остаётся `widgets/surface-details`: здесь сходятся entity mutations и feature-контроллер сценариев. Выделить предметную функцию доступности и небольшой hook/handlers координатора, передавать одинаковые признаки и команды header, checklist и lifecycle. Не помещать UI-черновик в entity и не импортировать внутренности feature.

| Статус                        | Действия MVP                                                       |
| ----------------------------- | ------------------------------------------------------------------ |
| draft                         | Сохранение доступного редактора; публикации нет                    |
| configured / review / sandbox | Публикация после проверки и сохранения непустого состава           |
| prod                          | Сохранение доступных изменений, отключение; без повторного publish |
| disabled                      | Возврат в работу, архивирование; без прямого publish               |
| archived                      | Только восстановление из операций записи                           |

Чистую политику проверять в обработчике перед каждым запросом, не полагаясь только на disabled UI. Один синхронный lock на полную операцию плюс состояние для controls блокируют save/publish/lifecycle и изменение параметров даже при двух быстрых кликах. Не держать lock во время простого просмотра подтверждения; после подтверждения заново проверить доступность.

Альтернатива — отдельные проверки в каждой кнопке — сохраняет текущие расхождения и гонку между двумя mutation hooks.

### 2. Публикация как последовательность существующих запросов

После подтверждения: lock → проверить статус/непустой текущий выбор → `controller.prepare()` с существующей перепроверкой навыков → `PUT enabled-skills` через текущий mutation API → принять подтверждённый состав → дождаться успешного свежего GET detail → проверить статус и непустой сохранённый состав → bodyless POST publish → дождаться GET detail → проверить prod → показать успех → unlock.

На любой ошибке дальнейшие записи прекращаются. После успешного PUT черновик синхронизируется с подтверждённым составом; ошибка более позднего publish не изображается ошибкой сохранения. При ошибке PUT введённые данные не сбрасываются. Отдельное сохранение пустого состава остаётся допустимым вне архива.

Использовать TanStack Query и существующие query keys, без второго хранилища серверной карточки. Для гарантированного свежего чтения явно ожидать запрос, а не только fire-and-forget invalidation. Результат чтения передавать в вызывающую последовательность явно. Если меняется публичный результат общего mutation-controller, проверить всех его потребителей и тесты; прежний факт успешной mutation не превращать в rejected mutation из-за GET.

Контракт обязательного refresh: успешный результат содержит `SurfaceDetails` именно из GET, начатого после соответствующего PUT/POST; неуспешный — отдельную ошибку чтения. Результат mutation хранится независимо. Координатор проверяет возвращённый `SurfaceDetails`, а не `surface` из замыкания, boolean либо React-state `refreshError`, который ещё мог не обновиться.

У обновления detail должен быть один владелец. Для записи сценариев заменить fire-and-forget detail invalidation на управляемое чтение: после успешной записи отменить/исключить ранее начатый detail-запрос, пометить detail устаревшим без запуска второго фонового refetch и явно дождаться нового GET через Query API. Старый запрос не может обновить cache поверх нового. Инвалидация реестра остаётся независимой. Для lifecycle использовать тот же принцип в существующем контроллере, не добавляя параллельный GET из widget. Единый lock охватывает обязательное чтение. Тест с отложенными ответами должен подтвердить порядок PUT → новый GET → POST → новый GET и отсутствие публикации по старому ответу.

Отдельное сохранение draft также ожидает свежий detail: подтверждённый configured с валидным непустым составом открывает обе кнопки публикации; подтверждённый draft оставляет их недоступными. Ни один вариант не отправляет PUT configuration или автоматический publish. Положительный сценарий моделируется component-fixture и не утверждает, что текущий runtime-мок умеет этот переход.

Альтернатива — сразу POST publish или повтор сохранённого серверного состава — теряет пользовательские изменения. Перезапись configuration текущим detail ради видимости «сохранена вся карточка» недопустима: editable draft отсутствует, а mock дополнительно меняет статус.

### 3. Серверное состояние и раздельные результаты

Различать этапы подготовки, записи сценариев, публикации и чтения. При ошибке команды оставить последний подтверждённый снимок; успешные предыдущие записи не откатывать локально. Повтор неуспешной публикации проходит подготовку заново. Если POST уже успешен, но GET неуспешен, кнопка повторяет только чтение. Success modal допускается лишь после подтверждения prod ответом команды и свежей карточкой.

Для ошибок сохраняется `ApiError`: 404 — поверхность недоступна, 422 — проверить данные, 409 — конфликт состояния и предложение обновить карточку. Если сервер передал `SURFACE_ARCHIVED` или `INVALID_STATE_TRANSITION`, можно дать соответствующее пояснение без объявления этих кодов гарантированной частью OpenAPI. Неожиданный `SANDBOX_CHECK_REQUIRED` не запускает sandbox: показать невозможность публикации при текущем ответе сервера и сохранить состояние. Не обещать пользователю повтор, который обязан сработать.

409 обрабатывается отдельно от общего retry: показать «Обновить карточку», не запускать автоматический GET и заблокировать повтор конфликтной последовательности во всех точках до успешного чтения. По нажатию выполнить только GET, сохранив несохранённый черновик. При ошибке GET оставить повтор только чтения. При успехе пересчитать доступность, но не продолжать оборванную цепочку: пользователь заново выбирает действие, а publish открывает новое подтверждение и выполняет полную подготовку. Этот порядок действует и для 409 на этапе PUT. Обновление не обещает устранить SANDBOX_CHECK_REQUIRED; sandbox не вызывается. Альтернатива «обновить и сразу повторить POST» отклонена, поскольку обновление данных не означает согласия на повторную запись.

Enable/restore не отправляют publish. При принятом mock-ответе prod показать prod и факт восстановления/возврата, не успех публикации. Не подменять результат configured. Правило аналитика о configured остаётся ожидаемой бизнес-семантикой сервера, но её исправление не является задачей этого change.

### 4. Минимальные UI-изменения

Удалить sandbox trigger и пункт обязательной sandbox-проверки, не удаляя API-метод или поддержку статуса. Архивную карточку сделать read-only во всех точках записи и заменить текст «доступна для редактирования» пояснением восстановления. История остаётся честной заглушкой. Embed-код, Clipboard API, формы регистрации и каталог навыков не меняются.

Сохранить две точки публикации: шапка и «Подключение»; сохранить lifecycle в «Обзоре». Delta `surface-overview-connection` заменяет прежние общие запреты записи и команд во вкладках адресным разрешением этих действий. Сведения вкладок по-прежнему read-only; открытие вкладки ничего не записывает. Факты checklist остаются серверными, доступность publish учитывает текущий черновик. При их расхождении пояснить предварительное сохранение; это не основание переписывать серверные факты локальным выбором. Песочницу удалить из checklist, а не оставить как невыполненное требование.

Размещать новые типы в `types/*.types.ts`, предметные константы в `constants/*.constants.ts`, именованные UI-обработчики в `handlers/`; один React-компонент на файл, внешние импорты только через публичные API слайсов. Использовать существующие Dialog/Button/live-feedback, без новых зависимостей.

## Risks / Trade-offs

- [Нет конфигуратора] → этот change не закрывает полный путь создания draft → configured. Не обещать полное выполнение исходной MOS-914; сценарий конфигурации остаётся отдельной зависимостью.
- [Мок возвращает предыдущий статус при восстановлении и configured после PUT configuration] → не менять мок, не подменять UI-статус; отдельно тестировать ответы configured и prod тестовыми fixtures. Это принятие ограничения, не доказательство корректности бэка.
- [Нет атомарного сохранения всей карточки] → фиксировать частичный успех, не делать rollback-команды или автоматические повторные записи. Новый конфигуратор позднее потребует подключения своей записи до publish.
- [Сервер может измениться между проверкой и командой] → клиентская политика не заменяет серверные ограничения; обработать отказ, обновить карточку, не добавлять несуществующие version-поля.
- [Изменение общего mutation-controller затрагивает configuration lifecycle] → предпочесть минимальное совместимое расширение результата refresh и проверить всех потребителей, не переписывая соседние сценарии.
- [Текущие component-тесты закрепляют sandbox и публикацию из disabled] → заменить именно эти ожидания новой политикой, сохранив проверки ошибок, повторов, отмены, фокуса и параметров.

## Migration Plan

Миграции данных и контракта нет. Реализовать политику и координатор, подключить все кнопки, обновить unit/component-тесты, затем выполнить проверки проекта. Runtime-mocks и их контрактные тесты не переписывать. Откат — отмена UI-change без преобразования данных; уже выполненные бизнес-команды не откатываются автоматически.
