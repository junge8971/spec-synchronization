# Design

## Context

Мотивация приведена в proposal.md. MOS-911 уже реализован коммитом 81b21e7 и архивирован. Общий редактор используется widgets регистрации и карточки; переписывать композицию не требуется.

В актуальном OpenAPI есть SkillStatus, status в list/detail и query status. getSkillRegistry уже передаёт этот фильтр. useSkillsCatalogQuery пока использует ключ ['skills', 'catalog'] без фильтра. SkillDetailsForSelection не включает status; validateSelectedSkill сначала проверяет наличие в каталоге. prepareEnabledSkills сводит любые ошибки detail к detail-error. Это не позволяет отличить выход из prod от удаления и ошибки сети.

При исследовании yarn api:check прошёл, целевые тесты редактора и двух widgets дали 34 passed / 11 failed. В fixtures карточки отсутствует обязательный status списка; в detail fixtures обоих экранов отсутствуют status/intents, которые runtime-схема уже требует. Эти данные нужно обновить без ослабления runtime-валидации и тестовых утверждений.

Действующая surface-skill-selection spec требует общий реестр без prod-фильтра. Новый delta явно изменяет три требования; прочие правила параметров и сохранения остаются действующими.

## Goals / Non-Goals

**Goals:** использовать серверный prod-фильтр во всех новых выборах, проверять свежий status выбранных навыков, сохранять черновик и давать точную причину блокировки.

**Non-Goals:** новый eligibility endpoint, изменение статусов из редактора поверхности, новая архитектура форм, новые библиотеки, изменение API и типов параметров. Статус prod не трактуется как разрешение для конкретной поверхности.

## Decisions

### 1. Серверный фильтр и отдельный кэш результата

Переиспользовать getAllSkills с status=prod, pageSize=100 и текущей сортировкой. Обобщённый entities hook получает status аргументом и включает его в query key; feature передаёт prod. Проверить все вызовы hook, чтобы общий реестр других экранов не оказался отфильтрованным. Не подменять существующий общий cache key продовым содержимым.

Все страницы используют одинаковый фильтр. На границе feature дополнительно не допускать non-prod записи к новым выборам, если сервер вернул их вопреки фильтру; это не замена серверной фильтрации. Группы и массовое включение используют только эту выборку. Полная загрузка всех статусов с локальным фильтром отвергнута: контракт уже позволяет не загружать лишние записи.

### 2. Сохранённый выбор живёт отдельно от продового каталога

Существующие selectedSkillIds и parametersBySkillId сохраняются независимо от каталога. Не отбрасывать ID на refetch или массовом включении. Detail-запросы выполняются для всех выбранных ID, в том числе отсутствующих в продовой выдаче. SkillDetailsForSelection получает status из существующего SkillDetails; не создавать отдельный enum или заново описывать DTO.

Модель проверки различает: non-prod по валидному detail; not-found по 404; detail-error по прочим отказам; несогласованное наличие, когда detail=prod, но полный продовый каталог не содержит ID. Ошибки первоначальной загрузки и prepare должны иметь одинаковую классификацию. Сохранить причины отказов loaders вместо сведения всех rejected результатов к одной ошибке. ApiError уже даёт HTTP status; никаких дополнительных endpoints для диагностики не нужно.

Non-prod и подтверждённо отсутствующие записи показываются отдельно с названием из detail/известного кэша или ID, доступным явным снятием и сохранёнными параметрами. Ошибки чтения получают retry, без ярлыка «удалён». Общий счётчик включает проблемные ID; отдельная подпись объясняет их количество. Снятие домена относится к его показанным prod-записям; «Снять все» явно очищает весь выбор. Это избегает скрытого удаления проблемных записей.

### 3. Финальная проверка перед существующими мутациями

Сохранить имеющийся prepare: обновить полный prod-каталог и details выбранных навыков, затем проверить status, принадлежность каталогу и параметры. Одного status из списка недостаточно: detail может уже сообщать переход в sandbox. Одного detail недостаточно при расхождении со списком: блокировать с retry до согласованного чтения.

Не принимать сохранённый в кэше успешный detail за результат неудачного свежего запроса. При ошибке реестра не классифицировать отсутствующие ID по частичной/старой выдаче. Блокировать запись, сохранять черновик. Выбор и повторная отправка остаются заблокированными во время prepare/мутации. Если последующий retry подтверждает возвращение в prod, снять статусную проблему без сброса значений и повторно проверить схему.

POST регистрации и PUT enabled-skills не меняются. Минимум одного сценария при регистрации и допустимый пустой состав карточки сохраняются. Server error после проверки не приводит к успеху или очистке черновика. Клиент не обещает атомарности: в контракте сохранения нет expected_version навыков.

### 4. Тексты, документация и проверки

В UI описывать «Навыки в проде» и пустое состояние «Продовые навыки не найдены». Технические оговорки об отсутствующем eligibility API оставить в документации, не перегружать ими основной пользовательский поток. Обновить устаревший абзац mocks/README.md о невозможности prod-фильтра.

Fixtures довести до существующих обязательных полей status/intents; намеренно невалидные ответы оставить отдельными негативными сценариями. Unit-тесты проверяют классификацию и сохранность параметров, component-тесты — выбор/счётчики/проблемные записи и оба способа сохранения. Client-тесты проверяют status на каждой странице; серверные тесты — уже поддерживаемую фильтрацию, без придумывания новых backend-ограничений PUT. Архив прежнего change остаётся историческим документом.

## Risks / Trade-offs

- Смена статуса между последним GET и записью → отображать серверный отказ без потери данных; гарантировать лишь проверку по последним успешным чтениям.
- Prod-список и detail могут расходиться во времени → блокировка с повтором вместо неверного утверждения об удалении; больше запросов, но endpoints уже используются.
- Сохранённая поверхность может содержать non-prod навыки → явное исправление состава пользователем, без автоматической миграции или очистки серверных данных.
- Кэш detail может хранить успех при текущей ошибке → учитывать состояние последнего запроса, покрыть отдельным тестом.
- 11 исходных падений могут включать дополнительные причины помимо fixtures → после исправления fixtures разбирать оставшиеся ошибки по существующим утверждениям, не ослаблять их.

## Migration Plan

Сначала обновить fixtures и запрос каталога, затем модель проверки и UI, затем интеграционные тесты обоих экранов. Изменений хранилища, generated API и backend не ожидается. Завершить проверками проекта и новым delta spec; исходный архив не редактировать. Откат frontend восстанавливает прежний выбор без удаления сохранённых на сервере параметров, но возвращает возможность выбора non-prod, что нужно учитывать при решении об откате.
