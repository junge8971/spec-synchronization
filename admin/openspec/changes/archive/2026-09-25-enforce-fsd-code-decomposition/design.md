## Context

См. `proposal.md` о мотивации и объёме. Приложение использует React Router Framework, TypeScript, React Hook Form, Zod и shadcn. Корень исходников `app/` одновременно содержит framework entrypoints и FSD-слои; создавать вложенный `app/app/` только ради названия слоя не требуется.

Наблюдаемые точки миграции:

- `features/surface-registration/model/surface-registration.ts` объединяет типы, runtime enum, справочник шагов, значения по умолчанию, схему и преобразования.
- `model/use-surface-registration.ts` объединяет оркестрацию формы и обработчики, замыкающие её состояние.
- `widgets/skills-registry/ui/skills-registry-states.tsx` содержит три компонента и тип props.
- Большинство страниц размещены как `app/pages/*.tsx`; пути route-модулей поступают в `app/routes.ts` из `shared/config/application-routes.ts`.
- `app/root.tsx` экспортирует framework-компоненты и `links`; `shared/ui/card.tsx` содержит составные shadcn-компоненты.
- Установлены `eslint-plugin-react`, `eslint-plugin-import`, `typescript-eslint`; проверок FSD сейчас нет. Полная и staged-команды ESLint не блокируют предупреждения, несмотря на существующее требование.
- В рабочем дереве уже есть пользовательские изменения. Их нельзя откатывать или заменять исходниками из HEAD.

Существующая спецификация проверки упоминает E2E без ограничения, тогда как `AGENTS.md` запрещает их без отдельного разрешения. Delta уточняет это ограничение, не добавляя E2E в миграцию.

## Goals / Non-Goals

**Goals:**

- Единообразные места объявления и понятные границы владения без глобальных технических свалок.
- Контроль структуры всего приложения, включая новые слайсы, без постоянного списка legacy-исключений.
- Сохранение поведения, типовой выводимости, framework-экспортов и генерации.

**Non-Goals:**

- Переписывание маршрутизации, форм, состояния, UI и API-контрактов.
- Универсальный собственный архитектурный линтер или определение смысла любой функции по её имени.
- Перенос инфраструктуры, серверных mocks и E2E в FSD.
- Создание пустых каталогов, отдельных файлов для каждой вспомогательной функции и barrel-файлов на каждом уровне.

## Decisions

### 1. FSD определяет владельца, технические папки находятся внутри сегментов

Направление зависимостей: слой приложения → pages → widgets → features → entities → shared. Слайсы одного слоя не импортируют друг друга. Внешние импорты слайса идут через его `index.ts`; внутри слайса используются прямые относительные импорты, а не собственный публичный API. Проверки учитывают также type-only импорты и re-export.

`shared` и слой приложения не делятся на предметные слайсы: shared-модули имеют собственные явные точки входа, без общего `shared/index.ts`. Общую логику размещают в нижнем подходящем слое только при реальной общей ответственности, а не ради обхода запрета импортов.

Страницы получают предметные каталоги `pages/<page>/ui/` и публичные API. Framework route-модули могут быть тонкими адаптерами в `app/routes/`, использующими эти API; зарегистрированные пути файлов меняются согласованно, URL остаются прежними. Метаданные навигации могут оставаться в shared, но сборка маршрутов и пути route-модулей принадлежат слою приложения.

Альтернатива с глобальными `app/types`, `app/constants`, `app/handlers` отвергнута: она размывает FSD-владение.

### 2. Размещение деклараций внутри владельца

Пример для регистрации поверхности:

```text
app/features/surface-registration/
|-- index.ts
|-- model/
|   |-- types/surface-registration.types.ts
|   |-- constants/surface-registration.constants.ts
|   |-- handlers/use-registration-handlers.ts
|   |-- schemas/surface-registration.schema.ts
|   |-- parse-domains.ts
|   +-- use-surface-registration.ts
+-- ui/
    +-- surface-registration-form/
        |-- surface-registration-form.tsx
        |-- types/surface-registration-form.types.ts
        +-- steps/
            +-- surface-details-step/
                +-- surface-details-step.tsx
```

- Именованные `type`/`interface`, включая props, находятся в `types/*.types.ts` ближайшего владельца. Анонимные объектные props выносятся в именованный тип; стандартные аннотации и использование готовых generic-типов не требуют новых алиасов.
- Выводимые из схем типы сохраняют `z.infer` и type-only зависимость от схемы; схемы не импортируют defaults, использующие эти типы. Проверяется отсутствие runtime-циклов.
- Runtime enum и фиксированные предметные справочники/defaults находятся в `constants/*.constants.ts`. Zod-схемы — в `schemas/`, а не в constants только потому, что объявлены через `const`.
- Локальные вычисления, hook results, callbacks библиотечных операций и изменяемые значения не считаются предметными константами. Массивы и объекты defaults сохраняют прежнюю семантику мутабельности и ссылочной идентичности.
- Именованные обработчики UI-событий находятся в `handlers/` соответствующего `ui`- или `model`-владельца. Простая JSX-привязка аргумента может остаться на месте; ветвления, валидация и последовательность эффектов выносятся. Преобразования и API-клиенты не объявляются обработчиками.
- Для обработчиков со state/form/router-зависимостями допустим специализированный React-хук в `handlers/`; hooks не вызываются в обычных функциях. Не вводить фабрики и искусственные контексты только ради перемещения кода.

Альтернатива «вынести каждый const и callback» отвергнута как изменение смысла требований и источник лишних зависимостей.

### 3. Один компонент на файл, вложенность по владению

Все собственные React-компоненты, включая внутренние, имеют отдельный файл. Приватные дети находятся в подпапках владельца. Если ребёнок имеет нескольких потребителей, его размещают у ближайшего общего допустимого владельца; не дублируют и не поднимают автоматически в shared. Файлы именуются kebab-case.

Тесты располагаются рядом с владельцем либо в его `tests/`; reusable fixtures/helpers следуют тем же правилам назначения. Локальные данные конкретного теста остаются в тесте. Тестовый harness-компонент при необходимости выделяется отдельно; тесты не становятся общим исключением архитектурных проверок.

### 4. Совместимость важнее механического переноса специальных файлов

- Сохранить `scripts/generate-api-types.mjs`, путь `shared/api/schema.d.ts` и команды генерации. Генерируемый файл не разделять вручную, не применять к нему правила рукописной структуры.
- Сохранить обязательные entrypoints, специальные экспорты и typegen React Router. При декомпозиции реализация специальных компонентов может выноситься, но framework-модуль сохраняет ожидаемые экспорты. Исключение допустимо только для действительно необходимого контрактного шаблона, а не всех route-файлов целиком.
- Shadcn не получает общего исключения. Перед изменением составных исходников подготовить точный список файлов, конфликтующих правил и последствий разделения для обновлений upstream. Запросить отдельное согласование исключений. Пока согласования нет, исключения не добавляются и эта часть миграции не считается завершённой; остальная работа может продолжаться.

### 5. Автоматизировать проверяемые признаки, не угадывать смысл

Первый выбор — установленный ESLint:

- `react/no-multi-comp` для компонентов;
- `no-restricted-syntax` с файловыми overrides для именованных типов вне разрешённых файлов;
- `import/no-restricted-paths` и ограничения импортов для слоёв и публичных API, с покрытием относительных путей и алиаса `~/`;
- `--max-warnings 0` для полной и staged-команд.

Границы должны охватывать автоматически обнаруживаемые слайсы, а не только сегодняшние имена. Сначала проверить возможности установленных правил на минимальных тестовых примерах. Если для структуры каталогов/новых слайсов их недостаточно, оценить готовый FSD-инструмент (например Steiger) и подключить только для доказанного пробела, зафиксировав совместимость и отсутствие дублирующихся проверок. Не создавать универсальную собственную AST-систему.

Все автоматизированные структурные проверки входят в `yarn lint`. Если архитектурная проверка требует полного дерева, staged-проверка запускает её по всему приложению, а не только переданным файлам.

Реализация использует `react/no-multi-comp`, core `no-restricted-syntax`, `import/no-restricted-paths` и `no-restricted-imports`; новые зависимости не нужны. Пути sibling-зон строятся при запуске ESLint по слайсам с `index.ts`/`index.tsx`, поэтому новый слайс получает те же границы. Размещение типов проверяется требованием `types/*.types.ts` и узкими file overrides. Согласованы точечные исключения shadcn: `react/no-multi-comp` — 15 перечисленных в `AGENTS.md` compound-файлов; для types правило допускает только `DrawerContextProps` в `drawer.tsx` и `SidebarContextProps` в `sidebar.tsx`.

Проверки получают исполняемые положительные и отрицательные примеры: слой вверх, соседний слайс, deep import, обход относительным путём, re-export, новый слайс, несколько компонентов, неверно размещённые типы, корректные внутренние импорты и допустимые generated/framework-границы. Тестовые нарушения не должны попадать в обычный lint приложения.

Смысл констант, сложных обработчиков и принадлежность компонента остаются обязательной частью агентской проверки и review. Не обещать семантическую полноту линтера и не навязывать префикс `handle` как способ её имитации.

## Risks / Trade-offs

- Большой объём перемещений → мигрировать снизу вверх небольшими проверяемыми этапами, не смешивать функциональные изменения.
- Скрытые циклы через barrels, enum или schemas → прямые внутренние импорты, type-only зависимости, unit-тесты и сборка.
- Stale closures или изменение порядка эффектов после переноса handlers → сохранить зависимости и покрытие submit/back/next, pending/error и повторных действий.
- Ложные срабатывания на framework/shadcn → контрактные тестовые примеры и только согласованные адресные исключения.
- Удорожание навигации по файлам → группировка по владельцу, отсутствие пустых папок и лишних barrels.
- Чужие незакоммиченные изменения → зафиксировать исходный status/diff, не использовать массовый reset/checkout, сверять итог по этапам.

## Migration Plan

1. Зафиксировать исходные проверки и пользовательский diff; составить конкретный список shadcn-кандидатов на отдельное согласование.
2. Обновить правила агентов и добавить тестируемые архитектурные проверки. Промежуточные нарушения устраняются миграцией, а не baseline-ignore.
3. Мигрировать shared, entities, features, widgets, pages и слой приложения; для каждого этапа обновлять все импорты и unit/component-тесты. Shadcn-часть завершать только после отдельного согласования исключений либо согласованного разделения.
4. Проверить весь рукописный код, в том числе оставшиеся провайдеры, test helpers и неиспользуемые legacy-каталоги. Удалять только подтверждённо ненужные файлы, без функциональных изменений.
5. Выполнить `yarn typecheck`, `yarn lint`, `yarn test`, `yarn format:check`, `yarn api:check`, `yarn build`; проверить отказ full/staged lint на предупреждениях. E2E не запускать и не редактировать.
6. Закрыть задачу только после полной миграции и согласования каждого оставшегося исключения. Откат — отмена собственных этапов миграции без затрагивания исходных пользовательских правок; данные и API не требуют миграции.
