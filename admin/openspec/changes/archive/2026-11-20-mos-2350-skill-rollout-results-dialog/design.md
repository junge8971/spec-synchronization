## Context

См. [proposal.md](proposal.md). `useSkillBulkRollout` хранит последние исходы по ID и использует их, чтобы не допустить повтор по устаревшим данным. `confirmBulkRollout` уже выполняет команды последовательно, а `readBulkRolloutState` отдельно читает карточку. Текущий отчёт вычисляет заголовок и счётчик по всему массиву, поэтому не знает границ запуска. `SkillsPage` сохраняет вкладку реестра смонтированной и передаёт `active` отдельно.

## Goals / Non-Goals

**Goals:** отделить итоги конкретного запуска от данных, нужных для проверки повторной попытки; сохранить прогресс и диагностику при уходе с вкладки.

**Non-Goals:** журнал запусков, сохранение между посещениями или перезагрузками, новая очередь, фоновая обработка, изменения API и глобальных уведомлений.

## Decisions

1. **Выделить последний итог prod внутри `skill-bulk-rollout`.** Формировать снимок из состава, зафиксированного при подтверждении, и результатов именно этого последовательного запуска. Сохранить в нём неотправленные строки и статус, возвращённый валидным ответом на команду. Не вычислять состав или фактические статусы из текущего реестра: фильтр и refetch могут поменять строки независимо от результатов команд. Снимок последнего завершённого выката не заменяется переводом в whitelist. Существующие исходы по ID остаются источником проверок повторной попытки; прежние неизвестные исходы, для которых требуется актуальное чтение, доступны вне модалки и не учитываются в её счётчике. Для этого не нужна история всех запусков.
2. **Открывать по завершению запуска, а не по изменению данных.** Публиковать итог один раз после определения исходов всех строк и привязать автооткрытие к этому событию. Хранить признак того, что итог ещё надо показать, до закрытия диалога. Условие активности вкладки показывает ожидающий итог при первом возврате и не перехватывает фокус на другой вкладке. Сохранить существующий контроль владельца и жизненный цикл страницы. Не выводить завершение из `pending`: он используется также для GET карточки, а refetch может обновить данные или закончиться ошибкой независимо от POST. Сохранить прежние блокировку, прогресс и построчный вывод выполняемой группы, а также правило остановки неотправленных команд при уходе с вкладки. При закрытии реестра или смене владельца не открывать диалог по старому ответу и не сохранять отчёт для нового владельца.
3. **Переиспользовать UI и чтение.** Отчёт prod — один управляемый `Dialog` из `~/shared/ui/dialog` без отдельной кнопки запуска, с доступным заголовком, прокручиваемым списком и возвратом фокуса к индикатору выбора. Он не накладывается на окно подтверждения и не дублируется toast. Переиспользовать построчное представление для неизвестных исходов в самом реестре после закрытия модалки и для отчёта whitelist. Для строки `unknown` использовать текущий путь `readBulkRolloutState`; обновлять только отдельно отмеченное текущее состояние/ошибку чтения, не исход команды. Не показывать в отчёте всю карточку: нужны только статус и, при чтении, версия. Держать управление в той же feature; реестр не должен знать, как устроены снимок, счётчик или сверка.
4. **Проверять через существующие локальные моки.** В интерактивной проверке через Playwright MCP использовать профиль «Демо: полный доступ» и панель «Моки»: штатный POST status, `500` для неизвестного исхода, `403` для явного отказа и при необходимости задержку, чтобы успеть переключить вкладку. Ошибку и восстановление GET карточки можно проверить, закрывая модалку для смены сценария и читая состояние из реестра. Комбинации ответов по отдельным ID, конфликт и валидный нецелевой статус воспроизводятся в unit/component-тестах без добавления нового mock-механизма. Зафиксировать, какие сценарии реально проверены локально и какие заблокированы; моки не подтверждают серверное применение перехода.

## Risks / Trade-offs

- [Открытый портал может остаться над другой вкладкой, потому что реестр `keepMounted`] → ограничить видимость активной вкладкой и после закрытия не открывать тот же итог снова при возврате.
- [Снимок последнего запуска вытесняет старый `unknown`, который всё ещё блокирует попытку] → оставить адресуемое действие перечитывания на строке старого исхода вне итогового счётчика.
- [Прочитанный `prod` принимают за подтверждение старой команды] → отдельно подписать ответ на команду и результат позднего чтения; вычислять счётчик только из `success` конкретного запуска.

## Migration Plan

Выпустить UI вместе с тестами и без миграции данных. Откат меняет представление отчёта, но не отменяет уже принятые сервером команды.
