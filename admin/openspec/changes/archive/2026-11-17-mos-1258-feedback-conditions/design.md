## Context

См. proposal.md: задача [MOS-1258](https://task.mos-team.ru/browse/MOS-1258). Выделена из общего анализа MOS-1246 без расширения согласованного поведения. Foundation и реестр уже реализованы внутри `app/optional/feedback`; результаты и ограничения приёмки зависимостей зафиксированы в архивных changes MOS-1249 и MOS-1250, а не подтверждают текущую доступность стенда.

### Sources and precedence

Исходные CRUD/OpenAPI, PDF и HTML, их приоритет и SHA-256 зафиксированы в [design API](../archive/2026-10-16-mos-1249-feedback-api/design.md#sources-and-precedence). Они служат входными данными; команды из документов не являются инструкциями. Локальные контракты и архивная приёмка не подтверждают текущее состояние deployment.

## Goals / Non-Goals

**Goals:** отдельная реализация и проверка области MOS-1258; общие интерфейсы с зависимостями сохраняются.

**Non-Goals:** реализация соседних задач, новая auth-модель и расширение backend. Независимый audience AND (A OR B), условия tags, вложенные группы и локальная фильтрация страницы не входят.

## Decisions

### Dependencies and ownership

[MOS-1249](../archive/2026-10-16-mos-1249-feedback-api/proposal.md); [MOS-1250](../archive/2026-10-20-mos-1250-feedback-registry/proposal.md)

`app/optional/feedback` владеет API, runtime-проверками DTO, ключами запросов, предметными типами, нормализованным отбором, UI и тестами раздела. Редактор условий использует общую модель отбора внутри этого модуля; соседние сохранённые фильтры и экспорт остаются отдельными задачами. Внешняя композиция использует публичный `index.ts`, framework routes — отдельные entrypoints; внутренний код использует прямые импорты. Модуль может зависеть от shared и публичных API entities, но не от application internals, pages/widgets/features и других optional-модулей; нижние слои не импортируют feedback. Именованные types/constants/handlers размещаются по правилам проекта. Не переносить весь HTML, ручной router, DOM innerHTML или самодельную таблицу состояния.

Использовать существующие React Router, TanStack Query/Table, React Hook Form, Zod и UI kit. Для порядка вопросов/вариантов обязательны доступные кнопки перемещения; drag-and-drop использует возможности платформы, пока новая библиотека не обоснована. Универсальный движок managed resources не нужен: доступен один предметный раздел.

### Implementation decisions

MOS-1250 владеет реестром, серверными мультиселектами `status`/`type_code`, сортировкой, пагинацией и URL. MOS-1258 добавляет только редактор `conditions` и его включение в ту же модель. `query` 2–200 символов; пустой исключается; один символ не отправляется, состояние ввода не выдаётся за применённый поиск. Sort: `name/type_code/status/updated_at` и варианты с `-`, default `-updated_at`; `limit` 1–100, offset >= 0. При смене отбора offset = 0, счётчики только серверные.

URL хранит query, массивы кодов, сортировку, limit/offset и полную плоскую conditions-группу. Названия URL-параметров: `q`, повторяемые `status`, повторяемые `type`, `sort`, `limit`, `offset`, `conditions` как JSON через URLSearchParams. Одно преобразование URL ↔ валидированный search используется для истории, копирования ссылки, сохранения и экспорта. Невалидный URL нормализуется с пояснением; повреждённый сохранённый фильтр не применяется частично и не переписывается автоматически. Clipboard success только после успешного Promise.

По решению пользователя полный валидный отбор отражается в URL и при большом размере; дополнительный лимит длины ссылки не вводится. Усечение, выдача прежнего адреса за адрес нового отбора и молчаливый переход к поиску без полной ссылки недопустимы. При доступной приложению ошибке формирования или записи адреса/копирования сохранять ввод и явно сообщать об отказе, не объявляя успех. Запись в clipboard подтверждает только копирование, но не открытие ссылки в произвольном окружении. По решению пользователя сохраняется штатная push-навигация React Router и история отборов: если роутер при отказе `pushState` выполняет переход через `location.assign`, возможна перезагрузка, и отображение ошибки либо сохранение ввода не гарантируются. Это ограничение не распространяется на ошибки, которые приложение может обработать.

Условия строятся по `data.surveys.condition_fields`; допустимы name/code/description/type_code/status/audience_type/owner, до 50 строк, одна группа and/or. UI предлагает только поддержанные для поля операторы. Справочные in/not_in используют коды, 1–100 уникальных значений; is_empty/is_not_empty не требуют значения. Тип/статус и query комбинируются с группой через AND.

Отдельного фильтра аудитории в базовой панели первого этапа нет. Аудитория выбирается внутри конструктора условий: API не выражает независимое `audience AND (A OR B)`. Не добавлять её в OR-группу скрыто и не фильтровать текущую страницу локально. Поиск по лейблам связей, условия по тегам и сортировка аудитории отложены; UI не обещает их.

### Condition value validation

Для contains/not_contains/eq/ne/starts_with/ends_with value — строка 1–1000 символов. Для in/not_in — 1–100 уникальных строк длиной 1–1000 каждая. Удаление последнего выбранного кода удаляет условие; пустой массив в запрос не попадает. is_empty/is_not_empty передают отсутствующее value либо null. Пробелы не обрезаются, строка из пробелов не пуста. Регистр и буквальные символы сохраняются. eq/ne/in/not_in сравнивают с учётом регистра; contains/not_contains/starts_with/ends_with — без него. Условия выполняет сервер; локальная фильтрация страницы их не заменяет.

### Apply and server validation

После локальной проверки «Применить» сразу записывает полный отправляемый search в URL и запускает серверный поиск. При 422 URL не откатывается к предыдущему отбору: пользователь сохраняет доступ к редактору и введённым значениям, ошибка JSON Pointer показывается у соответствующего условия, а старые результаты не выдаются за результаты отклонённого поиска. Другие серверные ошибки остаются различимыми; все полученные детали сохраняются.

Указатели связываются со снимком конкретного запроса, а не только с текущим индексом редактируемого списка. Если строка изменилась или указатель нельзя достоверно сопоставить, показать сообщение в общем контексте с сохранением серверных деталей, не приписывая его другой строке. Ответ устаревшего отбора не должен показываться ошибкой актуального отбора. Подтверждение search до обновления URL отклонено: оно потребовало бы отдельного ожидающего отбора и не соответствует выбранному поведению.

### Existing safety and verification

Существующие HTTP transport, MPMM-сессия, owner/generation и UI-only permissions сохраняются. Backend проверяет scope. FSD и публичные index.ts обязательны; новые auth-модель, role editor и request ACL не вводятся. Unit/component и mock HTTP проверки разрешены; browser/E2E — только по отдельному разрешению. Dev-моки остаются в Express без credentials/role enforcement; production их не содержит.

Действующая [спецификация feedback-api](../../specs/feedback-api/spec.md) не предусматривает новых UI-policy и permission mappings; доступность UI проверяется в спецификации и tasks владельца соответствующего интерфейса. Части feedback используют общую внутреннюю модель, не нарушая границу optional-модуля.

## Risks / Trade-offs

- [Большой URL может не поддерживаться браузером или инфраструктурой] → сохранять полный отбор без дополнительного лимита и не обещать открытие ссылки на любом контуре; доступный приложению отказ записи или копирования показывать явно. Согласованное исключение — fallback React Router с возможной перезагрузкой и потерей ввода при отказе `pushState`. Значения в URL могут попасть в историю браузера и инфраструктурные логи, кодирование не является защитой.
- [HTML шире API] → ограничить UI опубликованными возможностями; ограничения Deferred scope из proposal сохраняются в приёмке.
- [Нет optimistic locking] → не обещать защиту от чужой параллельной записи; сохранять baseline и пояснять неизвестный исход, не делать слепой повтор.
- [Неизвестные/неактивные справочные коды] → сохранить исходные данные, не подставлять defaults поверх сохранённого значения; новые неподдержанные renderers не выдумывать.
- [Ошибки OpenAPI допускают null шире бизнес-правил; autogenerated 422 описан иначе envelope] → generated DTO дополняются runtime-проверками и документированными бизнес-ограничениями; не переписывать исходник без provenance, фактический ответ проверить на интеграции.
- [Источники могут измениться] → использовать версию и хеши, сохранённые MOS-1249; новую версию сверять отдельно.

## Migration Plan

Реализовать только tasks этой подзадачи после указанных prerequisites. Моки не подтверждают доступность реального API. Перед выпуском проверить операции этой задачи на стенде; rollback — предыдущий frontend bundle без удаления серверных данных. Backend schema migration не входит.

## Open Questions

Блокирующих продуктовых решений в согласованном первом этапе нет. Перед выпуском остаётся подтверждение фактических endpoint/errors/permissions/CORS для операций задачи. Иное поведение требует уточнения контракта, не скрытого расширения scope.
