## Context

Мотивация и scope — в proposal.md. `scripts/generate-api-types.mjs` читает полный OpenAPI и поддерживает generate/check. `mocks/app.mjs` перечисляет операции этого же JSON и падает при отсутствии handler; единственное исключение — Access `/me`. `contract.mjs` валидирует входы и успешные ответы через AJV, `state.mjs` клонирует seed, `list.mjs` уже содержит пагинацию и однополевую сортировку.

Новая выгрузка добавляет только Assistant modules. Её security сохранится в документах, но локальные бизнес-моки по действующему соглашению не требуют Bearer. OpenAPI описывает формы данных, но не задаёт полные правила переходов, ошибок 404/409 и вычисления preview.

## Goals / Non-Goals

**Goals:** синхронное обновление источника, документации, generated-типов и работоспособного mock API; единое состояние для трёх представлений модулей; проверяемые локальные конвенции.

**Non-Goals:** UI модулей, клиентские query hooks, изменения auth, персистентная БД, новые зависимости, новый генератор разделов или общая машина состояний.

## Decisions

### 1. Единый источник и существующая генерация

Полный `docs/api/contracts/openapi.json` берётся из свежей выгрузки без семантических правок. Новый `assistant-modules.openapi.json` содержит пять исходных paths, транзитивное замыкание используемых схем и security schemes по образцу соседних разделов. Markdown описывает параметры, required/default/nullable, ответы и ограничения исходника. Индекс обновляется до 33 операций, 5 заполненных и 6 отсутствующих разделов. Остальные самостоятельные контракты остаются без изменений.

Типы создаются только `yarn api:generate`, согласованность проверяется `yarn api:check`. Альтернатива ручных DTO или собственного генератора не нужна.

### 2. Новый раздел в существующем mock server

Добавить `mocks/assistant-modules.mjs` и подключить его operationId-handler map в `app.mjs`. В `seed.json` добавить небольшую коллекцию: включённый разрешённый модуль, отключённый разрешённый модуль и включённый модуль с запретом отключения; предусмотреть предупреждение о последствиях. Использовать валидные UUID, required nullable-поля и fixed business actor (by), не текущего пользователя. Существующий structuredClone обеспечивает изоляцию; отдельный storage не нужен.

Summary и preview вычисляются из modules на каждом чтении, без дополнительных изменяемых snapshots. Summary считает total/enabled/disabled/disable_allowed/not_disable_allowed по всей коллекции. Любой disabled означает degraded/warning, отсутствие disabled — healthy/success. Preview содержит одну fallback-карточку на disabled-модуль, использует его user_message либо «Модуль временно недоступен». Caption, banner и sample_user_message — явные детерминированные mock-тексты, не попытка воспроизвести неизвестную backend-логику.

### 3. Ограниченные mock-конвенции мутаций

Порядок после schema-validation: найти модуль (404), проверить expected_version (409), для disable проверить disable_allowed и подтверждение непустого disable_impact_message (409), только затем изменить состояние. Любой отказ не меняет данные. Успех возвращает ModuleResponse, увеличивает version, обновляет updated_at/by; повтор целевого статуса с актуальной версией также считается успешной мутацией. Disable сохраняет user_message с default пустой строкой; enable очищает его до null.

Использовать существующие `sendSuccess`/`sendError`; новые 404/409 документировать в mocks/README.md как локальную конвенцию, не добавлять в исходный OpenAPI. Idempotency-Key для модулей не вводится: источник его не требует. Альтернатива выдуманной backend-спецификации отвергнута.

### 4. Query-массивы нормализуются на общей границе

В новой операции sort — массив enum, но сейчас `coerceParameter` преобразует только integer: один `?sort=name` будет отвергнут как строка. Для query-параметра с array-схемой нормализовать одиночное значение в массив перед AJV; повторённые значения уже приходят массивом. Не менять поведение scalar-параметров существующих операций. Проверить всех потребителей общей валидации и покрыть одиночный/множественный/невалидный sort тестами.

Список переиспользует `page`/`sort`. Упорядоченные критерии можно применить существующей стабильной сортировкой от последнего к первому, не вводя универсальный query engine. Локальные defaults: name; query — регистронезависимый поиск по code/name/description; status — точное совпадение, неизвестная строка даёт пустую выборку, поскольку схема не объявляет enum для фильтра. Limit/offset сохраняют контрактные defaults 20/0.

### Исправление общего sort (согласовано при реализации)

Новые тесты выявили прежнюю ошибку `list.mjs`: default accessor использовал исходный field с префиксом `-`, а не вычисленный key. Исправить accessor в общей функции, сохранив custom accessor API, стабильность и неизменность входного массива. Регрессионные тесты покрывают строки, даты, числа, nullable-поля, одинаковые значения и custom accessor; существующие HTTP-сценарии проверяют потребителей helper. Пользователь согласовал расширение change на это исправление.

### 5. Проверяемое покрытие вместо замены счётчиков

Сохранить fail-fast регистрации handlers. Обновить контрактный тест до 33/32 и проверять множество реально вызванных method/path либо operationId против всех бизнес-операций, а не только число ручек. Добавить пять успешных сценариев и отдельные связанные/негативные сценарии модулей в существующем node:test подходе. Проверить разрешимость ссылок самостоятельного раздела и соответствие его операций/схем полному источнику; существующую проверку актуальности generated-типов сохранить.

## Risks / Trade-offs

- Недокументированная семантика backend → все дополнительные переходы, тексты, поиск и 409 обозначить как mock-конвенции; не менять исходник под реализацию.
- Изменение общей query-нормализации → ограничить array query-схемами, проверить старые scalar sort и числовые параметры.
- Расхождение views после мутации → вычислять summary/preview из одной коллекции и тестировать цепочку disable/read/enable/read.
- Обновление только JSON ломает startup → контракт, обработчики и тесты поставлять вместе.
- Исходная выгрузка лежит вне репозитория → при реализации импортировать её в versioned OpenAPI; дальнейшие генерация и проверки не должны зависеть от пути Downloads.

## Migration Plan

Обновить источник и документы, перегенерировать типы, добавить seed/handlers/валидацию, затем обновить тесты и mock README в одном change. Запустить typecheck, lint без предупреждений, test, format:check, api:check и build (регрессия production isolation). E2E/browser-тесты не создавать, не менять и не запускать. Перед завершением проверить diff; rollback — совместный откат контрактов, generated-типов и моков, без миграции постоянных данных.
