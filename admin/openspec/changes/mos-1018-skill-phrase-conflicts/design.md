## Context

См. proposal.md. В прототипе используется поиск по локальному массиву. DTO фраз, GET карточки с intents, PUT intents, редактор MOS-945 и мастер MOS-942 уже реализованы. В `docs/api/contracts/openapi.json` отсутствует global-check метод; сохранение фраз не подтверждает отсутствие конфликтов.

## Goals / Non-Goals

**Goals:** достоверный результат проверки актуального ввода во всём серверном реестре.

**Non-Goals:** собственный классификатор, обход всех страниц GET навыков, клиентские permissions или имитация семантической близости.

## Decisions

- **BLOCKED API:** согласовать метод/тело, нормализацию (пробелы, регистр, Unicode, пунктуация), область поиска, исключение собственного навыка, exact/semantic, шкалу score и безопасные сведения о другой команде. Определить команду, для которой результат обязателен, и её серверную повторную валидацию. Без этого не добавлять guessed endpoint.
- Result относится к конкретному набору фраз/версии. При изменении ввода или skill ID сбрасывать пригодность результата; поздний ответ старого запроса не разблокирует новый ввод. Для запросов использовать существующий transport и AbortSignal.
- Exact блокирует согласованную отправку, semantic предупреждает; network error/pending/stale не являются «конфликтов нет» и не дают отправлять непроверенный набор.
- Backend возвращает допустимые детали; если название/ссылка другого навыка не раскрыты, показать нейтральное описание конфликта без отдельного запроса на раскрытие. Это не повод вводить RBAC на клиенте.
- Композицию редактора MOS-945 и результата выполнять общим widget/страницей, API-предикаты актуальности держать у предметного владельца, без cross-feature импорта.

## Risks / Trade-offs

- TOCTOU после проверки → серверная проверка при отправке обязательна в согласовании; UI не гарантирует глобальную уникальность самостоятельно.
- Ложная независимость от данных MOS-945 → переиспользовать опубликованный формат фраз и согласовать привязку результата проверки к версии/вводу, но принимать отображение конфликтов отдельно.

## Migration Plan

После API-gate заменить только unavailable-сценарий проверки; добавить unit/component проверки гонки, exact/semantic и ошибки. Без API остаётся неготовая интеграция, а не завершённая Jira-задача.
