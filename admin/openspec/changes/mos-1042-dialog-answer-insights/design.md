## Context

См. proposal.md. MOS-1041 предоставляет единый messages snapshot; готовых UI-блоков диалогов в проекте нет. PDF 2.3.1 определяет оценки и ответы как представления переписки, а не самостоятельные ресурсы.

## Goals / Non-Goals

**Goals:** чистые преобразования snapshot, одно представление оценки с несколькими потребителями и точное различение неизвестного основания.

**Non-Goals:** отдельный endpoint, редактирование оценок, вывод причин ответа по его тексту, несуществующие ссылки статей, связь с route steps.

## Decisions

1. **Gate:** принять detail-схемы messages/rating/basis в MOS-1041; проверить пять kind и принятую семантику вопроса (PDF 2.3.1, 8.14). Не трактовать проектный PDF как опубликованный OpenAPI.
2. **Один проход по сообщениям:** сохранять последнее сообщение user как вопрос; каждый non-user ответ получает эту связь. Несколько ответов подряд используют тот же вопрос; ответ до первого user получает явное отсутствие вопроса. Порядок при одинаковом occurred_at сохраняется из источника. Вопрос только с вложениями не превращается в пустой текст или предыдущий текстовый вопрос.
3. **UI-владелец:** преобразования и приватная вкладка рядом с карточкой. Общий компонент оценки поднять к ближайшему владельцу переписки и вкладки, не в глобальный shared по умолчанию. Поиск и вкладки не загружают messages повторно.
4. **Оценки:** messages.rating good/poor относятся к ответу, в том числе операторскому; operator_rating 1–5 относится к диалогу и уже отображается MOS-1041. Блок оценок включает только rating != null. Poor без comment всё равно показывает reason; good/poor не кодируются одним цветом, пояснения доступны с клавиатуры, а не только hover.
5. **Основания:** external_system, knowledge_base, model, operator_template, no_data; basis=null — источник не сообщил основание. Пояснение собирается из kind и автора, не угадывается по тексту ответа. Sources отображаются в исходном порядке, relevance 0–1 форматируется локализованно; null не заменяется 0. Model/no_data не получают выдуманных источников.
6. **Навигация:** title/code без url остаются текстом. Неподдерживаемые схемы URL не исполняются. Skill service_id не становится route UUID; применяется только resolver, согласованный в MOS-1041. Во вкладке время ответа не подписывать как время вопроса, хотя HTML ставит его рядом с вопросом.

## Risks / Trade-offs

- Ответ и вопрос связаны порядком, не reply_to → не обещать точную ветвящуюся связь, которой нет в контракте.
- Статья без URL → текст вместо привлекательной, но нерабочей ссылки.
- Будущий kind → контрактная ошибка/явная недоступность основания, не no_data по умолчанию.

## Migration Plan

После MOS-1041 добавить read-only представления и проверить все kinds, оценки, вопросы только с вложениями и ответы подряд. Не менять структуру detail API ради UI. Откат убирает представления, оставляя переписку и серверные данные неизменными.
