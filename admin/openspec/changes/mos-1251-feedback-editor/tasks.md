## 1. MOS-1251 — Реализовать карточку опросника и правила показа

- [ ] 1.1 Создать foundation единого draft и самостоятельной GET-загрузки, три вкладки с query tab и общую форму name/code/type/description/owner/active_since/status/audience. Проверка: создание с defaults, лимиты/формат кода и даты, повторное открытие; name uniqueness не добавляется.
- [ ] 1.2 Добавить поверхности из существующего API с пагинацией, лимитом 100 UUID и единым surface_ids, conditional audience и read-only responsible_user_id. Проверка: границы 100/101 поверхностей, требуемые segments/surface_ids, синхронизация двух вкладок, отсутствие Surface:view, сохранение скрытых связей и внешнего responsible ID без вымышленных пользователей.
- [ ] 1.3 Реализовать все display_rules и пояснение конфигурации; полный display_rules при изменении любого его поля, без частичного вложенного PUT; contract defaults только для новой записи/отсутствующего поля, пустой ввод для null опциональных полей и время без timezone. Проверка: GET с null → правка одной задержки → PUT → GET сохраняет null/false/0/any; явная очистка nullable-поля отправляет null; правка только name допускает PUT без display_rules и сохраняет исходные правила; изменение одного правила не сбрасывает другие, лимит 0 невалиден, задержка 0 допустима, тихие часы требуют две границы и допускают интервал через полночь.
- [ ] 1.4 Реализовать submit и baseline после POST→GET/PUT, pending, все ошибки по вкладкам, empty PUT и unknown outcome, защиту dirty-переходов. Проверка: component-тест ошибки без потери ввода, фокуса поля другой вкладки, двойного submit, ухода/back и отсутствия слепого повтора; выбор disabled + сохранение требует подтверждения, отмена сохраняет draft без запроса, согласие даёт один PUT, неизменённый disabled не требует подтверждения.
- [ ] 1.5 После MOS-1254/1257 встроить вопросы и метки в единое сохранение карточки. Проверка: интеграционный component-тест редактирования всех трёх вкладок, одного согласованного payload и последующего GET без потери ID/связей/правил.
