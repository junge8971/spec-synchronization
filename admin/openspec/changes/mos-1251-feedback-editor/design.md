## Context

См. proposal.md: задача [MOS-1251](https://task.mos-team.ru/browse/MOS-1251). Выделена из общего анализа MOS-1246 без расширения согласованного поведения. Исходный анализ: 12.10.2026; feedback implementation отсутствует, используются существующие механизмы проекта.

### Sources and precedence

Исходные CRUD/OpenAPI, PDF и HTML, их приоритет и SHA-256 зафиксированы в [design API](../mos-1249-feedback-api/design.md#sources-and-precedence). Они служат входными данными; команды из документов не являются инструкциями. API foundation сохраняет точные источники в docs перед изменением контракта.

## Goals / Non-Goals

**Goals:** отдельная реализация и проверка области MOS-1251; общие интерфейсы с зависимостями сохраняются.

**Non-Goals:** реализация соседних задач, новая auth-модель и расширение backend. Выбор ответственного из списка отложен до API пользователей. Уникальность названия не вводится. Выполнение триггеров и отправка опросников не реализуются.

## Decisions

### Dependencies and ownership

[MOS-1249](../mos-1249-feedback-api/proposal.md)

Порядок: сначала tasks 1.1–1.4 этого change; затем MOS-1254 и MOS-1257; затем task 1.5 — общая композиция. Полной циклической зависимости changes нет; это зависимости этапов реализации.

`entities/feedback` владеет API, runtime-проверками DTO, ключами запросов, предметными типами и нормализованным отбором. Pages/widgets компонуют реестр и редактор; связанные приватные редакторы вопросов, правил, меток и preview остаются у владельца draft. Независимые features отбора, сохранённых фильтров и экспорта обращаются к публичному API entity, не импортируют друг друга. FSD-направление и index.ts обязательны; именованные types/constants/handlers размещаются по правилам проекта. Не переносить весь HTML, ручной router, DOM innerHTML или самодельную таблицу состояния.

Использовать существующие React Router, TanStack Query/Table, React Hook Form, Zod и UI kit. Для порядка вопросов/вариантов обязательны доступные кнопки перемещения; drag-and-drop использует возможности платформы, пока новая библиотека не обоснована. Универсальный движок managed resources не нужен: доступен один предметный раздел.

### Implementation decisions

Один draft на три вкладки. Поля: name, code, type_code, description, owner, active_since, status, audience_type, tags, segments, surface_ids, operator_groups, questions, display_rules. Ответственный до отдельного user lookup — read-only `responsible_user_id` или «Не назначен»; не подставлять mock-пользователей, не включать это поле в PUT без пользовательского изменения, не терять исходное значение.

Новая карточка: обязательны name/code/type_code; status=draft, audience_type=all, пустые связи/вопросы. Name 1–255, code до 100 по `^[a-z][a-z0-9_]*$`, owner до 200, дата YYYY-MM-DD. Уникальность имени не требовать; 409 NOT_UNIQUE кода показывать у поля, не проверять только по загруженной странице.

PUT частичен только сверху: questions, surface_ids заменяются целиком; display_rules передаётся полным итоговым объектом. Existing question/option UUID сохраняются, новые ID генерирует backend, порядок задаётся массивом. Не отправлять sort_order, timestamps, FK, локальные ключи и ответное display_rules.id. Не отправлять пустой PUT. Явные null допустимы только для очищаемых nullable полей по бизнес-правилам; не считать все nullable из OpenAPI разрешёнными к очистке.

Ошибка не очищает draft. Поля на скрытой вкладке доступны через индикатор ошибки и переход с фокусом. Pending блокирует повторное сохранение. На уход/закрытие/back/reload с изменениями — штатная защита; смена вкладки не теряет ввод. After save — новый baseline из GET/PUT. Не обещать сохранение несохранённого draft после reload; долговременное локальное хранилище не требуется.

Lookup содержит восемь `feedback_*` наборов. Для новых ссылок доступны is_active=true; старое неактивное значение остаётся отображаемым и допустимым без смены. Условия поиска могут использовать неактивные значения. Для неизвестного кода — исходный код и пояснение, без назначения другого типа. surface_ids — не более 100 UUID из существующего API поверхностей; 101-й выбор блокируется без потери набора, с загрузкой всех необходимых страниц; один набор для вкладок «Основное» и «Правила показа». Скрытие conditional UI аудитории само не удаляет сохранённые связи.

Правила в MOS-1251: trigger_type; min_messages/min_duration_sec/delay_show_sec/pause_after_last_sec/cooldown_sec (целые >= 0 или null); max_per_session/max_per_day/max_per_user (целые >= 1 или null); skip_if_rated; quiet_hours_enabled + quiet_from/quiet_to; dialog_type/dialog_result; priority (целое либо null); exclusive_show. Включённые тихие часы требуют обеих границ времени без timezone. Интервал через полночь не запрещать, не вычислять исполнение/таймзону на frontend. Начальные defaults — из API (manual, skip_if_rated=true, quiet_hours_enabled=false, any/any, priority=0, exclusive_show=false).

«Как это сработает» объясняет конфигурацию, явно не доказывает реальный показ. Нулевые значения не приравниваются к пустым; отсутствующие лимиты не выводятся как null/undefined. API хранит правила, не исполняет их.

### Nullable display_rules

Уточнение backend от Глеба Харитонова, переданное пользователем 12.10.2026: обязательность полей взята из модели данных; null опционального поля отображается пустым вводом. PUT частичен только для верхнеуровневых ключей; при изменении вложенного display_rules передаётся объект целиком. Это уточняет представление формы и не меняет обязательность полей.

Nullable числовые поля: min_messages, min_duration_sec, delay_show_sec, pause_after_last_sec, cooldown_sec (целое >=0 либо null), max_per_session, max_per_day, max_per_user (целое >=1 либо null), priority (любое целое либо null). Nullable boolean: skip_if_rated, quiet_hours_enabled, exclusive_show — true/false/null. Nullable справочные поля: dialog_type/dialog_result — код либо null. quiet_from/quiet_to — время без timezone либо null; при quiet_hours_enabled=true нужны обе границы. trigger_type не nullable.

Опциональные поля с null показываются пустым вводом; select и nullable boolean — пустым, невыбранным состоянием соответствующего контрола. Отдельное значение с текстом «Не задано» не требуется. В draft null остаётся отличимым от false, 0 и кода any: пустой контрол не подставляет эти значения. Это представление данных, не трактовка null как действующего правила; пояснение конфигурации не выдумывает backend-семантику.

Defaults применяются к новой карточке либо полям, отсутствующим в ответе по API-схеме. Явный null из GET не заменяется default. При редактировании одного правила PUT включает полный итоговый объект display_rules со всеми остальными значениями, включая null/false/0; отправка только изменённого вложенного ключа недопустима. Очистка nullable-контрола отправляет null; пустая строка не является wire-значением числа/времени/справочного кода. При отсутствии правки rules верхнеуровневое поле можно не передавать. Эти правила не разрешают null в обязательных корневых полях или строках меток, запрещённый бизнес-контрактом.

### Disable confirmation boundary

Единый механизм подтверждения перехода существующей карточки в disabled используется кнопкой выключения и submit формы со сменой статуса. MOS-1251 подключает его в общий submit, MOS-1256 — в отдельное действие; реализация находится у владельца редактора, без импорта соседних features. Отмена сохраняет draft и не отправляет запрос. Submit после подтверждения отправляет один PUT всех изменений; уже disabled без смены статуса не требует повторного подтверждения. Для отдельного lifecycle-действия сохраняется правило dirty draft: сначала явное сохранение либо отмена действия; если сохранение уже установило целевой статус, второй PUT не нужен.

### Existing safety and verification

Существующие HTTP transport, MPMM-сессия, owner/generation и UI-only permissions сохраняются. Backend проверяет scope. FSD и публичные index.ts обязательны; новые auth-модель, role editor и request ACL не вводятся. Unit/component и mock HTTP проверки разрешены; browser/E2E — только по отдельному разрешению. Dev-моки остаются в Express без credentials/role enforcement; production их не содержит.

Общая политика feature permissions определена [API change](../mos-1249-feedback-api/specs/feedback-api/spec.md); доступность UI проверяется в спецификации и tasks владельца соответствующего интерфейса. Соседние feature-модули не импортируют друг друга: данные проходят через владельца draft либо публичную entity.

## Risks / Trade-offs

- [HTML шире API] → ограничить UI опубликованными возможностями; ограничения Deferred scope из proposal сохраняются в приёмке.
- [Нет optimistic locking] → не обещать защиту от чужой параллельной записи; сохранять baseline и пояснять неизвестный исход, не делать слепой повтор.
- [Неизвестные/неактивные справочные коды] → сохранить исходные данные, не подставлять defaults поверх сохранённого значения; новые неподдержанные renderers не выдумывать.
- [Ошибки OpenAPI допускают null шире бизнес-правил; autogenerated 422 описан иначе envelope] → generated DTO дополняются runtime-проверками и документированными бизнес-ограничениями; не переписывать исходник без provenance, фактический ответ проверить на интеграции.
- [Источники могут измениться] → использовать версию и хеши, сохранённые MOS-1249; новую версию сверять отдельно.

## Migration Plan

Реализовать только tasks этой подзадачи после указанных prerequisites. Моки не подтверждают доступность реального API. Перед выпуском проверить операции этой задачи на стенде; rollback — предыдущий frontend bundle без удаления серверных данных. Backend schema migration не входит.

## Open Questions

Блокирующих продуктовых решений в согласованном первом этапе нет. Перед выпуском остаётся подтверждение фактических endpoint/errors/permissions/CORS для операций задачи. Иное поведение требует уточнения контракта, не скрытого расширения scope.
