## Purpose

Реализовать реестр опросников и базовый отбор в разделе обратной связи ЦАМ по опубликованному API, с отдельной приёмкой и сохранением ограничений первого этапа.

## ADDED Requirements

### Requirement: Survey navigation and registry

Приложение SHALL предоставлять `/feedback`, `/feedback/new`, `/feedback/:surveyId` в общей оболочке под существующим basename. Таблица SHALL показывать название/код, тип, аудиторию с доступными сегментами/поверхностями и статус; labels SHALL браться из lookup, неизвестные значения отображаться кодом. Переход в карточку SHALL быть доступен с клавиатуры; маршрут карточки SHALL передавать UUID модулю MOS-1251 независимо от текущей страницы списка; загрузкой detail владеет MOS-1251. Loading, empty dataset, no matches, error/retry и 404 SHALL различаться. Новая карточка MUST NOT запрашиваться как ID `new`.

#### Scenario: Direct card link

- **WHEN** разрешённый пользователь открывает валидный UUID вне загруженной страницы после подключения модуля карточки MOS-1251
- **THEN** route передаёт UUID модулю карточки, крошки ведут в реестр; GET/404 проверяются в MOS-1251, в изолированной приёмке реестра проверяются сопоставление маршрута и параметры

#### Scenario: Empty filtered page

- **WHEN** поиск завершился без совпадений
- **THEN** показаны серверные нулевые счётчики и возможность сброса; ошибка загрузки не маскируется этим состоянием

### Requirement: Server search and base filters

Реестр SHALL использовать query 2–200 символов, мультиселекты status/type_code, серверные limit/offset и sort name/type_code/status/updated_at с направлением `-`. Default sort SHALL быть -updated_at. Пустой query SHALL исключаться; один символ MUST NOT отправляться или выдаваться за применённый поиск. Изменение отбора SHALL сбрасывать offset в 0. Счётчики SHALL браться из pagination, не из длины страницы. Поиск SHALL соответствовать name/code/description/type_code API, без обещания поиска по отображаемому типу и связанным меткам. Неподдержанные сортировки MUST NOT вычисляться только по странице.

#### Scenario: Multi value search

- **WHEN** выбраны active и paused, тип assistant и query «оценка»
- **THEN** сервер получает массивы кодов и query, OR внутри фильтра и AND между фильтрами; смена фильтра начинает первую страницу

#### Scenario: Clearing and stale response

- **WHEN** query очищен после отправки предыдущего чтения
- **THEN** новый запрос не содержит query, поздний старый ответ не заменяет актуальные данные

### Requirement: Reproducible registry selection

Применённый search SHALL полностью восстанавливаться из URL, истории и скопированной ссылки: query, status/type_code, sort, limit/offset и conditions после подключения MOS-1258. Limit SHALL быть 1–100, offset — неотрицательным. Повреждённый URL SHALL давать пояснение и валидное состояние; неполный отбор MUST NOT выдаваться за исходный. Copy success SHALL появляться только после успешной записи clipboard.

#### Scenario: Restore registry link

- **WHEN** пользователь открывает ссылку с фильтрами и пагинацией либо возвращается назад
- **THEN** реестр восстанавливает применённый search и серверные счётчики; ошибка clipboard не даёт сообщения об успешном копировании

### Requirement: Accessible registry interactions

Область этой задачи — реестр, базовые фильтры и навигация — SHALL поддерживать клавиатуру, доступные названия/ошибки, предсказуемый фокус и узкую компоновку. Приёмка SHALL проверять собственные элементы; реализация и приёмка соседних UI-возможностей MUST NOT требоваться для закрытия этой задачи сверх явно указанных зависимостей интеграции. Недоступные API MUST NOT имитироваться успешными заглушками.

#### Scenario: Keyboard and narrow layout within this task

- **WHEN** пользователь работает с элементами этой задачи клавиатурой на узком экране
- **THEN** действия и ошибки доступны, содержимое не перекрывает управляющие элементы, закрытие имеющихся диалогов возвращает фокус
