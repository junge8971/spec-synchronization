## Context

См. proposal.md. Данные поступают в detail MOS-1041. PDF 2.3.7 определяет kind и готовые тексты, серверные итоги покрытия и available. В отличие от старой формулировки задачи, step_id и ссылки на сообщения отсутствуют.

## Goals / Non-Goals

**Goals:** достоверный read-only разбор последовательности и сбоев без реконструкции событий.

**Non-Goals:** граф трассировки, кликабельные связи шаг–сообщение, отдельный route endpoint, локальный расчёт времени покрытия, редактирование действий оператора.

## Decisions

1. **Gate:** подтвердить контрактные traced_sec/untraced_sec и происхождение operator_actions (8.12–8.13). Отсутствующие step IDs фиксируются как ограничение, не блокируют простой список. Если нужна связанная навигация, сначала расширить контракт и этот план.
2. **Список, не граф:** приватная вкладка карточки получает route и duration_sec. Отображает steps в порядке источника, без сортировки по локализованному времени и без dedup одинаковых событий. occurred_at форматируется в общем согласованном поясе. duration_ms остаётся длительностью шага, не диалога.
3. **Контрактная легенда:** user_request, platform_module, skill, operator, core; component/action/detail — готовые строки, безопасный текстовый рендер. failed показывает доступно подписанный блок «Сбой обработки»; цвет не единственный сигнал.
4. **Итоги:** использовать traced_sec, untraced_sec, duration_sec как отдельные серверные значения. Не суммировать duration_ms: переходы, паузы и параллельные шаги делают такую сумму неверной. Если traced_sec больше duration_sec, не исправлять серверный снимок клиентским вычитанием; показывать полученные итоги, untraced_sec=0 означает полное покрытие по контракту.
5. **Unavailable не empty:** available=false показывает объяснение недоступности и не рисует нулевое покрытие. При available=true и steps=[] показывать отсутствие шагов в полученных данных. Пустые operator_actions не создают блок действий; каждый элемент содержит собственного operator_id/operator_name, action и до двух details.
6. **Без дополнительных чтений:** смена вкладки использует snapshot MOS-1041. При повторном чтении карточки данные заменяются целиком; не склеивать шаги двух снимков по локальному индексу.

## Risks / Trade-offs

- Нет идентификаторов шагов → нет серверных deep links; локальные render keys не публикуются как IDs.
- События оператора и завершение имеют разные времена → не корректировать их для визуального совпадения, показать источник как есть.
- Дублирующиеся времена → сохранять порядок источника и все шаги.

## Migration Plan

После gate и detail MOS-1041 добавить вкладку и unit/component-тесты доступного/недоступного/сбойного маршрута. Откат касается только вкладки, не переписки и не контрактного has_failure реестра.
