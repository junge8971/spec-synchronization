## Purpose

Реализовать расширенные условия отбора опросников в разделе обратной связи ЦАМ по опубликованному API, с отдельной приёмкой и сохранением ограничений первого этапа.

## ADDED Requirements

### Requirement: Isolated feedback integration

Возможности этой задачи SHALL поставляться внутри обособленного модуля раздела «Обратная связь», с общим foundation MOS-1249 и ограниченными точками подключения приложения по образцу базы знаний. Внешние потребители SHALL обращаться через публичный API модуля; framework route entrypoints SHALL подключаться отдельно. Бизнес-слои приложения MUST NOT зависеть от внутренних модулей feedback. Существующие transport, обработка ошибок и механизмы сессии SHALL сохраняться. Новая UI-policy, mappings permissions и новые ограничения интерфейса по пользователю MUST NOT добавляться в текущую поставку.

#### Scenario: Integrate the task without expanding module boundaries

- **WHEN** реализация задачи подключается к приложению и общей модели feedback
- **THEN** предметная логика и тесты остаются у владельца раздела, composition использует публичный API и отдельные route entrypoints; действующие защитные механизмы сохраняются без новых permission mappings

### Requirement: Advanced conditions and reproducible selection

Условия SHALL строиться по metadata condition_fields: одна плоская группа and/or, максимум 50 условий. Поля — name/code/description/type_code/status/audience_type/owner; операторы только разрешённые для поля. Справочные in/not_in SHALL использовать 1–100 уникальных кодов; is_empty/is_not_empty SHALL не требовать значения. Обычные фильтры и query SHALL объединяться с группой через AND. В первом этапе аудитория SHALL выбираться только внутри конструктора; независимый мультиселект аудитории и условие tags MUST NOT предлагаться.

Применённый search SHALL полностью восстанавливаться из URL, истории и скопированной ссылки, включая conditions, сортировку и пагинацию. Неприменённый draft условий MUST NOT попадать в экспорт/сохранённый фильтр. Повреждённые параметры SHALL давать явное пояснение и валидное состояние; неполный отбор MUST NOT молча выдаваться за исходный. Copy success SHALL показываться только после записи в clipboard.

Для contains/not_contains/eq/ne/starts_with/ends_with value SHALL быть строкой 1–1000 символов. Для in/not_in каждая из 1–100 уникальных строк SHALL иметь 1–1000 символов; очистка последнего выбранного значения SHALL удалять условие, не отправлять пустой массив. Для is_empty/is_not_empty value SHALL отсутствовать либо быть null. Пробелы MUST NOT обрезаться: строка из пробелов не пуста, регистр и буквальные символы SHALL сохраняться. eq/ne/in/not_in сравнивают с учётом регистра; contains/not_contains/starts_with/ends_with — без него. UI MUST NOT заменять серверную семантику локальной фильтрацией.

#### Scenario: Or group with basic filter

- **WHEN** status=active и условия name contains «оценка» OR owner eq «ЦАМ» применены
- **THEN** сервер получает status отдельно и плоскую or-группу, URL восстанавливает весь отбор, счётчики/экспорт используют тот же search

#### Scenario: Audience does not change logic secretly

- **WHEN** пользователь хочет аудиторию вместе с условиями ИЛИ
- **THEN** аудитория доступна как явная строка этой группы с той же логикой; UI не обещает дополнительное независимое AND и не подмешивает скрытые условия

#### Scenario: String length and whitespace

- **WHEN** введено значение из пробелов либо строка длиной 1000/1001 символ
- **THEN** пробелы сохраняются буквально, 1000 символов допустимы, 1001 блокирует применение с ошибкой без потери draft

#### Scenario: Clear the final membership value

- **WHEN** пользователь убирает последний код из in/not_in
- **THEN** условие удаляется из draft; после применения оно отсутствует в search, пустой массив не отправляется

### Requirement: Accessible conditions interactions

Область этой задачи — редактор условий и панель применённого отбора — SHALL поддерживать клавиатуру, доступные названия/ошибки, предсказуемый фокус и узкую компоновку. Приёмка SHALL проверять собственные элементы; реализация и приёмка соседних UI-возможностей MUST NOT требоваться для закрытия этой задачи сверх явно указанных зависимостей интеграции. Недоступные API MUST NOT имитироваться успешными заглушками.

#### Scenario: Keyboard and narrow layout within this task

- **WHEN** пользователь работает с элементами этой задачи клавиатурой на узком экране
- **THEN** действия и ошибки доступны, содержимое не перекрывает управляющие элементы, закрытие имеющихся диалогов возвращает фокус
