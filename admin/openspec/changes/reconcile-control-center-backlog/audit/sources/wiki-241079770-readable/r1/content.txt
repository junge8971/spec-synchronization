API Contract
Общая информация
Версия контракта: v1 draft 0.5.
Статус: DRAFT. Работа приостановлена до уточнения статуса MOS-659. Контракт с frontend и параметры внутреннего СУДИР не согласованы.
Тип изменения:
новые методы входа, обработки OIDC callback, получения текущей сессии и выхода из административной панели ЦАМ.
Назначение: предоставить административному интерфейсу вход через внутренний СУДИР и управление серверной прикладной сессией.
Базовый путь: /api/access/api/v1.
Формат обмена: JSON. Методы login и callback возвращают HTTP redirect; правила ответов описаны в соответствующих разделах.
Аутентификация: серверная прикладная сессия; браузер предъявляет непрозрачный секрет в защищённой HttpOnly cookie. Токены СУДИР не передаются в SPA.
Общие заголовки
| Заголовок | Обязательность | Описание
| X-Request-Id | Нет в запросе, да в ответе | UUID запроса. Backend генерирует значение, если заголовок не передан. Невалидное значение заменяется новым UUID, предложение для ревью
| Cookie | Для текущей сессии; при logout может отсутствовать | __Host-tsam_admin_session=<opaque>; login и callback не требуют действующей прикладной сессии
| Origin / Referer | Для logout | Backend проверяет точный разрешённый origin; правило fallback описано в 3.2
| Idempotency-Key | Для logout, предложение | UUID одной команды; сохраняется при повторе после сетевой ошибки. Применимость общего A-15 к logout согласовать в TBD-04
| Accept | Рекомендуется для session/logout | application/json
Все ответы auth-endpoints содержат Cache-Control: no-store и X-Request-Id. Redirect-ответы также содержат Pragma: no-cache и Referrer-Policy: no-referrer. UUID в примерах условные. СУДИР не обязан возвращать исходный X-Request-Id: login и callback являются разными HTTP-запросами, связанными внутренним correlation_id транзакции.
Общая модель ответа
JSON-ответы используют оболочку из контракта управления пользователями:
{
"code": "SUCCESS",
"data": {},
"message": "Операция выполнена успешно.",
"errors": []
}
| Поле | Тип | Описание
| code | string | Машиночитаемый код результата
| data | object или null | Результат; при ошибке null
| message | string | Безопасное описание результата
| errors | array[object] | При успехе пустой массив; элементы могут содержать code, message, field, details
Исключение: login/callback возвращают 302 Found с Location, без JSON-оболочки. Их ошибки доставляются на фиксированную страницу SPA также через 302, с безопасными code и request_id. HTTP-статус такого ответа именно 302, а не 400/403/503. Таблица 2.6 разделяет два транспорта. Если маршрут ошибки не сконфигурирован, используется безопасный JSON 503 AUTH_CONFIGURATION_ERROR без редиректа.
1. Цель задачи
Предоставить административному интерфейсу контракт для:
начала OIDC-входа через внутренний СУДИР;
проверки callback и создания собственной сессии;
получения текущего сотрудника и снимка его прав;
завершения сессии;
настройки cookie, сроков жизни и отзыва сессии;
записи событий входа, отказа, выхода, отзыва и принудительного завершения в аудит.
MOS-659 заканчивается описанием и согласованием контракта. Реализация сервиса и развёртывание инфраструктуры в эту работу не входят. API управления пользователями и Query API аудита принадлежат своим контрактам. Просмотр всех сессий и административное завершение здесь описаны как требования к сессии и событиям; отдельные публичные endpoints для них не вводятся.
2. Методы API
2.1 Начать OIDC-вход
GET /api/access/api/v1/auth/login
Разрешение: действующая прикладная сессия не требуется. Вызов выполняется top-level переходом браузера. Предлагаемый транспорт 302 должен подтвердить frontend в TBD-04.
Параметры запроса
| Параметр | Тип | Обязательность | Описание
| return_url | string | Нет | Относительный путь внутри административного SPA; по умолчанию настроенный маршрут после входа
Разрешены только пути того же origin, начинающиеся с одного /. Запрещены внешние URL, //host, обратные слеши, управляющие символы и переходы на login/callback/error, создающие цикл. Проверка выполняется после нормализации URL. Значение сохраняется на backend и не принимается повторно из callback. Между разными приложениями центра управления отдельный redirect allowlist пока не определён (TBD-04).
Пример запроса
GET /api/access/api/v1/auth/login?return_url=%2Fusers HTTP/1.1
Host: admin.example.org
admin.example.org, /users и /auth/error во всех примерах иллюстративны, это не зарегистрированные адреса проекта.
Обработка
Проверить конфигурацию провайдера и return_url.
Создать случайные state, nonce, PKCE code_verifier, внутренний correlation_id и привязку к браузеру.
Сохранить одноразовую транзакцию в Memcached: хэш state, nonce, verifier, точный redirect URI, return URL, issuer, client ID, browser-binding hash, created_at, expires_at и состояние обработки.
Срок транзакции предлагается 600 секунд по аналогии с 2.9 контракта виджета; для админки это предложение в TBD-02.
Установить временную cookie привязки браузера из 3.2; сформировать authorization URL из доверенной конфигурации.
Вернуть 302 на authorization_endpoint.
Параметры authorization request:
| Параметр | Значение
| response_type | code
| client_id, redirect_uri | Из конфигурации зарегистрированного клиента
| scope | openid и согласованные дополнительные scopes; полный набор TBD-03
| state, nonce | Новые случайные значения
| code_challenge | BASE64URL(SHA256(code_verifier)), без padding
| code_challenge_method | S256
| prompt | По умолчанию не передаётся; none не зашивается из виджета
Успешный ответ
HTTP/1.1 302 Found
Location: https://sudir.example.org/authorize?response_type=code&client_id=admin-example&redirect_uri=https%3A%2F%2Fadmin.example.org%2Fapi%2Faccess%2Fapi%2Fv1%2Fauth%2Fcallback&scope=openid&state=STATE&nonce=NONCE&code_challenge=CHALLENGE&code_challenge_method=S256
Set-Cookie: __Host-tsam_admin_oidc=BROWSER_BINDING; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=600
X-Request-Id: 89902ade-eab6-47b3-9e6e-7b75a895c192
Cache-Control: no-store
Pragma: no-cache
Referrer-Policy: no-referrer
Это схематичный URL: endpoint и значения заменяются конфигурацией, а не копируются из примера.
Ошибки
VALIDATION_ERROR, SUDIR_UNAVAILABLE, SESSION_STORE_UNAVAILABLE передаются через 302 на фиксированную страницу ошибки по правилам 2.6. При неудаче сохранения транзакции переход в СУДИР не выполняется.
2.2 Обработать OIDC callback
GET /api/access/api/v1/auth/callback
Разрешение: действующая прикладная сессия не требуется; обязательна валидная транзакция, связанная с этим браузером.
Параметры запроса
| Параметр | Тип | Обязательность | Описание
| state | string | Да | Одноразовая транзакция, созданная методом 2.1
| code | string | Условно | Код авторизации при успехе СУДИР
| error | string | Условно | Код ошибки провайдера вместо code
| error_description | string | Нет | Недоверенное описание; не передаётся в SPA, URL возврата или аудит
| iss | string | Если возвращает СУДИР | Должен совпасть с ожидаемым issuer; не задаёт адрес token endpoint
Должен присутствовать ровно один из code и error. Повторяющиеся обязательные query-параметры отклоняются. Временная cookie обязательна в предлагаемой схеме browser binding.
Пример запроса
GET /api/access/api/v1/auth/callback?code=CODE&state=STATE HTTP/1.1
Host: admin.example.org
Cookie: __Host-tsam_admin_oidc=BROWSER_BINDING
Callback с отказом СУДИР:
GET /api/access/api/v1/auth/callback?state=STATE&error=access_denied HTTP/1.1
Host: admin.example.org
Cookie: __Host-tsam_admin_oidc=BROWSER_BINDING
Обработка
Проверить параметры, срок транзакции, issuer и привязку к браузеру.
Атомарно перевести транзакцию в использованное состояние. Параллельные callback с одним state не должны приводить к двум обменам или двум сессиям. Обычная пара get + delete не является достаточной гарантией.
Если передан error, не вызывать token endpoint; записать неуспешный вход, вернуть безопасный код ошибки.
При code выполнить server-to-server обмен с сохранёнными redirect_uri и code_verifier; client authentication определяется регистрацией клиента.
Проверить OIDC-ответ и ID token: подпись, разрешённый алгоритм, issuer, audience, применимые azp, сроки и nonce. Нельзя подменять OIDC-проверку простым чтением JWT access token. Если ID token не выдаётся, требуется отдельное согласованное описание получения идентичности (TBD-01), а не пропуск проверок.
Получить стабильный subject и сопоставить с локальным sudir_subject_id. Базовое предложение: sub проверенного ID token. При UserInfo его sub должен совпасть с ID token. Идентификатор не выводится из email или логина без подтверждения СУДИР.
Найти активный локальный профиль и снимок прав. Неизвестный, pending или suspended профиль не получает действующую сессию. Автоматическое заведение pending-профиля, если потребуется, согласуется с MOS-660 (TBD-06).
Повторно проверить допустимость профиля и версию снимка прав перед созданием сессии.
Создать новую активную серверную сессию и новый случайный секрет cookie. Существующий секрет не переиспользуется.
Синхронно отправить событие access.authentication.succeeded в API сервиса аудита. Успешная запись или ошибка публикации не меняют результат входа. Ошибка даёт метрику и alert на стороне сервиса доступа, повтор выполняется с тем же event_id по политике TBD-05.
Вернуть 302 на сохранённый return URL. Для повторного входа в том же браузере прежняя связанная сессия заменяется после успешного нового входа; сессии других устройств не затрагиваются. Механизм замены и несколько вкладок фиксируются при реализации и ревью.
Успешный ответ
HTTP/1.1 302 Found
Location: /users
Set-Cookie: __Host-tsam_admin_session=OPAQUE_SESSION_SECRET; Path=/; Secure; HttpOnly; SameSite=Strict
X-Request-Id: 21a588c5-4d76-44f3-8797-55103d40a854
Cache-Control: no-store
Pragma: no-cache
Referrer-Policy: no-referrer
Секрет не возвращается в JSON. Callback не создаёт гостевую сессию. Ошибка публикации аудита не заменяет успешный redirect ошибкой входа. Временная browser-binding cookie живёт не более 600 секунд; её досрочное удаление допустимо только без нарушения других незавершённых входов этого браузера. Предложенный вариант использует независимые state и общую короткую browser-binding cookie; гонку её первоначальной установки в нескольких вкладках нужно покрыть проверкой, при несовпадении вход начинается заново.
Ошибка входа
HTTP/1.1 302 Found
Location: /auth/error?code=OAUTH_STATE_INVALID&request_id=21a588c5-4d76-44f3-8797-55103d40a854
X-Request-Id: 21a588c5-4d76-44f3-8797-55103d40a854
Cache-Control: no-store
Pragma: no-cache
Referrer-Policy: no-referrer
Маршрут ошибки задаётся серверной конфигурацией и доступен без сессии. В него не попадают code, state, токены, ПДн или исходный error_description. Неуспешный callback не выдаёт новую session cookie и не отзывает уже действующую сессию по недоверенным параметрам.
2.3 Получить текущую сессию
GET /api/access/api/v1/auth/session
Разрешение: действующая прикладная сессия активного профиля. Отдельное permission не требуется.
Параметры пути, query и тело запроса отсутствуют.
Пример запроса
GET /api/access/api/v1/auth/session HTTP/1.1
Host: admin.example.org
Accept: application/json
Cookie: __Host-tsam_admin_session=OPAQUE_SESSION_SECRET
X-Request-Id: 89902ade-eab6-47b3-9e6e-7b75a895c192
Успешный ответ
HTTP/1.1 200 OK
Content-Type: application/json
X-Request-Id: 89902ade-eab6-47b3-9e6e-7b75a895c192
Cache-Control: no-store
{
"code": "SUCCESS",
"data": {
"session": {
"id": "5d64bc26-5f63-4280-9a57-54b4cf2fbb98",
"created_at": "2026-09-07T08:10:00Z",
"last_activity_at": "2026-09-07T08:24:30Z",
"idle_expires_at": "2026-09-07T08:39:30Z",
"absolute_expires_at": null
},
"user": {
"id": "52f411aa-977b-4d26-9a5b-d896ca9c1e64",
"sudir_subject_id": "6748921",
"name": {
"family_name": "Иванов",
"name": "Иван",
"middle_name": "Иванович"
},
"email": "ivan.ivanov@example.org",
"roles": ["platform_admin"],
"permissions": ["users.read", "users.block"]
}
},
"message": "Текущая сессия получена.",
"errors": []
}
15 минут в примере иллюстрируют расчёт, а не утверждённый default. absolute_expires_at: null показывает предлагаемую nullable-схему до решения TBD-02; это не согласование бессрочной активной сессии.
Поля ответа data
| Поле | Тип | Обязательность | Описание
| session.id | UUID | Да | Публичный идентификатор записи; не является секретом аутентификации
| session.created_at | date-time | Да | Время создания, UTC
| session.last_activity_at | date-time | Да | Последняя активность, учитываемая сервером
| session.idle_expires_at | date-time | Да | Граница бездействия по серверной политике
| session.absolute_expires_at | date-time или null | Да | Абсолютный предел; nullable и политика требуют TBD-02
| user.id | UUID | Да | Локальный идентификатор профиля
| user.sudir_subject_id | string | Да | Идентификатор субъекта СУДИР; формат TBD-01
| user.name.family_name | string | Да | Фамилия из профиля
| user.name.name | string | Да | Имя из профиля
| user.name.middle_name | string или null | Да | Отчество из профиля
| user.email | string или null | Да | Email из профиля
| user.roles | array[string] | Да | Коды ролей; пустой массив допустим
| user.permissions | array[string] | Да | Снимок функциональных разрешений; окончательное решение всегда принимает backend
Backend проверяет наличие записи, состояние active, сроки, активность профиля и актуальность версии доступа. В обязательном пути нет introspection. Объектные ограничения не определяются одним массивом permissions и проверяются доменным модулем.
Предложение: bootstrap и фоновый polling GET /auth/session сами не продлевают idle TTL; иначе открытая вкладка предотвращает выход по бездействию. Какие запросы считаются активностью, уточняется с frontend и аналитикой в TBD-02/TBD-04.
Нет действующей сессии
HTTP/1.1 401 Unauthorized
Content-Type: application/json
Set-Cookie: __Host-tsam_admin_session=; Path=/; Secure; HttpOnly; SameSite=Strict; Max-Age=0
X-Request-Id: 89902ade-eab6-47b3-9e6e-7b75a895c192
Cache-Control: no-store
{
"code": "UNAUTHENTICATED",
"data": null,
"message": "Требуется повторный вход.",
"errors": []
}
Одинаковый 401 используется для отсутствующей cookie, неизвестной, истёкшей или отозванной сессии. Если запись ещё найдена, но профиль уже не active, предлагается 403 USER_NOT_ACTIVE, отзыв и очистка cookie, как в общем контракте пользователей. Если отзыв уже выполнен, последующий запрос получает 401. SPA в обоих случаях снимает локальный auth-контекст; 403 не запускает автоматический цикл входа.
Недоступное хранилище не маскируется под неизвестную сессию: 503 SESSION_STORE_UNAVAILABLE, cookie сохраняется для повтора. Недоступность обязательной проверки профиля/версии: 503 AUTHORIZATION_UNAVAILABLE; доступ не разрешается. Этот код здесь не означает обязательную introspection.
2.4 Завершить текущую сессию
POST /api/access/api/v1/auth/logout
Разрешение: завершение только собственной предъявленной сессии. Отсутствие сессии не мешает идемпотентному локальному выходу. CSRF-проверка и валидация запроса выполняются и без cookie.
Тело запроса отсутствует. session_id, user_id и произвольный redirect URL от клиента не принимаются.
Пример запроса
POST /api/access/api/v1/auth/logout HTTP/1.1
Host: admin.example.org
Origin: https://admin.example.org
Accept: application/json
Cookie: __Host-tsam_admin_session=OPAQUE_SESSION_SECRET
Idempotency-Key: 2cf23bc5-d4e7-4491-aaee-0348523cceec
X-Request-Id: 89902ade-eab6-47b3-9e6e-7b75a895c192
Обработка
Проверить Origin/Referer и Idempotency-Key.
Сделать текущую сессию недействительной. Повтор не восстанавливает сессию и не отзывает другие сессии пользователя.
Синхронно отправить access.session.logged_out для фактического завершения найденной сессии. Ошибка публикации не восстанавливает сессию и не меняет HTTP-результат logout; сервис доступа создаёт метрику и alert, повторяет то же событие с прежним event_id по политике TBD-05.
Очистить cookie и вернуть успех. Отсутствующая сессия даёт успех без выдуманного события о завершении неизвестного пользователя.
Успешный ответ
HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: __Host-tsam_admin_session=; Path=/; Secure; HttpOnly; SameSite=Strict; Max-Age=0
X-Request-Id: 89902ade-eab6-47b3-9e6e-7b75a895c192
Cache-Control: no-store
{
"code": "SUCCESS",
"data": { "redirect_url": null },
"message": "Сессия завершена.",
"errors": []
}
| Поле data | Тип | Обязательность | Описание
| redirect_url | string или null | Да | В базовом локальном logout всегда null. Ненулевой URL допустим только после согласования federated logout и allowlist
SPA снимает локальное auth-состояние и переходит на согласованный маршрут после выхода. Локальный logout не завершает SSO-сессию СУДИР. Повторный вход может пройти через SSO без пароля. Нужен ли выход из СУДИР, остаётся TBD-03; в диаграмме это обозначено явно.
Ошибка публикации аудита
Клиент не получает отдельную ошибку аудита. Если сессия завершена, logout возвращает обычный 200 SUCCESS и очищает cookie. Сервис аудита честно отвечает источнику ошибкой, но политика сервиса доступа остаётся fail-open. Ошибка должна быть видна по метрикам и alert, а повтор использует тот же event_id.
Если Memcached недоступен и отзыв не подтверждён, возвращается 503 SESSION_STORE_UNAVAILABLE без очистки cookie; нельзя сообщать, что серверная сессия завершена. Таймауты, бюджет повторов и место временного хранения события остаются TBD-05.
2.5 Повторные и конкурентные запросы
login создаёт новую транзакцию, повтор старого state не используется.
callback с неизвестным, истёкшим или использованным state возвращает один безопасный OAUTH_STATE_INVALID через 302. Replay не запускает новый обмен code.
Logout идемпотентен по состоянию. При повторе одного ключа, метода, URI и исходной операции backend не создаёт повторный отзыв. Повтор публикации того же audit-события использует тот же event_id; source_service сервис аудита выводит из transport identity вызывающего. Связь ключа с исходной сессией должна сохраняться после очистки cookie.
Тот же ключ с другой операцией, в том числе logout новой предъявленной сессии, возвращает 409 IDEMPOTENCY_KEY_REUSED. Ключ нельзя использовать как способ получить чужой результат; срок и привязка записи повторов являются TBD-05.
expected_version профиля в logout не передаётся: пользователь завершает предъявленную сессию, а не редактирует профиль. Это адаптация A-15, которую нужно подтвердить вместе с Idempotency-Key.
После подтверждённого отзыва позднее обновление активности не должно восстановить запись. Проверка версий, условные обновления и массовый отзыв должны учитывать параллельное создание сессии (4.2).
2.6 Формат ошибок
Пример ошибки JSON для logout при отсутствии обязательного ключа в предлагаемой версии:
{
"code": "VALIDATION_ERROR",
"data": null,
"message": "Запрос содержит некорректные данные.",
"errors": [
{
"code": "REQUIRED",
"field": "Idempotency-Key",
"message": "Обязательный заголовок."
}
]
}
| HTTP для JSON | code | Условие | Транспорт login/callback
| 400 | VALIDATION_ERROR | Некорректные параметры/заголовки | 302 на страницу ошибки
| Не применяется | OAUTH_STATE_INVALID | Нет валидной одноразовой транзакции или browser binding | 302 на страницу ошибки
| Не применяется | OAUTH_ACCESS_DENIED | СУДИР отказал во входе | 302 на страницу ошибки
| Не применяется | OIDC_RESPONSE_INVALID | Обмен отклонён либо проверки OIDC-ответа не пройдены | 302 на страницу ошибки
| 401 | UNAUTHENTICATED | Нет действующей прикладной сессии | Не применяется
| 403 | USER_NOT_ACTIVE | Подтверждённый профиль не active | 302 при callback
| Не применяется | ACCESS_DENIED | При callback не найден допущенный локальный профиль | 302 на страницу ошибки
| 403 | CSRF_CHECK_FAILED | Logout пришёл с недопустимым источником | Не применяется
| 409 | IDEMPOTENCY_KEY_REUSED | Logout повторён с ключом другой операции | Не применяется
| Не применяется | SUDIR_UNAVAILABLE | Недоступны discovery, token endpoint или необходимое получение identity при входе | 302 на страницу ошибки
| 503 | SESSION_STORE_UNAVAILABLE | Не удалось проверить/сохранить состояние в Memcached | 302 на страницу ошибки
| 503 | AUTHORIZATION_UNAVAILABLE | Недоступна обязательная локальная проверка профиля/версии | 302 при callback
| 503 | AUTH_CONFIGURATION_ERROR | Нет безопасного настроенного маршрута ошибки | JSON 503 без redirect
Коды, отсутствующие в образце управления пользователями, являются предложением MOS-659, а не уже утверждённым общим справочником. Код ошибки страницы SPA не является доказательством аутентификации; его можно вручную изменить в адресной строке.
Для JSON-ошибок 403/409/503 используется та же оболочка с соответствующим code, безопасным message и data: null. errors.details не содержит токенов или идентификаторов неизвестного пользователя. Frontend показывает временную ошибку при 503 и не запускает бесконечный вход; при ошибке callback предлагает начать новый вход.
3. Cookie и браузерное взаимодействие
3.1 Сессионная cookie
Предложение для SPA и API на одном origin или через единый reverse proxy:
| Атрибут | Значение | Статус / назначение
| Name | __Host-tsam_admin_session | Предложение имени
| Value | Случайный непрозрачный секрет, не менее 256 бит энтропии | Не UUID пользователя и не JWT; не раскрывает профиль и права
| Path | / | Для префикса __Host-
| Domain | Отсутствует | Cookie привязана к host, который её установил
| Secure | Да | Только HTTPS, A-08
| HttpOnly | Да | Не читается JavaScript, A-08
| SameSite | Strict | Предварительный ответ Глеба, финальное значение TBD-04
| Max-Age / Expires | Не устанавливаются при выдаче | Предложение session cookie; срок серверной сессии всегда проверяет backend
| Очистка | То же имя и Path, без Domain, Max-Age=0 | В ответе logout или после подтверждения недействительности сессии
Закрытие браузера не является надёжным серверным logout: браузер может восстановить session cookie. Сроки и отзыв контролируются сервером.
SameSite и host-only решают разные задачи. Разные поддомены могут быть same-site, но cookie одного host не становится cookie другого host. Cross-origin SPA может обращаться к host API с cookie при корректных credentials/CORS; такую схему здесь не считаем согласованной. Не следует автоматически расширять Domain до mos.ru. Финальные origin, CORS и bootstrap проверяются в TBD-04. Основание атрибутов: Set-Cookie.
3.2 Защита login/callback и logout
Предлагается отдельная краткоживущая cookie __Host-tsam_admin_oidc: случайный browser-binding secret, Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=600, без Domain. Она не даёт доступа к API и не содержит state, nonce или verifier. Сервер хранит её хэш в OIDC-транзакции. State без подходящей browser-binding cookie не принимается.
Lax выбран для возврата top-level GET callback при возможном cross-site переходе. Не следует ослаблять для этого основную session cookie. Если СУДИР требует form_post или иной способ возврата, схема нуждается в отдельной переработке. Временная cookie и response mode остаются TBD-03/TBD-04.
Для logout предложение следующее: если есть Origin, он должен точно совпасть с разрешённым origin. При его отсутствии проверяется origin из Referer. Наличие неправильного Origin нельзя «исправить» правильным Referer. Если оба отсутствуют или Origin равен null, запрос отклоняется. Недопустимый запрос не отзывает сессию и не очищает cookie. Решение об отдельном CSRF token принимается с frontend и ИБ после фиксации хостов, а не выводится только из SameSite.
На маршрутах callback и ошибки не размещаются сторонние ресурсы, которым может уйти URL авторизации. Из технических логов, трассировки и аудита исключаются cookie, code, state, verifier, client secret, access/ID/refresh token и полный URL callback. Для диагностики используются request_id и correlation_id. Защита callback основана на OAuth Security BCP и OIDC Core.
4. Серверная сессия в Memcached
4.1 Модель
session_id является публичным UUID записи, session_token является секретом из cookie. Они не взаимозаменяемы.
| Поле | Тип | Обязательность | Описание
| session_id | UUID | Да | Ссылка на запись для аудита и управления
| session_token_hash | string | Да | Ключ поиска по хэшу секрета; исходный секрет не пишется в логи
| user_id | UUID | Да | Локальный профиль
| sudir_issuer | string | Да | Доверенный issuer, в пределах которого определён subject
| sudir_subject_id | string | Да | Подтверждённый стабильный subject, маппинг TBD-01
| roles, permissions | array[string] | Да | Снимок ролей и функциональных прав
| policy_version | string | Да | Версия эффективного доступа; не обязательно равна user.version; тип и источник согласовать с владельцем RBAC
| created_at, last_activity_at | date-time | Да | UTC, серверное время
| idle_expires_at | date-time | Да | Граница бездействия
| absolute_expires_at | date-time или null | Да | Смысл null и максимальный срок TBD-02
| status | enum | Да | Предложение: active, revoked; публикация аудита не является состоянием сессии
| revoked_at, revoke_reason | date-time/string или null | Да | Для отозванной записи; запись может быть удалена после фиксации результата
| access_token_encrypted, credential_expires_at | string/date-time | Условно | По итогам TBD-01, не читаются SPA; refresh token отсутствует
| sudir_sid, token_jti | string | Нет | Только если выдаются и нужны согласованному внешнему отзыву
| client_ip, user_agent | string | Нет | Только после согласования состава и хранения данных с ИБ; не являются самостоятельным доказательством личности
Scopes СУДИР не превращаются автоматически в прикладные permissions. Изменение областей доступа тоже должно менять действительность снимка. Подробная модель объектных scope остаётся в контракте RBAC/доменного сервиса.
4.2 Сроки, отзыв и конкуренция
Idle timeout настраивается в диапазоне 15-60 минут по локальной фиксации ответа Глеба. Default, изменение настройки для действующих сессий и определение активности остаются TBD-02.
idle_expires_at = last_activity_at + idle_timeout. Если absolute/credential пределы применяются, эффективная граница является минимумом соответствующих сроков. Продление не превышает ни один принятый предел.
Время проверяется до продления. Истёкшая, отозванная или вытесненная запись не восстанавливается из cookie. Memcached miss означает 401; ошибка связи с ним означает 503.
Обновление активности должно быть условным: оно не создаёт отсутствующую запись и не отменяет конкурирующий отзыв. Уменьшать частоту записей можно только без нарушения согласованной точности idle timeout.
Массовый отзыв не должен зависеть только от перебора найденных ключей: параллельно создающаяся сессия со старой версией доступа тоже должна перестать приниматься. Перед выдачей cookie и при проверке доступа сверяется актуальная версия профиля/прав. Конкретный механизм фиксации версии и гонок требует проверки при реализации.
При изменении профиля, ролей или областей доступа все сессии сотрудника становятся недействительными по A-13. Повторная активация пользователя не восстанавливает старые сессии.
Число параллельных сессий не ограничивается по локально зафиксированному ответу Глеба. Это не отменяет ограничение нагрузки на login endpoint; точные лимиты не определяются MOS-659.
4.3 Требуемые операции и ограничения
| Операция | Требование к результату
| Найти по секрету cookie | Вернуть одну запись по хэшу либо отсутствие; не раскрывать секрет
| Отозвать одну сессию | После подтверждения новые проверки этой сессии дают отказ
| Отозвать все сессии пользователя | Инвалидировать все записи, включая гонки создания/продления со старой версией доступа
| Просмотреть активные сессии | Обеспечить индексы пользователя и общего списка; не рассчитывать на сканирование всех ключей Memcached
| Обновить активность | Атомарно проверить действительность и обновить допустимые сроки
| Обработать restart/eviction | Потеря записи ведёт к повторному входу; повреждённые индексы не дают доступ по умолчанию
Индексы имеют собственные сроки и могут содержать устаревшие ссылки. Список фильтруется по действующим записям; пропавший индекс не является доказательством отсутствия всех сессий. Дизайн полного списка, восстановления индексов и массового отзыва требует отдельной проработки реализации, не меняющей A-12.
Memcached не является долговечным журналом или буфером аудита. TTL и удаление не дают автоматического надёжного события об истечении сессии; его наблюдение и полнота аудита требуют отдельного механизма (TBD-05). CAS/условные операции и TTL описаны в документации Memcached. Здесь зафиксировано требуемое поведение, но не заявлена готовность реализации индексов, повторов аудита или устойчивость после перезапуска.
4.4 Внешний отзыв
Локальный logout, блокировка профиля, изменение прав и команда администратора безопасности должны делать прикладную сессию недействительной.
Глобальная блокировка и SSO-logout в СУДИР являются отдельным вопросом. Без согласованного механизма нельзя обещать их мгновенное отражение в админке. Introspection не входит в обязательную проверку. RabbitMQ указан только как неподтверждённая возможность внутреннего СУДИР, без выдуманных exchange, очередей, payload и гарантий доставки. Возможности, идентификаторы и допустимую задержку уточняет владелец СУДИР в TBD-07.

6. События аудита
6.1 Граница контрактов
MOS-659 определяет, при каких auth-сценариях сервис доступа создаёт события и чем заполняет предметные поля. Формат публикации берётся из API-контракта сервиса аудита, результата MOS-661.
Внутренний вызов: POST /api/audit-service/api/v1/events. Одно событие на один вызов. Передача синхронная, Kafka и Transactional Outbox отсутствуют. Публикация работает fail-open: ошибка audit-service не меняет результат auth-операции, но обязательно вызывает метрику и alert у источника.
source_service, received_at и record_id отсутствуют в теле запроса. source_service сервис аудита выводит из transport identity вызывающего; два остальных поля назначает сам. Механизм аутентификации сервисов-источников ещё не выбран в контракте аудита.
6.2 Состав auth-событий
action использует правило <система>.<объект>.<действие>, глагол в прошедшем времени. Следующие значения являются предлагаемым каталогом MOS-659 и требуют подтверждения владельца схемы событий:
| action | result.status | Когда | subject и object
| access.authentication.succeeded | success | Сервис доступа создал действующую сессию после успешного OIDC-входа | Идентифицированный сотрудник; object session с session_id
| access.authentication.failed | denied или error | СУДИР или локальная политика отказали во входе, либо вход сорвался из-за ошибки | subject employee только после подтверждения личности, иначе unknown; object session без id
| access.session.logged_out | success | Пользователь завершил локальную сессию | Сотрудник и завершённая сессия
| access.session.revoked | success или error | Сессия отозвана после изменения доступа; внешний отзыв только после TBD-07 | Инициатор, если известен; объект session
| access.session.terminated | success или error | Администратор безопасности завершил чужую сессию | Администратор в subject; объект session; владелец сессии требует отдельного представления TBD-05
| access.session.expired | success | Истечение было достоверно зафиксировано источником | Сотрудник, если известен; объект session. Memcached сам не гарантирует такое событие
Для отказа прав или политики используется denied. Для технического сбоя используется error. При denied или error поле result.reason обязательно и содержит машинный код причины.

Предлагаемые result.reason: OAUTH_ACCESS_DENIED, OAUTH_STATE_INVALID, OIDC_RESPONSE_INVALID, SUDIR_UNAVAILABLE, PROFILE_NOT_FOUND, PROFILE_NOT_ACTIVE, IDLE_TIMEOUT, ABSOLUTE_TIMEOUT, ACCESS_CHANGED, ADMIN_TERMINATED. Причины внешней блокировки и отзыва добавляются после TBD-07.
6.4 Ответ, идемпотентность и отказ публикации
Успех первой записи возвращает 200 SUCCESS с record_id, received_at и duplicate: false. Повтор совпадающего события возвращает тот же результат первой записи и duplicate: true. Повтор является успехом.
Ключ идемпотентности состоит из source_service и event_id. Источник должен генерировать один детерминированный event_id на логическую операцию и сохранять его при повторах. Если ключ совпал, а нормализованное тело отличается, audit-service возвращает 409 EVENT_ID_CONFLICT и не записывает новое событие.
| Сценарий | Поведение сервиса доступа | Сигнал
| Событие принято | Продолжить auth-операцию, сохранить record_id только для диагностики при необходимости | Счётчик отправленных и принятых совпадает
| Ответ потерян или 5xx/timeout | Не менять результат auth-операции; повторить то же тело с тем же event_id | Метрика ошибки и retry
| 401/403 публикации | Не менять результат auth-операции; событие не записано | Срочный alert о сломанной identity или правах источника
| 400/409 публикации | Не менять результат auth-операции; автоматический повтор без исправления не поможет | Alert о несовместимой схеме или конфликте event_id
| Источник не смог доставить событие после бюджета повторов | Auth-операция остаётся выполненной | Расхождение sent/accepted и инцидент по правилам эксплуатации
Синхронный HTTP-вызов не обеспечивает атомарность двух систем и exactly-once доставку. Fail-open является принятой политикой, но место хранения события до повторной отправки, бюджет retry и восстановление после перезапуска ещё не определены в доступных контрактах. Memcached нельзя автоматически считать надёжной очередью. Эти детали остаются TBD-05.

9. Открытые вопросы
Из какого атрибута внутреннего СУДИР формируется стабильный sudir_subject_id, нужен ли сервису доступа access token после входа и как срок токена связан со сроком прикладной сессии. До решения токены не передаются в SPA, refresh token не используется, обязательный introspection не вводится.
Каковы idle timeout по умолчанию, absolute timeout, срок OIDC-транзакции, критерий пользовательской активности и правила применения новой настройки к действующим сессиям. Диапазон idle timeout 15-60 минут зафиксирован предварительно, точное значение не выбрано.
Какие issuer, discovery path, client credentials, scopes, claims, response mode и redirect URI зарегистрированы для административной панели. Также нужно решить, достаточно ли локального logout или требуется завершение SSO-сессии СУДИР.
Какие origin и маршруты использует SPA, подтверждается ли flow через 302, какие поля нужны в session response и какие правила применяются для cookie, CORS, CSRF, browser binding и повторов logout.
Какие значения action закрепить за auth-событиями, как представить владельца сессии при административном завершении и где хранить событие до повторной доставки. Общая схема, endpoint, идемпотентность и fail-open уже определены контрактом сервиса аудита.
Как обрабатывать неизвестный или pending профиль, нужна ли автоматическая регистрация pending-профиля, как версионируются эффективные права и какой контракт владеет просмотром и административным завершением сессий.
Как глобальная блокировка и SSO logout во внутреннем СУДИР отзывают прикладные сессии, какие идентификаторы и гарантии доступны и какая задержка допустима. До решения мгновенный внешний отзыв и готовая интеграция через RabbitMQ не обещаются.
