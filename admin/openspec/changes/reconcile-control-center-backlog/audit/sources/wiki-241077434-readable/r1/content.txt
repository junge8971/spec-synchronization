API Contract: Сервис аудита
Общая информация
Назначение: Хранить неизменяемый журнал действий сотрудников над административной системой и центром управления ассистентом. Сервис принимает события от сервисов-источников и предоставляет уполномоченным сотрудникам поиск, просмотр и выгрузку записей.
Базовый URL: /api/audit-service/api/v1
Формат обмена: JSON. Единственное исключение - выгрузка (3.4): при успехе она отдаёт файл, при ошибке возвращается обычный JSON-envelope.
Две зоны API. У сервиса аудита две независимые зоны с разными потребителями, разными учётными данными и разными правами:
| Зона | Методы | Потребитель | Кто проверяет доступ
| Внутренняя публикация | 3.1 | сервис доступа и администрирования, API сервиса управления ассистентом | Ingest guard по identity вызывающего сервиса
| Публичный поиск | 3.2, 3.3, 3.4 | Аудит UI административного SPA | Access guard через сервис доступа и администрирования
Примечание: Ingest guard - новый компонент в архитектуре, который возникает из-за потребности аутентификации вызывающих сервисов. Это решение еще требует согласования.
Разделение зон обязательно. Учётные данные публикации не дают права на поиск, просмотр и выгрузку. Сессия сотрудника не даёт права публиковать события. Компрометация источника не должна превращаться в чтение всего журнала.
Identity вызывающего сервиса. Механизм аутентификации сервисов-источников ещё не выбран (см. 7.1). Контракт от него не зависит и опирается только на инварианты:
identity вызывающего устанавливается на транспортном уровне;
значение source_service записи выводится из этой identity;
тело события не содержит поля, которым источник называет себя;
учётные данные публикации не дают доступа к поиску и выгрузке.
Версия контракта: v1.0
1. Цель задачи
Согласовать контракты, которые позволят:
доменным модулям центра управления и сервису доступа публиковать события аудита синхронным вызовом API сервиса аудита;
административному интерфейсу искать, просматривать и выгружать записи аудита;
закрыть журнал от подделки: источник не может подписать запись чужим именем, а повторная доставка не порождает дубликата;
сохранить работоспособность журнала при отказах: недоступность сервиса аудита не блокирует операцию сотрудника, но и не остаётся незамеченной.
Событийного транспорта в контуре нет: Kafka не используется, публикация синхронная.
2. Модель записи аудита
2.1 Состав записи
Модель одна на все источники и все классы событий. Источник передаёт событие (3.1), сервис аудита дополняет его своими полями и хранит как запись.
{
"record_id": "01J9F7K2M4N6P8Q0R2S4T6V8W0",
"event_id": "b3f1c2a0-3b4e-4c5a-9f21-77e0a1b2c3d4",
"schema_version": "1.0",
"occurred_at": "2026-09-07T11:42:17.312Z",
"received_at": "2026-09-07T11:42:17.508Z",
"source_service": "access-service",
"action": "access.role.assigned",
"subject": {
"type": "employee",
"employee_id": "e-10245",
"sudir_id": "1000234567",
"session_id": "s-77e0a1b2",
"ip": "10.12.4.31"
},
"object": {
"type": "role_assignment",
"id": "ra-88123",
"name": "security_admin для e-10312"
},
"result": {
"status": "success",
"reason": null
},
"correlation": {
"correlation_id": "c-4f2a9e18",
"trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
"request_id": "r-0d1e2f3a"
}
}
| Поле | Тип | Кто заполняет | Описание
| record_id | string | сервис аудита | Идентификатор записи в журнале. Адресует запись в методах 3.3 и в ссылках из интерфейса. Монотонно возрастает в порядке записи.
| event_id | string | источник | Идентификатор события в пределах источника. Вместе с source_service образует ключ идемпотентности (5.3).
| schema_version | string | источник | Версия схемы события. Сервис аудита проверяет её до разбора остальных полей.
| occurred_at | string | источник | Время совершения действия в источнике. RFC 3339, UTC, с миллисекундами.
| received_at | string | сервис аудита | Время записи события в журнал. RFC 3339, UTC, с миллисекундами.
| source_service | string | сервис аудита | Сервис-источник. Выводится из аутентифицированной identity вызывающего, в теле запроса отсутствует.
| action | string | источник | Выполненное действие в нотации <система>.<объект>.<действие> (2.5).
| subject | object | источник | Субъект действия - сотрудник, совершивший операцию (2.1.1).
| object | object | источник | Объект действия (2.1.2).
| result | object | источник | Результат операции (2.1.3).
| correlation | object | источник | Идентификаторы корреляции (2.1.4).
| selection | object | источник | Критерий отбора и объём, когда действие адресовано множеству объектов (2.1.5). Отсутствует, когда действие адресовано одному объекту.
2.1.1 subject - субъект действия
| Поле | Тип | Обязательность | Описание
| type | string | Да | "employee" - действие совершил идентифицированный сотрудник; "unknown" - субъект установить не удалось.
| employee_id | string | При type = "employee" | Идентификатор профиля сотрудника в сервисе доступа.
| sudir_id | string | Нет | Идентификатор сотрудника в СУДИР. Позволяет связать запись с идентичностью, когда профиль уже удалён.
| session_id | string | Нет | Прикладная сессия, в рамках которой выполнено действие.
| ip | string | Нет | Сетевой адрес, с которого пришёл запрос.
Субъект может быть неизвестен, и это штатный случай. Отказ по отсутствующей, истёкшей или отозванной сессии - тоже событие аудита, и терять его нельзя. При type = "unknown" поле employee_id отсутствует, а известные признаки (ip, session_id) заполняются в том объёме, в каком они есть. Запись без субъекта остаётся полноценной записью об отказе.
2.1.2 object - объект действия
| Поле | Тип | Обязательность | Описание
| type | string | Да | Тип объекта: employee, role, role_assignment, team, skill, surface, dialog, incident, report и далее по мере роста системы.
| id | string | Нет | Идентификатор объекта в владеющем сервисе. Отсутствует, когда действие не адресовано конкретному объекту (отказ на уровне маршрута, выгрузка по критерию).
| name | string | Нет | Человекочитаемое представление объекта на момент события. Хранится снимком: объект может быть переименован или удалён, а журнал обязан оставаться читаемым.
2.1.3 result - результат
| Поле | Тип | Обязательность | Описание
| status | string | Да | "success" - операция выполнена; "denied" - отказано проверкой прав или ограничением объекта; "error" - операция не выполнена из-за ошибки.
| reason | string | При status = "denied" или "error" | Код причины. Машиночитаемый, не текст для пользователя.
2.1.4 correlation - идентификаторы корреляции
| Поле | Тип | Обязательность | Описание
| correlation_id | string | Да | Сквозной идентификатор операции. Связывает записи, порождённые одним действием сотрудника в разных сервисах.
| trace_id | string | Нет | Идентификатор trace в формате W3C Trace Context. Шов с наблюдаемостью: по нему из записи журнала переходят в traces.
| request_id | string | Нет | Идентификатор HTTP-запроса в сервисе-источнике.
Корреляция работает в одну сторону: из записи аудита можно перейти в traces, но технические логи и traces в журнал не втекают. Аудит хранит действия сотрудников, наблюдаемость хранит техническую картину - это разные системы с разными сроками жизни данных.
2.1.5 selection - критерий отбора
Заполняется, когда действие адресовано не одному объекту, а множеству, отобранному по условию. Обязателен для событий выгрузки, допустим для чтений, выполненных по критерию.
| Поле | Тип | Обязательность | Описание
| criteria | object | Да | Снимок условия отбора в том виде, в каком его задал сотрудник. Состав полей определяет источник, сервис аудита хранит объект как есть и не разбирает его.
| matched_count | integer | Да | Число объектов, попавших в отбор.
Без этого поля запись о выгрузке не отвечает на главный вопрос разбора утечки: сколько данных и по какому условию покинуло систему. Запись "сотрудник выгрузил диалоги" не отличает один диалог от сорока тысяч, и класс событий "выгрузка" теряет смысл.
Пример события выгрузки, обязательные поля записи (2.1) в нём опущены:
{
"action": "control.dialog.exported",
"object": {
"type": "dialog"
},
"selection": {
"criteria": {
"occurred_from": "2026-08-01T00:00:00Z",
"occurred_to": "2026-09-01T00:00:00Z",
"channel_id": "city_web"
},
"matched_count": 40231
},
"result": {
"status": "success"
}
}
2.2 Два времени и зачем нужны оба
occurred_at - бизнес-время, его задаёт источник в момент действия. received_at - серверное время, его проставляет сервис аудита в момент записи. Между ними лежит задержка вызова, а при повторах источника - и больше.
Разделение ролей жёсткое:
| Что | Какое поле | Почему
| Фильтрация по периоду | occurred_at | Сотрудник ищет "что происходило во вторник", а не "что мы записали во вторник".
| Сортировка и пагинация по умолчанию | received_at + record_id | Значение назначает одна сторона, оно не убывает и не приходит задним числом. Курсор на нём устойчив.
| Расследование инцидента | оба | Расхождение между ними - признак задержки или повтора доставки и само по себе улика.
2.3 Применимость полей к классам событий
Модель обязана одинаково описывать четыре класса событий. Поле, обязательное для изменения, может быть неизвестно для отказа. Это заложено в модель, а не обходится на месте.
| Поле | Изменение | Защищённое чтение | Выгрузка | Отказ
| occurred_at, received_at | обязательны | обязательны | обязательны | обязательны
| source_service, action | обязательны | обязательны | обязательны | обязательны
| subject.type | employee | employee | employee | employee или unknown
| subject.employee_id | обязателен | обязателен | обязателен | может отсутствовать
| object.type | изменяемый объект | прочитанный объект | тип выгружаемых объектов | запрошенный объект
| object.id | обязателен | обязателен при чтении одного объекта | отсутствует: отбор задан критерием, а не одним объектом | может отсутствовать
| result.status | success или error | success или error | success или error | denied
| result.reason | при error | при error | при error | обязателен
| correlation.correlation_id | обязателен | обязателен | обязателен | обязателен
| selection | отсутствует | при чтении по критерию | обязателен | отсутствует
2.4 Именование действий
action строится как <система>.<объект>.<действие>, глагол в прошедшем времени. Значение неизменяемо: переименование действия ломает историю поиска.
| Класс | Пример action | Что означает
| Изменение | access.role.assigned | Роль назначена сотруднику
| Изменение | control.skill.disabled | Навык отключён
| Защищённое чтение | control.dialog.viewed | Открыта карточка диалога жителя
| Выгрузка | control.dialog.exported | Подборка диалогов выгружена
| Отказ | access.authorization.denied | Доступ закрыт проверкой прав
Каталог значений ведёт владелец схемы событий (см. 7.5).
3. Методы API
3.1 Публикация события аудита
Внутренний метод. Вызывается источником синхронно в ходе обработки операции сотрудника. Одно событие на вызов.
Сервис-исполнитель: audit-service HTTP метод: POST URL: /api/audit-service/api/v1/events
Заголовки запроса: учётные данные вызывающего сервиса. Способ их передачи определяется механизмом аутентификации, который ещё не выбран (5.2, 7.1); на состав тела запроса и ответа он не влияет.
Тело запроса:
{
"event_id": "b3f1c2a0-3b4e-4c5a-9f21-77e0a1b2c3d4",
"schema_version": "1.0",
"occurred_at": "2026-09-07T11:42:17.312Z",
"action": "access.role.assigned",
"subject": {
"type": "employee",
"employee_id": "e-10245",
"sudir_id": "1000234567",
"session_id": "s-77e0a1b2",
"ip": "10.12.4.31"
},
"object": {
"type": "role_assignment",
"id": "ra-88123",
"name": "security_admin для e-10312"
},
"result": {
"status": "success"
},
"correlation": {
"correlation_id": "c-4f2a9e18",
"trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
"request_id": "r-0d1e2f3a"
}
}
| Поле | Тип | Обязательность | Описание
| event_id | string | Да | Идентификатор события, генерирует источник. Уникален в пределах источника; вместе с source_service образует ключ идемпотентности (5.3).
| schema_version | string | Да | Версия схемы события.
| occurred_at | string | Да | Время совершения действия, RFC 3339, UTC.
| action | string | Да | Выполненное действие (2.5).
| subject | object | Да | Субъект действия (2.1.1).
| object | object | Да | Объект действия (2.1.2).
| result | object | Да | Результат операции (2.1.3).
| correlation | object | Да | Идентификаторы корреляции (2.1.4).
| selection | object | При выгрузке и при чтении по критерию | Критерий отбора и объём (2.1.5).
source_service в теле запроса отсутствует. Это не упущение схемы, а свойство контракта: значение выводится из аутентифицированной identity вызывающего. Если бы источник называл себя сам, любой скомпрометированный источник подписывал бы записи чужим именем, и журнал перестал бы быть доказательством. Поле, переданное в теле, отвергается как ошибка валидации.
received_at и record_id источник не передаёт: их присваивает сервис аудита.
Успешный ответ (HTTP 200):
{
"code": "SUCCESS",
"data": {
"record_id": "01J9F7K2M4N6P8Q0R2S4T6V8W0",
"received_at": "2026-09-07T11:42:17.508Z",
"duplicate": false
},
"message": "Событие принято",
"errors": []
}
| Поле в data | Тип | Описание
| record_id | string | Идентификатор созданной записи.
| received_at | string | Время записи в журнал.
| duplicate | boolean | false - создана новая запись; true - событие с таким ключом идемпотентности уже было записано ранее и его содержимое совпало, повторной записи не произошло.
Повторная публикация того же события (HTTP 200):
{
"code": "SUCCESS",
"data": {
"record_id": "01J9F7K2M4N6P8Q0R2S4T6V8W0",
"received_at": "2026-09-07T11:42:17.508Z",
"duplicate": true
},
"message": "Событие уже было записано ранее",
"errors": []
}
Повтор - это успех, а не ошибка. record_id и received_at возвращаются от первой записи, новая не создаётся. Источник может безопасно повторять вызов при таймауте или сетевом сбое, не выясняя, дошёл ли предыдущий.
Повтором считается только полное совпадение: тот же ключ идемпотентности и то же содержимое события. Если ключ тот же, а содержимое другое, это конфликт, а не повтор, и сервис отвечает 409 (5.3).
Ошибка валидации (HTTP 400):
{
"code": "VALIDATION_FAILED",
"data": null,
"message": "Событие не прошло валидацию",
"errors": [
{ "field": "subject.employee_id", "message": "Обязательное поле при subject.type = employee" }
]
}
Неподдерживаемая версия схемы (HTTP 400):
{
"code": "SCHEMA_VERSION_UNSUPPORTED",
"data": null,
"message": "Версия схемы события не поддерживается",
"errors": [
{ "field": "schema_version", "message": "Получено 2.0, поддерживается 1.0" }
]
}
Конфликт идентификатора события (HTTP 409):
{
"code": "EVENT_ID_CONFLICT",
"data": null,
"message": "event_id уже использован этим источником для другого события",
"errors": [
{ "field": "event_id", "message": "Содержимое события отличается от ранее записанного с тем же ключом" }
]
}
Вызывающий не аутентифицирован (HTTP 401) - UNAUTHORIZED. Вызывающий аутентифицирован, но не имеет права публиковать (HTTP 403) - FORBIDDEN.
Примечания:
Идемпотентность держится на паре source_service и event_id и обязательна. Публикация синхронная, транзакции между источником и журналом нет, поэтому retry источника - штатный сценарий, а не исключение.
Публикация не входит в транзакцию изменения сущности в источнике. Транзакция источника закрывается по своим правилам, независимо от результата этого вызова.
Fail-open - политика вызывающего, а не поведение сервиса аудита. Сервис аудита на отказ отвечает честной ошибкой и никогда не подтверждает незаписанное событие. Как поступить с этой ошибкой, решает источник: по принятому решению он не отклоняет операцию сотрудника. Читать раздел как разрешение игнорировать ошибку нельзя - см. 5.4.
Пакетная публикация контрактом не предусмотрена.
3.2 Поиск записей
Публичный метод для Аудит UI. Возвращает страницу записей по фильтру.
Сервис-исполнитель: audit-service HTTP метод: GET URL: /api/audit-service/api/v1/records
Заголовки запроса:
Authorization: Bearer <session_token>
Параметры запроса:
| Параметр | Тип | Обязательность | Описание
| occurred_from | string | Да | Начало интервала по occurred_at, включительно. RFC 3339, UTC.
| occurred_to | string | Да | Конец интервала по occurred_at, исключительно. RFC 3339, UTC.
| subject_employee_id | string | Нет | Фильтр по субъекту действия.
| action | string | Нет | Точное совпадение действия.
| object_type | string | Нет | Фильтр по типу объекта.
| object_id | string | Нет | Фильтр по идентификатору объекта. Применяется вместе с object_type.

| source_service | string | Нет | Фильтр по сервису-источнику.

| limit | integer | Нет | Размер страницы. По умолчанию 50, максимум 200.
| cursor | string | Нет | Курсор следующей страницы из поля next_cursor предыдущего ответа. При его передаче параметры фильтра и сортировки должны совпадать с исходным запросом.
Временной интервал обязателен. Журнал append-only и растёт без верхней границы; запрос без интервала - это запрос по всей истории. Обязательный интервал делает стоимость поиска предсказуемой. Предельная длина интервала ограничивается конфигурацией (7.3).

Курсор строится на паре "значение поля сортировки плюс record_id", что даёт стабильный проход и не зависит от глубины страницы.

Общее число найденных записей не возвращается. Точный подсчёт на растущем журнале стоит дороже самой выборки; для навигации достаточно has_more.
401 и 403 означают разное и обрабатываются по-разному. 401 - сессия истекла или отозвана, интерфейс ведёт сотрудника на повторную аутентификацию. 403 - сессия действительна, но права на журнал нет, и повторная аутентификация ничего не изменит.
Каждое обращение к этому методу само является защищённым чтением - см. 7.6.

3.4 Выгрузка записей
Отдаёт файл с записями, отобранными теми же фильтрами, что и поиск. Выгрузка - это тот же отбор, отданный файлом.
Сервис-исполнитель: audit-service HTTP метод: GET URL: /api/audit-service/api/v1/records/export
Заголовки запроса:
Authorization: Bearer <session_token>
Параметры запроса: все фильтры метода 3.2 - occurred_from (обязателен), occurred_to (обязателен), subject_employee_id, action, object_type, object_id, result_status, source_service. Параметры постраничного обхода (limit, cursor) не применяются. Дополнительно:
| Параметр | Тип | Обязательность | Описание
| format | string | Нет | csv (по умолчанию) или jsonl.
| sort | string | Нет | То же, что в 3.2. По умолчанию occurred_at:asc: выгрузка читается как хронология.
Успешный ответ (HTTP 200): тело ответа - файл, не envelope.
Заголовки ответа:
Content-Type: text/csv; charset=utf-8 для csv, application/x-ndjson; charset=utf-8 для jsonl
Content-Disposition: attachment; filename="audit-<occurred_from>-<occurred_to>.<ext>"
Состав данных совпадает с составом записи (2.1). В jsonl запись сериализуется как один JSON-объект на строку, структура вложенных объектов сохраняется. В csv вложенные объекты разворачиваются в колонки с точкой в имени: subject.employee_id, object.type, result.status, correlation.trace_id и так далее; первая строка - заголовки колонок.
Отбор превышает предел выгрузки (HTTP 413):
{
"code": "EXPORT_TOO_LARGE",
"data": null,
"message": "Отбор превышает предел выгрузки, сузьте интервал или добавьте фильтры",
"errors": []
}
Ошибка валидации (HTTP 400) - VALIDATION_FAILED. Сессия недействительна (HTTP 401) - UNAUTHORIZED. Нет прав на выгрузку (HTTP 403) - FORBIDDEN. Проверка доступа не выполнена (HTTP 503) - ACCESS_CHECK_UNAVAILABLE, см. 5.5.
Примечания:
Выгрузка синхронная. Сервис аудита не имеет ни worker'а, ни объектного хранилища: в архитектуре они есть у отчётов центра управления, но не у журнала. Асинхронное задание со скачиванием по ссылке потребовало бы нового контейнера и новой связи, поэтому в этот контракт не входит.
Предел объёма обязателен. Сервис заранее оценивает число записей под фильтром и, если оно превышает настроенный предел, отказывает кодом EXPORT_TOO_LARGE, не начиная формировать файл. Иначе на растущем журнале метод оказывается без границ. Числовое значение предела не согласовано (7.3).
Ошибки возвращаются в обычном envelope. Файл отдаётся только при успехе; клиент отличает случаи по Content-Type.
Права на выгрузку проверяются так же, как на поиск, и отдельно от прав публикации.

5. Соображения безопасности
5.1 Разделение зон
Публикация и чтение разведены не только по правам, но и по учётным данным. Источник, скомпрометированный целиком, позволяет писать поддельные события от своего имени, но не позволяет прочитать журнал. Сессия сотрудника с правом на аудит позволяет читать, но не позволяет писать. Ни одна учётная запись не имеет обеих возможностей.
5.2 Identity вызывающего сервиса
Механизм не выбран (7.1), но требования к нему от выбора не зависят:
identity вызывающего устанавливается на транспортном уровне, а не сообщается в теле или в прикладном поле запроса;
source_service записи выводится из этой identity;
источник не может опубликовать событие от имени другого источника;
учётные данные публикации не дают доступа к методам 3.2, 3.3 и 3.4.
Пока механизм не выбран, контракт не фиксирует ни заголовок, ни формат учётных данных. Их появление не меняет ни тело запроса, ни ответы: изменения ограничатся составом заголовков запроса в 3.1.
5.3 Идемпотентность, повторы и конфликты
Ключ идемпотентности - пара source_service и event_id, а не один event_id. Источников несколько, каждый генерирует идентификатор сам, и требовать от них глобально уникальных значений означало бы вводить общий генератор, которого нет. Дедупликация в пределах источника снимает это требование: event_id обязан быть уникален только внутри своего сервиса.
Область ключа - не деталь реализации. source_service выводится из аутентифицированной identity (5.2), подделать его источник не может, поэтому и погасить чужое событие, заняв его идентификатор, тоже не может. Дедупликация по одному event_id такую возможность бы открыла: событие второго источника было бы принято с ответом об успехе и в журнал не попало.
Пара закрывает два сценария одним механизмом: сетевой повтор источника при таймауте и повторную доставку того же события. Оба приводят к одной записи в журнале.
Следствие для источника: event_id должен быть детерминирован для одной и той же логической операции. Если источник генерирует новый идентификатор на каждой попытке, идемпотентность не работает и журнал получает дубликаты.
Конфликт содержимого не считается повтором. Повтор - это когда совпали и ключ, и событие. Если ключ совпал, а полезная нагрузка отличается, сервис аудита отвечает 409 EVENT_ID_CONFLICT и не записывает событие. Сравнение выполняется по хэшу нормализованного тела запроса, вычисленному при первой записи и сохранённому вместе с ней.
Отвечать в этом случае успехом нельзя: источник, по ошибке переиспользовавший идентификатор для другой операции, получил бы подтверждение записи, которой нет. Явный отказ превращает молчаливую потерю события в видимую ошибку источника.
5.4 Отказ сервиса аудита и fail-open
Принятая политика: недоступность сервиса аудита не отклоняет операцию сотрудника. Из этого следует то, что легко упустить:
Сервис аудита никогда не подтверждает незаписанное событие. На отказ он отвечает ошибкой; молчаливого проглатывания в контракте нет.
Отказ аутентификации при fail-open даёт тихий пропуск в журнале. Просроченные или неверные учётные данные источника дают 401 или 403, источник по своей политике продолжает работать, операции выполняются, записи не появляются. Снаружи это выглядит как затишье, а не как инцидент.
Поэтому 401 и 403 на публикации - это alert на стороне источника, а не строка в логе. У источника должна быть метрика "событий отправлено против событий принято": расхождение - единственный сигнал, по которому пропуск обнаруживается до аттестации, а не на ней.
5.5 Отказ проверки доступа и fail-closed
Методы чтения (3.2, 3.3, 3.4) обязаны получить решение о доступе от сервиса доступа и администрирования. Если проверка не выполнена - сервис доступа недоступен, ответил ошибкой или не уложился в таймаут, - доступ закрывается: сервис аудита отвечает 503 ACCESS_CHECK_UNAVAILABLE и журнал не отдаёт. Отсутствие подтверждённого решения не приравнивается к разрешению.
Политики двух путей намеренно противоположны:
| Путь | Отказавшая зависимость | Политика | Почему так
| Публикация (3.1) | сервис аудита недоступен источнику | fail-open | операция сотрудника не блокируется, риск пропуска в журнале принят
| Чтение (3.2, 3.3, 3.4) | сервис доступа недоступен аудиту | fail-closed | журнал не выдаётся тому, чьи права не подтверждены
Практическое следствие: приём событий продолжает работать, когда чтение уже закрыто. Отказ сервиса доступа делает журнал временно непросматриваемым, но не создаёт в нём пропусков.
5.6 Неизменяемость журнала
Контракт не содержит методов изменения и удаления записей, и это осознанно. Единственный процесс, который удаляет данные из журнала, - применение сроков хранения; он выполняется внутри сервиса аудита и наружу не публикуется.

7. Открытые вопросы
Механизм аутентификации сервисов-источников. Рассматриваются два варианта: mTLS с identity из клиентского сертификата и OAuth 2.0 client credentials с локальной проверкой подписи JWT. До решения контракт описывает только инварианты (5.2).
Сроки хранения: оперативный и архивный. От них зависит, с какого момента запись перестаёт отдаваться методами 3.2 и 3.3 и нужен ли отдельный контракт доступа к архиву.
Числовые пределы: предельная длина интервала поиска, максимальный размер страницы, предел выгрузки. Задать их можно только зная ожидаемый объём событий в сутки, а он не зафиксирован. Механизмы ограничения в контракте описаны, значения - нет.
Состав колонок выгрузки. Сейчас он повторяет состав записи. Требуется подтверждение, что для аттестации не нужен другой набор или другой порядок колонок.
Фиксируется ли обращение к самому журналу как событие аудита. Поиск и выгрузка журнала - действия сотрудника над персональными данными, и для диалогов такие действия аудируются. При этом у сервиса аудита в архитектуре нет компонента публикации, то есть собственные чтения и выгрузки он сейчас не фиксирует. Для аттестуемого контура это скорее пробел, чем решение.
Нужны ли значения изменённых атрибутов. Модель отвечает на вопрос "кто, что и над чем сделал", но не хранит прежнее и новое значение. Если аттестация требует восстановления содержания изменения, модель придётся расширить.
Действия над двумя объектами. Назначение роли сотруднику затрагивает и роль, и сотрудника. Сейчас это описывается одним объектом связи (role_assignment); требуется подтверждение, что такой формы достаточно для поиска.
