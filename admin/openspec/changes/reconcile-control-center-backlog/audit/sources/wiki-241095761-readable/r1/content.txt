API Contract: Дашборд модуля аналитики центра управления
Общая информация
Назначение: Обеспечить сотруднику центра управления функционал страницы "Дашборд": сводные показатели, распределения и временные ряды по выборке диалогов за выбранный период и канал, а также настройку доски - состава и порядка виджетов, которые сотрудник видит на этой странице.
Базовый URL: /api/control/api/analytics/v1
По C4-модели дашборды строит компонент analyticsModule контейнера managementApi, ему же принадлежат отчёты и агрегаты. Дашборд - ресурс внутри аналитики, поэтому отчётам не понадобится второй базовый URL.
Формат обмена: JSON в кодировке UTF-8. Ответы приходят с заголовком Content-Type: application/json без параметра charset. Тело запроса передаётся с Content-Type: application/json: тело другого типа сервер как JSON не разбирает и отвечает 422 VALIDATION_ERROR (4.1).
Потребитель: компонент Аналитика UI web-интерфейса центра управления. Запрос проходит через оболочку центра и Access guard контейнера managementApi; модуль получает уже сформированный авторизационный контекст.
Два источника данных. Они отвечают на разные вопросы, отказывают независимо и имеют разный жизненный цикл.
| Источник | Что содержит | Кто заполняет | Какие методы обслуживает
| Отчётная read-модель (reportingStore) | Производные агрегаты по диалогам: показатели, распределения, ряды | Worker проекций центра управления, фоново | 3.1 Данные дашборда, 3.2 Пересчёт
| БД модуля (managementDb) | Каталог виджетов и личные доски сотрудников | Модуль аналитики в ходе операций сотрудника | 3.3 Каталог, 3.4 Чтение доски, 3.5 Сохранение доски
Решение по технологии отчётной read-модели в C4-модели помечено как нерешённое. Контракт описывает состав агрегатов и не выбирает хранилище.
Правила авторизации:
Во все методы передаётся session_token в заголовке Authorization: Bearer <session_token>.
Access guard проверяет сессию и передаёт модулю авторизационный контекст: сотрудника, его область доступа и функциональные роли. Отдельного функционального разрешения на дашборд нет: при действительной сессии доступны все пять методов. Сбой проверки закрывает доступ.
Область видимости данных задают область доступа и функциональная роль сотрудника, и модуль применяет её к отбору выборки (5.1).
Открытие дашборда - защищённое чтение, оно регистрируется событием аудита (5.3). Изменение доски - защищённое изменение, оно регистрируется своим событием (5.4).
Глубина хранения: агрегаты доступны в пределах установленной глубины. Текущее значение - 30 дней, оно регулируется конфигурацией сервиса и в контракте не фиксируется.
Версия контракта: v1.0
1. Цель задачи
Согласовать контракт, который позволит:
показать страницу "Дашборд" за выбранный период и канал: доску по умолчанию из двенадцати виджетов и данные по каждому доступному виджету каталога, который сотрудник может поставить на доску;
получить сведения о выборке, по которой посчитаны числа, и о моменте их расчёта, чтобы сотрудник не принимал решение по данным неизвестной свежести;
применить область видимости роли к отбору выборки и объяснить сотруднику, почему его числа отличаются от чужих;
дать сотруднику собрать свою доску: прочитать каталог доступных виджетов, узнать, почему часть из них пока недоступна, и сохранить состав и порядок;
переживать частичный отказ агрегатов, не гася весь экран;
зафиксировать открытие дашборда и изменение доски в журнале аудита, не изобретая собственный формат события;
Отчёты и выгрузки в контракт не входят, хотя обслуживаются тем же модулем.
2. Модель дашборда
2.1 Три сущности для формирования дашборда
Контракт оперирует тремя разными сущностями: они живут в разных местах, меняются с разной частотой и принадлежат разным методам.
| Сущность | Отвечает на вопрос | Где живёт | Кто меняет
| Показатель | что измеряем и каким числом | отчётная read-модель | worker проекций, фоново
| Доска | что из этого сотрудник видит и в каком порядке | БД модуля | сам сотрудник
| Каталог виджетов | что вообще можно поставить на доску и почему сейчас нельзя | БД модуля | платформа по мере готовности данных
Настройка доски оперирует виджетом, а не показателем. Каталог называется "Добавить виджет", его элементы - виджеты, и удаляется с доски тоже виджет. Внутри одного виджета показателей может быть несколько: у карточки это значение, дельта и ряд спарклайна. Доска хранит список идентификаторов виджетов, а не список метрик.
Что в контракт не входит. Перетаскивание виджета, подсветка слота, само модальное окно, порядок его вкладок и то, что виджет в узком слоте отрисовывается меньше - это поведение клиента. Контракту принадлежит то, что клиент один знать не может: каталог с признаками доступности, сохранённый состав доски и правила его проверки.
2.2 Виджет: две формы данных
Виджет ответа - это discriminated union. Дискриминатор type, у каждого значения своя схема полезной нагрузки. Обобщённого поля data произвольной структуры в контракте нет: оно не описывает формы, а переносит их смысл в клиент.
| Поле | Тип | Обязательность | Описание
| widget_id | string | Да | Идентификатор виджета.
| type | string | Да | Дискриминатор формы данных: metric, distribution.
| title | string | Да | Заголовок виджета. Единственный источник заголовка - этот ответ и каталог; они обязаны совпадать.
| subtitle | string / null | Да | Подзаголовок. null у виджетов, у которых его на экране нет.
| status | string | Да | ok - данные посчитаны; error - агрегат недоступен, полезная нагрузка отсутствует (3.1.5).
| error | object / null | Да | При status = "error" - code и message, поясняющие, почему виджет не посчитан (3.1.5); при status = "ok" - null.
Форма metric - показатель: значение за период, дельта и ряд по времени.
| Поле | Тип | Обязательность | Описание
| value | number / null | Да | Значение показателя за период. null - за период нет данных для расчёта.
| unit | string | Да | Единица значения (2.3).
| delta | object / null | Да | Изменение к базе сравнения (2.4). null - база недоступна или дельта у виджета не выводится.
| series | array of objects | Да | Точки ряда: date - календарные сутки в UTC в формате YYYY-MM-DD, value - значение показателя за эти сутки с той же точностью, что и value виджета (2.5). Разреженный ряд (2.5). Пустой массив - точек нет.
Форма distribution - распределение по категориям.
| Поле | Тип | Обязательность | Описание
| value | number / null | Да | Сводное значение распределения за период, если виджет его выводит: "2,7" обращений на пользователя у "Частота использования". null - сводного значения у виджета нет или его не из чего посчитать (2.6).
| unit | string / null | Да | Единица сводного значения (2.3). null вместе с value.
| measure | string | Да | Чем измерены категории: share - доля в процентах, count - абсолютное число.
| items | array of objects | Да | Категории: code, name, value. Значение читается по measure.
| truncated | boolean | Да | Признак того, что перечень усечён и остаток свёрнут в категорию other (2.6.1).
Подача виджета зависит от слота, а не от формы данных. Один и тот же виджет формы metric в узком слоте рисуется карточкой со спарклайном, а в широком - графиком с дневной осью и подсказкой по точке. На доске по умолчанию "Ошибки NLP" выводится графиком, а "Среднее время ответа бота" - карточкой; на доске с новыми виджетами наоборот. Поэтому форма описывает только состав данных, а способ отрисовки выбирает клиент по размеру слота (2.1).

| unique_users | Уникальные пользователи | metric | Число различных жителей в выборке | count | 54
| dau | DAU / Дневная аудитория | metric | Дневная аудитория | count | 3

Остальные доступные виджеты каталога. Кроме доски по умолчанию, сотрудник может поставить на доску ещё восемь доступных виджетов (2.7). Их вид и значения показаны на экране доски с новыми виджетами.

| mau | MAU / Месячная аудитория | metric | Месячная аудитория | count | 54, дельта +2,4%
| technical_failure_rate | Технические отказы | metric | Доля диалогов с техническим отказом | percent | 7,4%, дельта -0,2 п.п.

| rated_dialogs_share | Доля оставивших оценку | metric | Доля диалогов, в которых житель поставил оценку | percent | 31,5%, без дельты

Все показатели - и доски по умолчанию, и остальных доступных виджетов - читаются из отчётной read-модели. Ни один показатель не приходит из другого источника. Какие показатели отдают дельту, задаёт таблица 2.5. Из семи новых показателей формы metric дельта есть у mau и technical_failure_rate; у остальных пяти её на экране нет, и они всегда отдают delta: null (7.21). У распределения usage_frequency поля delta нет, как у любого распределения. Определения части новых показателей из прототипа не выводятся (7.19, 7.20).
Значения идентификаторов из прототипа не читаются. На экранах виден только заголовок виджета. Идентификаторы выведены из заголовков и нужны, чтобы доска и каталог ссылались на одно и то же. Идентификаторы и формы всех тридцати четырёх виджетов каталога, включая недоступные, приведены в 2.7.1 и 2.7.2; это рабочие значения, окончательные назначает владелец каталога (7.1).
Единицы:
| unit | Что означает | Как выводится
| count | Целое число объектов | как есть
| percent | Проценты, 0..100 | с суффиксом "%"
| seconds | Секунды | "1,1 с", "5 мин 23 с" - форматирует интерфейс
| score | Средний балл по шкале 1..5 | как есть
| ratio | Отношение двух величин, дробное число | как есть: "2,7"
2.3.1 У каждого процента назван знаменатель
Знаменатель процентных показателей неочевиден, и числа с экранов это доказывают.
| Роль | Выборка | Переключений | Решено без оператора | Сумма | Покрыто диалогов
| Администратор платформы | 54 | 27,8% | 64,8% | 92,6% | 15 + 35 = 50 из 54
| Владелец навыка | 28 | 28,6% | 71,4% | 100,0% | 8 + 20 = 28 из 28
| Владелец поверхности | 8 | 37,5% | 62,5% | 100,0% | 3 + 5 = 8 из 8
У администратора четыре диалога не попали ни в одну корзину, у двух других ролей корзины сходятся точно.
| Показатель | Числитель | Знаменатель
| operator_handoff_rate | диалоги, переведённые на оператора | все диалоги выборки
| resolved_without_operator | диалоги, закрытые ассистентом без перевода | все диалоги выборки
| nlp_errors | запросы, не распознанные классификатором | все запросы жителей в выборке, а не все диалоги
| technical_failure_rate | диалоги с техническим отказом | все диалоги выборки
| rated_dialogs_share | диалоги, в которых житель поставил оценку | все диалоги выборки
| low_ratings_share | низкие оценки оператора | все оценки оператора, то есть operator_rating_count
| returning_users | вернувшиеся жители | все различные жители выборки, то есть unique_users
Две первые корзины не покрывают выборку целиком. Остаток - диалоги, которые не были ни переведены на оператора, ни закрыты ассистентом успешно. В справочнике типов диалога соседнего контракта ровно три значения: chatbot, operator и failure, и две корзины отвечают первым двум. Остаток - сбойные диалоги: у администратора это 4 диалога и 7,4%, у двух других ролей сбойных диалогов в выборке нет, поэтому их корзины и дают ровно 100%. Третьей корзины на экране нет, отдельным виджетом остаток не выводится. Подтверждение вынесено в открытые вопросы (7.2). Показатель "Технические отказы" на экране с новыми виджетами равен 7,4%, то есть ровно тем же 4 диалогам из 54.
Знаменатель nlp_errors отличается от остальных. Показатель называется "Запросы, не распознанные классификатором", то есть считается по запросам, а не по диалогам. Из экрана это не проверяется: 6,4% одинаковы во всех ролях при выборках 54, 28 и 8, что для доли по разным множествам невозможно. Значение прототипа - константа мока; знаменатель зафиксирован по подзаголовку виджета и вынесен в открытые вопросы (7.3).
2.4 Дельта и база сравнения
| Поле в delta | Тип | Обязательность | Описание
| value | number | Да | Величина изменения, один знак после запятой. Знак задаёт направление: положительное значение - рост. Нулевое изменение приходит как 0.0.
| unit | string | Да | Единица дельты: percent, percentage_points, seconds, score (2.5).
База сравнения - предыдущий период такой же длины. Границы базы возвращаются в ответе всегда, в том числе когда база недоступна и дельта null (3.1.3), чтобы сотрудник и разработчик видели, с чем сравнивают.
Дельта считается по неокруглённым значениям. Дельта в percent - изменение относительно значения базы в процентах, в остальных единицах - разность значения за период и значения базы.
Единица дельты не всегда совпадает с единицей значения. У показателя в штуках дельта в процентах ("54" и "3,1%"), у показателя в процентах - в процентных пунктах ("27,8%" и "0,3 п.п."), у показателя в секундах - в секундах ("1,1 с" и "0,1 с"), у среднего балла - в баллах ("2,6" и "0,1"). Поэтому unit у дельты собственный, а не наследуется от значения.
Направление улучшения контрактом не передаётся. На всех экранах дельта одного цвета, в том числе направленная вниз: снижение переключений на оператора подано так же, как рост решённых без оператора. Цвет не кодирует "лучше или хуже", поэтому поля вида "рост это хорошо" в контракте нет.
delta равна null, когда базу сравнения посчитать нельзя: база начинается раньше границы хранения, то есть раньше текущего момента минус глубина хранения; в базе нет ни одного диалога; агрегат показателя за базу не посчитан (3.1.5); значение за период или за базу не определено; у дельты в percent значение базы равно нулю. Ноль в этих случаях не отдаётся: он означал бы "изменений не было", а это другое утверждение. null отдаётся и у показателей, у которых дельты на экране нет вовсе (2.5, 7.21).
Здесь контракт упирается в глубину хранения. Глубина агрегатов - 30 дней, а на всех экранах активен период "Месяц" и дельта показана. База сравнения месячного периода при такой глубине лежит за границей хранения и недоступна. По той же причине дельта null у периода по умолчанию: он равен глубине хранения (3.1.1).
2.5 Числа форм, точность и разреженность
Разные диаграммы оперируют разными числами. Кольцевые распределения отдают доли: подсказка "ЖКХ : 60.9" совпадает с легендой "60.9%". Столбчатые отдают абсолютные значения: "1 / v : 5" у оценок оператора и "Таймаут навыка / v : 41" у точек отказа. Линейные графики отдают ряд значений самой метрики по времени; ключ dialogs и значения 2 и 3 в подсказках прототипа - предположительно его артефакт, а не смысл ряда.
Округляет сервер, интерфейс печатает как есть. Число десятичных знаков - свойство показателя, а не клиента: на одном экране доли доменов идут с одним знаком (60.9, 21.7, 17.4), а доли платформ целыми (61, 24, 15). Клиент не может знать, сколько знаков показывать, поэтому значение приходит уже округлённым и выводится без дополнительной обработки.
| Виджет | Знаков после запятой | Дельта
| unique_users, dau, mau | 0 | percent
| operator_rating_count | 0 | нет
| operator_handoff_rate, resolved_without_operator, technical_failure_rate, nlp_errors | 1 | percentage_points
| rated_dialogs_share, low_ratings_share, returning_users | 1 | нет
| bot_response_time_avg | 1 | seconds
| session_duration_avg | 0 | нет
| user_rating_avg | 1 | score
| operator_rating_avg | 1 | нет
| domain_distribution | доли - 1 | поля нет
| platform_distribution | доли - 0 | поля нет
| operator_rating_distribution, technical_failure_points | 0 | поля нет
| usage_frequency | столбцы - 0, сводное значение - 1 | поля нет
Точки ряда округляются так же, как значение показателя. Половина округляется от нуля: 2,25 даёт 2,3. Значение без знаков после запятой приходит целым числом JSON (54), остальные - дробным (27.8, 25.0). "Нет" в колонке дельты означает, что показатель всегда отдаёт delta: null.
Доли к 100 не нормализуются. Сумма долей в одном распределении может отличаться от 100 на ошибку округления. Интерфейс не имеет права вычислять недостающую категорию как "100 минус сумма". На обоих распределениях прототипа сумма даёт ровно 100, но это свойство данных, а не гарантия контракта (7.5).
Ряд разреженный. Точка возвращается только за те дни, за которые есть данные; нулями пустые дни не заполняются. У владельца навыка в ряду отсутствует 28.07, у владельца поверхности точки разбросаны по месяцу. Клиент рисует пропуск равным промежутком и не должен считать ряд равномерной сеткой. Порядок точек задаёт сервер: ряд приходит упорядоченным по возрастанию даты. Ось, отсортированная как строки у владельца поверхности (12.08 перед 15.07), - ошибка шаблона прототипа, а не поведение API.
Пустые категории шкал сохраняются. У шкал с фиксированным набором значений - оценок оператора и частоты использования - категория с нулевым значением из ответа не исчезает: у владельца поверхности столбцы стоят только на оценках 2 и 4, но подписи 1, 3 и 5 на оси остались. Платформы тоже отдаются целиком, включая нулевые. У доменов и точек технического отказа нулевые категории в ответ не входят (2.6.1). При пустой выборке items пуст у всех распределений (3.1.6).
2.6 Справочные значения
Категория - это код и подпись, а не одна подпись. Каждый элемент распределения возвращает code и name, как это уже принято в соседнем контракте для каналов. Без кода переименование справочника меняет данные API, а сопоставить две выдачи между собой нечем. Коды справочников на экранах не видны и назначаются владельцами справочников (7.6).
Домены. Домен - справочник модуля навыков: он объединяет навыки, и каждый навык относится ровно к одному домену. На экране навыков доменов четыре: ЖКХ (6 навыков), Образование, МЭШ (3), Базовые навыки (4), Транспорт (2). Перечень не закрыт: домены создаются на том же экране. Диалог попадает в распределение по домену своих навыков; правило для диалога, в котором отработали навыки разных доменов, не определено (7.7). На дашборде доменов три - ЖКХ 60.9%, Образование, МЭШ 21.7%, Транспорт 17.4%, - и домена "Базовые навыки" среди них нет (7.18). У владельца навыка домен ровно один и равен 100%: все навыки его команды лежат в одном домене.
Платформы. Веб, iOS, Android. Перечень не закрыт. На всех трёх экранах доли одинаковы - 61%, 24%, 15% - при разных выборках; это данные прототипа, распределение зависит от области видимости. Перечень отдаётся целиком, без усечения и вместе с нулевыми категориями, по убыванию доли.
Точки технического отказа. Таймаут навыка, Ошибка 5xx, Нет ответа ЕСК, Прочее. Перечень не закрыт (7.8).
Шкала оценок оператора. Целые от 1 до 5. Шкала фиксированная: все пять категорий возвращаются всегда, включая нулевые; исключение - пустая выборка (3.1.6). Код и подпись категории - сама оценка строкой, от "1" до "5".
Шкала частоты использования. Категории от "1" до "5" - число обращений жителя за период; последняя категория - пять обращений и больше. Значение категории - число жителей. Шкала фиксированная и отдаётся так же, как шкала оценок. Сводное значение - среднее число обращений на жителя, unit = "ratio"; если жителей в выборке нет, value и unit равны null, а все пять категорий нулевые.
2.6.1 Усечение перечня и категория "Прочее"
Число категорий в распределении ограничено, и на экране это видно: последняя категория точек технического отказа называется "Прочее", то есть свёртка остатка уже происходит.
Усечение применяется к открытым справочникам: домены и точки технического отказа. Шкалы оценок оператора и частоты использования и перечень платформ отдаются целиком.
Категории с ненулевым значением упорядочены по убыванию, категории с нулевым значением в ответ не входят. Если категорий больше предела, остаток сворачивается в категорию с кодом other и подписью "Прочее".
Категория other всегда последняя, даже если её значение больше предыдущих.
Если read-модель сама отдаёт категорию с кодом other, она тоже выводится последней, свёрнутый остаток прибавляется к ней, а её место входит в предел.
truncated = true только тогда, когда свёрнута хотя бы одна категория. Собственная категория other read-модели без свёртки даёт truncated = false.
Доли считаются от суммы категорий, вошедших в ответ, вместе с other.
Свёртку выполняет сервер. Клиент получает готовый перечень и признак truncated.
Предельное число категорий вместе с "Прочее" задаётся конфигурацией и в контракте не фиксируется. Текущее значение - 5.
Является ли "Прочее" на экране остатком свёртки или самостоятельным значением справочника точек отказа, из прототипа не следует (7.8).
2.7 Каталог виджетов
Каталог - серверная сущность. Клиент не может вычислить ни один из её признаков: доступность виджета зависит от того, размечены ли шаги навыка и подключены ли данные внешней системы Writer, а подпись окна прямо говорит, что виджеты "появятся после соответствующих доработок", то есть состав каталога меняется во времени. Захардкоженный на клиенте список этого не выдержит.
Подпись окна: "Каталог из проработки аналитики. Виджеты, требующие разметки навыков или данных из системы Writer, помечены и появятся после соответствующих доработок."
| Поле элемента каталога | Тип | Обязательность | Описание
| widget_id | string | Да | Идентификатор виджета. На него ссылается доска.
| group | string | Да | Вкладка каталога: kpi - "KPI", diagnostic - "Диагностические".
| title | string | Да | Название виджета.
| subtitle | string / null | Да | Подзаголовок. null у элементов, у которых его на экране нет.
| type | string | Да | Форма данных виджета: metric, distribution (2.2). По ней интерфейс выбирает подходящий слот.
| available | boolean | Да | Можно ли поставить виджет на доску.
| unavailable_reason_code | string / null | Да | При available = false: markup_required - нужна разметка; writer_data_required - нужны данные из системы Writer. При available = true - null.
| unavailable_reason | string / null | Да | При available = false - пояснение для сотрудника, выводится под названием. При available = true - null.
| on_board | boolean | Да | Стоит ли виджет на доске сотрудника прямо сейчас, то есть в выдаче метода 3.4. У сотрудника без сохранённой доски - по составу доски по умолчанию. Недоступный виджет сохранённой доски скрыт (3.4) и получает false. Выводится бейджем "на доске".
available и on_board - разные признаки. Виджет, стоящий на доске, остаётся доступным; бейдж "на доске" лишь сообщает, что добавлять его повторно незачем. Признак on_board вычисляется для конкретного сотрудника, поэтому каталог всегда персонален.

| 3.4 | GET /board | Доска сотрудника
| 3.5 | PUT /board | Сохранение доски
3.1 Данные дашборда
Возвращает данные всех виджетов за выбранный период и канал. Вызов - защищённое чтение, он порождает событие аудита (5.3).
Компонент-исполнитель: managementApi, компонент Модуль аналитики и отчётности HTTP метод: GET URL: /api/control/api/analytics/v1/dashboard
Заголовки запроса:
Authorization: Bearer <session_token>
Заголовки ответа:
Cache-Control: no-store - у успешного ответа (5.2)
3.1.1 Параметры запроса
| Параметр | Тип | Обязательность | Описание
| started_from | string | Нет | Начало интервала по времени начала диалога, включительно. Дата и время с часовым поясом (RFC 3339); любое смещение приводится к UTC. Без параметра - текущий момент минус глубина хранения.
| started_to | string | Нет | Конец интервала, исключительно. Формат тот же. Без параметра - текущий момент.
| channel_id | string | Нет | Фильтр по каналу. Одно значение: список на экране одиночного выбора. Отсутствие параметра - это "Все каналы". Неизвестное значение, в том числе пустая строка, ошибкой не считается: сервер применяет его к отбору как есть.
Имена и семантика совпадают с соседним контрактом. Экран диалогов и экран дашборда несут одну и ту же панель фильтров: те же быстрые периоды "Сегодня", "Неделя", "Месяц" и тот же список каналов - Все каналы, Портал, Наш город, Электронный дневник, Мобильное приложение, Портал поставщиков. Быстрые кнопки - способ интерфейса задать пару started_from и started_to, отдельного параметра под них нет. Фильтра по навыку на дашборде нет, хотя на экране диалогов он есть.
Разбор времени. Сервер принимает дату и время с часовым поясом: 2026-07-13T00:00:00Z, 2026-07-13T03:00:00+03:00. Секунды можно опустить, дату и время можно разделить пробелом, буквы T и Z принимаются в любом регистре. Время без часового пояса и дата без времени отвергаются ответом 400 INVALID_ARGUMENT (3.1.7). Число читается как Unix-время в UTC: в секундах, а при значении больше 20 000 000 000 по модулю - в миллисекундах; дробная часть допустима. В ответе границы всегда приходят в UTC с суффиксом Z.
Интервал необязателен, и каждая граница подставляется отдельно. Без started_from интервал начинается за глубину хранения до текущего момента, без started_to заканчивается текущим моментом; без обоих данные считаются по всей доступной глубине хранения, которая ограничена сверху и потому предсказуема по стоимости. Подставленные сервером границы отсчитываются от момента обработки запроса и приходят с дробной частью секунды, например 2026-08-12T09:05:31.123456Z. Явный интервал по глубине хранения не обрезается.
Данные приходят по всем доступным виджетам каталога. Метод отдаёт данные по каждому виджету с available = true (2.7) в порядке каталога - сначала 2.7.1, затем 2.7.2 - независимо от того, что сотрудник поставил на доску; клиент сам выбирает, что рисовать. Параметра со списком виджетов в запросе нет. Недоступные виджеты в ответ не входят, а виджет, ставший доступным, появляется в ответе без изменения запроса. Множество виджетов, которое принимает сохранение доски (3.5), совпадает с множеством, по которому метод отдаёт данные: виджет, поставленный на доску, всегда есть в ответе, в том числе сразу после добавления в режиме правки.
3.1.2 Один ответ, а не запрос на каждый виджет
Запрос на каждый виджет означал бы на одно открытие страницы столько проверок доступа, походов в read-модель и событий аудита, сколько на ней виджетов; согласованность чисел между виджетами при этом не гарантировалась бы вовсе. Поэтому метод один. Цена решения - отказ одного агрегата способен погасить весь экран, и она снимается частичной деградацией (3.1.5).

3.1.4 Весь ответ - один согласованный срез
calculated_at относится к ответу целиком, а не к отдельному виджету. Все виджеты одного ответа посчитаны по одному снимку отчётной read-модели: иначе выборка сообщила бы 54 диалога, а распределение по доменам было бы построено уже по 55, и числа на экране перестали бы сходиться между собой. Поля момента расчёта у отдельного виджета в контракте нет намеренно.
3.1.5 Отказ части агрегатов
Виджет, агрегат которого посчитать не удалось, приходит со status = "error" и блоком error с code AGGREGATE_UNAVAILABLE и message "Агрегат не посчитан за выбранный период"; полезной нагрузки у него нет. Остальные виджеты приходят обычным образом, и ответ остаётся 200.
Так же приходит доступный виджет каталога, для которого у сервера нет правила расчёта: это отказ одного виджета, а не всего ответа. Непосчитанный агрегат проверяется только при непустой выборке: при пустой выборке виджет приходит пустым (3.1.6).
Решение выбрано против альтернативы "падать целиком": один непосчитанный агрегат не повод гасить страницу, на которой остальные читаются. Интерфейс показывает такой виджет как недоступный, а сотрудник видит, что именно не посчиталось, вместо пустого экрана.
sample, scope и calculated_at при этом остаются заполненными: они описывают срез, а не отдельный агрегат.

3.1.7 Ошибки
В ошибке data равен null, code называет вид ошибки, а message - фиксированный текст для сотрудника (4.2).
Неверный параметр (HTTP 400) - code INVALID_ARGUMENT, message "Ошибка валидации запроса". Так метод отвечает, когда значение параметра не удаётся разобрать: неверный формат, время без часового пояса, дата, которая выходит за поддерживаемый диапазон при переводе в UTC. В errors - поле, вид ошибки поля и причина:
{
"code": "INVALID_ARGUMENT",
"data": null,
"message": "Ошибка валидации запроса",
"errors": [
{ "field": "/started_from", "code": "INVALID", "message": "Input should have timezone info" }
]
}
Недопустимый период (HTTP 422) - code VALIDATION_ERROR, message "Ошибка валидации запроса". Так метод отвечает, когда оба параметра разобраны, но вместе не задают допустимый период: интервал перевёрнут или пуст либо база сравнения выходит за поддерживаемый диапазон дат:
{
"code": "VALIDATION_ERROR",
"data": null,
"message": "Ошибка валидации запроса",
"errors": [
{ "field": "/started_from", "code": "INVALID", "message": "started_from must be earlier than started_to" }
]
}
Сессия недействительна (HTTP 401) - code FAILED, message "Требуется аутентификация." без токена и "Недействительный токен доступа." с недействительным токеном. Отчётная read-модель недоступна (HTTP 503) - code REPORTING_STORE_UNAVAILABLE, message "Отчётная read-модель недоступна". Агрегаты за период ещё не построены (HTTP 503) - code AGGREGATES_NOT_READY, message "Агрегаты за выбранный период ещё не построены".
3.2 Пересчёт данных
Метод за действием "Обновить данные". Возвращает сведения о выборке и момент расчёта; сами агрегаты не отдаёт.
HTTP метод: POST
URL: /api/control/api/analytics/v1/dashboard/refresh
Тело запроса: те же started_from, started_to и channel_id, что у метода 3.1, с теми же форматами и значениями по умолчанию (3.1.1), чтобы пересчёт относился к тому же отбору, который сотрудник видит на экране. Каждое поле может быть null или отсутствовать.
{
"started_from": "2026-07-13T00:00:00Z",
"started_to": "2026-08-12T00:00:00Z",
"channel_id": null
}
Успешный ответ (HTTP 200):
{
"code": "SUCCESS",
"data": {
"sample": { "dialog_count": 54, "source": "chat_bd" },
"calculated_at": "2026-08-12T09:41:07Z"
},
"message": "Данные пересчитаны",
"errors": []
}
Состав ответа выведен из уведомления на экране: "Данные пересчитаны" и "Выборка: 54 диалогов за выбранный период". Больше интерфейс после нажатия ничего не показывает.
Метод не возвращает агрегаты. Получив ответ, клиент повторно вызывает 3.1. Из этого следует и ответ на вопрос об аудите: событие защищённого чтения публикует метод 3.1, а метод 3.2 своего события чтения не порождает, потому что данных не отдаёт. Иначе каждое нажатие кнопки удваивало бы записи в журнале.
Метод затрагивает общие агрегаты, поэтому защищён:
Ограничение частоты. Число вызовов на сотрудника в скользящем окне ограничено; при превышении метод отвечает 429 с message "Превышено ограничение частоты пересчёта" и заголовком Retry-After - числом секунд до освобождения окна, округлённым вверх и не меньше 1. В предел входит каждый вызов, прошедший проверку сессии и валидацию, в том числе получивший 409 или 503; вызовы с ошибкой валидации и отклонённые ответом 429 не учитываются. Числовые значения задаются конфигурацией; текущие - шесть вызовов за 60 секунд.
Параллельный вызов. Пересчёт по одному и тому же отбору не запускается дважды. Отбор сравнивается по присланным границам периода, приведённым к UTC, но без подстановки значений по умолчанию, по каналу и по области видимости; сотрудник в сравнении не участвует. Если пересчёт уже идёт, метод отвечает 409 с message "Пересчёт по этому отбору уже выполняется"; повторять вызов до его завершения не нужно.
Повтор после сетевого сбоя безопасен: он попадает в 409, в 429, если предел частоты исчерпан, или в обычный успех с новым calculated_at.
Что метод делает внутри, контрактом не зафиксировано - настоящий пересчёт агрегатов или обновление кэша выборки. Это открытый вопрос (7.10), и он важен: по C4-модели отчётную read-модель наполняет Worker проекций, а не API, и метод пересчёта в эту связь не укладывается.
Ошибки: 422 VALIDATION_ERROR "Ошибка валидации запроса" - поле тела не разобрано или период недопустим, по тем же причинам, что у метода 3.1 (3.1.7): параметры отбора здесь приходят в теле, поэтому и неверный формат поля получает 422, а не 400; 401 FAILED; 409 REFRESH_IN_PROGRESS "Пересчёт по этому отбору уже выполняется"; 429 TOO_MANY_REQUESTS "Превышено ограничение частоты пересчёта" с Retry-After; 503 REPORTING_STORE_UNAVAILABLE "Отчётная read-модель недоступна". Тело запроса обязательно, хотя каждое его поле может быть null: запрос без тела получает 422 VALIDATION_ERROR с элементом { "field": "/", "code": "REQUIRED", "message": "Field required" }.

Порядок элементов задаёт сервер и повторяет порядок каталога на экране. Клиент выводит их как есть и не сортирует.
Ошибки: 401 FAILED (4.2).
3.4 Доска сотрудника
Возвращает состав и порядок виджетов, которые сотрудник видит на дашборде.
HTTP метод: GET
URL: /api/control/api/analytics/v1/board
Успешный ответ (HTTP 200):
{
"code": "SUCCESS",
"data": {
"version": 4,
"is_default": false,
"widgets": [
"unique_users",
"dau",
"operator_handoff_rate",
"resolved_without_operator",
"bot_response_time_avg",
"operator_rating_distribution",
"session_duration_avg",
"platform_distribution",
"technical_failure_points",
"nlp_errors"
]
},
"message": "",
"errors": []
}
| Поле в data | Тип | Описание
| version | integer | Версия доски для optimistic locking. Передаётся обратно в метод 3.5. У доски по умолчанию - 0.
| is_default | boolean | true - сотрудник ничего не настраивал и получил состав по умолчанию. После первого сохранения - false, в том числе у пустой доски.
| widgets | array of string | Идентификаторы виджетов в порядке вывода. Порядок массива и есть порядок на экране.
Доска личная. Ключ хранения - сотрудник, а не роль и не команда. Чужую доску сотрудник не читает и не правит; параметра, которым можно было бы запросить чужую доску, в контракте нет.
Доску по умолчанию задаёт сервер. Сотрудник, который ничего не настраивал, получает её тем же методом с is_default = true, а не отдельным вызовом: интерфейсу нужен один запрос независимо от того, настраивал сотрудник доску или нет. Состав по умолчанию - двенадцать виджетов из 2.3 в порядке экрана дашборда: unique_users, dau, operator_handoff_rate, resolved_without_operator, bot_response_time_avg, user_rating_avg, domain_distribution, operator_rating_distribution, session_duration_avg, platform_distribution, technical_failure_points, nlp_errors. Недоступный виджет исключается и из доски по умолчанию, так же как из сохранённой.
Недоступный виджет в ответе не возвращается. Если виджет, стоящий в сохранённом составе, стал недоступен, сервер исключает его из widgets, и сотрудник его не видит. Прятать виджет на клиенте нельзя: клиент не знает о доступности, пока не прочитал каталог, а доска обязана быть отрисована и без каталога.
Из сохранённого состава такой виджет не вычищается. Он остаётся в БД модуля и вернётся в выдачу, когда снова станет доступен. Из этого следует правило для метода 3.5: сохранение полностью заменяет состав тем, что прислал клиент, а клиент прислать скрытый виджет не может, потому что не видел его. Поэтому первое же сохранение после того, как виджет был скрыт, удалит его насовсем. Поведение названо в открытых вопросах (7.11).
Ошибки: 401 FAILED (4.2).
3.5 Сохранение доски
Сохраняет состав и порядок виджетов. Вызов - защищённое изменение, он порождает событие аудита (5.4).
HTTP метод: PUT
URL: /api/control/api/analytics/v1/board
Тело запроса:
{
"version": 4,
"widgets": [
"unique_users",
"dau",
"operator_handoff_rate",
"resolved_without_operator",
"bot_response_time_avg",
"operator_rating_distribution",
"session_duration_avg",
"platform_distribution",
"technical_failure_points",
"nlp_errors"
]
}
| Поле | Тип | Обязательность | Описание
| version | integer | Да | Версия, полученная методом 3.4, целое число от 0. Первое сохранение с version = 0 создаёт доску с версией 1; каждое следующее увеличивает версию на 1, даже если состав не изменился.
| widgets | array of string | Да | Полный состав доски в порядке вывода, идентификаторы виджетов строками. Пустой массив допустим: доска без виджетов.
Полная замена, а не частичное изменение. Форму диктует экран: правки копятся на клиенте между "Настроить доску" и "Сохранить", промежуточные удаления и перестановки на сервер не уходят, а кнопка "Отменить" отбрасывает их целиком. Сервер получает итоговый состав одним телом и заменяет прежний. Метода добавления или удаления одного виджета в контракте нет - он не соответствовал бы ни одному действию на экране.
Успешный ответ (HTTP 200):
{
"code": "SUCCESS",
"data": {
"version": 5,
"is_default": false,
"widgets": ["unique_users", "dau", "operator_handoff_rate"]
},
"message": "",
"errors": []
}
Ответ повторяет состав метода 3.4 с новой версией, чтобы клиент мог сохранить ещё раз без промежуточного чтения.
Конфликт версий (HTTP 409):
{
"code": "BOARD_VERSION_CONFLICT",
"data": null,
"message": "Доска изменена в другой сессии",
"errors": []
}
Повтор запроса при сетевом сбое небезопасен молча, и это осознанно. Если первый вызов дошёл, версия уже сдвинулась, и повтор получит 409. Клиент обязан прочитать доску заново методом 3.4 и решить, что делать. Отвечать успехом на повтор нельзя: одинаковое тело с устаревшей версией неотличимо от чужой правки, которую нельзя затирать молча.
Недоступный или неизвестный виджет (HTTP 400):
{
"code": "WIDGET_NOT_AVAILABLE",
"data": null,
"message": "Виджет нельзя поставить на доску",
"errors": [
{
"field": "/widgets/2",
"code": "UNAVAILABLE",
"message": "Виджет skill_funnel недоступен: нужна разметка шагов навыка"
},
{ "field": "/widgets/3", "code": "NOT_FOUND", "message": "Виджет revenue отсутствует в каталоге" }
]
}
Элемент errors приходит на каждый такой виджет: field - позиция виджета в widgets, code - UNAVAILABLE, если виджет есть в каталоге, но недоступен, и NOT_FOUND, если его в каталоге нет; message - "Виджет <widget_id> недоступен: <unavailable_reason из каталога со строчной буквы>" или "Виджет <widget_id> отсутствует в каталоге".
Проверяет сервер, а не клиент. Каталог живёт своей жизнью, доска - своей: между чтением каталога и сохранением доски виджет мог стать недоступным или исчезнуть. Клиентская проверка здесь не считается.
Дубликаты в widgets отвергаются ошибкой валидации 422 с code VALIDATION_ERROR и message "Ошибка валидации запроса": один виджет не может стоять на доске дважды. Элемент errors приходит на каждый повтор - на вторую и следующие позиции одного виджета, например { "field": "/widgets/2", "code": "INVALID", "message": "Widget dau is already on the board" }.
Порядок проверок. При действительной сессии сначала проверяется формат тела (422 VALIDATION_ERROR), затем версия (409 BOARD_VERSION_CONFLICT), затем дубликаты (422 VALIDATION_ERROR), затем доступность виджетов (400 WIDGET_NOT_AVAILABLE). Запрос получает ошибку первой не пройденной проверки.
Ошибки: 422 VALIDATION_ERROR "Ошибка валидации запроса" - тело не прошло проверку, в том числе из-за дубликатов; 400 WIDGET_NOT_AVAILABLE "Виджет нельзя поставить на доску"; 401 FAILED; 409 BOARD_VERSION_CONFLICT "Доска изменена в другой сессии".
4. Общие структуры данных и коды ошибок
4.1 Формат ответа
Все методы возвращают JSON следующей структуры:
{
"code": "SUCCESS",
"data": { },
"message": "",
"errors": []
}
| Поле | Тип | Описание
| code | string | Код результата: SUCCESS при успехе, при ошибке - код её вида из таблицы 4.2.
| data | object / null | Полезная нагрузка. При ошибке - null.
| message | string | При успехе - пустая строка, у метода 3.2 - "Данные пересчитаны". При ошибке - текст для сотрудника из таблицы 4.2.
| errors | array of objects | Ошибки отдельных полей запроса. Пустой при успехе и у ошибок, которые не относятся к конкретному полю.
Элемент errors описывает ошибку одного поля:
| Поле | Тип | Описание
| field | string | Адрес поля запроса в виде JSON Pointer, без указания, пришло поле в строке запроса или в теле: /started_from, /widgets/2. Адрес / означает тело целиком: тело не передано (REQUIRED) или не является JSON-объектом (INVALID).
| code | string | Вид ошибки поля: REQUIRED - поле или тело не передано, INVALID - значение не прошло проверку. У 400 WIDGET_NOT_AVAILABLE метода 3.5 - UNAVAILABLE или NOT_FOUND (3.5).
| message | string | У ошибок валидации - технический текст на английском для разработчика, например Field required или Widget dau is already on the board; сотруднику выводится message ответа. У 400 WIDGET_NOT_AVAILABLE метода 3.5 адресован сотруднику (3.5).
Поле details модуль не заполняет, поэтому в элементах errors его нет.
Значения запроса разбираются нестрого. Целое число принимается и строкой ("4"), и числом без дробной части (4.0), а логическое значение читается как 1 или 0; время принимается и Unix-временем (3.1.1). Строковые поля числа не принимают, лишние поля тела игнорируются. Контракт описывает типы, в которых значения передаёт клиент; другие формы сервер принимает, но клиент на них не опирается.
4.2 Коды ответов HTTP и сообщения ошибок
| HTTP Status | code | message | Условие
| 200 | SUCCESS | пустая строка; у 3.2 - "Данные пересчитаны" | Операция выполнена, в том числе когда выборка пуста или часть виджетов пришла с ошибкой.
| 400 | INVALID_ARGUMENT | "Ошибка валидации запроса" | Значение параметра не удаётся разобрать: неверный формат, время без часового пояса, дата вне поддерживаемого диапазона при переводе в UTC (только 3.1).
| 400 | WIDGET_NOT_AVAILABLE | "Виджет нельзя поставить на доску" | В составе доски виджет, которого нет в каталоге или который недоступен (только 3.5).
| 401 | FAILED | "Требуется аутентификация." | session_token не передан: заголовка Authorization нет, схема в нём не Bearer или токен пуст. Схема сравнивается без учёта регистра.
| 401 | FAILED | "Недействительный токен доступа." | session_token недействителен.
| 409 | BOARD_VERSION_CONFLICT | "Доска изменена в другой сессии" | Версия доски устарела (только 3.5).
| 409 | REFRESH_IN_PROGRESS | "Пересчёт по этому отбору уже выполняется" | Пересчёт по тому же отбору ещё идёт (только 3.2).
| 422 | VALIDATION_ERROR | "Ошибка валидации запроса" | Тело не прошло проверку, в том числе отсутствует (3.2, 3.5); период недопустим: интервал перевёрнут или пуст, база сравнения вне поддерживаемого диапазона дат (3.1, 3.2); дубликаты в составе доски (3.5).
| 429 | TOO_MANY_REQUESTS | "Превышено ограничение частоты пересчёта" | Превышено ограничение частоты пересчёта (только 3.2). Ответ несёт Retry-After.
| 500 | FAILED | "Internal Server Error" | Внутренняя ошибка, в том числе сбой проверки доступа.
| 503 | REPORTING_STORE_UNAVAILABLE | "Отчётная read-модель недоступна" | Отчётная read-модель недоступна (3.1, 3.2).
| 503 | AGGREGATES_NOT_READY | "Агрегаты за выбранный период ещё не построены" | Агрегаты за выбранный период ещё не построены (3.1).
Клиент различает ошибки по code. message - текст для сотрудника, который клиент выводит как есть. Коды и тексты из таблицы - часть контракта и меняются только вместе с ним. Ошибки с одним статусом и разным смыслом - два 400, два 409, два 503 - различаются code. У 401 и 500 code один - FAILED: вид ошибки у них задаёт статус, а два 401 различаются только message.
401 ведёт сотрудника на повторную аутентификацию. Отдельного функционального разрешения на дашборд нет (5.1), поэтому 403 методы дашборда не отдают.
Два 503 метода 3.1 разведены намеренно и различаются code. Отказ отчётной read-модели гасит дашборд, но настройка доски продолжает работать; неготовые агрегаты - временное состояние, при котором сотруднику стоит предложить другой период.
Пустая выборка и неготовые агрегаты - разные случаи. Первое - 200 с нулём (3.1.6), второе - 503 AGGREGATES_NOT_READY с message "Агрегаты за выбранный период ещё не построены". Смешивать их нельзя: ноль это утверждение о данных, а неготовность - утверждение о системе.
5. Соображения безопасности
5.1 Проверка доступа и область видимости
Проверка выполняется в два шага, и оба обязательны.
Сессия. Access guard контейнера managementApi проверяет сессию и передаёт модулю авторизационный контекст: сотрудника, его область доступа и функциональные роли. Отдельного функционального разрешения на дашборд нет: при действительной сессии доступны все пять методов.
Область видимости данных. Поверх сессии модуль применяет к отбору выборки правило области доступа и функциональной роли. Отбор выполняет сервер; клиент не может ни расширить его параметром, ни узнать, что осталось за границей.
Область доступа бывает двух видов: global - доступ без ограничения командами, team_membership - доступ в пределах команд, в которых состоит сотрудник. Функциональные роли - client_service, assessor, skill_team, surface_owner, product_manager; на отбор выборки влияет только surface_owner.
| Область доступа | Функциональная роль | Отбор выборки | scope.kind | scope.notice
| global | любая | вся выборка | all | null
| team_membership | surface_owner, в том числе вместе с другими ролями | диалоги поверхностей команд сотрудника | surface | "Метрики рассчитаны по вашей поверхности."
| team_membership | любая другая или роли нет | диалоги по навыкам команд сотрудника | team_skills | "Метрики рассчитаны по навыкам вашей команды."
Команды сотрудника определяет сервер по его членству в командах центра управления, а не по параметру запроса. Отбор строится по всем командам, в которых состоит сотрудник; параметра, которым клиент мог бы выбрать команду или поверхность, в контракте нет.
Текст баннера приходит с сервера. Он собирается не на клиенте, потому что зависит от правила отбора, которое клиенту неизвестно. Поле scope.notice - часть ответа, а не строка в интерфейсе.
Разные числа у разных ролей - следствие правила, а не разных данных. На прототипе одна и та же страница показывает 54, 28 и 8 диалогов выборки. Это тот же отбор, суженный областью видимости.
Сбой проверки закрывает доступ. Без действительной сессии метод отвечает 401. Если авторизационный контекст сформировать не удалось из-за сбоя, метод отвечает 500 и данных не отдаёт. Отсутствие подтверждённого контекста не приравнивается к разрешению.
5.2 Характер данных и запрет кэширования
Персональных данных жителей дашборд не отдаёт. На экране нет ни одного сообщения, ни одного идентификатора диалога и ни одного признака жителя. Всё, что возвращает метод 3.1, - агрегаты по множеству диалогов.
Это не делает ответ безобидным. Выборка строится по диалогам жителей, а при узкой области видимости и малом периоде агрегат приближается к единичным данным: у владельца поверхности выборка равна восьми диалогам, и распределение оценок оператора при таком объёме описывает конкретных людей. Поэтому просмотр отнесён к защищённому чтению (5.3).
Ответ метода 3.1 не кэшируется. Успешный ответ отдаётся с Cache-Control: no-store, и клиент не имеет права хранить его или показывать повторно из кэша. Ответ с ошибкой данных не несёт, и этого заголовка у него нет.
Причина не только в приватности. Просмотр порождает событие аудита, а ответ, показанный из кэша, события не порождает: журнал получит тихие пропуски, которые нечем объяснить на аттестации. Отсюда инвариант, который обязаны соблюдать обе стороны: одно открытие страницы - одно событие аудита. Повторный показ ранее полученных данных без обращения к методу 3.1 запрещён.
5.3 Регистрация просмотра дашборда
Открытие дашборда - защищённое чтение. Модуль публикует событие аудита синхронным вызовом API сервиса аудита через компонент Audit API client в ходе обработки запроса 3.1. Формат события - контракт сервиса аудита; собственного формата у модуля нет.
Это чтение по критерию, а не чтение одного объекта. Сотрудник не открывает конкретный объект: он задаёт период, канал и получает агрегат по множеству диалогов. Модель записи аудита предусматривает для такого случая блок selection.
{
"event_id": "4d2b8e17-7c31-4a0e-9b62-15c0f4a7e908",
"schema_version": "1.0",
"occurred_at": "2026-08-12T09:41:07.312Z",
"action": "control.dashboard.viewed",
"subject": {
"type": "employee",
"employee_id": "e-10245",
"iam_id": "1000234567",
"session_id": "s-77e0a1b2",
"ip": "10.12.4.31"
},
"object": {
"type": "dashboard",
"id": "control-dashboard",
"name": "Дашборд центра управления"
},
"result": { "status": "success" },
"correlation": {
"correlation_id": "c-4f2a9e18",
"trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",

},

}
| Поле события | Что кладёт модуль аналитики
| event_id | Идентификатор события, детерминированный для одной логической операции: выводится из идентификатора операции чтения, который модуль назначает в начале обработки запроса. Новый идентификатор на каждой попытке публикации сломал бы идемпотентность.
| schema_version | Версия схемы события, "1.0".
| occurred_at | Момент чтения. RFC 3339, UTC, с миллисекундами.
| action | control.dashboard.viewed в нотации <система>.<объект>.<действие>, класс "защищённое чтение".
| subject | Сотрудник из авторизационного контекста. Субъект всегда известен: до модуля запрос доходит только после подтверждённой проверки доступа.
| object | type = "dashboard" - новое значение в перечне типов объектов контракта аудита, который прямо допускает рост. Объект один на всю систему, поэтому id постоянный.
| result | status = "success" при отданном ответе; status = "error" и код причины, когда данные отдать не удалось. Частичный отказ виджетов остаётся успехом: ответ отдан.
| correlation | correlation_id сквозной операции, trace_id в формате W3C Trace Context, request_id HTTP-запроса.
| selection.criteria | Снимок условия отбора: период, канал и область видимости роли. Без области видимости запись не отвечает на вопрос, какие именно диалоги были агрегированы.
| selection.matched_count | Число диалогов выборки - то самое, что интерфейс показывает подписью "Рассчитано по 54 диалогам выборки".
| source_service | Модуль не передаёт: значение выводится сервисом аудита из аутентифицированной identity вызывающего.
Метод пересчёта 3.2 собственного события чтения не порождает. Он не возвращает агрегаты, а только сведения о выборке; данные сотрудник получает следующим вызовом 3.1, который событие и публикует. Иначе каждое нажатие "Обновить данные" удваивало бы записи в журнале, а кнопку можно нажимать сколько угодно раз.
Публикация fail-open. Отказ или timeout сервиса аудита не отклоняет операцию сотрудника: дашборд отдаётся. Отсюда два обязательства модуля: 401 и 403 от сервиса аудита - это alert, а не строка в логе, и модуль ведёт метрику "событий отправлено против событий принято".
5.4 Регистрация изменения доски
Сохранение доски (3.5) - изменение, и оно тоже публикуется в аудит.
{
"event_id": "b9a71c40-2e5d-4f18-8a33-07d1c6b25e44",
"schema_version": "1.0",
"occurred_at": "2026-08-12T09:44:51.006Z",
"action": "control.dashboard_board.updated",
"subject": {
"type": "employee",
"employee_id": "e-10245",
"iam_id": "1000234567",
"session_id": "s-77e0a1b2",
"ip": "10.12.4.31"
},
"object": {
"type": "dashboard_board",
"id": "e-10245",
"name": "Доска дашборда сотрудника e-10245"
},
"result": { "status": "success" },
"correlation": {
"correlation_id": "c-51ba7702",
"trace_id": "1f8c0b3d9e2a47c6b5d0e1f2a3b4c5d6",
"request_id": "r-88ca1f04"
}
}
Объект события - доска конкретного сотрудника. Доска личная, поэтому object.id совпадает с employee_id субъекта. Совпадение не повод опускать object: запись обязана отвечать на вопрос "над чем совершено действие" самостоятельно, без вывода из субъекта.
selection в этом событии отсутствует: действие адресовано одному объекту, а не отбору по критерию.
Состав доски в событие не попадает. Модель записи аудита не хранит прежнее и новое значение изменяемых атрибутов, и это её собственный открытый вопрос. Расширять чужой контракт молча нельзя, поэтому запись отвечает на вопрос "кто и когда изменил свою доску", но не на вопрос "что именно изменилось". Если разбор потребует второго, это отдельное решение по контракту аудита, а не по этому контракту (7.12).

7. Открытые вопросы
Окончательные значения идентификаторов виджетов. На экранах виден только заголовок, а доска, каталог и данные обязаны ссылаться на одно и то же. Идентификаторы и формы виджетов в 2.3, 2.7.1 и 2.7.2 выведены из заголовков и приняты рабочими значениями; окончательные назначает владелец каталога. Если они изменятся после первых сохранений досок, идентификаторы в сохранённых досках нужно перенести вместе с изменением каталога.
Третья корзина процентных показателей. "Переключений на оператора" и "Решено без оператора" покрывают 50 диалогов из 54 у администратора и ровно всю выборку у двух других ролей. Контракт исходит из того, что остаток - сбойные диалоги, по третьему значению справочника типов из контракта диалогов. Требуется подтверждение; при другом ответе меняются знаменатели. На экране с новыми виджетами (которые по умолчанию не отображаются на доске) показатель "Технические отказы" равен 7,4%, то есть ровно тем же 4 диалогам из 54: остаток может оказаться диалогами с техническим отказом.
Знаменатель показателя "Ошибки NLP". Подзаголовок говорит о запросах, а не о диалогах, поэтому контракт закладывает долю от числа запросов жителей. Проверить это по прототипу нельзя: 6,4% одинаковы во всех трёх ролях при выборках 54, 28 и 8, что для доли по разным множествам невозможно.
База сравнения дельты против глубины хранения. Глубина агрегатов, которая сейчас установлена, - 30 дней, база сравнения - предыдущий период такой же длины. При выбранном периоде "Месяц" база лежит за границей хранения, но на всех экранах дельта показана. Нужно решить, какая в итоге будет глубина хранения агрегатов.
Нормализация долей к 100. Контракт не нормализует: сумма долей может отличаться от 100 на ошибку округления. На обоих распределениях прототипа сумма даёт ровно 100, и неясно, это свойство данных или требование.
Коды справочников. Домены, платформы и точки технического отказа на экранах представлены только подписями. Соответствие "подпись - код" не зафиксировано ни в одном из доступных документов. У доменов на экране навыков виден сегмент адреса - gkh, mesh, core, transport; является ли он кодом домена, не подтверждено.
Отнесение диалога к домену. Навык относится ровно к одному домену, но в одном диалоге могут отработать навыки разных доменов. Доли распределения по доменам дают ровно 100%, значит диалог учитывается один раз, но правило не определено. Варианты: по домену первого навыка; по домену навыка с наибольшим числом сообщений; в каждом домене, где отработал навык диалога, - тогда доли перестают давать 100%.
Перечень точек технического отказа и значение "Прочее". Перечень не закрыт. Отдельно нужно понять, "Прочее" на экране - это остаток свёртки или самостоятельное значение справочника.
Система Writer. Четыре виджета каталога помечены как требующие данных из системы Writer. В C4-модели и в глоссарии виджета такой системы нет; она названа только в подписях каталога.
Что делает метод пересчёта внутри. Настоящий пересчёт общих агрегатов или обновление кэша выборки. От ответа зависит и право вызова, и значения ограничения частоты. Отдельно: по C4-модели отчётную read-модель наполняет worker проекций, а не API.
Судьба скрытого виджета при следующем сохранении. Виджет, ставший недоступным, из выдачи доски исключается, но в хранилище остаётся. Клиент его не видел и не пришлёт, поэтому первое же сохранение удалит его окончательно. Нужно решить, приемлемо ли это или сохранение должно щадить скрытые виджеты.
Нужны ли в аудите значения изменённых атрибутов. Событие изменения доски отвечает "кто и когда", но не "что именно". Это ограничение модели записи аудита, а не этого контракта.
Хранилище за именем chat_bd. Поле источника заложено в ответ, но чем оно заполняется и как соотносится с отчётной read-моделью, не решено.
Как считаются DAU и MAU. DAU выводится при выбранном периоде "Месяц" со значением 3, и за какой именно день берётся дневная аудитория, не зафиксировано. MAU на экране с новыми виджетами равен 54 - столько же, сколько уникальных пользователей за месяц; как считается месячная аудитория при периодах "Сегодня" и "Неделя", не зафиксировано.
Подтверждение серверного хранения доски. Контракт написан исходя из серверного хранения, но по экранам оно неотличимо от браузерного.
Возврат к доске по умолчанию. Действия сброса на экранах нет, метода в контракте тоже. Если возврат нужен, это отдельный метод.
Гранулярность ряда при коротких периодах. Оси на экранах размечены по дням при выбранном периоде "Месяц". Ряд всегда идёт по суткам в UTC (3.1.3), поэтому при периоде "Сегодня" в нём одна-две точки. Нужен ли коротким периодам более мелкий шаг, из прототипа не следует.
Домен "Базовые навыки" на дашборде. Доменов на экране навыков четыре, в распределении на дашборде три, и "Базовых навыков" среди них нет. Либо в выборке не было их диалогов, и нулевая категория не выводится по правилу открытых справочников (2.6.1), либо домен исключается из распределения намеренно.
Определения новых показателей. "Вернувшиеся пользователи" (38%) - доля от различных жителей выборки (2.3.1), но ни одна пара чисел экрана это значение не даёт, и какой житель считается вернувшимся, за какой период возврата, не определено. "Процент низких оценок" - какая оценка считается низкой. "Доля оставивших оценку" считается от диалогов (2.3.1), хотя в прототипе число диалогов и жителей совпадает, 54, и выбор по экрану не проверяется. "Средняя оценка оператора" - чем отличается от показателя "Оценки пользователей", если на экранах оба равны 2,6.
Частота использования. Контракт закладывает категории 1-5 как число обращений жителя, последнюю - как пять обращений и больше, а столбцы - как число жителей (2.6); подсказки на экране нет, и это требует подтверждения. Сводное значение 2,7 при 54 диалогах соответствует 20 жителям, а "Уникальные пользователи" на тех же экранах равны 54, так что числа прототипа между собой не сходятся.
Дельта у новых показателей. У пяти из семи новых показателей формы metric (которых нет на доске по умолчанию) дельты на экране нет. Контракт считает это свойством показателя и отдаёт для них delta: null (2.5), но не установлено, свойство ли это показателя или данные прототипа.
