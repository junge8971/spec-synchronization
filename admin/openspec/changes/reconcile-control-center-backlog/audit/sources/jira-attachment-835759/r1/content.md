# План тестирования MOS-1145: временное отключение и повторное включение навыка

## Что проверяем

Проверяем временное отключение навыка без релиза, сохранение причины и пользовательского текста, повторное включение с восстановлением предыдущего статуса, историю действий, контроль версии, идемпотентность, конкурентные запросы и доступ.

Отключение и включение выполняются отдельными endpoint. Поле `action` клиент не передаёт, действие определяется выбранным endpoint.

## Тестовая версия

Функциональность доступна на тестовых контурах A, C и T.

```text
Тег: develop.18.prod
Pipeline: https://gitlab.mos-team.ru/tsam/back/tsam-assistant-management-service-back/-/pipelines/962343
```

Тесты, сборка, проверки безопасности и джобы `A:deploy:prod`, `C:deploy:prod` и `T:deploy:prod` завершились успешно.

## Подготовка

Swagger UI:

```text
A: https://nchat-a-tech.mos.ru/api/control/docs/
C: https://nchat-c-tech.mos.ru/api/control/docs/
T: https://nchat-t-tech.mos.ru/api/control/docs/
```

Для запросов нужны заголовки:

```http
X-Admin-Token: <admin_token>
X-Access-Token: <access_token>
Idempotency-Key: <uuid>
```

Для каждого независимого изменения используется новый `Idempotency-Key`. Повтор ключа нужен только в сценариях идемпотентности.

Для проверки нужны:

- пользователь с доступом к команде навыка;
- пользователь без доступа к команде навыка;
- навык в статусе `draft`;
- навык в одном из последующих статусов, например `review` или `prod`;
- UUIDv7 несуществующего навыка;
- доступ на чтение тестовой БД.

## Эндпоинты

| Операция | Запрос |
| --- | --- |
| Получить карточку навыка | `GET /api/control/api/skills/v1/skills/{skill_id}` |
| Получить список навыков | `GET /api/control/api/skills/v1/skills` |
| Изменить статус навыка | `POST /api/control/api/skills/v1/skills/{skill_id}/status` |
| Отключить навык | `POST /api/control/api/skills/v1/skills/{skill_id}/disable` |
| Повторно включить навык | `POST /api/control/api/skills/v1/skills/{skill_id}/enable` |

## Справочник причин отключения

Выполните запрос к БД:

```sql
SELECT code, display_name, sort_order, is_active
FROM disabling_reasons
ORDER BY sort_order;
```

Ожидаемый результат:

| `code` | `display_name` | `sort_order` | `is_active` |
| --- | --- | --- | --- |
| `incident` | Инцидент | 10 | `true` |
| `planned_maintenance` | Плановые работы | 20 | `true` |
| `team_obligation_violation` | Нарушение обязательств команды | 30 | `true` |

Проверьте, что значения `code` и `sort_order` не повторяются, а все начальные причины активны.

В справочнике статусов должна присутствовать запись:

| `code` | `display_name` | `sort_order` | `is_active` |
| --- | --- | --- | --- |
| `disabled` | Отключён | 90 | `true` |

## Отключение навыка

Получите карточку активного навыка и сохраните его текущие `status` и `version`.

```http
POST /api/control/api/skills/v1/skills/{skill_id}/disable
```

```json
{
  "reason": "incident",
  "fallback_text": "Навык временно недоступен. Попробуйте позже.",
  "expected_version": 1
}
```

Ожидаемый результат:

- HTTP `200`;
- сообщение `Навык отключён.`;
- в ответе возвращаются `skill_id`, статус `disabled` и созданное действие;
- действие содержит `action: disable`, переданные `reason` и `fallback_text`, строковый `actor_id` и `created_at`;
- карточка и список навыков возвращают статус `disabled`;
- версия навыка увеличилась на единицу;
- остальные данные навыка не изменились.

Проверьте отключение с каждой из трёх активных причин.

## История отключения

После успешного отключения выполните запрос:

```sql
SELECT id, action, reason, fallback_text, actor_id, created_at
FROM skill_disabling
WHERE skill_id = '<skill_id>'
ORDER BY created_at, id;
```

Проверьте последнюю запись:

- `action` равен `disable`;
- `reason` и `fallback_text` совпадают с запросом;
- `actor_id` содержит строковый идентификатор текущего пользователя;
- `created_at` соответствует времени выполнения запроса;
- для одного успешного запроса создана одна запись.

Проверьте связанную историю статусов:

```sql
SELECT old_status, new_status, changed_at, actor_sso_id, reason
FROM skill_status_history
WHERE skill_id = '<skill_id>'
ORDER BY changed_at, id;
```

В последней записи `old_status` должен быть равен статусу до отключения, `new_status` должен быть равен `disabled`, а `reason` должен совпадать с кодом причины.

## Повторное включение навыка

Используйте текущую версию отключённого навыка.

```http
POST /api/control/api/skills/v1/skills/{skill_id}/enable
```

```json
{
  "reason": "planned_maintenance",
  "expected_version": 2
}
```

Ожидаемый результат:

- HTTP `200`;
- сообщение `Навык включён.`;
- восстановлен статус, который был у навыка непосредственно перед отключением;
- версия увеличилась на единицу;
- ответ содержит действие с `action: enable`, переданной причиной и `fallback_text: null`;
- карточка и список навыков возвращают восстановленный статус.

В `skill_disabling` должна появиться одна новая запись `enable`. В `skill_status_history` должна появиться одна запись перехода `disabled` в восстановленный статус.

## Восстановление предыдущего статуса

Проверьте отключение и включение независимо для навыков в статусах:

```text
draft, checking, training, autotest, sandbox, review, whitelist, prod
```

В каждом сценарии после включения должен восстановиться исходный статус. Отключение не должно переводить навык в `draft` и не должно продвигать его по основной цепочке статусов.

Также проверьте два последовательных цикла:

1. Отключите навык в одном статусе и включите его.
2. Переведите навык в следующий разрешённый статус.
3. Повторно отключите и включите навык.

Во втором цикле должен восстановиться новый статус, который был непосредственно перед вторым отключением.

## Недопустимые операции

| Сценарий | Ожидаемый результат |
| --- | --- |
| Повторное отключение уже отключённого навыка с новым ключом | `422 VALIDATION_ERROR`, поле `/status` |
| Включение навыка, который не отключён | `422 VALIDATION_ERROR`, поле `/status` |
| Смена статуса через `/status`, пока навык отключён | `422 VALIDATION_ERROR` |
| Неизвестная или неактивная причина | `422 VALIDATION_ERROR`, поле `/reason` |

После ошибки статус, версия, `skill_disabling` и `skill_status_history` не изменяются.

## Контроль версии

После успешного изменения повторите запрос со старым `expected_version` и новым `Idempotency-Key`.

Ожидаемый результат:

- HTTP `409`;
- код `VERSION_CONFLICT`;
- в деталях указаны `id`, `expected_version` и `current_version`;
- статус и версия не изменились;
- новые записи истории не созданы.

Проверка версии выполняется до проверки причины. Запрос со старой версией и неизвестной причиной должен вернуть `VERSION_CONFLICT`.

## Идемпотентность

### Повтор одинакового запроса

Повторите успешный запрос отключения с тем же `Idempotency-Key` и тем же телом.

Ожидаемый результат:

- оба запроса возвращают HTTP `200` с одинаковым ответом;
- версия увеличилась один раз;
- в обеих таблицах истории создано по одной записи.

Отдельно повторите таким же способом успешный запрос включения.

### Повтор ключа с другим телом

Повторите использованный ключ, изменив `reason`, `fallback_text` или `expected_version`.

Ожидаемый результат:

- HTTP `409`;
- код `IDEMPOTENCY_KEY_REUSED`;
- статус, версия и история не изменились.

## Конкурентное отключение

Одновременно отправьте два запроса отключения с одной актуальной `expected_version`, но с разными `Idempotency-Key`.

Ожидаемый результат:

- один запрос возвращает HTTP `200`;
- второй возвращает `409 VERSION_CONFLICT`;
- версия увеличилась на единицу;
- статус изменился один раз;
- в `skill_disabling` и `skill_status_history` создано по одной записи.

## Валидация

| Условие | Ожидаемый результат |
| --- | --- |
| Нет `Idempotency-Key` или ключ не является UUID | HTTP `422` |
| Нет `reason`, значение пустое или длиннее 32 символов | HTTP `422` |
| Причины нет в справочнике или она неактивна | `422 VALIDATION_ERROR` |
| Нет `fallback_text` в запросе отключения | HTTP `422` |
| `fallback_text` пустой или состоит только из пробелов | HTTP `422` |
| Нет `expected_version`, значение равно `0` или отрицательное | HTTP `422` |
| `skill_id` не является UUIDv7 | HTTP `422` |
| Навык не существует | `404 NOT_FOUND` |

После каждого ошибочного запроса состояние навыка и история должны оставаться прежними.

## Доступ и авторизация

| Условие | Ожидаемый результат |
| --- | --- |
| Пользователь с глобальным доступом | Операция разрешена |
| Пользователь с доступом к команде навыка | Операция разрешена |
| Пользователь без доступа к команде навыка | `404 NOT_FOUND`, существование навыка скрыто |
| Нет одного из обязательных токенов | `401`, `Требуется аутентификация.` |
| Токен недействителен | `401`, `Недействительный токен доступа.` |

В успешном ответе и таблице `skill_disabling` поле `actor_id` должно содержать идентификатор пользователя из текущего контекста авторизации.

## Список и фильтрация

- `GET /api/control/api/skills/v1/skills?status=disabled` возвращает отключённые навыки;
- каждый найденный элемент содержит статус `disabled`;
- после включения навык исчезает из выборки `status=disabled`;
- фильтр работает вместе с поиском, сортировкой и пагинацией.

## Атомарность и события

После каждой успешной операции одновременно должны сохраниться новый статус, запись `skill_status_history`, запись `skill_disabling` и доменное событие.

Проверьте события:

```sql
SELECT event_type, payload, actor_sso_id, occurred_at
FROM domain_events
WHERE aggregate_type = 'Skill'
  AND aggregate_id = '<skill_id>'
  AND event_type IN ('SKILL_DISABLED', 'SKILL_ENABLED')
ORDER BY occurred_at, id;
```

Ожидаемый результат:

- отключение создаёт одно событие `SKILL_DISABLED`;
- включение создаёт одно событие `SKILL_ENABLED`;
- в событиях указаны идентификатор действия, причина и соответствующий предыдущий или восстановленный статус;
- ошибочные и повторно воспроизведённые запросы не создают дополнительные события.

## Ограничения текущей реализации

- Публичного endpoint для чтения справочника причин и истории отключений нет, эти данные проверяются в БД.
- Реальной интеграции с исполнением навыка в рамках задачи нет, `fallback_text` сохраняется как данные отключения.
- Идемпотентность хранится в памяти процесса и сбрасывается после перезапуска сервиса.
