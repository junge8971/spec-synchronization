1. Назначение
Раздел «API» - это реестр программных интерфейсов платформы ЦАМ. На основе описаний эндпоинтов формируется публичный справочник API на лендинге для внешних систем. Раздел позволяет администраторам платформы:
вести единый каталог всех эндпоинтов - внутренних (BE↔FE), исходящих (ЦАМ-панель → внешние системы) и входящих (МПММ / ЕСК / ЦХЭД → ЦАМ);
описывать для каждого эндпоинта метод, путь, версию, параметры запроса, тело запроса и коды ответов;
отмечать, какие эндпоинты публикуются на публичном лендинге, а какие остаются внутренними;
управлять статусами (Черновик / Активен / Устарел / Архив) и владельцами.
Прототип полностью соответствует модели данных из PDF: 9 таблиц с префиксом api_ (3 сущности, 6 справочников, 1 внешняя зависимость на СУДИР).
Особенность раздела: доступ только для администратора платформы - на это указывает явная метка «🔒 Доступ только для администратора платформы» под заголовком.
2. Общая структура
Раздел состоит из двух экранов:
Список эндпоинтов - стартовый экран с вкладками-группами, таблицей, поиском, фильтрами и кнопкой создания.
Карточка эндпоинта - экран редактирования с тремя вкладками: «Основное», «Запрос», «Ответы».
Переход между экранами - по клику на строку таблицы или по хлебным крошкам. При закрытии карточки без сохранения показывается модалка подтверждения.
3. Экран «Список эндпоинтов»
3.1. Вкладки-группы
Над таблицей - четыре вкладки, каждая со счётчиком:
| Вкладка | Значение group_code | Что показывает
| Все | all | Все эндпоинты
| Внутренние | internal | BE↔FE эндпоинты ЦАМ
| Исходящие | outgoing | Эндпоинты ЦАМ-панели → внешние системы
| Входящие | incoming | Внешние эндпоинты МПММ / ЕСК / ЦХЭД → ЦАМ
Счётчики обновляются автоматически при переключении.
3.2. Таблица
Отображает эндпоинты со следующими колонками:
| Колонка | Источник | Сортировка
| Метод | api_endpoint.method - цветной бейдж | ✓
| Эндпоинт (название + путь) | name, path | ✓
| Группа / Источник | group_code + source_code | ✓
| Версия | version | ✓
| Статус | status → api_statuses.display_name | ✓
| Стрелка «›» | - | -
Цвета бейджей метода:
GET - зелёный
POST - синий
PUT / PATCH - жёлтый
DELETE - красный
Статусы подсвечиваются:
Активен - зелёный
Устарел - жёлтый
Черновик - светлый
Архив - серый
Клик по заголовку сортирует по возрастанию, повторный клик - по убыванию, третий - снимает сортировку.
3.3. Поиск
Поле поиска (минимум 2 символа) ищет по:
названию эндпоинта,
служебному коду,
пути,
описанию.
3.4. Мультиселект-фильтры
| Фильтр | Источник | Значений
| Все методы | api_methods | 5 (GET, POST, PUT, PATCH, DELETE)
| Все источники | api_sources | 4 (ЦАМ панель, МПММ, ЕСК, ЦХЭД)
| Все статусы | api_statuses | 4 (Черновик, Активен, Устарел, Архив)
У каждого значения рядом с названием выводится код (monospace). Кнопка «Все ...» очищает фильтр.
3.5. Расширенный фильтр «⚙ Условия»
Конструктор произвольных условий:
Логика: И (все условия) / ИЛИ (любое условие).
Поля:
Название (текст)
Служебный код (текст)
Метод (enum - 5 методов)
Путь (текст)
Группа (enum - 3 группы)
Источник (enum - 4 источника)
Версия (текст)
Статус (enum - 4 статуса)
Категория на лендинге (enum - 6 категорий)
Операторы: для текста - содержит / не содержит / равно / не равно / начинается с / заканчивается на / пусто / не пусто; для enum - входит в / не входит в (с чипсами).
Применённые условия отображаются в панели-баре под фильтрами. На кнопке «⚙ Условия» - бейдж с числом активных условий.
3.6. Меню «⋮»
Сохранить текущий фильтр - сохраняет поиск, мультиселекты и расширенные условия под именем.
Скопировать ссылку на отбор - формирует URL с параметрами и копирует в буфер.
Сохранённые фильтры - список с возможностью применить или удалить.
3.7. Прочее
Кнопка «Сбросить» - видна при активных фильтрах.
Счётчик справа - сколько эндпоинтов найдено.
Кнопка «＋ Создать эндпоинт» - открывает пустую карточку.
Кнопка «⤓ Экспорт» - модалка выбора полей api_endpoint.
4. Экран «Карточка эндпоинта»
4.1. Шапка
Содержит:
название (name),
описание (description),
статус (цветная точка + подпись),
код (code, monospace),
владельца (owner).
Ниже - превью эндпоинта: цветной бейдж метода + путь. Обновляется в реальном времени при вводе метода и пути.
Кнопки действий:
| Кнопка | Действие
| ⤓ Экспорт | Модалка выбора разделов
| Сохранить | Валидирует уникальность name и code, обязательность path
| Приостановить | Переключает status между paused и active
| В архив | Устанавливает status = 'archived' с подтверждением
| Закрыть | Модалка «Выйти без сохранения?»
4.2. Вкладка «Основное»
Две колонки: метаданные (слева) и публикация на лендинге (справа).
Левая - «Основное» (поля api_endpoint):
| Поле | Тип | Валидация
| Название | input | обязательное, уникальное
| Служебный код | input (monospace) | обязательное, уникальное
| Метод | select из api_methods (5) | обязательное
| Версия | input | -
| Путь | input (monospace) | обязательное, поддерживает {param}
| Группа | select из api_groups (3) | обязательное
| Источник | select из api_sources | динамический - набор опций зависит от группы
| Статус | select из api_statuses (4) | -
| Команда-владелец | input (owner, строка) | -
| Ответственный | select (responsible_user_id) | -
| Описание | textarea | -
| Теги | input через запятую | -
Логика селекта «Источник»:
Группа internal - поле скрыто, источник не задаётся.
Группа outgoing - доступен только «ЦАМ панель».
Группа incoming - доступны «МПММ», «ЕСК», «ЦХЭД».
Правая - «Публикация на лендинге»:
| Поле | Модель
| Показывать на публичном лендинге API | publish_on_landing (switch)
| Требуется авторизация (API-key / Bearer) | auth_required (switch)
| Базовый URL | base_url
| Категория на лендинге | landing_category из api_landing_categories (6)
| Пример cURL | curl_example (textarea, monospace)
4.3. Вкладка «Запрос»
Две колонки: параметры запроса (слева) и тело запроса (справа).
«Параметры запроса» (api_endpoint_param):
Строка параметра содержит:
| Колонка | Поле модели
| Место (path / query / header / body) | location - FK на api_param_locations
| Имя | name
| Тип | data_type (integer, string, boolean, array, object)
| Описание | description
| Обязательность | required (чекбокс)
| Ручка ⠿ + крестик | sort_order + удаление
Drag-and-drop за ручку меняет порядок параметров - это влияет на порядок отображения на лендинге.
Кнопка «＋ Добавить параметр» - берёт место из соседнего селекта и добавляет новую строку.
«Тело запроса (JSON)» - большая textarea в моноширинном шрифте. Схема тела для POST / PUT / PATCH, отображается на лендинге.
4.4. Вкладка «Ответы»
Две колонки: список кодов (слева) и предпросмотр выбранного (справа).
«Коды ответов» (api_endpoint_response):
Строка ответа содержит:
| Колонка | Поле модели
| HTTP-код (200, 400 и т. п.) | http_code
| Описание | description
| Пример тела ответа (JSON) | example
| Крестик удаления | -
Клик по строке делает её активной (красная рамка) - её содержимое показывается в предпросмотре.
Предпросмотр - тёмный code-блок, где выводится:
строка «HTTP {код} - {описание}»,
пустая строка,
пример тела ответа.
Кнопка «＋ Добавить ответ» добавляет дефолтную пару 200 / 400.
5. Справочники
5.1. Статические (соответствуют api_* из PDF)
| Константа | Таблица | Значений
| DICT_API_METHODS | api_methods | 5 (GET, POST, PUT, PATCH, DELETE)
| DICT_API_GROUPS | api_groups | 3 (internal, outgoing, incoming)
| DICT_API_SOURCES | api_sources | 4 (cam_panel, mppm, esk, tshed)
| DICT_API_STATUSES | api_statuses | 4 (draft, active, deprecated, archived)
| DICT_API_LANDING_CATEGORIES | api_landing_categories | 6 (skills, dialogs, feedback, kb, experiments, external)
| DICT_API_PARAM_LOCATIONS | api_param_locations | 4 (path, query, header, body)
Все коды и подписи совпадают с PDF один-в-один.
5.2. Внешние данные
Ответственные (RESPONSIBLE_USERS) - из СУДИР, пара id → name.
5.3. Демо-данные
Массив API_DATA содержит 11 эндпоинтов:
3 внутренних (GET /api/v1/skills, GET /api/v1/dialogs/{id}, GET /api/v1/experiments),
3 исходящих (POST /api/v1/tickets, PATCH /api/v1/tickets/{id}/status, POST /api/v1/analytics/events),
5 входящих (2 от МПММ, 1 от ЕСК, 2 от ЦХЭД).
У каждого - полный набор параметров и кодов ответов.
6. Вспомогательные механизмы
6.1. Тост-уведомления
Появляются в правом нижнем углу на 2 секунды: «Изменения сохранены», «Параметр добавлен», «Ответ удалён», «Эндпоинт переведён в архив», «Фильтр сохранён».
6.2. Модальные окна
Экспорт списка/карточки - чекбоксы полей/разделов, кнопка «Выгрузить».
Подтверждение выхода - «Выйти без сохранения?».
Подтверждение архивации - стандартный confirm().
6.3. Drag-and-drop
Реализован для параметров запроса (api_endpoint_param.sort_order). Визуальная индикация: прозрачность у источника, красная рамка у цели. После перетаскивания порядок пересчитывается.
6.4. Валидация
При сохранении проверяется:
name не пусто и уникально,
code не пусто и уникально,
path не пусто.
При неудаче - тост «Проверьте обязательные поля», проблемное поле подсвечивается красным.
6.5. Клавиатурные сокращения
Esc - закрыть модалку.
Клик по бэкдропу - закрыть модалку.
7. Соответствие модели данных
| Таблица PDF | Реализация
| api_endpoint | Объект draft + API_DATA, все 20+ полей в UI
| api_endpoint_param | draft.params[] - массив параметров с location, name, data_type, description, required, sort_order
| api_endpoint_response | draft.responses[] - массив ответов с http_code, description, example, sort_order
| api_methods | DICT_API_METHODS через method
| api_groups | DICT_API_GROUPS через group_code
| api_sources | DICT_API_SOURCES через source_code
| api_statuses | DICT_API_STATUSES через status
| api_landing_categories | DICT_API_LANDING_CATEGORIES через landing_category
| api_param_locations | DICT_API_PARAM_LOCATIONS через location
Все коды и подписи совпадают с PDF. Поле team_id не используется - владелец хранится строкой в owner. source_code скрыт для группы internal, как указано в модели.
8. Ограничения и не реализовано
Согласно разделу «Таблицы, которые не создаются» из PDF, в прототипе отсутствуют:
api_endpoint_call_log - логи вызовов в интерфейсе не отображаются.
api_endpoint_check - проверки соединения нет.
api_endpoint_version - версия хранится полем api_endpoint.version.
api_landing_page - лендинг формируется по данным api_endpoint, отдельного хранилища нет.
api_endpoint_param_group - параметры хранятся плоским списком с порядком.
saved_filter, export_registry - хранение не подтверждено интерфейсом.
Также не реализовано:
Серверная валидация - всё на клиенте, данные в памяти браузера.
Soft delete (deleted_at) - не задействован.
Реальная загрузка ответственных - статический массив.
Журнал изменений - только updated_at в модели, в UI не выводится.
Автогенерация curl_example - заполняется вручную.
9. Типичный сценарий работы
Открыть раздел «API» в меню слева (блок «Платформа»).
Выбрать вкладку-группу (Все / Внутренние / Исходящие / Входящие).
Найти эндпоинт через поиск, мультиселекты или расширенные условия.
Кликнуть по строке - открыть карточку.
Вкладка «Основное»: проверить метод, путь, версию, группу, источник, статус, владельца, теги. При необходимости отметить publish_on_landing и выбрать категорию.
Проверить превью эндпоинта в шапке: цветной метод + путь.
Вкладка «Запрос»: добавить/отредактировать параметры (path, query, header, body), расставить порядок перетаскиванием. Заполнить тело запроса JSON, если применимо.
Вкладка «Ответы»: добавить коды ответов с описанием и примером, выбрать активный для предпросмотра.
Нажать «Сохранить».
При необходимости - «Приостановить» или «В архив».
Вернуться к списку по хлебным крошкам.

Префикс таблиц раздела: api_.
2. Основные таблицы
2.1. api_endpoint
Назначение: эндпоинты платформы. Ядро раздела, отображается в списке и карточке.
Где используется:
список эндпоинтов - строка: метод, название и путь, группа и источник, версия, статус;
список эндпоинтов - вкладки-группы "Все", "Внутренние", "Исходящие", "Входящие" со счётчиками;
список эндпоинтов - поиск по названию, пути и описанию от 2 символов;
список эндпоинтов - фильтры по методу, источнику, статусу;
список эндпоинтов - сортировка по колонкам;
карточка эндпоинта - предпросмотр вида "МЕТОД /путь", обновляемый при вводе;
карточка эндпоинта, вкладка "Основное" - все поля эндпоинта;
карточка эндпоинта, вкладка "Основное" - блок публикации на лендинге;
карточка эндпоинта - сохранение, приостановка, выключение;
карточка эндпоинта - проверка уникальности названия, кода и заполненности пути;
модалка экспорта - состав полей выгрузки.

2.2. api_endpoint_param
Назначение: параметры запроса эндпоинта. Порядок меняется перетаскиванием.
Где используется:
карточка эндпоинта, вкладка "Запрос" - таблица параметров: место, имя, тип, описание, обязательность;
карточка эндпоинта, вкладка "Запрос" - перетаскивание строк для смены порядка;
карточка эндпоинта, вкладка "Запрос" - селектор места нового параметра и кнопка добавления;
карточка эндпоинта, вкладка "Запрос" - удаление параметра;
карточка эндпоинта, вкладка "Запрос" - правило: обязательные параметры попадают в блок Required на лендинге.
| Поле | Тип | Обязательность | Ключ | Комментарий
| id | UUID | да | PK | Идентификатор параметра
| endpoint_id | UUID | да | FK api_endpoint.id | Эндпоинт
| location | varchar(16) | да | FK api_param_locations.code | Место параметра: path, query, header, body
| name | varchar(255) | да | - | Имя параметра
| data_type | varchar(32) | да | - | Тип: integer, string, boolean, array, object
| description | text | нет | - | Подсказка для разработчика
| required | boolean | да | - | Признак обязательности
| sort_order | integer | да | - | Порядок отображения
| created_at | datetime | да | - | Дата создания записи
| updated_at | datetime | да | - | Дата последнего изменения
Индексы: обычный по endpoint_id.
Примечание: параметры и тело запроса дополняют друг друга. Параметры это конструктор вызова, тело это его содержимое.
2.3. api_endpoint_response
Назначение: коды ответов эндпоинта с примерами тела.
Где используется:
карточка эндпоинта, вкладка "Ответы" - строка: код, описание, пример;
карточка эндпоинта, вкладка "Ответы" - предпросмотр примера тела ответа по клику на строку;
карточка эндпоинта, вкладка "Ответы" - добавление и удаление кода ответа.
| Поле | Тип | Обязательность | Ключ | Комментарий

| http_code | varchar(8) | да | - | HTTP-код ответа
| description | varchar(500) | да | - | Что означает код
| example | text | нет | - | Пример тела ответа в формате JSON
| sort_order | integer | да | - | Порядок отображения
| created_at | datetime | да | - | Дата создания записи
| updated_at | datetime | да | - | Дата последнего изменения
Индексы: обычный по endpoint_id. Ограничение: уникальный по (endpoint_id, http_code).
