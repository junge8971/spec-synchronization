## Подготовка

Тестирование проводится на контурах A и C:

```text
A: https://nchat-a-tech.mos.ru/api/control/docs/
C: https://nchat-c-tech.mos.ru/api/control/docs/
```

Для проверки нужны:

- пользователь с доступом к команде навыка;
- новый навык;
- навык, созданный до выкладки MOS-1119, если такой доступен;
- доступ на чтение тестовой БД.

Основные эндпоинты:

```http
POST /api/control/api/skills/v1/skills/{skill_id}/status
GET /api/control/api/skills/v1/skills/{skill_id}
```

## Справочники статусов и переходов

```sql
SELECT code, display_name, sort_order, is_active
FROM skill_statuses
ORDER BY sort_order;

SELECT from_status, to_status, is_active
FROM skill_status_transitions
ORDER BY from_status, to_status;
```

Статусы:

| `code` | `display_name` | `sort_order` |
| --- | --- | --- |
| `draft` | Черновик | 10 |
| `checking` | Проверка | 20 |
| `training` | Обучение модели | 30 |
| `autotest` | Автотесты | 40 |
| `sandbox` | Песочница | 50 |
| `review` | Ревью | 60 |
| `whitelist` | Белые списки | 70 |
| `prod` | Прод | 80 |

Переходы:

```text
draft -> checking
checking -> training
training -> autotest
autotest -> sandbox
sandbox -> review
review -> draft
review -> whitelist
whitelist -> review
whitelist -> prod
```

Проверить:

- все начальные записи активны;
- `code`, `sort_order` и пары переходов не дублируются;
- статусы в переходах существуют в `skill_statuses`;
- в обеих таблицах отсутствует поле `updated_at`.

## История нового навыка

Создать навык и проверить запись:

```sql
SELECT id, skill_id, old_status, new_status, changed_at, actor_sso_id, reason
FROM skill_status_history
WHERE skill_id = '<skill_id>'
ORDER BY changed_at, id;
```

Ожидаемый результат:

- навык создан в статусе `draft` с версией `1`;
- в истории одна запись;
- `old_status` равен `NULL`;
- `new_status` равен `draft`;
- `changed_at` совпадает со временем создания навыка;
- `actor_sso_id` содержит SSO ID пользователя;
- `reason` равен `NULL`.

Идемпотентный повтор создания не добавляет вторую запись.

## Смена статуса с причиной

```json
{
  "status": "checking",
  "expected_version": 1,
  "reason": "Навык готов к проверке"
}
```

Ожидаемый результат:

- HTTP `200`;
- статус изменился на `checking`, версия увеличилась до `2`;
- в истории появилась одна запись `draft -> checking`;
- сохранены SSO ID пользователя, время и переданная причина;
- предыдущая запись истории не изменилась.

## Смена статуса без причины

Выполнить следующие переходы отдельными запросами:

```json
{
  "status": "training",
  "expected_version": 2
}
```

```json
{
  "status": "autotest",
  "expected_version": 3,
  "reason": null
}
```

Оба запроса должны завершиться с HTTP `200`. Для каждой смены статуса создаётся одна запись истории с `reason = NULL`.

## Ошибочный переход

Для навыка в статусе `draft` запросить переход в `prod`.

Ожидаемый результат:

- HTTP `422`, код `VALIDATION_ERROR`;
- статус и версия не изменились;
- запись истории не создана.

Аналогично проверить запрос перехода в текущий статус.

## Конфликт версии

После успешной смены статуса отправить следующий запрос со старым `expected_version` и новым `Idempotency-Key`.

Ожидаемый результат:

- HTTP `409`, код `VERSION_CONFLICT`;
- статус, версия и история не изменились.

## Идемпотентность

Повторить успешную смену статуса с тем же `Idempotency-Key` и тем же телом.

Ожидаемый результат:

- повторный ответ совпадает с первым;
- версия увеличилась один раз;
- в истории создана одна запись.

Повторить ключ с другим `status` или `reason`.

Ожидаемый результат:

- HTTP `409`, код `IDEMPOTENCY_KEY_REUSED`;
- статус, версия и история не изменились.

## Конкурентное изменение

Одновременно отправить два допустимых запроса с одной `expected_version` и разными `Idempotency-Key`.

Ожидаемый результат:

- один запрос возвращает HTTP `200`;
- второй возвращает `409 VERSION_CONFLICT`;
- статус и версия изменились один раз;
- в истории создана одна запись.

## Навык, созданный до MOS-1119

Для существующего навыка выполнить один разрешённый переход.

Ожидаемый результат:

- исходный статус сохранился после миграции;
- начальная запись задним числом не создаётся;
- переход сохраняется с фактическими `old_status` и `new_status`;
- сохраняются автор, время и причина;
- карточка навыка возвращает новый статус и версию.

## Атомарность

После каждого ошибочного запроса проверить карточку навыка и таблицу истории.

Статус не должен меняться без записи истории. Запись истории не должна появляться без изменения статуса. Версия не должна увеличиваться при ошибке.

## Миграция

Проверить на A и C:

- сервис успешно запускается после применения миграций;
- созданы таблицы `skill_statuses`, `skill_status_transitions`, `skill_status_history`;
- справочники заполнены начальными данными;
- для `skill_status_history.skill_id` создан индекс;
- поля статусов связаны внешними ключами со `skill_statuses.code`;
- текущие статусы существующих навыков сохранены;
- Alembic содержит одну актуальную вершину миграций.
