## Architecture

Framework route config consumes the composed descriptor registry; canonical modules and seven non-root compatibility modules are real entrypoints. Root index separately re-exports the same redirect. `app/root.tsx:21–25` exports session bootstrap and ApplicationRoot; ApplicationRoot nests Outlet under SessionBoundary and ApplicationLayout. Layout derives allowed navigation, supplies filtered tabs through context, and mounts either permitted children/breadcrumbs or AccessDenied. UI permissions are not server authorization; this inspection does not audit transport/session implementation.

Shared tab tables feed `useSectionTab`, which reads `tab` from the URL. `handleSectionTabChange` ignores invalid/same values, clones other query values, deletes `tab` for the original default or sets a non-default, and calls Router search navigation without replace. Section history tests assert PUSH and no redundant same-tab entry. Filtered defaults preserve the original table default; domain-only users therefore select domains and receive the domains breadcrumb even when query `tab` is absent. Explicit known forbidden tabs deny instead of falling back.

Dynamic breadcrumbs share entity query hooks with their pages, not route loader data. Dialogue tests explicitly assert one fetch for page plus breadcrumb. Surface and skill names also come from detail queries; no broader cache correctness claim is made. Unknown route access is deliberately passed through rather than treated as permission denial, and root error boundary renders 404 (`app/application/ui/root-error-boundary.tsx:5–28`).

## Important boundaries and residual risks

1. **Specification reconciliation remains separate.** Jira's fallback clause does not prescribe the destination. Approved auth design gives canonical skills then denial/available links, not a second home redirect. Current shell spec also specifies exact tab destinations, collisions and history. Report these distinctions instead of inventing policy or declaring the Jira task closed.
2. **High confidence in static wiring, limited integration coverage.** Most tests assemble their own memory route objects rather than importing `app/routes.ts` and mounting the production bootstrap/root. Redirect assertions use stub destinations. Tests do not establish production typegen/bundle inclusion, host basename behavior, deep reload, real browser history or live auth.
3. **Placeholders remain meaningful.** Teams, operations and metrics are mounted but unfinished. Surface/dialogue cards and creation screens have real query/form composition, superseding the historical comment's broad placeholder claim; that is not an audit of complete business scenarios or API deployment.
4. **Coverage gaps are bounded observations, not all-repository absence claims.** Full-root no-skills home fallback, all legacy aliases combined with permission-filtered actual destinations, and surface `/new` versus dynamic-card ranking under basename are not demonstrated in the inspected tests. Parameterized redirect assertions are partly registry-driven, so incorrect table changes could change both expected and actual destinations; independently compared current table to primary/spec context here.
5. **Query/history boundary:** other values/repetitions and hash are retained by the redirect, forced tabs override collisions, and replace is explicit. Destination-specific normalization, trailing-slash/case edge cases and arbitrary query serialization were not exhaustively tested/audited. Tab-switch handler does not explicitly carry a hash; hash-preserving tab switching is not asserted as a requirement here.
6. **Server fallback is code, not deployment evidence.** Local serve script and its test cover selected examples; the currently deployed server/CDN/reverse proxy was not contacted. Paths containing dots are excluded by the local fallback guard; this was not generalized into a new card-ID policy.
7. Permission visibility, no-fetch assertions with doubles and approved matrix do not establish backend request authorization, object scopes, shared-session availability or production readiness. No auth rewrite or new auth model is proposed.
