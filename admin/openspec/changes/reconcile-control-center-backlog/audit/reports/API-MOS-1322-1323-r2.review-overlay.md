# Обязательный overlay API-MOS-1322-r2 / API-MOS-1323-r2

Основание: независимый `reviews/R-D092-OPTIONAL.md`, поправки C1–C3. Исходные отчёты и их hashes сохраняются. При использовании их summary/findings/recommendations этот overlay обязателен и заменяет противоречащие рекомендации; корректные структурные сравнения сохраняются.

1. Live r2 содержит формальный OR, local/merged — уже согласованную нормализацию AND двух raw-заголовков X-Access-Token и X-Admin-Token. Это известное документированное отличие, не новая неопределённость модели доступа и не основание отменять нормализацию. Фактическое backend enforcement и deployment compatibility остаются отдельно неподтверждёнными.
2. В API-MOS-1322-r2 исключается security из новых вопросов контрактного согласования и удаляется вопрос о повторном выборе OR/AND. В API-MOS-1323-r2 предложение отдельно согласовать синхронизацию OR/AND заменяется сохранением действующей нормализации и известных release gates. Нет auth-change, OR в local, новых permission enums или RBAC в бизнес-моках.
3. Гарантии, не выраженные проверенными JSON operation/schema objects, нельзя объявлять отсутствующими во всём контрактном наборе. `docs/api/contracts/crud-api.md` §§19.1/20.1 уже описывает partial PUT/replacement, IDs/order, soft-delete, nullable/reference правила, сумму долей, saved-status tag restriction и ошибки. Общий CSV-раздел и §§19.2/20.2 описывают весь отбор независимо от limit/offset и 422 EXPORT_LIMIT_EXCEEDED. Запрашивается backend evidence соблюдения этих правил и оставшихся действительно неописанных случаев, а не повторное принятие существующей семантики.

Нормативные основания C1/C2: `docs/api/contracts/README.md` («Правила объединения»), `access-session.md` («Источники и согласование»), archive integrate-mpmm-auth-permissions design §10, update-control-center-contracts-put design, update-control-center-api-contracts design §1/tasks1.2. Точные fingerprints и независимая проверка находятся в R-D092-OPTIONAL.

Body-only неизвестности REQ-отчётов остаются именно ограничениями Jira description. Supplementary правила не приписываются самому Jira. Документация не доказывает runtime. Planning/code/spec no-op для обоих backend members; frontend/mocks не принимаются за серверную поставку. Применение overlay принимает parent с сохранением исходного REVISE provenance.
