## 3. Декомпозиция и параллельный анализ — G2

- [ ] 3.1 Supervisor: материализовать отдельные work-items для каждого компактного сценария/источника по ролевой таблице design; при необходимости добавить нумерованные подпункты в этот checklist до запуска волны. Проверка: нет задания «разобрать весь раздел» одному исполнителю; у каждого задания есть inputs/revisions, owner, output, dependencies, reviewer, acceptance и stop conditions.
- [ ] 3.2 Requirement analysts: выполнить назначенные сценарные задания по Jira/Confluence и сформировать атомарные требования с locators. Проверка: отдельные принятые отчёты по каждому work-item; неоднозначности сохранены как вопросы, не выдуманные требования.
- [ ] 3.3 API analysts: параллельно разобрать операции назначенных сценариев и дельту live/local без изменения contracts. Проверка: method/path, DTO, ошибки и ограничения привязаны к evidence; unknown отделён от missing, согласованные локальные уточнения не отменены автоматически.
- [ ] 3.4 OpenSpec analysts: по отдельным changes/capabilities прочитать полные proposal/design/specs/tasks, основные specs и релевантные архивные решения. Проверка: coverage и внутренние противоречия имеют locators; в том числе отдельно проверен кандидат `mos-1249-feedback-api` без заранее заданного вывода.
- [ ] 3.5 Implementation analysts: по отдельным сценариям исследовать code paths и существующие tests, включая optional-модули и mocks, без записи и browser/E2E. Проверка: file/line/ref evidence различает UI, mock, transport, test coverage и неподтверждённый deployment.
- [ ] 3.6 Integration owner: собрать `coverage.json` из принятых отчётов; supervisor принимает G2. Проверка: каждое требование, Jira item, активный change и основная capability имеют результат сопоставления либо явный gap/blocker; отчёты не заменены одним общим резюме.

## 4. Сверка, зависимости и независимые решения — G3

- [ ] 4.1 Supervisor: выдать reconcilers отдельные задания на сценарии; принять findings с рекомендациями keep/update/new/split/merge/defer/question. Проверка: каждый вывод связывает точные sources, requirement и целевой артефакт; предположения маркированы.
- [ ] 4.2 Dependency analyst: собрать `dependencies.json` из findings, не открывая внешние задачи. Проверка: у blocker есть причина, затронутый сценарий/этап, prerequisite, owner либо unknown и условие снятия; циклы выделены.
- [ ] 4.3 Независимые reviewers: проверить каждое предлагаемое изменение по исходным evidence в узких review work-items. Проверка: автор не принимает свою работу единолично; сохранены review IDs, замечания и исходы accept/revise/escalate.
- [ ] 4.4 Supervisor: записать решения в `decisions.md`, выделить вопросы пользователю и принять G3 для непротиворечивых локальных пакетов. Проверка: спорный scope, снятие deferred ограничений и разрушительные операции не одобрены автоматически; внешние рекомендации остались локальными.

## 5. Запись и интеграция локального OpenSpec — G4

- [ ] 5.1 Supervisor: назначить по одному writer на каждый принятый change, выделить изолированные копии либо последовательную запись при невозможности изоляции. Проверка: ownership не пересекается, исходные hashes актуальны, пользовательские изменения не committed/stashed/reset автоматически.
- [ ] 5.2 Artifact writers: выполнить отдельные work-items обновления существующих changes с согласованными proposal/design/specs/tasks. Проверка: каждый diff связан с decision IDs, сохраняет ранее согласованные ограничения и проходит strict validation соответствующего change; feature checkboxes не закрыты по одному аудиту.
- [ ] 5.3 Artifact writers: создать недостающие связные продуктовые changes штатным scaffold и артефактами применимой схемы; если таких решений нет, зафиксировать no-op. Проверка: metadata/status корректны, deltas не дублируют существующие capabilities, tasks проверяемы, dependencies и sources указаны; код не реализован.
- [ ] 5.4 Fresh reviewers: проверить итог каждого writer-пакета; integration owner повторно проверяет входные версии и интегрирует только принятые актуальные diffs. Проверка: stale изменения остановлены, журнал содержит hashes/decision IDs/пути; отсутствуют записи в main specs/archive, код и внешние системы.
- [ ] 5.5 Integration owner: проверить совокупную согласованность updated/new changes, устранить подтверждённые межпакетные противоречия через их владельцев. Проверка: нет дублированного ownership capability, потерянных references и незафиксированных циклов; G4 имеет отдельный receipt.
