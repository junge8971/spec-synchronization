## Why

Backlog админки распределён между Jira, Confluence, опубликованным API, основными specs, активными и архивными changes; статус задачи и наличие мока сами по себе не подтверждают реализацию. Нужна воспроизводимая многоагентная сверка, которая обновит локальный OpenSpec, сохранит основания решений и явно покажет пробелы и блокировки.

## What Changes

- Ввести процесс сверки с ограниченным Jira scope: MOS-623, все напрямую связанные эпики, их задачи и подзадачи. Произвольные связи не расширяют scope; задачи соседних отделов не исследуются.
- Сопоставлять требования Confluence, текущую опубликованную API-документацию, весь локальный OpenSpec и read-only свидетельства из кода и тестов.
- Разделить сбор источников, анализ узких сценариев, принятие решений, независимую проверку и запись артефактов между сабагентами; supervisor управляет покрытием и интеграцией, но не выполняет аудит единолично.
- Сохранить версионированные источники, реестр заданий, матрицу покрытия, расхождения, решения, зависимости и журнал публикации внутри audit-пакета управляющего change.
- Вносить доказанные непротиворечивые обновления в локальные planning artifacts; новые продуктовые работы оформлять штатными OpenSpec changes. Не разрешать спорные продуктовые вопросы автоматически.
- Jira и Confluence оставить строго read-only: любое внешнее изменение требует отдельного явного апрува пользователя на конкретные действия. Текущий change таких действий не поручает.

## Capabilities

### New Capabilities

- `control-center-backlog-reconciliation`: воспроизводимый процесс многоагентной сверки backlog с ограничением доступа к источникам, доказательным покрытием, независимой приёмкой и безопасным обновлением OpenSpec.

### Modified Capabilities

Нет. Это контракт процесса сопровождения backlog, а не изменение поведения бизнес-разделов. Конкретные продуктовые deltas определяются только по результатам будущего аудита и оформляются отдельно.

## Impact

- Планируемая область записи при apply: `openspec/changes/reconcile-control-center-backlog/audit/`, новые и существующие активные OpenSpec changes. Основные specs читаются; необходимая коррекция оформляется delta spec, без автоматического sync/archive. Архив используется как история решений и не переписывается.
- Read-only источники: https://task.mos-team.ru/browse/MOS-623 ; https://wiki.mos-team.ru/spaces/KR/pages/238324523/ ; https://nchat-a-tech.mos.ru/api/control/docs ; локальные `docs/api/contracts/`, код и тесты.
- Код приложения, API-контракты в `docs/`, generated DTO, конфигурация инструментов и зависимости не изменяются. Новая runtime-инфраструктура не создаётся.
- Browser MCP используется только для чтения разрешённых источников; browser/E2E-тесты, Swagger Try it out и вызовы бизнес-операций стенда не входят.
- На стадии propose создаются только плановые артефакты. Аудит и изменение остального backlog начинаются лишь после отдельного запуска apply.
