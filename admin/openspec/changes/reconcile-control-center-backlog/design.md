## Context

См. мотивацию и полномочия в proposal.md. Это процессная задача, не разработка нового сервиса; design необходим из-за многопоточной работы, общего браузера и риска несогласованной записи backlog.

При подготовке плана обнаружены 20 активных changes, 40 основных specs и 41 архивный change (до создания этого change). Это стартовое наблюдение, не замороженный инвентарь будущего запуска. `docs/api/contracts/README.md` описывает локальный снимок 15.10.2026, 94 пути / 128 операций / 380 схем и отдельную согласованную нормализацию security; считать его актуальным live-контрактом без повторной сверки нельзя. В `mos-1249-feedback-api` design и tasks содержат различающиеся указания об экспортном дополнении и unavailable handlers: это кандидат на проверку, а не уже принятое исправление.

Код организован в `app/`, включая optional-модули, моки — отдельно. Тесты не находятся в едином `tests/`: есть colocated tests, `app/test`, тесты scripts. `package.json` содержит Vitest, отдельный E2E script и API typegen. Аудит должен учитывать разные места свидетельств, не выполнять typegen и не запускать E2E. Внешние сайты, доступность MCP и Astra в ходе propose не проверялись.

## Goals / Non-Goals

**Goals:** воспроизводимость выводов, полнота учёта даже при недоступных источниках, мелкая декомпозиция по сценариям и источникам, независимая приёмка и безопасное продолжение между сессиями.

**Non-Goals:** новая платформа оркестрации, автоматический Jira sync, обход всей wiki, исследование соседних отделов, бизнес-мутации стенда, реализация новых функций, исправление кода, регенерация контрактов или пересмотр согласованной auth-модели. Скрипты/конфигурация агентов в репозитории не добавляются: используются существующие средства делегирования.

## Decisions

### 1. Scope manifest before fanout

Supervisor сначала фиксирует Git HEAD, dirty state и начальные hashes затрагиваемых planning files. Сборщик читает MOS-623 и строит разрешённый граф: прямые связи с эпиками, membership задач этих эпиков, затем parent membership подзадач. Для каждого ребра сохраняется доказательство; произвольные issue links не обходятся. Дубли устраняются по Jira key, циклы не расширяют обход. Пагинация и скрытые/недоступные ветки отмечаются явно.

Confluence начинается с https://wiki.mos-team.ru/spaces/KR/pages/238324523/ и включает относящиеся к админке дочерние материалы, страницы и вложения из разрешённых задач. Неоднозначные границы уточняются до перехода. API начинается с https://nchat-a-tech.mos.ru/api/control/docs ; фактический URL спецификации извлекается из документации, не угадывается. Читается документация, не проверяется поведение бизнес-endpoints.

Локальный инвентарь включает все основные specs и активные changes, включая не сопоставленные с Jira; архив сначала индексируется, затем читаются связанные решения. Текущий управляющий change помечается как процессный и не считается бизнес-пробелом. Альтернатива «обходить любую ссылку» отвергнута: она нарушает границу отделов и не даёт конечного scope.

### 2. Single browser owner, parallel evidence analysis

Один browser collector имеет доступ к общей MCP-сессии и обслуживает очередь конкретных разрешённых URL. После двух infrastructure blockers пользователь явно согласовал, что роль collector выполняет родительская сессия через доступный ей MCP; Astra medium-сабагенты независимо анализируют и проверяют сохранённые материалы. Это изменение владельца браузера, а не переход к единоличному аудиту. Остальные агенты работают с сохранёнными материалами и запрашивают недостающее через supervisor. Разные вкладки не считаются изоляцией. Коллектор не меняет формы, статусы, комментарии и не запускает Try it out; при необходимости входа запрашивает действие пользователя, не извлекает cookies/tokens.

Сохраняются только нужные материалы, без секретов и лишних персональных данных. Для очищенного извлечения hash относится именно к извлечению; его нельзя выдавать за hash исходной страницы. Если полное сохранение невозможно, фиксируются excerpt, locator и ограничение воспроизводимости. Доступ через MCP не означает разрешение browser/E2E-тестов приложения. Альтернатива «все агенты управляют браузером» отвергнута из-за конкурирующей навигации и смешения источников.

### 3. Small bounded assignments, not one agent per section

Для дочерних заданий используется Astra с thinking medium. Перед запуском supervisor проверяет фактический доступный model ID и инструменты; недоступность фиксируется как infrastructure blocker, замена модели без согласования не выполняется. Supervisor остаётся на своей текущей модели. Рекомендуемый начальный лимит — 4 параллельных аналитика и 1 browser collector; лимит является операционным default, а не требованием создать фиксированное число агентов.

| Role / unit                                          | Input                                                | Output and acceptance                                     | Authority                                             |
| ---------------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------- |
| Browser collector / страница или компактная группа   | Разрешённые URL и конкретные вопросы                 | Снимок/извлечение, metadata, completeness                 | Чтение браузера; запись только своего evidence packet |
| Jira index analyst / один эпик                       | Снимки связей и membership                           | Реестр дочерних ключей, связи, статусы, ограничения       | Без браузера и изменения Jira                         |
| Requirement analyst / один пользовательский сценарий | Точные Jira/Confluence fragments                     | Атомарные требования и источники, без решения за продукт  | Собственный отчёт                                     |
| API analyst / операции одного сценария               | Live snapshot и локальные contracts                  | method/path, DTO, ошибки, missing operations, расхождения | Read-only contracts; собственный отчёт                |
| OpenSpec analyst / один change либо capability       | Полные артефакты, связанные specs/archive            | Сценарии, покрытия, внутренние противоречия, зависимости  | Read-only OpenSpec; собственный отчёт                 |
| Implementation analyst / один сценарий               | Requirement IDs, конкретные модули и tests           | file/line/ref evidence, mock vs real, gaps                | Read-only код и тесты; собственный отчёт              |
| Reconciler / один сценарий                           | Принятые отчёты трёх сторон                          | Finding и предложение действия, без записи backlog        | Собственный отчёт                                     |
| Reviewer / одно решение или компактный пакет         | Finding и исходные evidence, не только резюме автора | Принято / исправить / эскалация с основаниями             | Не редактирует проверяемое решение                    |
| Artifact writer / один change                        | Принятые решения и конкретные файлы                  | Согласованные proposal/design/specs/tasks, validation     | Только выделенный change в изолированной копии        |
| Integration owner                                    | Проверенные пакеты авторов                           | Совокупный diff, journal, проверки связей                 | Единственная запись в основной checkout               |

Supervisor выдаёт задания динамически после inventory. Каждый пакет содержит ID, цель, cwd/ref, source IDs и версии, scope и запреты, владельца выходного пути, зависимости, критерии приёмки, способ проверки и stop conditions. Контекст fresh; передавать весь чат каждому агенту не нужно. Собственное создание дочерних агентов запрещено: исполнитель возвращает запрос на дальнейшее разбиение supervisor.

Пример единицы «CSV экспорт»: отдельные задания на требования к отбору/колонкам, API выгрузки, OpenSpec coverage, код/тесты, затем сверка и review. Не делить механически каждый абзац: одна единица должна давать самостоятельно проверяемый результат. Задачи анализа хранятся в work-items; новые продуктовые поставки оформляются OpenSpec changes, не по одному change на каждый агентский отчёт.

### 4. Durable audit packet, no new tooling

Все постоянные результаты будущего apply хранятся под `openspec/changes/reconcile-control-center-backlog/audit/`. Это обычные Markdown и JSON, а не новая БД или автоматически исполняемый workflow. Ниже — план структуры; на стадии propose папка не создаётся.

```text
audit/
  README.md
  manifest.json
  inventory.json
  sources/<source-id>/<revision>/content.*
  sources/<source-id>/<revision>/metadata.json
  work-items/<work-id>.md
  findings/<finding-id>.md
  reviews/<review-id>.md
  coverage.json
  dependencies.json
  decisions.md
  publication-log.md
  summary.md
```

- `manifest`: run ID, root/ref/dirty state, scope, модель, лимиты, source cutoff и версии пакета.
- `inventory`: ключ/путь, тип объекта, причина включения, parent edge, source ID, состояние обработки и причина недоступности. Baseline и финальные множества сохраняются раздельно.
- `source metadata`: URL/path, external key/version, retrievedAt, content hash, формат raw/extracted/redacted, locator, ограничения доступа и полноты.
- `work-item`: входные IDs/revisions, роль/исполнитель/run ID, output ownership, dependsOn, критерии приёмки, reviewer, статус `queued/running/blocked/review/accepted/stale`, checkpoint и причина остановки.
- `finding`: requirement/scenario IDs, expected/observed, доказательства с локаторами, вывод, уверенность, затронутые файлы, рекомендация `keep/update/new/split/merge/defer/question`, reviewer decision.
- `coverage`: связи Jira → requirement → API → main/delta spec → code/test → finding → target change/task; отсутствующая связь представляется явно с причиной. Состояния покрытия, API, реализации и стенда разделены.
- `dependencies`: направление prerequisite → dependent, тип blocker, scope воздействия (планирование/реализация/интеграция/выпуск), основание, owner либо unknown, условие снятия. Циклы выносятся как findings.
- `decisions`: принятые и отклонённые варианты, основание, reviewer, требуемое продуктовое согласование и ссылка на него при наличии.
- `publication-log`: decision IDs, входные hashes, изменённые пути, пакет/diff, результаты validation; `summary` — итоги и остаточные ограничения.

Стабильные IDs назначает supervisor; каждый дочерний отчёт имеет уникальный путь. Общие реестры собирает один integration owner. Временные файлы и transcripts исполнения не являются единственным источником результата. Альтернатива «всё оставить в чате» отвергнута из-за потери контекста и невозможности проверить основания.

### 5. Evidence precedence and decision gates

Нет единого правила «Jira главнее Confluence» или «самый новый документ побеждает». Согласованное продуктовое решение определяет scope, API — опубликованный wire-контракт, код — фактическую локальную реализацию. Противоречие между ними является finding, а не лицензией переписать требования. Согласованные локальные уточнения API (включая security) нельзя отменять только потому, что live отличается. Изменения auth scope эскалируются, не выводятся автоматически из API.

Волны и gates:

1. **G0 — readiness:** scope, инструменты, модель, Git baseline и output ownership зафиксированы. Неизвестные доступы не скрыты.
2. **G1 — inventory/evidence:** все обнаруженные объекты имеют статус, pagination проверена либо помечена неполной; evidence пригодно для анализа.
3. **G2 — analysis:** для каждого сценария есть независимые requirement/API/OpenSpec/implementation reports либо явный blocker. Пробелы покрытия, orphan items и несогласованность артефактов видимы.
4. **G3 — decision review:** отдельный reviewer проверяет вывод по источникам; supervisor принимает непротиворечивые локальные изменения. Спорный продуктовый scope, разрушительное удаление/объединение и внешние изменения требуют решения пользователя. Общий повторный апрув на каждую доказанную локальную правку не нужен: право на локальный OpenSpec согласовано.
5. **G4 — publication:** writer меняет только назначенные planning artifacts; fresh reviewer проверяет итоговый diff и сохранение scope; integration owner проверяет combined conflicts и зависимости.
6. **G5 — delivery:** реестры сверены с baseline, каждый элемент имеет результат или честное ограничение; готов итог по добавленному/обновлённому/заблокированному/непроверенному.

Нельзя ставить feature task `[x]` по одному наличию кода, мока или закрытой Jira. При подозрении на уже выполненную задачу сохраняется evidence и рекомендация отдельной проверки. Tasks этого управляющего change отмечаются только по принятым результатам аудита. Недоступный источник блокирует соответствующую проверку, а не обязательно всю независимую работу.

### 6. Publication isolation and resume

Параллельные writers работают в раздельных worktrees/копиях и владеют непересекающимися changes. Если managed worktree требует чистого checkout, supervisor не делает автоматический commit/stash/reset пользовательских изменений: выбирает последовательную запись одним владельцем либо запрашивает решение. Аналитические задания при этом остаются параллельными. Общие файлы принадлежат integration owner; работающие writers не меняют их напрямую. При propose обнаружено, что новые OpenSpec-файлы игнорируются Git: обычные git status/diff и worktree не гарантируют их учёт и перенос. Поэтому baseline и review включают явный файловый manifest/hashes, а изолированный writer получает проверенную копию нужных planning artifacts. Интеграция таких файлов выполняется по адресному файловому diff с проверкой hashes; force-add и изменение ignore rules не подразумеваются.

Для нового продуктового change используется `openspec new change`, затем status/instructions в порядке зависимостей и применимые навыки propose/update. Вход каждого изменения — принятые finding/decision IDs. Изменение main spec представляется delta в change; автоматические sync/archive запрещены. Нельзя переименовывать/удалять существующие changes или снимать deferred scope без отдельного решения. Изменения кода, `docs/api/contracts`, generated файлов и workflow config не входят.

Перед интеграцией сравниваются baseline hashes локальных файлов и доступные версии внешних источников. Если версия недоступна, перед публикацией повторно читается затронутый материал либо фиксируется невозможность проверить свежесть; связанное изменение остаётся blocked. Новая редакция источника не перезаписывает старую: создаётся revision, связанные задания получают stale. Частичный сбой сохраняет checkpoint, output paths и состояние lane; повторы не создают дубли changes по уже опубликованным decision IDs. После прерывания сначала читаются manifest/work-items/publication-log, затем переиспользуются только актуальные accepted outputs.

### 7. Validation of the audit, not the application

Для самого audit-пакета проверяются полнота inventory, разрешённость каждого Jira key, существование локаторов/ссылок, единственность owners, замкнутость references, отсутствие секретов, циклы зависимостей, соответствие решения опубликованному diff и отсутствие изменений вне scope. Проверка не требует писать новый валидатор.

Для OpenSpec выполняются strict validation затронутых changes, общий validation/doctor с отделением baseline ошибок и format check. Контрольные случаи из delta spec проверяются по реальным evidence packets: разрешённый потомок, внешняя связь без перехода, недоступная страница, API+mock без deployment evidence, спорные источники, конкурирующая запись и resume. Если случай не встретился, reviewer выполняет документированный tabletop-разбор по контракту, не выдавая его за наблюдение внешней системы.

Read-only анализ существующих тестов включён; массовый запуск тестов приложения не является доказательством полноты аудита. Browser/E2E не запускаются. При отсутствии изменений runtime/API/build соответствующие build/typegen проверки не нужны; в отчёте явно указывается, что они не запускались и почему.

## Risks / Trade-offs

- [Большое число мелких заданий увеличивает расходы] → ограниченная параллельность, повторное использование evidence, разбиение по проверяемому результату, не по числу строк.
- [Сбор браузером становится узким местом] → сначала inventory и нужные снимки, затем параллельный анализ; дополнительные чтения обслуживаются очередью.
- [Источники меняются во время аудита] → версии, hashes, повторная проверка перед публикацией и stale propagation.
- [Совпадение мнений агентов создаёт ложную уверенность] → отдельный reviewer читает первоисточники; неопределённость не разрешается голосованием.
- [Неполнота доступа выглядит как отсутствие требования/API] → `unavailable/unknown` отдельно от подтверждённого `missing`.
- [Запись секретов или лишних данных] → минимальные извлечения и проверка перед сохранением/интеграцией; не сохранять session credentials.
- [Неподтверждённая инфраструктура] → preflight в apply; при сбое остановить lane и сообщить причину, не заменять многоагентную работу единоличным аудитом.

## Migration Plan

Deploy приложения отсутствует. После отдельного запуска apply: readiness → inventory/evidence → параллельные аналитики → сверка/review → изолированные авторы → интеграция/validation → итоговый отчёт. Принятые локальные обновления выпускаются небольшими пакетами с журналом. Rollback — адресный обратный diff только конкретного пакета после сверки текущего состояния, без reset/clean и без удаления evidence. Сам rollback не выполняется автоматически при любой ошибке.

## Open Questions

- Точный Astra model ID, доступность нужных child tools и браузерной сессии определяются preflight; это не разрешение выбрать другую модель или расширить полномочия.
- Число эпиков, сценариев, страниц и необходимых заданий определяется разрешённой инвентаризацией. До неё нельзя заявлять точную длительность и полноту.
