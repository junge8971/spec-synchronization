# Proposal

## Why

Полная реализация MOS-958 «Доработать мастер поверхности и подключить регистрацию» зависит от уточнения и расширения backend-контракта. Этот proposal сохраняет отложенные требования и условия возврата к ним, чтобы существующие CRUD-методы и поведение моков не считались подтверждением исходных критериев приёмки.

## What Changes

Зафиксированы ответы бэков, переданные пользователем 13.10.2026, и оставшиеся зависимости. После этого MVP реализован, а [обновление контрактов от 15.10.2026](../archive/2026-10-15-update-control-center-api-contracts/design.md) добавило optional configuration и модель ответственных по бизнес-ID. Этот proposal не отменяет действующий `surface-registration` и не объявляет подтверждёнными оставшиеся интеграционные gates. Это план последующей работы; детальные specs, design и tasks потребуют отдельного согласования.

### Конфликт домена при создании — ожидается доработка backend

- По ответу бэков от 13.10 проверка занятости при создании ещё требовала уточнения. Наличие реальной серверной проверки не подтверждается локальным mock.
- Актуальные материалы упоминают `DOMAIN_ALREADY_IN_USE`, но точные HTTP-статус, envelope и field pointer остаются неподтверждёнными. Для распознавания отказа нужны согласованные примеры backend и проверка отсутствия создания; локальная mock-конвенция не является доказательством wire-контракта.
- После появления контракта фронт должен показать ошибку у адреса, сохранить введённые данные и не раскрывать название, ID или другие сведения недоступной чужой конфигурации.
- До доработки нельзя считать выполненным критерий приёмки о показе конфликта домена. Результат поиска в реестре не подтверждает глобальную уникальность.

### Предварительная проверка домена — исключена из текущего объёма

- По ответу бэков отдельной ручки нет; предусмотрен подход с ошибкой при создании поверхности.
- Не планировать новую предварительную проверку как обязательную backend-доработку. Вернуться к ней только при отдельном согласовании такого сценария и API.
- Проверка через список поверхностей не заменяет отсутствующий метод; UI не должен обещать «домен свободен» на основании результатов поиска.

### Конфигурация и приветствие при создании — редактор и реальная интеграция

- Актуальный `CreateSurfaceRequest` поддерживает optional configuration; существующие API-клиент и локальный mock передают её атомарно. Отсутствие/null сохраняет серверные defaults. В существующем мастере редактора нет, поэтому он опускает configuration и не выполняет скрытый PUT.
- До проектирования редактора при регистрации нужны отдельное согласование UI, проверка фактической доступности обновлённого POST, server defaults и ошибок. Наличие DTO и mock не подтверждает развёртывание на контуре.
- Для возврата уточнить правила взаимодействия пользовательской конфигурации с `submit_for_check`, её подтверждение чтением и обработку частичного или неизвестного результата.
- После согласования введённое приветствие должно сохраняться вместе с остальными данными регистрации и подтверждаться серверным чтением. До этого нельзя объявлять введённое приветствие сохранённым или молча терять его при отправке формы.

### Модель ответственных — актуальная модель и открытые проверки

- Актуальный POST использует строковые бизнес-ID в `responsible.product` и `responsible.connection`; мастер выбирает пользователей через существующий API, а GET возвращает объекты с ID и nullable ФИО/email. Произвольные ФИО не преобразуются в ID.
- До real rollout остаётся проверить обработку старых назначений и недоступных либо удалённых пользователей на backend, а также согласовать wire-формат соответствующего отказа. Локальные фикстуры этого не подтверждают.
- Существующий выбор сотрудников не следует заменять свободным текстом или вымышленным справочником; иные изменения модели требуют отдельного согласования.
- Связь отдельного `owner` с `team_id` также остаётся открытым вопросом, если доработка затрагивает владельца; ответ бэков не устанавливает их эквивалентность.

### Неизвестный результат POST и отсутствие дублей — гарантия отложена

- Бэки подтвердили отсутствие поддержки `Idempotency-Key` и предложили пока работать без идемпотентности. Обязательная доработка этого механизма на текущем этапе не согласована.
- Блокировка повторного клика во время запроса предотвращает параллельную отправку из формы, но не гарантирует отсутствие дубля после потери ответа. Клиентский заголовок сам по себе такой гарантии не даёт.
- В MVP уже реализовано ограниченное временное поведение: при неопределённом результате не показывать успех и блокировать повтор создания в текущем мастере. Оно не восстанавливается после перезагрузки и не гарантирует отсутствие дубля между вкладками.
- Для возврата к полной гарантии нужен согласованный способ безопасного восстановления результата: серверная идемпотентность либо другой механизм. При выборе идемпотентности определить срок действия ключа, повтор с тем же телом и конфликт при изменённом теле.
- Критерий MOS-958 об отсутствии незаметного дубля остаётся незакрытым до появления серверной гарантии. Конфликт домена сам по себе не доказывает успешность предыдущего запроса.

## Capabilities

### New Capabilities

Нет. Базовая `surface-registration` уже существует.

### Modified Capabilities

- `surface-registration`: последующее уточнение пользовательской конфигурации, подтверждённых серверных отказов и безопасного восстановления результата после решения соответствующих зависимостей. Предварительная проверка доменов исключена из текущего объёма.

Существующие `surface-skill-selection`, `surface-overview-connection` и `surface-lifecycle-publication` сохраняют свои требования; этот proposal их не заменяет.

## Impact

- Контракт: `docs/api/contracts/surfaces.openapi.json` и соответствующая часть полного OpenAPI; в этом proposal не изменяются. Снимок и локальная реализация optional configuration и ответственных зафиксированы в `update-control-center-api-contracts`; фактическое развёртывание и wire-примеры отказов остаются отдельными gates.
- После согласования API работа затронет `app/features/surface-registration`, `app/widgets/surface-registration`, `app/entities/surface`, связанные component/unit-тесты и surface-моки. Моки должны следовать согласованному контракту, а не служить доказательством возможностей backend.
- Уже существующие методы чтения статуса и `channel_id`, POST с `submit_for_check` и выбор продовых навыков через `/skills?status=prod` не включаются в список отсутствующих API. Серверные значения не должны вычисляться клиентом.
- Для оставшихся пунктов уточнить недостающие решения и wire-контракты, привязать backend-задачи и подготовить остальные OpenSpec-артефакты. До этого change остаётся незавершённым планом; закрытие MOS-958 целиком не заявляется.
