# Proposal

## Why

Полная реализация MOS-958 «Доработать мастер поверхности и подключить регистрацию» зависит от уточнения и расширения backend-контракта. Этот proposal сохраняет отложенные требования и условия возврата к ним, чтобы существующие CRUD-методы и поведение моков не считались подтверждением исходных критериев приёмки.

## What Changes

Зафиксированы ответы бэков, переданные пользователем 13.10.2026, и следующие зависимости. Это план последующей работы, а не описание уже реализованного поведения. Сейчас создаётся только proposal; детальные specs, design и tasks потребуют отдельного согласования после уточнения API.

### Конфликт домена при создании — ожидается доработка backend

- Бэки сообщили, что проверка занятости при создании, вероятно, ещё не реализована, и планируют завести задачу. Номер задачи пока не передан; наличие проверки не подтверждено.
- Для возврата к реализации нужны серверная проверка уникальности при POST, согласованные HTTP-статус и тело ошибки с указанием конфликтующих адресов. Упомянутый в MOS-958 `DOMAIN_ALREADY_IN_USE` пока не описан в проверенном OpenAPI; не считать этот код согласованным контрактом.
- После появления контракта фронт должен показать ошибку у адреса, сохранить введённые данные и не раскрывать название, ID или другие сведения недоступной чужой конфигурации.
- До доработки нельзя считать выполненным критерий приёмки о показе конфликта домена. Результат поиска в реестре не подтверждает глобальную уникальность.

### Предварительная проверка домена — исключена из текущего объёма

- По ответу бэков отдельной ручки нет; предусмотрен подход с ошибкой при создании поверхности.
- Не планировать новую предварительную проверку как обязательную backend-доработку. Вернуться к ней только при отдельном согласовании такого сценария и API.
- Проверка через список поверхностей не заменяет отсутствующий метод; UI не должен обещать «домен свободен» на основании результатов поиска.

### Конфигурация и приветствие при создании — ожидается расширение POST

- Сейчас поверхность создаётся с серверной конфигурацией по умолчанию, затем конфигурация редактируется отдельно. В `CreateSurfaceRequest` нет приветствия; `PUT /configuration` принимает полную конфигурацию.
- Бэки предложили доработать POST для передачи объекта конфигурации. Состав этого объекта и сроки реализации пока не согласованы.
- Для возврата нужны обновлённая схема POST, обязательность полей и defaults, ошибки валидации и правила взаимодействия конфигурации с `submit_for_check`. Необходимо определить, сохраняется ли вся конфигурация до отправки на проверку и возможен ли частичный успех.
- После согласования введённое приветствие должно сохраняться вместе с остальными данными регистрации и подтверждаться серверным чтением. До этого нельзя объявлять введённое приветствие сохранённым или молча терять его при отправке формы.

### Модель ответственных — ожидается решение и контракт

- Текущий POST содержит строковые `responsible.product` и `responsible.connection`. Бэки указали, что здесь также нужна доработка, но целевая модель не определена.
- Для возврата нужно выбрать: свободный текст или ссылки на сотрудников. Во втором случае нужны источник поиска/выбора сотрудников, формат идентификаторов, request/response и ошибки для недоступного либо удалённого сотрудника.
- Выбор сотрудников пока не является принятым решением. Не придумывать справочник, идентификаторы или преобразование ФИО в ссылку.
- Связь отдельного `owner` с `team_id` также остаётся открытым вопросом, если доработка затрагивает владельца; ответ бэков не устанавливает их эквивалентность.

### Неизвестный результат POST и отсутствие дублей — гарантия отложена

- Бэки подтвердили отсутствие поддержки `Idempotency-Key` и предложили пока работать без идемпотентности. Обязательная доработка этого механизма на текущем этапе не согласована.
- Блокировка повторного клика во время запроса предотвращает параллельную отправку из формы, но не гарантирует отсутствие дубля после потери ответа. Клиентский заголовок сам по себе такой гарантии не даёт.
- Предлагаемое временное поведение фронта: при неопределённом результате не показывать успех и не предлагать безусловный повтор создания. Это предложение для будущей реализации, а не уже внесённое изменение.
- Для возврата к полной гарантии нужен согласованный способ безопасного восстановления результата: серверная идемпотентность либо другой механизм. При выборе идемпотентности определить срок действия ключа, повтор с тем же телом и конфликт при изменённом теле.
- Критерий MOS-958 об отсутствии незаметного дубля остаётся незакрытым до появления серверной гарантии. Конфликт домена сам по себе не доказывает успешность предыдущего запроса.

## Capabilities

### New Capabilities

- `surface-registration`: будущая спецификация регистрации с сохранением конфигурации, согласованной моделью ответственных, обработкой серверного конфликта домена и восстановлением результата создания. Конкретные требования будут оформлены после решения перечисленных зависимостей; предварительная проверка доменов исключена из текущего объёма.

### Modified Capabilities

Не определены на этом этапе. Существующие `surface-skill-selection`, `surface-overview-connection` и `surface-lifecycle-publication` сохраняют свои требования; этот proposal их не заменяет.

## Impact

- Контракт: `docs/api/contracts/surfaces.openapi.json` и соответствующая часть полного OpenAPI; сейчас не изменяются. Источник сведений — проверенный OpenAPI и ответы бэков в обсуждении MOS-958; сроки и номера backend-задач неизвестны.
- После согласования API работа затронет `app/features/surface-registration`, `app/widgets/surface-registration`, `app/entities/surface`, связанные component/unit-тесты и surface-моки. Моки должны следовать согласованному контракту, а не служить доказательством возможностей backend.
- Уже существующие методы чтения статуса и `channel_id`, POST с `submit_for_check` и выбор продовых навыков через `/skills?status=prod` не включаются в список отсутствующих API. Серверные значения не должны вычисляться клиентом.
- Условия возобновления по каждому пункту: получить решение и обновлённый контракт, привязать backend-задачу, уточнить критерии и затем подготовить остальные OpenSpec-артефакты. До этого change остаётся незавершённым планом; закрытие MOS-958 целиком не заявляется.
