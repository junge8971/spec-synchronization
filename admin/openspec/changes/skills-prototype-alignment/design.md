Источник интерфейса: `/home/user/Загрузки/Прототип. Центр управления.html`. Ориентиры внутри bundle: Rne/Q9 — оболочка, Ane — реестр, jne — домены, Sne — мастер, US/VS/HS — карточка и шкала. Это ссылки на исследованный артефакт, не имена для будущего кода. MOS-909 виден лишь частично: покрываются шкала и одиночные переходы из обсуждения и HTML, невидимое описание не достраивается.

## Goals / Non-Goals

**Goals:** один серверный источник состояния; визуальный эталон до вёрстки; последовательные формы без потери ввода; независимая поставка доступных работ при явных API-gates; проверяемая трассировка 20 пакетов работ к шести Jira-задачам.

**Non-Goals:** копирование bundle, редизайн всего приложения, замена установленных библиотек, собственный workflow engine, runtime-фикстуры, локальное обучение/семантический поиск, атомарность нескольких HTTP-запросов, долговременное хранение мастера, реализация профильных changes вместо их владельцев. Ролевой demo-контекст не служит источником team/contact и не переносится.

## Decisions

### 1. Визуальный эталон — часть каждой поставки

Зафиксировать следующую начальную матрицу; она извлечена из HTML, а не является результатом измерения в браузере:

| Элемент | Эталон и критерий |
| --- | --- |
| Общая плотность | body 13.5px, вторичные подписи 12px/10.5px, заголовок страницы text-2xl; текущий text-3xl и крупный intro не сохранять автоматически |
| Поверхности | Светло-серый background `oklch(97.8% .002 247)`, белые карточки, базовый radius 0.5rem, спокойные границы |
| Шапка | Надпись «Подключение», один h1, разделитель, справка и действие справа, вкладки без дублирующего заголовка |
| Фильтры | Поле поиска около 300px, высота 32px; статус около 190px, домен около 210px; общий счётчик справа; перенос на узком экране |
| Таблица навыков | Навык/назначение/ID/версия в одной ячейке; домен/команда; статус; готовность; диалоги справа; изменён/создан справа; переход в карточку |
| Домены | Пропорции колонок прототипа 24/30/20/14/7/5%; API под названием, зоны бейджами, число навыков ссылкой |
| Форма домена | Dialog около max-w-lg, вертикальные поля, кнопки снизу, текстовые ошибки у полей |
| Мастер | Четыре равных индикатора; активный выделен, будущие приглушены/пунктирные; анкета в две колонки, название на всю ширину; фразы отдельными карточками; навигация снизу |
| Lifecycle | Компактная строка этапов в карточке, перенос при недостатке места, доступные обозначения ошибок и состояния |

Допустимые отличия: дополнительный выбор команды/контакта, поддерживаемый фильтр команды, серверная пагинация, неизвестные значения вместо demo-метрик, недоступный статусный фильтр, отсутствие ролевых ограничений и массовой панели до MOS-1021. Пустой набор групп допускается текущей спецификацией фраз, несмотря на более строгий демомастер.

Точную гарнитуру и метрики проверять по CSS прототипа до выбора значения: наличие Geist в проекте не доказывает совпадение. Не менять preset и не переустанавливать shared/ui. Для изменений применять существующие semantic tokens и варианты; предметную компоновку держать у владельца. Глобальные изменения app.css проверять на оболочке, поверхностях и существующей карточке, а не только в новом реестре. Отвергнута альтернатива «стандартный shadcn сейчас, сходство потом»: она меняет высоты, переносы и композицию всех экранов.

Начальные контрольные ширины для последующей разрешённой визуальной приёмки: 1440, 1280 и 390 CSS px; это предложенные контрольные точки, не сведения о viewport из Jira-скриншотов. Сравнение выполняется с одинаковыми данными, viewport и масштабом; до разрешения браузера доступны анализ классов и component-проверки, но не подтверждение совпадения пикселей.

### 2. Сохранить существующий поток данных и FSD

- Страницы собирают widgets/features; route-модули остаются адаптерами существующего Framework SPA. URL-состояние — React Router/useSectionTab/существующие helpers, серверное состояние — установленный TanStack Query и apiRequest. Нет второй системы загрузки через ad hoc effects.
- Доменный CRUD получает владельца `entities/skill-domain` (не `entities/surface`), формы — `features/skill-domain-editing`, реестр — `widgets/skill-domains-registry`. Существующие domain options навыков сверять с новым владельцем через композицию верхнего слоя/общую техническую инвалидизацию, без импорта entity-слайса из соседнего entity.
- Мастер — `features/skill-registration`, собранный страницей создания. Draft принадлежит одной форме RHF, шаги — приватные компоненты, а не глобальное хранилище или набор самостоятельных маршрутов. Dirty-навигация использует useBlocker и штатное предупреждение закрытия документа; после успешного сохранения блокировка снимается.
- UI существующей `SkillTrainingPhrases` привязан к сохранённой карточке и публично экспортирует только этот компонент. Не импортировать её внутренности из новой feature. Повторно используемые чистые схемы/преобразования фраз и подключения поднимать к `entities/skill` через публичный API, если они действительно нужны двум потребителям. Редактируемую draft-часть можно переиспользовать на нижнем слое без переноса HTTP-оркестрации; не делать универсальный form framework.
- Именованные types/constants/handlers размещать у владельца; не менять generated schema вручную. Новые зависимости и FSD-исключения не нужны.

### 3. Контрактные gates — не разрешение выдумывать API

| Gate | Необходимое решение | Пока gate открыт | Пакеты |
| --- | --- | --- | --- |
| G1: расширенный реестр | Поля lifecycle/readiness/dialogs/warnings, семантика query и полный allowlist sort/filter; способ получения без N+1 по строкам | Поддерживаемые поля и серверная пагинация работают; новые ячейки unknown, новые фильтры недоступны | 5–8 |
| G2: домены | Принятые ограничения/нормализация name/api_url, уникальность, правила ошибок и конкурентного обновления | Реализуется опубликованный CRUD; не вводить demo maxLength=100, предварительную гарантию уникальности или неописанный preflight | 10–11 |
| G3: контакты | Предметный источник допустимых contact_user_id и его контракт чтения/выбора | Мастер доступен для ввода, финальная отправка недоступна с объяснением; никаких seed users/ручного случайного UUID | 13, 16 |
| G4: регистрация | Подтвердить POST → GET → PUT как неатомарную бизнес-операцию; поведение потерянного ответа, срок/семантику идемпотентности; отдельные операции неполного черновика/проверки | Оркестрация проверяется на test doubles, но её production-приёмка заблокирована; доступны только подтверждённые операции | 15–16 |
| G5: lifecycle | Серверные состояния, допустимые переходы, версии, команды, подтверждение результата/неизвестного исхода, обновления | Текст unavailable, никакого PATCH status, активной шкалы или вымышленных команд | 17–19 |
| G6: профильные данные | Контракты/реализации MOS-1018/1019/1020/1025/1026 для конфликтов, готовности, ревью, свежести/инцидентов | Честная недоступность соответствующего блока без синтетического успеха | 4, 8, 14–15, 18 |

План фиксирует обязательные результаты этих решений, но не их неизвестные wire-форматы. Получение согласованного контракта не входит в полномочия frontend-реализации: на gate надо остановиться, записать блокер и продолжить независимые задачи. Если решение меняет выбранную последовательность/поведение, сначала пересмотреть artifacts; не молча заменить их во время apply.

### 4. Реестр и формы доменов

Переиспользовать текущие фильтры и сброс page, limit/offset и AbortSignal. Имена query-параметров сохранять текущие (`query`, `domain_id`, `team_id`); не копировать q/domain из HTML. Подпись поиска до решения G1 — нейтральная «Поиск навыков» без обещания конкретных полей. Статусный фильтр визуально недоступен с объяснением до G1/G5, фильтр команды сохраняется.

Реестр доменов запрашивает страницы, а не все навыки для подсчёта. Ссылка skills_count ведёт на первую страницу `/skills?domain_id=<id>` без tab=domains и без случайного старого фильтра команды. Формы используют Domain detail, POST/PATCH; после успешной записи инвалидировать реестр доменов, его options и затронутые данные навыков. Ошибка refetch после подтверждённой записи не является поводом повторно отправлять мутацию.

Список skills получает компактные новые ячейки со смыслом «не предоставляется API». Для отсутствующих данных не включать сортировку. Отвергнута загрузка карточки на каждую строку и локальный расчёт total/metrics. Выделение строк и массовая панель принадлежат MOS-1021.

### 5. Мастер и восстановление частичной записи

Предлагаемый поток по имеющимся операциям (production-включение после G3/G4):

```text
Draft --> POST skill --confirmed ID--> GET detail/version --> PUT intents --> Detail
              |                            |                    |
              v                            v                    v
        Unknown outcome               Read error           Save error/conflict
        same logical key              retry GET            preserve ID + phrases
```

- POST возвращает EntityCreatedResponse с ID, не полную карточку; поэтому версию для PUT нельзя угадывать как 1.
- `zones` — массив рабочих зон. `connection.auth_required` — отдельное требование подключения. При отсутствии connection передавать разрешённое отсутствие; при заданном connection использовать явное значение auth_required, не брать его из zones. Базовый шаг endpoint не дублирует полный редактор параметров MOS-1022.
- После подтверждённого POST фиксировать созданный ID и не позволять повторному нажатию создать новый объект. При ошибке GET повторять GET; при ошибке PUT сохранять фразы и повторять PUT с правилами версии/ключа. Не откатывать создание удалением: такого согласованного метода нет.
- Изменённая анкета после создания не превращается во второй POST: уже созданные поля редактируются в существующей карточке. В мастере восстановления пользователь видит сохранённую анкету, несохранённые группы и ссылку на карточку. Уход предупреждает о потере несохранённых групп.
- При конфликте PUT не менять expected_version автоматически. Потребовать явное сопоставление с новой серверной версией; до него сохранять draft. Пока исход POST неизвестен, заморозить повтор с изменённым телом и не начинать новую логическую операцию до разрешения неопределённости.
- Полное восстановление локального draft/ключей после закрытия браузера не обещается. Предупреждение об уходе и серверная карточка дают путь продолжения после подтверждённого ID; долговременный draft потребует отдельного требования. Это не серверный неполный черновик из демо.

Альтернатива атомарного create с intents предпочтительна только если появится согласованный контракт; сейчас такого поля нет. Локальный «успех» или помещение intents в PATCH анкеты отвергнуты.

| MOS-1022 | Предметные схемы connection | Повторная реализация редактора параметров |

Delta `control-center-shell` изменяет то же требование, что MOS-1020. Новый полный текст сохраняет условное review-поведение MOS-1020 и разрешает мастер/домены. При sync/archive в любом порядке сверять итог: нельзя восстановить обязательные заглушки domains/new или удалить ревью. Другие уже реализованные профильными changes карточки также не возвращать к заглушке. Существующие artifacts здесь не редактируются.

В `control-center-api-integration` устраняется устаревший сценарий SkillResponse без intents: по актуальному контракту intents обязательны. Принцип «не синтезировать отсутствующее» сохраняется, включая неизвестные предупреждения.

### 7. Проверки и критерий завершения

Каждый пакет UI имеет functional check и визуальные критерии; component snapshots сами по себе не заменяют визуальную приёмку. Расширить существующие Vitest/RTL/MemoryRouter/fetch doubles; серверные проверки переиспользуют mocks. Проверять существенный сценарий и границу: длинные данные, null/0, два предупреждения, 101-й элемент справочника, ошибка/отмена, конфликт версии, потерянный ответ и частичная запись.

Перед завершением реализации: `yarn typecheck`, `yarn lint` без предупреждений, `yarn test`, `yarn format:check`; при API-типах — `yarn api:check`, при изменениях сборки — `yarn build`. E2E/browser-файлы не менять и не запускать без отдельного разрешения. При согласованном визуальном просмотре проверить матрицу экранов/состояний и контрольные ширины. Если разрешения нет, оставить соответствующую приёмку незавершённой, а не отмечать весь change готовым.

## Risks / Trade-offs

- [API беднее прототипа] → сохранить композицию с явным unknown и не принимать заблокированные задачи как завершённую интеграцию.
- [Общие токены меняют другие экраны] → минимальные правки с перечнем потребителей; проверка оболочки, поверхностей и карточки, не смена preset.
- [Контракт и демо расходятся по зонам/контакту/обязательности фраз] → контракт и существующие specs определяют сохранение; отличия включены в визуальную приёмку.
- [Неатомарная регистрация оставила объект без фраз] → сохранённый ID, раздельный результат, повтор только незавершённой операции; нет вымышленного rollback.
- [Неизвестный исход и потеря локального состояния] → предупреждение об уходе, стабильный ключ в рамках логической операции, gate восстановления; не обещать устойчивость draft после закрытия браузера.
- [Параллельные changes перезаписывают shell/spec или код] → объединение актуальных требований перед sync; пользовательские staged/untracked изменения не переписывать.
- [Нет разрешения браузера] → честно непроверенное визуальное совпадение при независимой функциональной приёмке.

## Migration Plan

1. Пакеты 1–2 фиксируют визуальную базу; 3–5, 7, 9–12 и доступные части 14–15 реализуются без lifecycle. G2 не блокирует опубликованный CRUD, но неподтверждённые правила отдельно отмечаются.
2. UI мастера собирается без фиктивных справочников; production-сохранение включается только после G3/G4. Протокол тестируется независимо через существующие test doubles.
3. Пакеты 6, 8 и 17–19 включаются после согласования нужных gates; профильные изменения подключаются по публичным API, а не переписываются.
4. Пакет 20 фиксирует матрицу приёмки и оставшиеся блокеры. Planning-ready не означает, что все 20 пакетов исполнимы прямо сейчас.
5. Откат UI не отменяет серверно созданные домены/навыки или выкат. Сохранять действующие detail URL и данные; запрещено компенсировать откат удалением ресурсов или возвратом runtime fixtures.
