## Purpose

Показывать подтверждённый сервером жизненный цикл навыка и безопасно выполнять одиночные переходы, не подменяя бизнес-процесс локальными статусами прототипа.

## ADDED Requirements

### Requirement: Contract-gated lifecycle

Жизненный цикл SHALL отображать состояния и допустимые команды только после согласования API чтения состояния, переходов, конкурентной версии, идемпотентности и восстановления неизвестного исхода. До этого UI SHALL показывать unavailable без вымышленного текущего этапа и активных команд. Наличие обычного PATCH анкеты MUST NOT считаться поддержкой lifecycle; неизвестный статус MUST NOT сопоставляться с «Черновик» или «Прод» по умолчанию.

#### Scenario: Current skill API

- **WHEN** карточка получена по текущему контракту без lifecycle
- **THEN** сведения анкеты доступны, жизненный цикл явно недоступен, запросы к придуманным endpoints и PATCH status не выполняются

#### Scenario: Unknown server state

- **WHEN** согласованный источник возвращает состояние, для которого нет поддерживаемого отображения
- **THEN** UI сообщает о неизвестном состоянии и не предлагает переход на основании угаданного этапа

### Requirement: Server-derived lifecycle timeline

После подключения согласованного API карточка SHALL показывать компактную шкалу с пользовательскими этапами прототипа: «Черновик», «Проверка», «Обучение модели», «Автотесты», «Песочница», «Ревью», «Белые списки», «Прод». Соответствие серверных состояний этапам SHALL быть явно согласовано, включая возврат с ревью, согласование и отключение. Текущий этап, подтверждённые завершённые этапы и ошибки SHALL различаться текстом/доступными обозначениями, а не только цветом. Integer version записи MUST NOT превращаться в номер релиза.

#### Scenario: Refresh during training

- **WHEN** пользователь повторно открывает карточку во время подтверждённого обучения
- **THEN** шкала восстанавливается из серверного состояния; успешные этапы, ETA и завершение не генерируются таймером frontend

#### Scenario: Rejected or disabled skill

- **WHEN** сервер сообщает возврат или отключение навыка
- **THEN** шкала и пояснение отражают согласованное бизнес-состояние без ложного успешного завершения всего процесса

### Requirement: Safe single-skill transitions

Действия отправки навыка и одиночного выката SHALL быть доступны по согласованным бизнес-данным состояния. Значимый переход SHALL явно показывать навык и целевой этап/контур перед подтверждением. Во время команды SHALL предотвращаться повторная отправка. Успех SHALL обновлять карточку и реестр по серверу; ошибка SHALL сохранять контекст и объяснять причину. Решения ревью, массовый выкат и глобальное отключение SHALL использовать свои профильные возможности, без дублирующих команд в этом сценарии.

#### Scenario: Concurrent state change

- **WHEN** состояние навыка изменилось после открытия подтверждения и сервер отклонил переход
- **THEN** UI показывает конфликт, перечитывает доступное состояние и не повторяет команду автоматически с новой версией

#### Scenario: Unknown transition result

- **WHEN** запрос выката завершился timeout без подтверждения результата
- **THEN** UI показывает неизвестный исход, восстанавливает результат только по согласованному протоколу и не объявляет ни успех, ни гарантированную отмену

#### Scenario: Confirmed rollout

- **WHEN** сервер подтвердил одиночный переход в целевой контур
- **THEN** карточка и реестр отображают подтверждённое состояние; повторное нажатие во время первоначального запроса не создало вторую команду
