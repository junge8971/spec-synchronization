# Design

## Context

Мотивация и границы описаны в [proposal.md](proposal.md). Изменение пересекает форму, widget-композицию и API-мутацию, поэтому требует дизайна последовательности записи и восстановления.

В `use-surface-registration.ts` React Hook Form хранит поля, отдельный редактор `surface-skill-selection` хранит параметры, widget синхронизирует выбранные ID. Проверка доменов использует debounce и поиск всех страниц реестра. Приветствие входит в schema/defaults, но отсутствует в `toCreateSurfaceRequest`. Успех текущей мутации сбрасывает форму и запускает переход в реестр. Мутация хранит ключ идемпотентности, которого нет в контракте POST.

`apiRequest` уже поддерживает строгий `successStatus` и структурированный `ApiError`. `refreshSurfaceDetails` отменяет предыдущие чтения и выполняет fresh fetch через TanStack Query. В регистрации навыка есть пример синхронной блокировки и отдельного состояния неизвестной записи, но импортировать его из соседнего feature или переносить его многосоставную запись/хранилище в этот мастер не требуется.

## Goals / Non-Goals

**Goals:** одна управляемая попытка создания, отдельная ошибка чтения после записи, достоверная сводка, повторное использование существующих библиотек и предметных функций.

**Non-Goals:** изменение wire-контракта, добавление endpoint проверки доменов, конфигуратор, новая модель сотрудников, lifecycle-переходы после создания, автосохранение или межвкладочная координация. Существующий HTTP-транспорт и проверки принадлежности асинхронного результата не обходятся и не расширяются в рамках этой задачи.

## Decisions

### 1. Удалить неподдержанный путь проверки целиком

В регистрации удалить domain query, debounce, статусы загрузки/ошибки проверки и зависимость `isStepReady`/`goNext` от поиска. Сохранить `parseDomains` и локальную проверку непустого результата без новых правил допустимости адресов. В UI заменить результат поиска на нейтральное пояснение «Занятость доменов не проверена».

Удалить генератор channel_id и связанные экспорты/тесты, только после проверки всех потребителей. Аналогично убрать ставшие неиспользуемыми domain helpers и API-методы; не трогать обычный реестр. Не оставлять скрытый поиск как fallback: его полнота и область видимости не гарантируют уникальность.

### 2. Приветствие становится информационным блоком

Убрать greeting из редактируемого draft, defaults, schema и списка полей шага; заменить textarea пояснением о настройках сервера. На итоговом шаге показать ту же границу вместо успешной галочки. Не показывать прежний локальный default как будущий серверный текст и не обещать существование готового редактора в карточке.

Альтернатива с дополнительным GET/PUT полной конфигурации отклонена: меняет последовательность регистрации, требует обработки частичной записи и выходит за согласованный MVP. Текстовых ответственных и связь owner с выбранной командой оставить по текущему поведению до отдельного согласования.

### 3. Одна попытка охватывает подготовку, POST и подтверждение

Контроллер регистрации в feature хранит фазу, отправленный snapshot и полученный ID; entity отвечает за отдельные API-операции. TanStack Query остаётся владельцем сетевого состояния. Синхронный ref-lock устанавливается до первого await, включая валидацию/подготовку, и предотвращает гонку двух событий до React rerender. После локального отказа валидации или подготовки lock снимается; новая попытка заново проверяет навыки.

| Фаза                 | Изменение данных | Допустимое действие                                      |
| -------------------- | ---------------- | -------------------------------------------------------- |
| editing / rejected   | Да               | Проверить и отправить                                    |
| preparing / creating | Нет              | Ожидать; уход с предупреждением                          |
| unknown              | Нет              | Просмотреть snapshot, перейти в реестр с предупреждением |
| reading / read-error | Нет              | Ожидать / повторить только чтение                        |
| confirmed            | Нет              | Открыть карточку или реестр                              |

Заблокировать не только кнопку, но и весь отправляемый набор: форму, переключатель submit_for_check, редактор навыков. При потере ответа нельзя снять блокировку через «Назад», переключатель или изменение request body. Snapshot относится к состоянию после успешной подготовки и остаётся видимым после отправки.

Снять `idempotent: true`, генерацию ключа и передачу `Idempotency-Key` только у создания поверхности; сохранить `retry: false`. Другие идемпотентные операции не менять. `createSurface` использует `successStatus: 201` и схему UUID. Автоматических повторов POST ни в мутации, ни в контроллере нет.

### 4. Ошибки классифицируются по этапу и достоверности

Ошибка до вызова создания возвращает мастер в редактирование: серверную запись ещё не пытались выполнить. После начала создания только контрактный 422 с корректной `HTTPValidationError` считается подтверждённым отказом. Использовать существующую схему validation error и сведения `ApiError`; не определять семантику по тексту message. Ошибки полей сопоставлять только известным полям формы, остальные показывать общей доступной ошибкой.

Все прочие непредусмотренные ответы после начала вызова, включая 0/network, 5xx, abort, некорректный 2xx и неизвестные 4xx, консервативно переводятся в unknown. Это может ограничить повтор при фактическом отказе сервера, но не объявляет произвольный HTTP-код гарантией отсутствия записи. Расширение списка подтверждённых отказов требует контрактного основания и теста.

Не распознавать выдуманный DOMAIN_ALREADY_IN_USE и не создавать field mapping для него до follow-up. Сообщение unknown объясняет риск дубля и даёт переход к реестру; поиск там не считается автоматическим восстановлением результата.

### 5. Полученный ID нельзя потерять из-за GET или обновления кэша

Разделить POST и последующие side effects. Текущий await invalidateQueries в `useCreateSurfaceMutation.onSuccess` не должен скрывать подтверждённый ID при ошибке обновления: сначала сохранить ID в контроллере, затем читать результат и обновлять кэш. Ошибка invalidation не превращается в ошибку создания и не разблокирует POST.

Для подтверждения переиспользовать `refreshSurfaceDetails` через публичный API entity с отменой старого запроса и staleTime=0, либо эквивалентный существующий механизм свежего чтения. Проверить совпадение response.id с ожидаемым до помещения чужой карточки в результат/кэш; при необходимости добавить проверку в `getSurfaceDetails`, покрыв остальные вызовы. Явно отключить автоматические повторы подтверждающего GET для управляемой кнопки «Повторить загрузку»; изменение общего helper не должно неявно менять поведение других потребителей.

Мастер остаётся на месте и показывает этапы. При read-error сохраняет ID и snapshot, кнопка повторяет исключительно GET. При confirmed показывает фактический статус, channel_id и ссылки на карточку/реестр; автоматического перехода нет. Для пары requested=false/status=draft сообщение «Черновик сохранён», requested=true/status=review — «Отправлено на проверку». Для прочих статусов — нейтральное «Поверхность создана» и пояснение о расхождении без скрытого PUT/POST для исправления статуса. null channel_id не считается ошибкой.

Выбор явного результата вместо прежнего немедленного перехода позволяет показать подтверждение и расхождение статусов без добавления уведомлений в другие страницы. Только confirmed снимает предупреждение о незавершённой регистрации; read-error сохраняет предупреждение о незавершённом подтверждении, не утверждая, что POST не сохранился.

### 6. Сводка использует существующий draft редактора

Widget уже владеет обоими feature-контроллерами. Он формирует данные сводки из `selection.draft`, catalog/details и существующей нормализации параметров и передаёт их registration через props/slot. Не создавать второе изменяемое хранилище параметров и не выполнять `prepare()` лишь для отображения: подготовка перед записью остаётся отдельной обязательной операцией.

Сводка выводит названия или известные ID, подписи параметров и значения для каждого выбранного навыка. Для невалидных/устаревших значений показывать проблему, а не фильтровать их молча; для необязательных пустых значений пояснять, что они не отправляются. Назначение, контекст, ответственные и домены отображаются с той же нормализацией, что POST. Рендерить все строки как текст.

Именованные типы, runtime-константы и обработчики размещаются в сегментах ближайшего владельца; новые приватные компоненты — отдельными файлами в подпапке регистрации. Между feature-слайсами прямых импортов нет.

### 7. Сохранение ввода ограничено текущим мастером

Существующие `useBlocker` и `useBeforeUnload` сохранить. Учитывать изменения параметров редактора, а не только form.isDirty, и фазу незавершённой попытки. При отмене перехода не сбрасывать данные/ошибки/ID. После confirmed переход разрешён. При unknown предупредить, что уход не отменяет возможное создание и новая регистрация может создать дубль.

Полноценное хранилище восстановления потребовало бы отдельного решения о сроке жизни и изоляции данных; оно не добавляется в этот MVP. Приложение не обещает сохранение черновика после подтверждённого ухода, закрытия или перезагрузки и не предлагает reload как восстановление неизвестного POST.

## Risks / Trade-offs

- Отсутствие backend-проверки доменов → явно показывать отсутствие подтверждения; не закрывать соответствующий критерий исходной MOS-958.
- Потерянный ответ блокирует текущий мастер даже при фактическом отказе → доступен просмотр введённых данных и переход к реестру; безопасное восстановление записи остаётся в follow-up.
- Перезагрузка/новая вкладка обходят локальную блокировку → предупреждение при уходе, никакой декларации глобальной защиты от дублей.
- Одновременно существует proposal follow-up с новой capability surface-registration → после архивации MVP follow-up должен расширять эту capability; его документы в этом change не редактируются.
- Текущий тестовый сценарий ожидает немедленный переход и повтор по ключу → заменить эти ожидания тестами POST+GET и неизвестного результата, сохранив проверки параметров, ошибок и навигации.

## Migration Plan

Изменение не требует миграции API или данных. Реализация обновляет клиент и unit/component-фикстуры в одном change; generated-контракт остаётся прежним. После проверки выполняется обычная поставка фронта. Откат — возврат фронтового изменения без серверных миграций; он возвращает известные ограничения прежнего мастера и не должен объявляться устранением backend-пробелов.
