# Proposal

## Why

Мастер MOS-958 сейчас выдаёт поиск по реестру за проверку занятости доменов, вычисляет channel_id и требует приветствие, которое не сохраняет. После POST он уходит в реестр без чтения результата, а повтор после потерянного ответа не защищён backend-идемпотентностью.

## What Changes

- Сохранить четыре шага регистрации, поддержанные поля POST, текстовых ответственных, текущий выбор команды-владельца, продовые навыки и параметры.
- Убрать запросы проверки доменов через реестр и связанную блокировку шага; сохранить локальную нормализацию и проверку непустого списка. Показывать отсутствие проверки уникальности без обещания проверки backend при создании.
- Убрать генерацию channel_id: до создания значение ещё не назначено, после создания отображается только ответ GET, включая явное отсутствие при null.
- Заменить редактирование приветствия видимым пояснением о серверной конфигурации по умолчанию и недоступности настройки при регистрации; убрать обязательность и фиктивную успешную проверку приветствия. Не добавлять PUT configuration.
- Дополнить итоговый шаг продуктовым контекстом, названиями выбранных навыков и значениями их параметров, сохранив существующую проверку перед POST.
- Обеспечить одну последовательность подготовки и создания без Idempotency-Key и автоматического повтора POST. Различать отказ валидации, неизвестный результат POST и ошибку GET после полученного ID.
- После валидного ответа создания выполнять свежий GET карточки. Показывать фактический статус и channel_id; при ошибке чтения повторять только GET того же ID. Не объявлять отправку на проверку только по значению переключателя.
- Сохранить ввод при переходах и ошибках, предупреждать перед уходом; защита от повторной записи действует в текущем открытом мастере. Восстановление после перезагрузки и гарантия отсутствия дублей между вкладками не входят в MVP.

## Capabilities

### New Capabilities

- `surface-registration`: достоверный четырёхшаговый мастер на текущем контракте, итоговая сводка, ограниченная конфигурация, обработка результата POST и подтверждение через GET.

### Modified Capabilities

- `surface-skill-selection`: уточнить требование `Registration and existing surface persistence` — при регистрации повтор записи допустим после подтверждённого отказа, но не при неизвестном результате POST; подтверждение результата требует GET. Правила карточки и проверки параметров сохраняются.

## Impact

- Основные владельцы: `app/features/surface-registration`, `app/widgets/surface-registration`, `app/entities/surface`; данные сводки сценариев передаются через widget и публичный API `features/surface-skill-selection` без импорта между feature-слайсами.
- Существующий `apiRequest` уже предоставляет `successStatus`, `ApiError` и валидацию ответа; React Hook Form, TanStack Query и React Router остаются основой формы, запросов и защиты переходов. Новые зависимости не нужны.
- Обновятся unit/component-тесты регистрации, API-клиента и мутации. Контракт и generated-типы не расширяются; production-возможности не достраиваются по мокам.
- Backend-зависимости остаются в [mos-958-registration-api-followup](../mos-958-registration-api-followup/proposal.md). Этот MVP вводит базовую capability `surface-registration`; при последующем оформлении follow-up его потребуется планировать как изменение уже существующей capability. Сам follow-up здесь не редактируется.
- MVP не закрывает исходную MOS-958 целиком: глобальная уникальность, серверная защита от дублей, конфигурация в POST и новая модель ответственных остаются отложенными.
