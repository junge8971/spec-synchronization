## Context

См. proposal.md. Вкладка мониторинга уже читает `GET /skills/v1/skills/{skill_id}/monitoring` через `useSkillMonitoringQuery` и показывает показатели MOS-1025. Локальный OpenAPI от 02.11.2026 дополнительно описывает отдельные GET `/responsibles` и `/incidents`. В интерфейсе они не подключены; локальный mock ответственных сейчас возвращает 501. Совпадение сохранённой схемы с развёрнутым API не проверялось.

Источники требований: [MOS-1026](https://task.mos-team.ru/browse/MOS-1026), [MOS-1398](https://task.mos-team.ru/browse/MOS-1398), [MOS-1397](https://task.mos-team.ru/browse/MOS-1397), [MOS-1146](https://task.mos-team.ru/browse/MOS-1146), [описание навыков](https://wiki.mos-team.ru/spaces/KR/pages/241080062/Админка.+Навыки) и предоставленный пользователем `/home/user/Загрузки/Прототип. Центр управления.html`.

## Goals / Non-Goals

**Goals:** воспроизвести эксплуатационные блоки прототипа на опубликованных read-only данных, сохранив доступность остальных сведений при ошибке отдельного запроса.

**Non-Goals:** новые бизнес-API, редактор ответственных/настроек, подтверждение инцидента, редактирование postmortem, вызов внутреннего upsert из интерфейса и подмена недостающих полей.

## Decisions

### Композиция и чтение

Во вкладке «Мониторинг» сохранить показатели слева, справа разместить карточку ответственных и плановых работ; ниже — таблицы зависимостей и инцидентов. На узком экране карточки перестраиваются, широкие таблицы прокручиваются внутри своего контейнера.

- Показатели, окно работ и зависимости используют **один** существующий query по skill ID. `metrics=null` или ненастроенные пороги не скрывают корректные зависимости. При ошибке или невалидном ответе общего GET эти сведения недоступны вместе: отдельных API для них нет. Сохранить действующую валидацию мониторинга и не делать дублирующий запрос.
- Ответственных и инциденты читать отдельными query с тем же transport, проверкой ответа, AbortSignal и ключом по skill ID. Их загрузка и ошибки независимы друг от друга и от мониторинга; повтор выполняет соответствующий GET. Смена навыка не показывает данные прежнего ID.
- Если один запрос завершился ошибкой, остальные блоки остаются доступны. `403`, `404`, `501`, невалидный ответ и сетевая ошибка не превращаются в «не назначен» или пустой список.

### Ответственные, работы и зависимости

GET `/responsibles` возвращает `items` с ролью, `user_id`, nullable `user` и `user_data_source`. `user_id` — строковый внешний идентификатор, не обязательно UUID. Для известных ролей `owner`, `tech`, `backup` использовать подписи прототипа; не считать список ролей закрытым и не скрывать другие назначения. Роль без назначения — «Не назначен», назначение с `user=null` — «Назначен, данные недоступны». Основной `contact` анкеты и участники команды не подставляются вместо назначений. Имя открывает доступный popover с полученными должностью и контактами; отсутствующие сведения не выдумываются, `mock` не представляется как реальные данные.

Плановые работы брать из `settings.maintenance_starts_at`, `maintenance_ends_at`, `maintenance_reason`, показывать период с часовым поясом и причину. API содержит одно сохранённое окно, а не список всех окон. Время проверки каждой зависимости — её `checked_at`, не время общего снимка; `ok`, `degraded`, `down` отображать как в прототипе, неизвестные коды сохранять без ложного статуса «Доступна».

### Инциденты

GET `/incidents` возвращает массив. Использовать серверные `id`, `external_id`, `level`, `title`, `message`, `cause`, `side`, `status`, даты и nullable поля postmortem. Заголовки таблицы следуют прототипу: уровень, что произошло, причина, кто устраняет, срок и состояние. `side=platform` — «Команда ЦАМ», `side=team` — «Команда навыка»; это сторона устранения, не конкретный исполнитель. Неизвестные коды не скрывают строки и не подменяются известными.

Коды уровней API `p0`–`p3` отображать как P0–P3. Согласованное представление из прототипа: P0 — норматив 30 минут, P1 — 4 часа, P2 — 2 суток, P3 — плановая работа. Подписывать их именно как **норматив**, не вычислять и не обещать дату/остаток времени устранения. При наличии `resolved_at` показывать фактическое время устранения. `postmortem_due_at` относится только к разбору и не является сроком устранения.

Показывать `external_id` текстом. URL внешнего источника в текущем DTO отсутствует — не строить ссылку по ID. Если согласованный API позднее вернёт URL, ссылку разрешать только с безопасной схемой; до этого соответствующее ограничение остаётся открытым. GET не задаёт пагинацию: отображать полученный серверный массив, не создавать фиктивную серверную пагинацию. При успешном пустом массиве сообщать об отсутствии записей, не утверждать, что источник подключён или инцидентов никогда не было.

### Локальная демонстрация

Использовать существующий Express: реализовать контрактный GET ответственных вместо его 501, дополнить фиксированные данные зависимостей и инцидентов. Данные синтетические, устойчивые и явно локальные; не использовать credentials, ролевое enforcement или новые продакшен-данные. Сохранить пустые и ошибочные сценарии. Mock инцидентов должен соблюдать порядок из MOS-1146: открытые, подтверждённые, устранённые; внутри группы — новые первыми. UI не вызывает внутренний upsert автоматически.

## Risks / Trade-offs

- Норматив прототипа принимают за срок из API → подпись «Норматив», без вычисленного дедлайна; дату устранения показывать только из `resolved_at`.
- Нет URL, признака подключения и пагинации инцидентов → показывать ID и фактически полученные записи, не симулировать отсутствующие возможности; полная внешняя интеграция остаётся непроверенной.
- Профиль ответственного недоступен либо код справочника неизвестен → сохранить назначение/строку и явно показать ограничение, не подставлять других людей или нормальное состояние.
- Общий GET мониторинга отказал → работы и зависимости недоступны вместе, но независимые ответственные и инциденты остаются видимыми.

## Migration Plan

Подключить существующие GET и локальные fixtures, добавить блоки и unit/component-тесты. При откате UI не изменяются инциденты или назначения backend. Browser/E2E-проверку не выполнять без отдельного явного разрешения пользователя; мок и локальная схема сами по себе не подтверждают работу на контуре.
