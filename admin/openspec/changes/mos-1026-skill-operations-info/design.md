## Context

См. proposal.md. В SkillResponse есть основной contact, но нет операционных ответственных/инцидентов. В прототипе инциденты явно только читаются из внешней системы.

## Goals / Non-Goals

**Goals:** read-only эксплуатационные блоки, независимо от доступности метрик.

**Non-Goals:** редактор контактов/постмортемов, подтверждение инцидента, вывод ролей сопровождения из состава команды.

## Decisions

- **BLOCKED API:** согласовать основной/технический контакт и backup, окна работ с часовым поясом, внешние системы/status/checkedAt, схему инцидента и пагинацию, внешние ID/URL. Определить различие пустого результата и отсутствия подключения к источнику.
- Составлять блоки внутри владельца skill-details рядом с мониторингом MOS-1025. Не создавать зависимость чтения инцидентов от наличия метрик; каждое чтение имеет свои loading/error/retry.
- Основной contact можно переиспользовать из карточки только в его текущем смысле. Не объявлять его техническим представителем или заместителем.
- Ссылки источника — безопасные внешние ссылки с проверкой допустимой схемы; небезопасный URL показывать текстом. Причину/описание рендерить как текст. Для ключей строк использовать ID источника, не название события.
- Локальную history из прототипа и операции внешней системы не переносить; audit MOS-1031 — отдельный предметный блок.

## Risks / Trade-offs

- Частичная недоступность источников → сохранять остальные блоки, явно показывая ошибку конкретного источника.
- Отсутствие backup → нейтральное «Не назначен» только по данным, без вымышленного назначения.

## Migration Plan

После API-gate добавить read-only блоки и контрактные test doubles. Откат UI не изменяет внешние инциденты. Приёмка не требует завершения MOS-1025 или MOS-1031.
