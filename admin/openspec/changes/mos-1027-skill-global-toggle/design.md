## Context

См. proposal.md. Пользователь согласовал сокращение MOS-1027 до чтения серверного состояния и команд включения/отключения по skill_id с подтверждением и обработкой ошибок. В текущем OpenAPI enable/disable есть только у модулей и поверхностей, а SkillStatus не содержит disabled. Сокращение объёма не снимает API-блокер.

## Goals / Non-Goals

**Goals:** один понятный сценарий «прочитать состояние → подтвердить переключение → показать серверный результат» для конкретного навыка.

**Non-Goals:** длительности, timestamps отключения, подробный список/пагинация затронутых поверхностей, отдельный impact API, собственный журнал причин, управление сообщениями жителю вне требований будущего контракта. Не изменять enabled-skills поверхностей и lifecycle для имитации глобального отключения.

## Decisions

- **Минимальный API-gate остаётся.** До реализации получить контракт чтения включённости и команд по skill_id, глобальную область действия, обязательные параметры и форму результата/ошибок. Уточнить, когда переключение считается применённым и как перечитать состояние при потере ответа. Это не требование отдельного endpoint для каждого аспекта; пути, wire-поля и модель concurrency не назначать предположительно. Отдельное согласование API должно уточнить эти артефакты до интеграции.
- **Не ждать расширенных данных.** Длительности и подробный список поверхностей не включать в запросы, подтверждение и приёмку MVP. Вместо списка объяснять подтверждённую контрактом глобальную область действия, не показывая выдуманное количество. Основание и сообщение жителю не вводить самостоятельно; если контракт сделает их обязательными, согласовать форму и сохранить бизнес-валидацию, не подставляя пустые defaults.
- **Простое размещение.** Чтение и команды — entities/skill, подтверждение — feature, сборка — существующий widget карточки. Переиспользовать transport, Query, диалог и состояния ошибок проекта. Без API сохранять текущее честное unavailable, не создавать новый экран ради заглушек.
- **Подтверждение перед каждой командой.** Показывать имя/ID навыка, текущее и целевое состояние, глобальную область действия. Отмена ничего не отправляет; pending блокирует второй запрос. При известном изменении состояния до отправки требовать нового подтверждения. Версии/guards применять только согласно будущему API, не требовать отдельного versioned impact.
- **Сервер — источник состояния.** Не делать optimistic update. Результат команды проверять по согласованному контракту и обновлять относящиеся к навыку данные. Ошибка чтения не означает «отключён»; старые данные обозначать как последние загруженные и не использовать для новой команды до успешного чтения.
- **Без автоматических повторов и откатов.** При неизвестном исходе показать неопределённость и предложить перечитывание. Полученное состояние не доказывает, какая команда его установила. Следующее действие возможно только после актуального чтения и нового подтверждения по согласованным правилам; противоположную команду не отправлять как автоматический откат. Не придумывать replay/job-протокол.

## Risks / Trade-offs

- [Команда отсутствует в контракте] → реализация остаётся заблокированной, UI модулей не используется как замена.
- [Глобальное действие без подробного списка поверхностей] → явное подтверждение области действия; детализация отложена осознанно.
- [Ответ потерян после принятия команды] → неизвестный исход, чтение состояния и отсутствие автоматического повторного/обратного запроса.

## Migration Plan

Сначала согласовать минимальный API и уточнить схемы/ошибки в артефактах, затем подключить чтение и подтверждённые команды. Unit/component-тесты проверяют оба переключения, отмену, ошибку и потерянный ответ; браузерные проверки не входят в работу. Откат UI не включает ранее отключённый навык и не обещает отмены серверных действий.
