## Context

См. proposal.md. В текущем OpenAPI enable/disable есть у модулей и поверхностей, но не навыков. Совпадение слов «отключить» не означает одинаковую область действия.

## Goals / Non-Goals

**Goals:** одна серверная команда для навыка с явным подтверждением последствий.

**Non-Goals:** изменение состава enabled-skills каждой поверхности, локальный статус вместо backend, управление ролями.

## Decisions

- **BLOCKED API:** согласовать чтение состояния/impact и команды навыка, основания, сообщение жителю, timestamps/длительности, version guard, idempotency и неизвестный исход. Не переиспользовать module ID как skill ID без явного соответствия контракта.
- Подтверждение принадлежит feature действия, состояние/API — entities/skill, размещение — widget. Показать все затронутые поверхности или согласованную пагинацию/количество, не вычислять их из загруженной страницы реестра.
- Отключение требует основания и непустого сообщения. Включение отдельно подтверждает возвращение ответов на всех связанных поверхностях. Пока запрос выполняется, повтор исключён.
- Не делать optimistic update: только подтверждённый ответ меняет статус. Конфликт/ошибка сохраняют объяснение и введённый текст; при изменившемся impact требуется новое подтверждение.
- Длительности опираются на серверные timestamps/значения, не на время открытия вкладки.

## Risks / Trade-offs

- Команда принята, HTTP ответ потерян → сначала перечитать состояние/операцию по согласованному протоколу, не отправлять противоположную команду как «откат».
- Устаревшее подтверждение → проверка версии/impact на сервере.

## Migration Plan

После gate добавить read и затем action-flow. Откат клиентской кнопки не возвращает отключённый навык; обратная операция требует отдельного осознанного подтверждения. Unit/component тесты охватывают отмену, обязательность полей и ошибку.
