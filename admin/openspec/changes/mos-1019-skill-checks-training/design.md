## Context

См. proposal.md. `checks-tab.tsx` сейчас не выдаёт фиктивные результаты. Прототип показывает анкету/фразы, обучение, автотесты и песочницу; OpenAPI не описывает серверный процесс.

## Goals / Non-Goals

**Goals:** один источник готовности — серверный запуск для конкретной версии.

**Non-Goals:** ML-процесс на фронте, произвольные переходы статусов, реализация песочницы и токенов MOS-1023.

## Decisions

- **BLOCKED API:** нужны операции запуска/чтения, run ID, skill/phrase version, этапы и ошибки, terminal states, правила повторного запуска и обновлений, признак доступности песочницы. Зафиксировать их в контракте до выполнения интеграционных задач; enum из прототипа не считается соглашением.
- API/hook — entities/skill, отображение — checks-tab и блок готовности обзора. Дублирующую state machine в двух вкладках не создавать.
- Если принятый API допускает polling, использовать штатный query refetchInterval с прекращением по terminal state и при уходе со страницы. SSE/WebSocket не добавлять без контрактной необходимости. Частоту и backoff определяет согласование, не статический таймер завершения.
- После перезагрузки читать серверный активный/последний запуск. Старый успешный запуск не подтверждает новую версию фраз. При сбое обновления можно оставить последний результат с явной отметкой неактуальности и retry.
- Переход в песочницу доступен по подтверждённым бизнес-данным, передаёт только skill ID; секреты принадлежат MOS-1023.

## Risks / Trade-offs

- Ответ предыдущего запуска пришёл позже → ключи запросов включают идентификатор запуска/версии по контракту.
- Polling создаёт нагрузку → прекращение в конечном состоянии, отсутствие параллельных дублирующих циклов.

## Migration Plan

После согласования процесса обновить типы и заменить заглушку checks. Компонентные тесты управляют ответами HTTP и временем; браузер и реальное обучение для проверки UI не нужны. Откат UI не отменяет серверные запуски.
