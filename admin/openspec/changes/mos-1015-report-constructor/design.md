## Context

Мотивация и граница поставки — в `proposal.md`. Исследованы `app/routes/reports.tsx`, клиенты/публичные API `entities/surface` и `entities/skill`, `shared/api/http-client.ts`, соседние страницы, `package.json`, `docs/api/contracts/{reports,dialogs}.md` и анализ `docs/tasks/control-center/analysis.md`.

В HTML `/home/user/Загрузки/Прототип. Центр управления.html` конструктор находится в `wne`, каталог колонок — `K9`, условия — `iC/aC/vC`, период — `qD/LD`. Preview и показатели вычисляются по локальным демодиалогам, даты фиксированы; эти механизмы не переносим. Ссылка на HTML — источник UI, не runtime-зависимость. Состав колонок и атрибутов полностью зафиксирован в delta specs.

React Router используется в Framework Mode; существующая загрузка справочников организована через entity-клиенты и React Query. Нового слоя серверного состояния или альтернативного HTTP-транспорта не требуется.

## Goals / Non-Goals

**Goals:** локальная форма с единым источником состояния, переиспользуемый предметный редактор условий, реальные справочники и проверяемая граница между настройками и недоступным результатом.

**Non-Goals:** DTO отчёта, фильтрация диалогов, морфология, preview/метрики, таблица с фиктивными строками, сохранение, экспорт, вкладка шаблонов, URL-сериализация условий и persistent storage. Не создаём entity отчёта до появления данных и контракта.

## Decisions

### 1. Композиция без импорта соседних слайсов

- `app/routes/reports.tsx` — тонкий адаптер публичного `pages/reports`.
- `pages/reports` — страница и владелец жизненного цикла формы, чтобы вкладки MOS-916 не уничтожали черновик.
- `widgets/report-constructor` — модель/схема черновика, форма параметров, каталог 24 колонок, unavailable-области результата. Минимальный публичный API формы и её состояния; без универсального конструктора отчётов «на будущее».
- `features/dialog-selection` — управляемый редактор одной группы AND/OR с собственными типами и каталогом атрибутов. Он не знает о странице отчётов и не импортирует другие features. Widget компонует редактор с остальными параметрами.
- Справочники получаем через публичные `entities/surface` и `entities/skill`. Каталоги и defaults живут в `constants`, именованные типы — в `types`, UI-обработчики — в `handlers` ближайшего владельца. Каждый React-компонент — отдельный файл.

Альтернативы: копировать фильтры в страницах — расходится семантика; разместить предметный редактор в shared — неверное владение; сразу строить дерево запросов — не требуется одной группой из прототипа.

### 2. UI-модель не является контрактом API

Внутренние стабильные ключи колонок и атрибутов нужны для React/state, но не называются подтверждёнными `field_codes` и никуда не отправляются. Отдельный mapper в предполагаемый API не создаётся. Полная длительность, оценки ответов и оценки оператора остаются разными понятиями.

Для локальной формы использовать существующие React Hook Form и Zod; массив условий — штатные возможности формы, без своего form framework. Изменение атрибута/оператора очищает неприменимые поля. Валидация проверяет форму, не обещает допустимость условий на сервере. На начальном экране группа условий пустая: пустую демостроку не трактуем как применённый фильтр.

### 3. Период и порядок колонок

Предустановки вычисляются средствами языка от локальной даты браузера; даты хранятся как календарные строки, без `toISOString()` с неявным сдвигом дня. Сегодня входит в 7/30 дней; прошлый месяц вычисляется по календарю, включая високосный февраль. Использовать нативные date inputs в раскрываемом редакторе собственного интервала, не добавлять date-picker библиотеку ради визуального повторения календаря HTML. Сохраняем не визуальный календарь на два месяца, а поведение: выбранный период и временный ввод раздельны, «Применить» переносит валидный ввод в черновик и закрывает редактор, закрытие/Escape отбрасывает ввод, «Сбросить» сразу выбирает актуальные «30 дней» и закрывает редактор. Сброс периода не затрагивает остальную форму. «За всё время» — отдельный локальный режим без границ; его нельзя валидировать как незаполненный custom. При открытии custom из этого режима поля пусты. Выбор предустановки немедленно заменяет локальный период; подтверждение требуется только для custom. Даты — локальная UI-семантика, будущий backend timezone потребует отдельного согласования.

Первые восемь колонок выбраны как в прототипе. Массив выбранных ключей задаёт порядок добавления; снятие и повторное добавление перемещает колонку в конец. Показывать этот порядок компактным списком рядом с выбором; отдельный drag-and-drop и библиотека сортировки не нужны.

### 4. Существующие справочники, но без ложного mapping

В `surface-registry-client.ts` уже есть приватный `getAllSurfaces`; в `skill-registry-client.ts` — `getAllSkills`. Узко переиспользовать эти операции через подходящие entity hooks/public exports, не копировать циклы пагинации в feature и не вызывать `getSurfacesByDomains` с фиктивными доменами. Не ограничивать выбор первыми 100 записями. Запросы передают AbortSignal, ошибки не превращаются в пустые options. Query cache общий; справочник навыков нужен только при соответствующем условии.

Поверхность хранится по `id`; nullable `channel_id` не заменяется этим ID. Для отчётного запроса mapping пока отсутствует. Для `channel` и `skill` доступны реальные options; остальные enum видны как unavailable: примерные значения причин/оценок/подсистем не принимаются за согласованные справочники. Прочие типы могут редактироваться как локальные значения, но весь отбор явно не применяется.

### 5. Честные результаты и защита данных черновика

Четыре показателя и preview — статически недоступные области, не loading и не empty. Не создавать client hooks, report endpoints, runtime fixtures или суммы из surface stats. Не создавать API capability registry: отсутствие интеграции выражается прямо в компонентах.

Постоянное пояснение сообщает об отсутствии применения и сохранения. Фразы и пользовательские идентификаторы остаются в памяти, не попадают в URL, storage и debug logs. Смена страницы/перезагрузка очищает черновик; переключение вкладок в последующем MOS-916 сохраняет его за счёт владельца формы выше панели вкладки.

### 6. Проверки

Unit-тесты каталогов (24/35), операторов/сброса неприменимых полей, порядка колонок и календарных границ. Для периода отдельно проверить отличие any от неполного custom, применение/отмену временного ввода, повторное открытие и сброс только периода; компонентные проверки Escape и disabled «Применить» обязательны. Component-тесты ввода, клавиатуры, ошибок, справочников за первой страницей, retry и unavailable-результатов. Отдельно проверять, что реальные справочники запрашиваются, но отчётные/auth endpoints — нет; запрет всех fetch подряд был бы неверным. Проверять отсутствие сохранения чувствительных условий в storage/URL.

## Risks / Trade-offs

- [Большая форма без серверного результата] → видимая граница локального черновика; полная MOS-1015 остаётся заблокирована, UI-поставка принимается отдельно.
- [Будущий контракт отличается от модели] → не генерировать speculative DTO; внутренние ключи не считать wire-кодами.
- [Объём справочников] → переиспользовать пагинацию и query cache, загружать только нужные справочники; для больших объёмов серверный поиск можно добавить по существующему query без смены UI-семантики.
- [Часть enum недоступна] → каталог не урезать, но не давать создать no-op условие; включение требует подтверждённого источника.
- [Нативный диапазон отличается внешне от календаря HTML] → сохраняем функциональный ввод дат и доступность без новой зависимости.

## Migration Plan

Один PR MOS-1015 без чужих бизнес-функций. Базовая поставка не зависит от остальных трёх changes. Откат возвращает маршрут-заглушку и удаляет добавленные модули; миграции серверных данных отсутствуют.

Дальнейшие независимые PR после базы: MOS-916 — вкладки; MOS-919 — недоступное действие экспорта; MOS-1016 — локальная подготовка имени/расписания. После получения отчётного API сначала обновить контракт и план, затем добавлять preview/метрики с защитой от stale-ответов и согласованными лимитами. Исторические «12 строк/5 колонок» не утверждаются этим change.

### Критерии заблокированного продолжения MOS-1015

Ниже сохранена целевая приёмка, а не дополнительные требования текущей delta spec. Переход к реализации требует подтверждённого API и отдельного обновления плана. Неизвестные wire-поля, формулы и лимиты остаются явно несогласованными.

- **B15.1 — Поля:** для каждой из 24 колонок из spec документировано соответствие подтверждённому полю, его типу, nullable/незавершённому состоянию и формату отображения. Сверка с `analysis.md#report-fields` не допускает подмены полной длительности `bot_duration`, объединения причин/комментариев оценки оператора с оценкой сообщения или исчезновения авторизации, участников, шагов, вложений/вложений оператору и оценок ответов. Неизвестное поле не заменяется пустой ячейкой как будто данные получены. Проверка: контрактная матрица 24 строк и тесты соответствующих значений, null и незавершённого диалога.
- **B15.2 — Применённый отбор:** период, поверхность, поля и условия передаются по согласованной схеме; явно определены календарные границы/timezone, any, AND/OR, диапазоны, пустые значения, enum/массивы и семантика фраз/областей. Нет no-op для группы оператора, типа ошибки и кнопки виджета. Проверка: одинаковая конфигурация даёт одинаковую серверную выборку preview и export (совместно с MOS-919), справочник опций не выдаётся за отфильтрованные диалоги; используемая обеими страницами модель не расходится.
- **B15.3 — Показатели:** сервер возвращает число диалогов, долю переходов на оператора, долю решённых без оператора и среднюю оценку оператора по всей выборке, независимо от лимита preview. Формулы/знаменатели и семантика отсутствующих данных подтверждены контрактом. Проверка: выборка больше preview, нулевая выборка и отсутствующая оценка; null не маскируется нулём, отсутствующие метрики не вычисляются по загруженным строкам.
- **B15.4 — Предпросмотр:** серверные строки отображаются с согласованными форматами и порядком выбранных колонок; UI различает количество выбранных/показанных колонок, полное число результатов и размер preview, поддерживает горизонтальный просмотр широкой таблицы. Проверка: успешный, пустой, loading и error/retry случаи, длинный текст и nullable значения. Конкретные лимиты согласуются отдельно: HTML показывает до 12 строк по всем колонкам, прежний анализ упоминает 12 строк/5 колонок; ни один вариант не назначается молча.
- **B15.5 — Ошибки и актуальность:** неверные серверу период/поле/условие показываются у соответствующих настроек без потери ввода; при изменении параметров старый preview не выдаётся за новый, поздний ответ старого запроса не заменяет актуальный. Проверка: ошибка валидации, сетевая ошибка с повтором, два ответа в обратном порядке, изменение и последующее исправление параметров. Точные error DTO и механизм запроса не выдумываются.

### Осознанные отличия от демонстрации

Нативные даты вместо двухмесячного календаря, пустая стартовая группа вместо пустой строки фразы и валидация неполных условий вместо их молчаливого игнорирования — решения текущего UI-плана, а не забытые функции. Демо-роли, локальная морфология, фиктивные данные и расчёты не переносятся. Шаблоны/CSV/сохранение остаются в отдельных changes MOS-916/MOS-919/MOS-1016.
