## Context

См. proposal.md. В карточке нет вкладки мониторинга и соответствующего DTO. HTML-прототип показывает показатели за сутки, пороги и давность внешних данных; значения/пороговые формулы не являются утверждённым контрактом.

## Goals / Non-Goals

**Goals:** read-only мониторинг конкретной skill ID с достоверными состояниями данных.

**Non-Goals:** расчёт метрик из списка навыков, редактирование регламента и реализация инцидентов MOS-1026.

## Decisions

- **BLOCKED API:** согласовать per-skill источник, availability/latency/quality, единицы, период/часовой пояс, знаки сравнения порогов, минимальную выборку, null, fresh/stale, dataUpdatedAt и lastCallAt. Не подставлять updated_at анкеты.
- Добавить отдельный запрос и блок внутри skill-details; ошибка мониторинга не должна скрывать анкету. Серверное «не подключён» отличается от отсутствия endpoint и от HTTP failure.
- Пороги сравниваются только при сопоставимых единицах и достаточной выборке. Если backend отдаёт готовое нарушение, следовать его контракту; не придумывать дополнительный «зелёный» статус для null.
- Структура вкладки общая с MOS-1026 на уровне widget. Каждая задача поставляет собственный блок, не импортируя соседний widget/feature и не ожидая его готовности.
- Использовать обычные карточки/табличные показатели из имеющегося UI вместо новой chart-библиотеки: временной ряд в задаче не требуется.

## Risks / Trade-offs

- Смешение периодов с MOS-1030 → явно подписывать период каждого блока, не переиспользовать 30-дневный агрегат как суточный.
- Данные устарели → показывать время/признак актуальности, не сравнивать даты с вымышленным регламентом.

## Migration Plan

После контракта добавить вкладку и запрос, сохранив существующие вкладки. Unit/component-тесты проверяют границу порога, null/0 и отсутствие подключения. Откат UI не влияет на сбор метрик backend.
